Baseline linking has four stages: the copy with compaction, the side tables, the bytecode map and finalization ([baseline/compiler.md](../baseline/compiler.md#linking)). And the DFG brings a whole category that has no counterpart in the baseline. `DFG::CommonData` carries three kinds of watchpoint (`CodeBlockJettisoningWatchpoint`, `AdaptiveStructureWatchpoint`, `AdaptiveInferredPropertyValueWatchpoint`), weak references to specific cells and `StructureID`s, transitions, `InlineCallFrameSet`, `CodeOriginPool`, catch entrypoints and jump replacements. This is OSR and invalidation bookkeeping, and it is this bookkeeping, not the four link stages, that makes the DFG much harder to serialize: a transported DFG artifact would have to rearm watchpoints against the consumer's heap and reinstate weak references to specific cells. The baseline has none of this because it does not speculate with exits.

`CommonData` also carries two things that are not invalidation bookkeeping. `RecordedStatuses` keeps the IC statuses the compilation relied on, whether computed from the ICs it read or derived by its own phases (`ConstantFoldingPhase`, `StrengthReductionPhase`). The GC prunes the dead ones (`RecordedStatuses::reconcileWeakReferences`) and `CodeBlock::getICStatusMap` hands the rest to later compilations, except the `CheckPrivateBrandStatus` and `SetPrivateBrandStatus` entries, so it is feedback carried forward, and no code is jettisoned because of it. `PCToCodeOriginMap` is profiling state, and the baseline has one too (`BaselineJITCode::m_pcToCodeOriginMap`). It maps a machine code address to a bytecode origin for the sampling profiler (`SamplingProfiler::processUnverifiedStackTraces`). Each JIT tier builds it only when the VM asks for the mapping, which a VM created with `useSamplingProfiler` or `alwaysGeneratePCToCodeOriginMap` does from the start and any VM does once a debugger attaches (the `VM` constructor, `Debugger::attach`).
