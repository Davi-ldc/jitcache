# Abstract

Installation gives a `CodeBlock` its baseline machine code and the per-`CodeBlock` state that code reaches at run time. It is two functions. `CodeBlock::setupWithUnlinkedBaselineCode` builds the state: it publishes the `BaselineJITCode`, points the exception handlers into it and creates the `BaselineJITData`. `ScriptExecutable::installCode` then makes the executable run that `CodeBlock` and relinks the calls that were entering the one it replaced.

Three doors lead there. The first is the end of a compilation, when a plan is finalized in the `CodeBlock` it compiled. The other two install an artifact that another `CodeBlock` of the same `UnlinkedCodeBlock` compiled and parked in the `UnlinkedCodeBlock`'s `m_unlinkedBaselineCode` slot: door 2 when the LLInt's tier-up slow path of a `CodeBlock` that is already being interpreted finds it, door 3 when `prepareForExecutionImpl` finds it for a newborn `CodeBlock`, which then enters baseline without ever being interpreted. All three run on the thread that runs JS in the `VM`, with collection deferred.

The artifact arrives finished, with its executable memory, both entry points, the IC molds and the side tables ([compiler.md](compiler.md#the-artifact)). Installation neither copies nor patches the code. It builds what differs per `CodeBlock` and trusts the artifact for the rest, including the facts the compilation baked from the `CodeBlock` it compiled for ([What installation does not check](#what-installation-does-not-check)).

# Doors

## Door 1: the end of a compilation

A compiled plan waits in the worklist, `Ready`, until a thread that owns the `VM` finalizes it. `JITWorklist::completeAllReadyPlansForVM` finalizes every ready plan of the `VM` at once, of any tier, each in its own `CodeBlock`, whoever called it. It runs from the tier-up slow paths (the LLInt's `jitCompileAndSetHeuristics`, `operationOptimize` from baseline to DFG, and the DFG's FTL tier-up operations) and from `Heap::completeAllJITPlans`, which first waits until every plan of the `VM` is ready. The heap does that before deleting all code (`deleteAllCodeBlocks`, only with no JS on the stack) and before walking every `CodeBlock` (`Heap::forEachCodeBlock`); the debugger does it when it changes breakpoints or stepping. Two settings finalize on the spot, on the thread that asked for the compilation: with `useConcurrentJIT` off, `JITWorklist::enqueue` compiles and finalizes before returning, and with the LLInt off, door 3's `setupJIT` calls `JIT::compileSync` with `JITCompilationMustSucceed`.

`BaselineJITPlan::finalize` calls `JIT::finalizeOnMainThread`, which adds the code's size per bytecode word to the `VM`'s statistic and runs `setupWithUnlinkedBaselineCode`. The plan then issues `crossModifyingCodeFence`, because a worklist thread may have written the code, and calls `installCode` and `jitSoon`. A plan that got no executable memory installs nothing: finalization sets `m_didFailJITCompilation` and defers the body's LLInt counter indefinitely ([compiler.md](compiler.md#handoff)).

## Door 2: an interpreted CodeBlock finds the parked artifact

The LLInt enters `jitCompileAndSetHeuristics` when the body's shared counter crosses zero, from three slow paths: `entry_osr` and its function and arity-check variants in the prologue, `loop_osr` at `loop_hint`, and `replace` at `ret` and at tail calls. Each applies the `shouldJIT` gate first (`useBaselineJIT`, `bytecodeRangeToJITCompile`, `jitAllowlist`). If the `CodeBlock` is not baseline yet and the slot holds an artifact, the slow path runs setup and `installCode` at once, without testing the threshold, calls `jitNextInvocation` and, except in `replace`, tells the LLInt to enter. Only when the slot is empty does it test the threshold, finalize ready plans (door 1) and enqueue a compilation.

## Door 3: a newborn CodeBlock finds the parked artifact

`ScriptExecutable::prepareForExecution` falls into `prepareForExecutionImpl` when the executable has no code for the requested kind: at the first call or construct of a function, reached from whatever is about to call it (the call-linking and virtual-call slow paths of every tier, the LLInt's call slow path, microtasks, the interpreter's entries), and at the first execution of a program, module or eval. Under `DeferGCForAWhile` it creates and links the `CodeBlock` (`newCodeBlockFor`, which runs `finishCreation`). If the slot holds an artifact, it runs setup; otherwise it calls `setupLLInt`, which points the `CodeBlock` at the LLInt's entry thunks, or `setupJIT` when the LLInt is off. It ends with `installCode`. This door applies no gate, neither `shouldJIT` nor a threshold.

## Embedder routes

`JIT::compileSync` is public, so an embedder can compile and install outside the doors. Bun's `node:vm` `Script` with `cachedData` decodes a program `UnlinkedCodeBlock`, creates its `ProgramCodeBlock` under a `DeferGC` that ends with the creation, and calls `JIT::compileSync` with `JITCompilationCanFail`. The plan's finalization installs the code with no GC deferral and no gate, and Bun then calls `installCode` a second time; if the compilation fails, the `CodeBlock` stays uninstalled and Bun reports the cached data as rejected (`NodeVMScript.cpp`). Bun's other `node:vm` paths go through door 3: `vm.compileFunction` links a wrapper program `CodeBlock` that it never installs and returns its `functionExpr(0)`, whose body reaches door 3 at its first call, and `vm.SourceTextModule` decodes its cached data only to validate it. No other Bun source calls `compileSync` or `installCode`.

| door | reached from | code compiled by | gate | GC | afterwards |
|---|---|---|---|---|---|
| 1 | tier-up slow paths, `Heap::completeAllJITPlans`, synchronous `enqueue`, `setupJIT` | this `CodeBlock` | `shouldJIT` and the threshold when the plan was enqueued; none through `setupJIT` | `DeferGC` inside `completeAllReadyPlansForVM`, or the caller's `DeferGCForAWhile` on the synchronous routes | `jitSoon` |
| 2 | `entry_osr*`, `loop_osr`, `replace` | another `CodeBlock` of the body | `shouldJIT` | `DeferGCForAWhile` | `jitNextInvocation`; the LLInt enters, except from `replace` |
| 3 | `prepareForExecutionImpl` | another `CodeBlock` of the body | none | `DeferGCForAWhile` | nothing |
| Bun `vm.Script` | its constructor, given `cachedData` | this `CodeBlock` | none | none | `jitSoon`, then a second `installCode` |

# Conditions around installation

Every engine door runs on the thread that holds the `VM`'s `JSLock` and heap access, inside a GC deferral scope, and installation calls nothing that stops for the collector (`stopIfNecessary`, `requestCollection`, `preventCollection`). Under deferral the allocation path neither stops nor requests a collection, so no stop-the-world phase starts during installation, and no finalization, IC reset, jettison by the GC or sweep interleaves with its steps. A collection already under way keeps marking concurrently. `DeferGCForAWhile` never collects when its scope ends; the `DeferGC` inside `completeAllReadyPlansForVM` may.

No collection may run inside door 1 at all. `completeAllReadyPlansForVM` moves every ready plan out of the worklist's map before finalizing the first, and the collector reaches plans only through that map, so a collection between two finalizations would not keep the remaining plans' `CodeBlock`s alive. `deleteAllCodeBlocks` completes all plans inside a `PreventCollectionScope`, whose `m_collectContinuouslyLock` is not recursive, so a nested `preventCollection` hangs. And `jitCompileAndSetHeuristics`, which holds door 2 and the LLInt's route into door 1, notes that its callers do not set the top call frame and that it does not want a GC there. Code that runs inside a finalization therefore must neither start nor wait for a collection, nor release heap access. `Heap::completeAllJITPlans` releases heap access while it waits for plans to become ready, which ends before the first finalization.

At doors 1 and 2 the `CodeBlock` is already its executable's, except when `setupJIT` compiles a newborn one, so other threads can reach it during installation: optimizing compiler threads read it when they inline it or collect its IC statuses, and concurrent markers visit it. Step 1 writes under the `CodeBlock`'s `m_lock` and step 3 publishes behind a fence for their sake. At door 3 the `CodeBlock` is new and unmarked, and no cell that a marker or a compiler thread can visit points to it until `installCode` stores it in the executable and barriers the executable. Bun's `vm.Script` route defers nothing, and its `CodeBlock` may already have survived a collection when the compilation starts.

# Installation

1. `setJITCode` stores a reference to the `BaselineJITCode` in the `CodeBlock`'s `m_jitCode`, under `m_lock`. From then on `jitType()` answers `BaselineJIT`, and the concurrent marker's first visit to the `CodeBlock` in each cycle drains its value profiles, as for any LLInt or baseline `CodeBlock`. Before storing, `setJITCode` reports the code's size to the heap as extra memory, because `BaselineJITCode` is not marked shared, so an artifact installed in N `CodeBlock`s counts N times. Until step 3 publishes the `BaselineJITData`, `baselineJITData()` returns null; every reader tests it, so one that arrives in between sees no IC and no counter.

2. Each exception handler's `nativeCode` pointed at the LLInt's `op_catch` dispatcher since linking. It becomes the address `m_jitCodeMap` gives for the handler's `catch` index.

3. The `BaselineJITData` is allocated once, sized by the artifact's mold and constant pool counts, and its constructor copies the global object and the stack pointer offset from the `CodeBlock`. Each mold becomes the IC at the same index ([IC initialization](#ic-initialization)), and each pool slot receives the `FunctionExecutable` that `finishCreation` linked at the recorded declaration or expression index. `setBaselineJITData` then publishes the block behind a `storeStoreFence`, so a GC thread that sees the pointer sees the finished contents.

   Three adjustments follow. Under `USE(BUN_JSC_ADDITIONS)` the fresh counter's count goes into `m_previousCounter`, the sample that code aging compares against ([bunpatches.md](../common/bunpatches.md#code-aging-pr-557-codeblockshouldjettisonduetooldage)). `optimizeAfterWarmUp` arms the baseline-to-DFG counter from `thresholdForOptimizeAfterWarmUp`, scaled by the `UnlinkedCodeBlock`'s quick DFG tier-up bit, the body's size factor and the `CodeBlock`'s reoptimization count ([basics.md](../../basics.md#tier-up)); it writes only through `baselineJITData()`, which is why it comes after publication. And `m_shouldAlwaysBeInlined` becomes false for global, module and eval code, while for function code it is ANDed with `canInline(capabilityLevel())` and `DFG::mightInlineFunction`, so a function can lose it and never gain it. That `&=` evaluates `capabilityLevel()` every time, so every baseline function `CodeBlock` leaves setup with its capability memo set; `noticeIncomingCall` relies on this and crashes when a baseline function caller's memo is unset.

   Last, if `m_isShareable` is still set, `useBaselineJITCodeSharing` is on and the `UnlinkedCodeBlock`'s slot is empty, the artifact is parked in the slot, so the first installer publishes it for the body's other `CodeBlock`s. It stays there until the `UnlinkedCodeBlock` dies or the slot is cleared by `deleteAllCode`, by an age jettison or, at the end of a full collection, by `Heap::releaseUnusedSharedBaselineCode` ([basics.md](../../basics.md#cb)).

4. `installCode` swaps the executable's `CodeBlock` for the kind, makes the `CodeBlock`'s `JITCode` the executable's entry and clears the cached arity-checking entry, which `entrypointFor` derives again on the next call. It also updates the executable's place in the heap's clearable-code set, registers the `CodeBlock` with the debugger and the per-bytecode profiler when they exist, relinks the calls that came into the `CodeBlock` it replaced, and barriers the executable.

   Relinking (`unlinkOrUpgradeIncomingCalls`) follows one rule in every tier. A monomorphic or direct call that pointed to the old `CodeBlock` stays linked and is repointed: it gets the new code's normal entry if its old target was the old `CodeBlock`'s normal entry, and the arity-checking entry otherwise. A polymorphic stub slot is repointed when `PolymorphicCallStubRoutine::upgradeIfPossible` finds the old `CodeBlock` in it, keeping the arity mode recorded when the stub was built; otherwise the call site is unlinked. At doors 1 and 2 the old and new `CodeBlock` are the same, and the comparison reads the old entry from that `CodeBlock`'s current `JITCode`, which is already the baseline code, so a monomorphic call that held the LLInt entry lands on the arity-checking entry (the same address when the function declares no parameters). At door 3 the executable had no `CodeBlock` of that kind (`newCodeBlockFor` asserts it), so nothing is relinked. With the LLInt off, `installCode` runs twice, from the plan's finalization and again at the end of `prepareForExecutionImpl`, and the second call finds the same `CodeBlock` with no incoming calls; Bun's `vm.Script` route repeats it the same way.

`installCode` also runs without setup when optimized code is jettisoned: `CodeBlock::jettison` installs its `alternative()`, a baseline `CodeBlock` whose `BaselineJITData` already exists.

# Entering the new code and spreading it

At door 2 the slow path that installed tells the LLInt where to go. `entry_osr` returns the normal entry, and its arity-check variants the arity-checking entry. `loop_osr` returns the `m_jitCodeMap` address of the current `loop_hint` and the frame's top as the new stack pointer. The baseline's `jitDataRegister` is the register the LLInt uses for its bytecode base (`PB`), so the LLInt reloads it from the `CodeBlock`'s `m_jitData` (`loadBaselineJITConstantPool`) before jumping; the metadata table register is the same in both tiers. `replace` runs while the frame returns, so it installs without entering. Door 1 enters the same way when it runs from the LLInt's slow path and the finished plan is that `CodeBlock`'s own; the `CodeBlock`s whose plans a drain finishes along the way are entered at their next call or crossing. At door 3 the caller enters through the executable's entry, or through a call IC once the call links.

Frames of the same `CodeBlock` deeper in the stack keep interpreting. The next time one of them crosses the counter, `jitCompileAndSetHeuristics` finds `jitType()` at `BaselineJIT`, skips the parked-artifact branch and, once the threshold test passes, returns an entry.

The counter change after installation is what spreads the artifact. Door 1 calls `jitSoon`, which re-arms the body's shared LLInt counter at `thresholdForJITSoon` (100 by default, scaled by the body's history), and door 2 calls `jitNextInvocation`, which sets it to zero. Since every `CodeBlock` of the body adds to that counter, the ones still in the LLInt reach the slow path soon, find the parked artifact and install it through door 2. Door 3 leaves the counter alone, since its `CodeBlock` never runs in the LLInt.

# BaselineJITData

The block holds what the code reaches through `jitDataRegister` and differs per `CodeBlock`: the ICs, the resolved constant pool, the `JSGlobalObject` and the baseline-to-DFG counter. It also holds the stack pointer offset, which is the same for the whole body and which the code already carries as an immediate; the copy exists for the IC handler code, which is shared across functions and cannot use the immediate.

It is a single allocation (`ButterflyArray`). The ICs form an array that ends at the object's base and the pool starts right after the object, so the code reaches IC `i` at `jitDataRegister - (i + 1) * sizeof(HandlerPropertyInlineCache)` and pool slot `i` at `jitDataRegister + offsetOfTrailingData() + i * sizeof(void*)`, and `propertyCache(index)` counts from the end of the span. The emitted code checks neither bound: an IC index too large reads before the allocation, and a pool index too large reads past its end. The allocation is not zeroed: the ICs are default-constructed, and the pool slots hold garbage until step 3 fills every one.

Installation reads four of the artifact's eleven fields (ten in upstream WebKit): the molds in `m_unlinkedPropertyInlineCaches`, `m_constantPool`, `m_jitCodeMap` for the handlers and `m_isShareable` for parking. The other seven stay in the shared artifact, where their readers find them. The emitted code and `operationSwitchStringWithUnknownKeyType` read the two switch tables. OSR exit from the DFG and FTL reads `m_unlinkedCalls` for the return address of an inlined call. The sampling profiler and `CodeBlock::findPC` read `m_pcToCodeOriginMap`, which is null unless the `VM` builds those maps. `shouldOptimizeNowFromBaseline` writes `m_livenessRate` and `m_fullnessRate`, so one `CodeBlock`'s measurement lands in an object other `CodeBlock`s may share. `~CodeBlock` stamps `m_ownerWentAwayAt`, the Bun field that code aging reads.

## IC initialization

`HandlerPropertyInlineCache::initializeFromUnlinkedPropertyInlineCache` turns each mold (`BaselineUnlinkedPropertyInlineCache`, ten fields) into a cold IC, writing every field the IC uses, its handler chain included.

Six fields pass through unchanged. `accessType` picks one of the thirty access types. `preconfiguredCacheType` is the shape the compilation chose: in `get_by_id` and the two `iterator_open`s, `GetByIdPrototype` where the LLInt's mode was `ProtoLoad` and `GetByIdSelf` for any other mode, a site that never ran included; in the other emitters a fixed shape, such as `get_length`'s `ArrayLength`. `propertyIsInt32` says a by-val subscript is a constant int32. `canBeMegamorphic` always arrives false. `doneLocation` is where the IC's fast and slow paths rejoin the code. The sixth is the name, `m_identifier`: a `CacheableIdentifier` holding a `UniquedStringImpl` of the `UnlinkedCodeBlock` or an immortal `VM` identifier, and empty for accesses without a constant name (by-val, `instanceof`, private brands).

`bytecodeIndex` becomes `codeOrigin`, the key under which the DFG finds what the IC learned, and `callSiteIndex`, which locates the exception handler covering the IC when something thrown inside it propagates. The last three bits, `propertyIsString`, `propertyIsSymbol` and `prototypeIsKnownObject`, are dropped. They record what DFG and FTL speculation already guarantees, and only the DFG's initializer copies them.

Only `ArrayLength` carries from `preconfiguredCacheType` into `m_cacheType`; every other IC starts `Unset`. The IC also receives the `CodeBlock`'s `JSGlobalObject` and, from a switch on `accessType`, its `m_slowOperation`, the `*Optimize` operation for the access. The same `accessType` fixes the registers that `registers()` computes on every query. The chain starts as a single node, the `VM`'s slow-path handler for the access type (`InlineCacheCompiler::generateSlowPathHandler`), which calls `m_slowOperation` through the IC. When the `VM` has no handler for that type yet, installation creates it around the `VM`'s slow-path thunk for the access family, generating that thunk if needed (`getCTIStub`, with a must-succeed `LinkBuffer`), and stores it in `SharedJITStubSet`.

`byIdSelfOffset` is the one field left indeterminate, since neither the allocation nor the constructor sets it. That is harmless: the emitted code compares the base's structure with `m_inlineAccessBaseStructureID` before using the offset, and that structure starts null. A GC reset reaches the same state by another route: `clearInlinedHandler` clears the structure and the mirrored handler and leaves `byIdSelfOffset` and `m_inlineHolder` with the dead case's values, inert behind the same comparison.

# What installation does not check

Setup has no failure return and no rollback. Its only code generation, the slow-path handlers and their thunks, uses must-succeed `LinkBuffer`s, so running out of executable memory there crashes the process. Its only assertion, `ASSERT(!m_jitData)` against a second setup, comes after step 2 has already retargeted the handlers.

Nothing compares the artifact's shape with the `CodeBlock`'s. The `BaselineJITData` takes its sizes from the artifact's vectors. A pool index reaches `functionDecl` or `functionExpr` unchecked: `FixedVector::operator[]` goes through `std::span::operator[]`, whose standard-library assertion (on by default through `USE_CXX_STDLIB_ASSERTIONS`, release builds included) kills the process on an index out of range, and an empty table has no storage, so `m_storage->at(i)` dereferences null first. `JITCodeMap::find` searches in `KeyMustBePresentInArray` mode, which in release returns the last candidate instead of null, so a `catch` index missing from the map yields another instruction's address. The layout constants the code bakes (the pool after `sizeof(BaselineJITData)`, the IC stride `sizeof(HandlerPropertyInlineCache)`, stack offsets in `sizeof(Register)` units, and the metadata sizes and alignments generated from the bytecode list) are used as the installing binary defines them, with no comparison to the compiling binary's.

Nothing compares the facts the compilation read from its own `CodeBlock` and turned into code ([compiler.md](compiler.md#sharing-between-codeblocks)) with the installing `CodeBlock`'s:

- The capability class decides whether the code has tier-up counters and profiling writes. If the installing `CodeBlock` is `CannotCompile` and the code has counters, then once its counter crosses, every entry and loop back edge calls `operationOptimize`, which returns at once without re-arming. If the installing `CodeBlock` can compile and the code has no counters, loops never count, and entries count only when `op_enter` takes its slow path, for traps or for the `CodeBlock`'s write barrier, which fires at most once per collection. Natively the `CodeBlock`s of one body disagree only through `setNeverOptimize`, an executable flag that only test code sets.
- `couldBeTainted()` decides whether `op_enter` sets the `VM`'s taint flag. Code compiled for an untainted `CodeBlock` never sets the flag when it runs for a tainted one, and the reverse only over-reports. This happens natively: `SourceCodeKey` has no taint field, so `CodeBlock`s whose providers differ in taint can share one `UnlinkedCodeBlock` and its parked artifact.
- The closure and module scope kinds are baked without a guard, and compiler.md lists what each one does in a `CodeBlock` whose link resolved differently. Natively every link of a body resolves them the same way.

Door 3 also installs without the `shouldJIT` gate that door 2 applies. The gate depends only on options and on the body (its instruction count, and its inferred name and hash for the allowlist), so natively it answers the same for every `CodeBlock` that can find the parked artifact.
