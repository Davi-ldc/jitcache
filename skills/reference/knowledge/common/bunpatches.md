# bun patches

the idea here is to document in a bit more depth what bun is changing that has not been upstreamed, and why it makes sense for them but not for webkit. Overall it is quite compatible with jsc and they merge almost every week, so it makes sense for us to work on top of it.

PS: of the 2,152 commits that separate `WebKit/WebKit@0d58b764f3` from `oven-sh/WebKit@2e2aa2290f`, 333 are merges and rewritten old history, and more than half of the volume is `#include` swaps. In practice, what is left lives in `runtime/`, `heap/`, the bytecode cache and the new `ffi/` directory; the baseline JIT has a single guarded site, a new field in `BaselineJITCode`, and no emitter changed.

## Code aging (PR #557, `CodeBlock::shouldJettisonDueToOldAge`):

The time limit during which a CB is protected upstream (5 s LLInt, 15 s baseline) can make a serverless app keep deleting CBs between calls and redoing the linking and the profiles, though not necessarily recompiling, because the baseline code can stay in the UCB. So, under `USE(BUN_JSC_ADDITIONS)` and with `useExecutionCountForCodeBlockAging` on, once the protection has run out the GC reads the tier's counter during marking (the UCB's `llintExecuteCounter().count()`, the `BaselineJITData`'s `executeCounter().count()`, the `DFG::JITData`'s `tierUpCounter().count()`) and compares it with `m_previousCounter`. If it changed (a loop iteration also counts), the GC updates the sample and sets `m_creationTime` to `now + 2 × TTL`, which keeps `timeSinceCreation() < TTL` true for another `3 × TTL` (`codeBlockAgingLeaseMultiplier`, default 3). That is another 15 s in the LLInt, 45 s in the baseline and 60 s in the DFG from that check on; after that it can renew again. If it did not change, the CB loses this protection, but another reference can still keep it alive. In the LLInt the counter is shared through the UCB, so another running CB of that body also counts.

The FTL has no tier-up counter, and after an FTL compilation failure the DFG can be compiled without the instructions that increment it. These cases cannot age through this system, so they can only die of old age in a collection that Bun marked as idle, if they were created at least 30 seconds ago and the VM has gone 30 seconds without a signal. Here a signal means a collection that finds more than 1 MiB allocated by the whole VM, accumulated since the last update; once past that, it zeroes the accumulated total and renews the timestamp. Without these conditions, they do not age. When an optimized CB ages, its live weak references stop saving it and it stops protecting its baseline alternative; both can still survive through other references. These changes also alter the behavior of the `BaselineJITCode` in the UCB: the slot is now cleared at the end of a full by `Heap::releaseUnusedSharedBaselineCode` if only the UCB still holds the code and the last owner CB died more than 45 s ago. The age `jettison` can also clear that slot, without waiting for the 45 s; the executable memory comes back when the last reference drops.

## Native boundary

The second block cuts copying and rediscovery on the JS→native crossing: a `JSRopeString` iterator that yields each piece without flattening, `ExternalStringImpl` with one extra pointer and static strings, typed arrays through DOMJIT, and the removal of a good share of the C API's `JSLockHolder`s because, in their words, the lock is handled by the bundler. At the embedder interface, `Config::disableEnvironmentOptions()` skips reading `JSC_*` from the environment (the next section covers what Bun sets instead), `Interpreter::executeProgram` accepts an `UnlinkedProgramCodeBlock` the embedder already has, and `VM::addTerminationDeadline` is a per-call wall-clock deadline, separate from the `Watchdog`.

The DFG and the FTL use the `BufferAccessorRegistry` to turn calls such as `Buffer.prototype.readInt32LE` into read or write operations with type and bounds tests, using the profiles and exits already collected. `bun:ffi`, in turn, can generate an entry stub per `JSFFIFunction`, specialized to the given signature, with arity and conversion tests; when a test fails, the call takes the generic path. That stub reuses an invocation thunk the process shares per signature (`SignatureRegistry::intern` and `Signature::invokeThunk`, in `ffi/FFISignature.cpp`). Once generated, the stub becomes the call entry of the `NativeExecutable`, which the `CallLinkInfo` stores as its target (`JSFFIFunction::create`, in `ffi/JSFFIFunction.cpp`).

## Options set by the host

Bun's `JSCInitialize` (`src/jsc/bindings/ZigGlobalObject.cpp`) runs once per process, before the first VM. It turns off `JSC_*`, allows restricted options (`Config::enableRestrictedOptions()`) and sets options in the `JSC::initialize` callback in three layers. Fixed values come first, such as `useSharedArrayBuffer`, `useShadowRealm`, `useJITCage=false` and `useWasmMemory64=false`. Values that depend on the command follow: `evalMode` for `bun --print`/`-p` and the REPL, `useConcurrentJIT=false` and `numberOfGCMarkers=1` for one-shot runs (`bun -e`, `bun --print`), and `thresholdForFTLOptimizeAfterWarmUp=1000000` for `bun test --isolate`. Last, each `BUN_JSC_<option>` environment variable overrides any option, restricted ones included. `notifyOptionsChanged` then derives further values, and the first VM's `Config::finalize()` freezes them all (`runtime/Options.cpp`, `runtime/InitializeThreading.cpp`, `WTF/wtf/WTFConfig.cpp`). One binary, with one build ID, can therefore run with different effective options from one command to the next, and the jsc shell resolves another set from the same WebKit build.

`evalMode` is the only one of these that changes bytecode; the rest change heuristics. With it on, function and module generators start with the call-ignore-result optimization off, so a call in statement position emits `call` instead of `call_ignore_result` and statement lists track completion values (`BytecodeGenerator.cpp`, the `m_defaultAllowCallIgnoreResultOptimization` initializers; `NodesCodegen.cpp`). No key records it: `SourceCodeKey` and the bytecode-cache key are the same under `bun --print` and `bun run` while the bytecode differs.

## Async context and modules

`AsyncLocalStorage` requires a job to carry the context of whoever scheduled it. The fork keeps that context in an `InternalFieldTuple` (a two-field cell with its own `JSType`) hanging from `JSGlobalObject::m_asyncContextData`, captures it when enqueuing promise reactions, and `AsyncContextSwapScope` installs and restores it around each job; until the embedder calls `VM::setAsyncContextTrackingEnabled`, all of it comes down to a flag test, and the DFG/FTL abandon the `PerformPromiseThenOneHandler` fast path when a context is active. For modules, `VM::m_synchronousModuleQueue` makes `require(esm)` load, link and evaluate without yielding to user microtasks and without C++ recursion proportional to the number of modules.

Module namespace lookups also change (`JSModuleNamespaceObject::getOwnPropertySlotCommon`). A lookup of `__esModule` that the module does not export falls through to the namespace object's own Structure. A lookup that finds an empty export slot first calls `SyntheticModuleRecord::materializeLazyExport` and then reads the slot again, so the namespace IC applies to the materialized value; only a `SyntheticModuleRecord` with lazy exports takes this path. Materializing calls the record's source object, which can run JS or throw, so an empty slot there means "materialize or throw", not only TDZ. Linking a module that imports such an export materializes it at link time (`CyclicModuleRecord`), because import reads go straight to the exporting slot.

## Startup

The stated goal is for a `bun build --compile --bytecode` to touch only the pages of what it decodes. The bytecode cache was rewritten in that direction: a per-region layout with the block's arrays up front, 32-bit offsets, deduplicated strings with short atoms inline, a metadata table carried as a per-opcode count and rebuilt with the local sizes (`UnlinkedMetadataTable::expandSteps`), and a portable, deterministic format. The structural change is `useBorrowedBytecodeFromCache`: an `InstructionStream` decoded from a payload the embedder marked as persistent (`CachePayload::setIsPersistent`) points to the mapped bytes instead of copying them, `InstructionStream` gained a `Borrow` mode and reads everything through `span`, and the `UnlinkedCodeBlock` counts the borrowed bytes toward GC pacing as if it had generated the bytecode; the copy savings do not reduce that count. Without an embedder marking a payload as persistent, none of this happens. Outside the cache: an atom table sized for a Bun VM, lazy `WebAssembly` and a skipped timezone prewarm.

## Memory and collector

`WTF::availableMemory()` accounts for the cgroup limit (`uv_get_constrained_memory()`, in `wtf/uv_get_constrained_memory.cpp`); the growth heuristic loses `GrowthMode` and rate limiting, and the one third that decides a full after an eden becomes the `minEdenToOldGenerationRatio` option; `Heap::setInitialAllocationBudget` lets the embedder postpone the first collection when it is about to build a large, entirely live graph. After a post-full sweep, `MarkedBlock::Handle::decommitUnusedPages` returns the pages of a block with no live cell to the OS, except in the `Structure` spaces, because a destructor may read the dead `Structure`. Reservations opt out of THP per mapping and get `MADV_DONTFORK` in `OSAllocatorPOSIX.cpp` (inference: Bun fork+execs children and does not want to copy gigabyte-sized reservations). All of this is policy for a long-lived server process, which explains why it stays in the fork. In Bun's local recipe, profiles without ASAN turn on `USE_MIMALLOC` and `USE_EXTERNAL_MIMALLOC`; with ASAN, the helper keeps the engine's defaults. Our build follows the chosen profile, without assuming libpas in every configuration.

## Yarr, BigInt and platform

Algorithmic work unrelated to the embedder: lookbehind JIT, alternation dispatch and Boyer-Moore in Yarr; Burnikel-Ziegler and Barrett division, divide-and-conquer `toString` and a `maxLengthBits` of 2³⁰ in `JSBigInt`. None of this goes into the baseline image. The rest is the fork as a product: unwind info over the JIT pool on Windows (the +251 in `ExecutableAllocator.cpp` are just that), cross builds and LTO, ARM64 with 64K pages, `$vm` and the JIT disassembler compiled out of release (`BUN_ENABLE_JSDOLLARVM`, `BUN_ENABLE_JIT_DISASSEMBLER`), a 1 MB cap on the per-thread cached assembler buffer, and Bun's inspector domains. Engine fixes that stayed in the fork: IC stub watchpoints outliving the cells of their conditions (`GCAwareJITStubRoutine.cpp`), `JSArray::setLength` clearing live slots with `memset` and racing with the marker, and the `op_check_traps` `InvalidationPoint` kept in every loop. Two `RELEASE_ASSERT`s on `hasAccessBit` in `Heap::stopIfNecessarySlow` are commented out with no justification in the code.

## Node compatibility

To deliver the same observable semantics as Node, the `VM` gains callbacks to format `Error.prototype.stack` (`onComputeErrorInfo`), append async frames (`onAppendStackTrace`, called at the end of `Interpreter::getStackTrace`) and, for CPU profiles, resolve line and column through a sourcemap (`computeLineColumnWithSourcemap`, which JSC only calls from `SamplingProfiler::stackTracesAsJSON`); `ErrorInstance::captureStackTrace` rewrites the stored stack; `JSGlobalObject::overridenDateNow` is honored by `Date.now()`, by the DFG/FTL intrinsic and by `Temporal.Now`; `useV8DateParser` swaps the date parser for V8's; the `ReferenceError` message and the `Function.prototype.toString` of native functions imitate V8; and there is a heap snapshot in V8's format (`heap/BunV8HeapSnapshotBuilder.cpp`). blah blah blah

## Conditions

Compiling with Bun's profiles does not automatically initialize the VM the way the Bun host does. Three regimes matter: the unconditional one applies to everyone, the one guarded by `USE_BUN_JSC_ADDITIONS` is compiled in, and the one that depends on an embedder call stays inert until someone makes it.

| topic | regime |
|---|---|
| heap heuristic, page decommit, THP and `MADV_DONTFORK`, assembler buffer cap, C API locks, Yarr and BigInt, engine fixes | unconditional |
| counter-based aging and release of the shared baseline, repositioned `gcMaxHeapSize`, smaller atom table | guarded, active in our build |
| FTL aging by quietness, error and stack callbacks, `overridenDateNow`, async context, `setInitialAllocationBudget`, bytecode borrowed from the cache, FFI, buffer accessors | depends on the embedder calling, registering or marking |
| mimalloc, `$vm` and disassembler, Windows unwind, 64K pages | CMake/profile or platform; do not assume the same allocator and instrumentation across debug/ASAN and release |

The host also discards code on its own schedule. In `bun run`/`bun <file>` and in workers, but not in standalone executables, once the entry graph's synchronous evaluation finishes while the event loop is alive or concurrent tasks are pending, Bun calls `JSC__VM__runGC(false)`: `Heap::deleteAllUnlinkedCodeBlocks(DeleteAllCodeIfNotCollecting)` followed by a full collection (`src/runtime/cli/run_command.rs`, `src/jsc/web_worker.rs`, `src/jsc/bindings/bindings.cpp`). `Bun.gc(true)` and `BUN_GARBAGE_COLLECTOR_LEVEL=2` call `JSC__VM__runGC(true)`, which uses `PreventCollectionAndDeleteAllCode` and also runs `clearSourceProviderCaches`. The deletion clears the code of every UFE that generated its UCB (UFEs decoded from a bytecode cache never join that set), and with `useBaselineJITCodeSharing` it empties the sharing slot of every live UCB. The non-sync form does nothing if a collection is already running. Live CBs keep their UCBs through `m_unlinkedCode`, but a function whose CB dies later regenerates a fresh UCB, with fresh profiles and an empty sharing slot.
