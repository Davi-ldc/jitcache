# Structures

## Basics
In JSC, `o = { x: 1, a: 2 }` produces a `JSFinalObject`. The hierarchy is:

`JSCell` (8 bytes) -> header, made up of `StructureID` (4); `indexingTypeAndMisc` (1); `type` (1); `flags` (1); `cellState` (1);
                   ↓
`JSObject` (8 bytes) -> only the `JSCell`; it exists so Wasm GC can allocate objects without a butterfly
                   ↓
`JSObjectWithButterfly` (16 bytes) -> `JSObject` + `butterfly`;
                   ↓
`JSFinalObject` (64 bytes with capacity 6) -> `JSObjectWithButterfly` + the inline slots (8 bytes each, usually 6);

These slots hold values, and the `StructureID` points to a `Structure` that describes the keys, the attributes[^attributes] and the offsets (which say which slot the value is in [`PropertyTable`]). So a thousand objs with different values and the same keys can share one structure, and an IC can optimize by going straight to the slot the offset indicates, `if (StructureID == StructureID_cached)`, without going through the structure.

Structures live in a 4 GiB reservation per process (the Linux default; it varies between builds and can be overridden with `structureHeapSizeInKB`), aligned to its own size. `OSAllocator::tryReserveUncommittedAligned` asks the kernel for 8 GiB and gives the ends back with `munmap`; if that fails, `StructureMemoryManager` tries seven more times, halving the size down to 32 MiB. `StructureID` holds the low 32 bits of the `Structure`'s address; `decode()` clears bit 0 (`nuke`, used to keep the GC from visiting the butterfly in the middle of a change) and adds `structureIDBase`. If a Structure dies in the GC, its ID can be reused, which is why the collector resets the ICs that held it as a weak reference before freeing its memory.

If the obj gains more properties than `m_inlineCapacity`, the keys stay in the `Structure` and the extra values go to the butterfly. The layout is `[named prop values][IndexingHeader][elements]` in the contiguous formats: the elements hold the values of indexed properties, such as `obj[1]`, and the header holds `publicLength`, the logical length (`array.length` for arrays), and `vectorLength`, the vector's capacity (without indexed storage, the header and elements are not allocated; without named props outside the object, that area is not allocated). In this layout the `butterfly` pointer points to element 0, with the header in the 8 bytes before it, and the props grow backward in memory: `[prop. 66][prop. 65][prop. 64][IndexingHeader][elem. 0][elem. 1]`, with both the props and the elements in 8-byte slots.

`StaticPropertyAnalyzer` estimates, during bytecode generation, how many properties the object will get. For classes, `FunctionRareData::initializeObjectAllocationProfile` uses the larger of that guess and the sum of the public/private fields across the hierarchy (up to 32 levels). Below 6, `initializeProfile` adds the prototype's non-function properties (up to 6; if it is still zero, it uses 6). In the allocator, leftover bytes become extra slots: `m_inlineCapacity` holds the final capacity inside the `JSFinalObject`, capped at 62 (`maxSizeInBytes = 512`: 16 for the `JSObjectWithButterfly` plus 62 × 8).

Structures form a graph: each one holds `m_transitionTable`, a hashmap (key, attributes, operation[^operation]) -> `*Structure` (with one child or none it stores the pointer directly, with a tag bit, and past that it becomes a `WeakGCMap` and never goes back; the link is weak either way), and `WriteBarrier<JSCell> m_previousOrRareData`, which points to the direct parent (`*Structure`) or to the intermediate `StructureRareData`, with the parent in `m_previous` as a `WriteBarrierStructureID`; the link is strong either way. The rare data holds the property offsets that reach 2¹⁶−2 (`m_maxOffset` and `m_transitionOffset`, which are 16 bits in the `Structure`), the replacement sets with their counter `m_activeReplacementWatchpointSet`, the shared poly-proto set, the cached `ToPrimitive` answer and three caches: the `for-in` enumerator, the own property name lists and the special properties, with their subscribers (I'll explain these later). Every live `JSFinalObject` holds its structure, which holds its parent, keeping the chain alive; in an eden the single child is still marked live, but in a full, `StructureTransitionTable::reconcileWeakReferencesAtGCEnd` clears the slot if nothing else holds it.

When you create an object, like `o1 = {a:b, c:d}`, jsc creates a graph S0 (empty object) with m_transitionTable + a -> S1 + c -> S2. S0 uses the key (prototype, inline capacity, `FunctionExecutable`, `ClassInfo`) in the realm's cache, so `o2 = {a:x}` lands on the same S1 because both capacities round to 2; a `{a:x, c:y, e:z}` rounds to 4 and is born from another S0. Create `o3 = {a:b, k:e}` and S1 now has 2 branches, S2 (+c) and S3 (+k). Removing also adds a child: `delete o3.k` becomes S3 + deletion k -> S4.

Some `Structure`s hold a `PropertyTable`, a hashmap `UniquedStringImpl*` (the key) → offset (into an inline slot or the butterfly) + attributes, consulted on the access slow path. On an addition, the child takes the parent's table, leaves `nullptr` in its place and adds an entry (if the table is pinned, the child copies it and leaves the parent with its own). If the table is not there on an access (the child took it, or the GC cleared it in `visitChildrenImpl`), the JS thread rebuilds it by climbing through `previousID()` until it finds a table or reaches the root. Then it replays the edges on the way back and stores the result in the structure (`materializePropertyTable`). To find `o.x`, the lookup returns the offset of `"x"`; from 0 to capacity−1 → inline, from 64 up → butterfly (so the test is just `< 64`).

If the table does not have the key, the lookup continues through the prototype, stored in `m_prototype` (if it is not poly-proto). In a `{}`, it points to `Object.prototype` (whose prototype is null and immutable). Normally, a prototype change calls `changePrototypeTransition`, which checks whether that transition is already registered and, if not, creates a child with a pinned copy of the `PropertyTable` and cuts the link to the parent (that is, in a `previousID()` chain that is not poly-proto, every shape has the same prototype). The `JSGlobalObject` and anything that has already been a dictionary don't even check that; they create a new shape directly.

When the same code re-creates a constructor (a nested function, or a class inside a function), each one gets its own `.prototype` object, and the instances can have the same keys but land on different Structures. So when an IC finds two different mono-proto shapes at the same access, `shouldConvertToPolyProto` checks whether they share the `sharedPolyProtoWatchpoint` box, have distinct prototypes, and have equal `m_propertyHash` on the object and on each link of chains of the same length. And if that passes, it fires `FunctionExecutable::m_polyProtoWatchpoint`, clearing the subscribed allocation profiles. With `singleton()` also invalidated (it tracks a single `JSFunction` for the executable; another creation, or its collection, invalidates that assumption), on the next creations `initializeProfile` makes the object start out poly-proto.

With poly-proto in the initialization profile, when the object is created, slot 0 of the `JSFinalObject` (`knownPolyProtoOffset`) receives the prototype, and the Structure uses an empty `m_prototype`, which lets objs with different prototypes share the shape. The executable caches that shape for the next profiles. The IC keeps checking the `StructureID` as usual, but to look something up on the prototype it loads the object slot 0 points to and compares that object's `StructureID` with the cached one (a prototype change writes to that slot instead of calling `changePrototypeTransition`), repeating this on the chain links it needs. Brands and private names have one identity per evaluation of the class; sharing a poly-proto root does not unify those identities.

### Array basics

Arrays and functions are objects too: `JSArray` and `JSFunction` descend from `JSObjectWithButterfly` through `JSNonFinalObject`, with no inline slots, and keep their elements (`arr[n]`) and properties (`arr.p`) in the butterfly. A key that parses as an index does not go into the named-property table: `obj["0"]` and `arr[0]` both use indexed storage, and what differs is the `IsArray` bit, the `length` and the JIT's fast paths.

The elements live in the butterfly, and the Structure records their format (normally an array's elements all have the same type, hence the split into `Int32`, `Double` and `Contiguous`) (`indexingModeIncludingHistory`, in `m_blob`): `Int32` (int JSValues), `Double` (raw untagged doubles), `Contiguous` (any JSValue), `ArrayStorage` (a vector with an optional sparse map) and `SlowPutArrayStorage` (the same, where a write to a hole asks the chain). `Undecided` means there are no initialized elements yet, even if `length` is greater than zero. The `CopyOnWrite` bit marks an immutable butterfly that can be shared, used in constant literals and name caches; when an operation needs to modify it, the object switches to its own copy. A format change swaps the Structure, but does not necessarily create a new one or convert the vector: `Int32 → Contiguous` only swaps the shape, because the ints are already represented as JSValues, and the target shape can be one of the realm's ready-made ones.

The realm pre-creates the array shapes, with `Array.prototype` and zero inline slots. So the realm's arrays with the same format can share the Structure, and the IC knows how to interpret the elements as long as the ID does not change. When it changes format, an original array can point to another ready-made shape; if it has gained named properties, it moves to derived shapes and normal transitions. `m_originalArrayStructureForIndexingShape` keeps that catalog; `m_arrayStructureForIndexingShapeDuringAllocation` starts out the same and supplies the shapes for new allocations. If a prototype starts intercepting indices, `haveABadTime` makes new allocations use `SlowPutArrayStorage`, invalidates the optimized code that ignored that possibility and converts the affected existing objects (the table of originals does not change).


## Dictionary

It turns out that a heavily modified object produces a giant chain, so on an addition, `addNewPropertyTransition` looks at how many slots the `JSFinalObject` occupies (`transitionCountEstimate`, holes included) and, past 512 (or 128 for `PutByIdEval` and `UnknownContext`), converts it to a private cacheable dictionary. On a delete or an attribute change, `shouldDoCacheableDictionaryTransitionForRemoveAndAttributeChange` checks whether it has gone past 4096 slots or 128 structures (climbing through `m_previous`) and converts it to a private uncacheable dictionary. The `JSGlobalObject` is born a cacheable dictionary (`JSGlobalObject::init`), and eval converts its `variableObject` before the declarations; a native object with lazy properties in a static table is converted when an operation asks for them to be created in bulk (like `Object.values`).

In both cases, it creates a structure private to the obj, with a new ID (a guard on the old ID does not match), copies the parent's table (or rebuilds it) and calls `pin()`, which sets `isPinnedPropertyTable` (so the GC does not drop the table), stores the table in `m_propertyTableUnsafe` and clears the parent and `m_transitionPropertyName`, taking the shape out of the chain. Then it records the `dictionaryKind` and sets `hasBeenDictionary`, which the children inherit and which blocks reuse in addition, removal and attribute transitions. The old chain, with nothing holding it, becomes garbage for the GC.

In a cacheable dictionary, an addition edits the table in place (`addOrReplacePropertyWithoutTransition`), and a removal or attribute change creates a child with the same `dictionaryKind`, until one of these ops finds more than 128 structures in the chain or more than 4096 slots and turns the obj uncacheable. Here the miss ICs and the prototype-read ICs stop working (since the ID does not cover additions, and an `o.x = 1` would leave an IC that reads `F.prototype.x` wrong), but the rest keeps working normally. Aaand, it gets a second chance the first time an unsupported IC hits it: `tryCacheGetBy` calls `flattenDictionaryStructure`, which brings it back to normal, keeping the ID and the pin, and also sets `hasBeenFlattenedBefore` (it does this with bit 0 of the ID [nuke] set in the header while it works, so the GC postpones its visit to the butterfly if it finds the swap half done). It also happens with uncacheable objs, but they have to be compacted first: `flattenDictionaryStructure` walks the table in insertion order, giving each entry the next offset, moves the values, empties the free list, zeroes whatever is left over inline and in the butterfly and, if the out-of-line capacity went down, swaps the butterfly for a smaller one, or for none when the out-of-line capacity drops to zero and `hasIndexingHeader` is false. The slow path returns `RetryCacheLater`, leaving the caching for a later execution (in theory this is only needed for the uncacheable one, but they do it for both ¯\_(ツ)_/¯). If it becomes a dictionary again, this caching path does not flatten it again (`hasBeenFlattenedBefore`, inherited by the children).

In an uncacheable dictionary, additions, removals and attribute changes all edit the table in place. A deleted offset goes back to the free list (`m_deletedOffsets`) and the next addition reuses it under the same ID, so `propertyAccessesAreCacheable()` keeps every IC (except the element ones) from caching. There is also a second chance on a property read or a private brand check (`actionForCell`; `prepareChainForCaching` and the LLInt's `get_by_id` through the prototype do the same), while `in`, `delete` and `put` give up right away. Every addition tries to reuse the free offsets; when it can't, it takes a new slot and increases `maxOffset`. And if the deleted entries reach a quarter of the hash index, the `PropertyTable` rebuilds itself with only the live ones (`PropertyTable::remove`).

`didPreventExtensions` blocks new public properties; `ReadOnly`, `DontDelete` and `Accessor` govern the existing ones. In arrays, the non-default attributes of indices and the read-only `length` mark live in the `SparseArrayValueMap`; its `sparseMode` is independent of the Structure's `dictionaryKind`. `freeze` does not turn off JS setters, does not make private fields read-only and does not freeze the objects the values reference.

## Watchpoint

A `Structure` has two main groups of watchpoints. `m_transitionWatchpointSet` fires once, when the structure gets its first child (the child's `finishCreation` calls `fireAll`) or when an original array changes format (adding a float to an array of ints converts all its elements without creating a child), and stays `IsInvalidated` forever. If it had subscribers when it fired, the parent sets `transitionWatchpointIsLikelyToBeFired`, which the children inherit: the DFG stops watching the whole shape (`dfgMayWatchIfPossible`), but can still watch conditions on properties. The adaptive subscribers recheck the condition on the new structure (`isWatchable`) and, if it is still valid and watchable, resubscribe to it; otherwise they reset the IC or jettison the CB. Whoever assumed the whole shape jettisons the CB without rechecking. The subscribers are the DFG, to access a known obj without checking the ID, and the IC, to watch the prototypes that the guard on `o` does not test: a `delete F.prototype.x` does not change `o`'s ID, and without the watchpoint the IC would read a deleted slot. A dictionary edited in place creates no child and fires nothing, which is why `prepareChainForCaching` flattens the ones in the chain before caching. Every tier has subscribers here, even the LLInt.

The sets in `m_replacementWatchpointSets` fire when a value is overwritten. The runtime sets up the watch with `ensurePropertyReplacementWatchpointSet(k)`, which creates the rare data if it is missing and, when it creates a set for offset k, sets `isWatchingReplacement`. Whoever assumes "slot k holds V" subscribes to a valid set; `Graph::tryGetConstantProperty` consults the existing one and gives up if it is missing or invalidated. On overwrites by the runtime, `didReplaceProperty()` tests the bit and, if it is set, looks up and fires the set for that offset; the bit clears when the last armed set fires (`m_activeReplacementWatchpointSet` keeps the count). They also fire when a replacement IC is created: `tryCachePutBy`, the LLInt slow path, the megamorphic cache and `tryCachePutToScopeGlobal` call `didCachePropertyReplacement(k)`, which fires k's set (creating it if needed), bringing down whoever assumed a fixed value, and leaves it `IsInvalidated` so that nobody makes that assumption again, since such an IC cannot coexist with code that inlined the value.

Some rare ops add caches to the `StructureRareData`, shared by the objs of the same structure: `Object.keys`, `for-in` and the special properties (`toString`, `valueOf`, `toPrimitive`, `toStringTag` and `toJSON`). The special-property cache stores the inherited value or its absence; for `toStringTag`, it stores the ready-made `[object X]` string. Through the transition watchpoint, it watches the prototypes in between (in case one gains the name) and the prototype that has the property, when there is one; on that last one it also watches for the slot being replaced. The `for-in` enumerator also depends on the whole chain, so it either watches the transition watchpoint of each link or compares the live chain with the cached one on each use, rebuilding only when they differ (`prototypeChain`). And `Object.keys` uses one of the four lists in `m_cachedPropertyNames` (enumerable strings, all strings, symbols, and both); when the shape allows caching, the first query leaves a mark and the second stores the list, without watching anything.

`Structure::defaultToPrimitiveFastAndNonObservable` consults the caches for `Symbol.toPrimitive`, `valueOf`, `toString` and `toStringTag` to decide whether converting a `JSFinalObject` can return the ready-made string without calling the conversion functions. It stores the answer in `m_cachedHasDefaultToPrimitiveFastAndNonObservable`, two bits in the rare data (undetermined, yes or no); clearing one of those caches sets the field back to undetermined.

## Layout

In declaration order:

| field | what it is |
|---|---|
| `m_blob` | 4 bytes used to initialize the header: the element format with history, `type`, the type flags and the initial `cellState` (`DefinitelyWhite`) |
| `m_outOfLineTypeFlags` | the type flags that did not fit in the blob |
| `m_inlineCapacity` | inline slots, fixed at the root |
| `m_lock` | protects the table and the transitions from the compilation threads and from the GC, which takes the lock when deciding whether to mark or drop the table |
| `m_bitField` | 22 fields, three of them wider than one bit (`dictionaryKind`, `transitionKind`, `definitelyNonThenableState`), plus bools such as `isPinnedPropertyTable`, `hasBeenDictionary`, `hasBeenFlattenedBefore`, `didPreventExtensions`, `isWatchingReplacement`, `transitionWatchpointIsLikelyToBeFired` and `mayBePrototype`, and the summaries "has getter/setter", "has non-enumerable" and "has non-configurable" |
| `m_transitionPropertyAttributes` | the attributes of the edge that created this shape |
| `m_structureVariant` | normal, branded (the brand for private instance methods/accessors) or Wasm GC |
| `m_transitionOffset`, `m_maxOffset` | the offset of the property the edge touched, and the largest offset assigned, holes included; both in 16 bits, with the top two values reserved as markers ("none" and "it's in the rare data"), so an offset from 2¹⁶−2 up lives there |
| `m_propertyHash` | XOR of the hashes on each name addition: removing does not change the hash, and re-adding the same name cancels its earlier contribution; this is what `shouldConvertToPolyProto` compares |
| `m_seenProperties` | a bloom filter of the `UniquedStringImpl*` pointers of the added names; when it guarantees absence, `Structure::get` doesn't even open the table; it can give false positives |
| `m_realm` | the `JSGlobalObject` associated with the shape; can be null |
| `m_prototype` | the prototype as a `JSValue`: an obj, `null` at the end of the chain, or empty for poly-proto |
| `m_cachedPrototypeChain` | the prototype chain as a list of IDs, for `put_by_id` in the LLInt and for the enumerator |
| `m_previousOrRareData` | the parent, or the `StructureRareData` that holds the parent |
| `m_transitionPropertyName` | the name of the edge that created this shape; null at the root, in nameless shapes and after `pin` or `pinForCaching` |
| `m_classInfo` | the C++ class of the cells that use this shape, with its method table |
| `m_transitionTable` | the children |
| `m_propertyTableUnsafe` | the table, if this shape has it |
| `m_transitionWatchpointSet` | the transition watchpoint |

[^attributes]: There are six, in bits 1 to 6 of a byte (bit 0 is unused), and JSC stores the negations: `ReadOnly` is non-writable, `DontEnum` is non-enumerable and `DontDelete` is non-configurable. Plus `Accessor`, which marks a getter/setter, and `CustomAccessor` and `CustomValue`, for properties implemented by the host.

[^operation]: There are eighteen `TransitionKind` values, and four use a name or symbol as the key: `PropertyAddition`, `PropertyDeletion`, `PropertyAttributeChange` and `SetBrand`, the last one with the private brand's symbol. `ChangePrototype` carries the new prototype in place of the name. Another twelve use a null key: `AllocateUndecided`, `AllocateInt32`, `AllocateDouble`, `AllocateContiguous`, `AllocateArrayStorage`, `AllocateSlowPutArrayStorage`, `SwitchToSlowPutArrayStorage` and `AddIndexedAccessors`, which deal with indexed storage, plus `PreventExtensions`, `Seal`, `Freeze` and `BecomePrototype`. `Unknown` is the constructors' default value and never becomes a key. Only `PropertyAddition`, `PropertyDeletion` and `PropertyAttributeChange` check the dictionary ceilings. `ChangePrototype` pins the table and cuts the parent; `Seal` and `Freeze` copy the table and mark `DontDelete` (and `ReadOnly`, for freeze, except on accessors) on every entry that is not a private name. `pinForCaching` keeps that table, which is where the rebuild stops. If the starting structure is not a dictionary, they keep the parent and register the child in `m_transitionTable`; in a dictionary, `pin()` cuts the link. `PreventExtensions`, `Seal` and `Freeze` set `didPreventExtensions`; on the obj, all three first call `enterDictionaryIndexingMode`, which moves the elements in ordinary indexed storage into the `ArrayStorage` sparse map.
