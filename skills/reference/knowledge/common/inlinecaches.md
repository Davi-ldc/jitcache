# Abstract

An inline cache (IC) is per-site state that an operation's slow path fills with what it met, such as a structure and an offset, a callee, a resolved scope or the operand types, and that the fast path tests before reusing it. Property ICs affect only what the next compilation produces. Linking a call IC also notifies the callee's `CodeBlock` (`noticeIncomingCall`), which can clear its `m_shouldAlwaysBeInlined`, and while that flag is set the callee does not tier up to the DFG. The baseline never patches machine code for a property or call IC, and the DFG patches only its direct calls: the emitted code dispatches through the IC's data, so a shareable baseline artifact can serve every `CodeBlock` of a body while each `CodeBlock` keeps its own caches. The optimizing tiers read what the ICs learned through the status classes (`GetByStatus`, `PutByStatus`, `CallLinkStatus` and the others). GC and watchpoints reset a property IC to empty when something it relied on dies or changes, and its learning counters survive the reset. There are four families.

1. `PropertyInlineCache` covers named and indexed access: get, put, `in`, `delete`, `instanceof` and private names and brands. Installation turns the artifact's mold for each access site into a `HandlerPropertyInlineCache` in the `CodeBlock`'s `BaselineJITData`. A learned case becomes either the IC's inlined handler or a node in its handler chain, backed by a shared thunk or a stub. At eight cases the IC folds into a megamorphic case or gives up, and an `instanceof` it cannot cache folds at once.
2. `CallLinkInfo` covers the 14 call opcodes. The LLInt and the baseline share one `DataOnlyCallLinkInfo` per site in the `CodeBlock` metadata. A site links monomorphically on its second slow-path trip; after that a `call` grows a polymorphic stub of up to eight callees, while a `construct` goes to virtual dispatch on its first different callee.
3. Scope caches are fields of the `resolve_scope`, `get_from_scope` and `put_to_scope` metadata, resolved at link time by `JSScope::abstractResolve`. The baseline guards the global types, which the runtime can still promote, and bakes the closure and module types into the code without a guard.
4. `JITMathIC` covers `add`, `sub`, `mul` and `negate`. It lives in the `BaselineJITCode`, so every `CodeBlock` sharing the artifact shares it, and it patches the artifact's code at most twice.

The LLInt keeps its own property caches in the opcode metadata, and only its slow paths fill them. The baseline reads them only to choose a code shape, and `GetByStatus` and `PutByStatus` fall back to them when the baseline IC has no information.

# Property inline cache

## Layout and the first test

`HandlerPropertyInlineCache` serves the baseline and the DFG, and `RepatchingPropertyInlineCache` the FTL ([In the FTL](#in-the-ftl)). The baseline and the DFG reach the IC at `jitDataRegister − (index + 1) × sizeof(HandlerPropertyInlineCache)` (`loadPropertyInlineCache`), with the register pointing to the `BaselineJITData` or the `DFG::JITData`. A property IC starts cold: installation builds each baseline IC from its mold with an empty mirror and a chain holding only the slow-path handler ([install.md](../baseline/install.md#ic-initialization)). Besides `doneLocation`, `codeOrigin`, `callSiteIndex`, the identifier and the `JSGlobalObject`, its fields fall into five groups:

| group | fields |
|---|---|
| identity | `accessType`, and the bits `propertyIsInt32`, `propertyIsString`, `propertyIsSymbol`, `prototypeIsKnownObject` and `canBeMegamorphic` |
| dispatch | `m_handler`, the chain head, and `m_slowOperation`, the C++ operation the last handler calls |
| inline mirror | `m_inlinedHandler`, with copies of its structure, offset and holder in `m_inlineAccessBaseStructureID`, `byIdSelfOffset` and `m_inlineHolder` |
| shape | `preconfiguredCacheType`, fixed by the compilation, and `m_cacheType`: `Unset` until a case first reaches the compiler and `Stub` from then on, even if compiling it fails; `get_length` starts at `ArrayLength` |
| learning | `countdown`, `repatchCount` and `numberOfCoolDowns`, and the bits `everConsidered`, `tookSlowPath`, `sawNonCell` and `resetByGC` |

At the by-id sites other than `get_length`, which tests the indexing type instead, the emitted code first compares the base's structure ID with the mirror and then uses the mirrored offset, plus the holder for `GetByIdPrototype`; every other site enters the chain directly. [compiler.md](../baseline/compiler.md#templates-that-leave-records) lists the by-id sites and the three opcodes (`get_by_id`, `iterator_open` and `async_iterator_open`) that choose their shape from the LLInt's `m_modeMetadata`.

Only `prependHandler` fills the mirror, and only when the IC has no inlined handler yet and the new handler's cache type equals `preconfiguredCacheType` (`setInlinedHandler`). Getters, misses, transitions and every case whose type differs from the compiled shape stay in the chain, even as the only case.

## The handler chain

An `InlineCacheHandler` is a ref-counted, malloc-allocated node. It holds a call target and a jump target into its code, the next node, the case's `AccessCase` and, when the case needs watchpoints, the handler's `PropertyInlineCacheClearingWatchpoint`. A node whose case calls JS is an `InlineCacheHandlerWithJSCall`, which embeds a `DataOnlyCallLinkInfo`. The code tests its case and, on a mismatch, loads the next node and jumps to that node's jump target. New nodes are prepended, so the newest case is tested first. The last node is the VM's slow-path handler for the access type, created on first use and shared through `SharedJITStubSet` by every IC of that type (`InlineCacheCompiler::generateSlowPathHandler`); it calls `m_slowOperation` through the IC pointer, checks for an exception and returns.

`compileOneAccessCaseHandler` backs each case with one of three kinds of code. The key it uses for sharing is the access type plus the identity bits.

1. A stateless stub serves cases whose code depends on no structure, such as the length accesses, the indexed accesses by storage format and the megamorphic cases. It is compiled once per VM for each key and case type, and `SharedJITStubSet` keeps it for the VM's life.
2. A handler thunk serves a case that is neither poly-proto nor reached through a global proxy, whose conditions are all watchable, and whose access and case types have one. 58 thunks are VM-independent and generated once per process (`sharedCommonThunks()`); 41 more (custom accessors and values, transitions, the megamorphic getter) are generated per VM on first use (`JITThunks`). A custom accessor with a DOM attribute also needs the case's structure to belong to a subclass of the attribute's class, and a DOMJIT getter gets code compiled for its signature and cached per VM.
3. Any other case gets a stub compiled for it. Through `SharedJITStubSet`, another IC with the same key reuses the stub when `AccessCase::canBeShared` accepts the case.

Thunks and stateless stubs read the case from their node: `createPreCompiled` copies the structure ID, the offset and the holder, new structure and sizes, custom accessor or module slot into it. A compiled stub embeds what it checks as immediates instead: the case's structures (`branchStructure`), the identifier for by-val keys, the prototype objects on a poly-proto chain, and one `branchStructure` per non-watchable condition against that condition's object (`generateWithConditionChecks`). Its node carries only the identifier.

Watchable conditions become adaptive watchpoints on the structures of their objects. When such a structure transitions, the watchpoint rechecks its condition and re-arms on the new structure if the condition still holds; an equivalence condition watches the property's value the same way. When a condition breaks, the watchpoint fires the handler's set, whose `PropertyInlineCacheClearingWatchpoint` resets the IC; other watchpoint sets a case depends on reset it directly when they fire. The reset can arrive while the handler's code is still running, for example when a getter's JS breaks a condition. Handler code reads its node only before calling out, and the stub routine is GC-aware, so the collector releases its code only after seeing it off every stack.

## Learning

Each `*Optimize` slow operation asks `considerRepatchingCache*` whether to cache, usually after performing the access; the int32-subscript path of `get_by_val` asks first. When the consideration sees a non-cell base, it sets `sawNonCell` and answers no. Otherwise the IC sets `everConsidered`, and then:

- a nonzero `countdown` is decremented and nothing is cached. `countdown` starts at 1, so the first slow-path trip only spends it and the second one caches.
- at zero, `repatchCount` is incremented, saturating, whether or not a case is added. The ninth such consideration since the last cool-down exceeds `repatchCountForCoolDown` (8): it zeroes `repatchCount`, sets `countdown` to `initialCoolDownCount << numberOfCoolDowns` (20, 40, 80, 160, then 254), increments `numberOfCoolDowns` and still answers yes. That trip caches, and the next `countdown` trips do not.

Generated code writes `countdown` too. The `failAndIgnore` exit of a compiled stub, and the module-namespace handler when its slot is still in TDZ, add 1 with a non-saturating `add8` before falling through. The slow operation that follows then decrements it instead of caching a miss that no case could fix. The cool-down stops at 254 to leave room for that increment.

The case is built from the `PropertySlot` of the operation's own lookup (`tryCacheGetBy` and its `tryCache*` siblings). A self access takes the slot's offset with no condition. A prototype hit or a miss first prepares the chain (`prepareChainForCaching`), which can flatten a dictionary and leave the caching for a later trip ([structures.md](./structures.md#dictionary)); otherwise the case gets a condition set for the hit, the custom hit or the miss, or a `PolyProtoAccessChain` when the chain is poly-proto. Some `getOwnPropertySlot` overrides reify a property on its first lookup (`JSFunction` for `prototype`, `length` and `name`, `ErrorInstance` for its error info, objects with static property tables), so the base's structure describes that slot only after the lookup has run for that object and name. The impurity flags, `GetOwnPropertySlotIsImpure` and `GetOwnPropertySlotIsImpureForPropertyAbsence`, cover answers that change without a transition and say nothing about lazy reification; `JSFunction` sets neither.

Before a case is added, `upgradeForPolyProtoIfNecessary` compares its structure with every listed case's, except for `instanceof`. If `Structure::shouldConvertToPolyProto` accepts a pair and their shared poly-proto watchpoint is still valid, the case is dropped, the watchpoint fires and the IC resets (`fireWatchpointsAndClearStubIfNeeded`), so later allocations start poly-proto ([structures.md](./structures.md)).

Up to `maxAccessVariantListSize` (8) cases accumulate. `tryFoldToMegamorphic` sees each new case together with the listed ones and first returns any megamorphic case among them, the new one included, so a megamorphic case added at any size replaces the list at once. `tryCacheInstanceOf` relies on this: when it cannot build a hit or miss case, it creates `InstanceOfMegamorphic`, the prototype walk, itself. Otherwise the fold waits for eight cases, and then `instanceof` always folds into the prototype walk.

The get, put and `in` forms, by id or by value, fold into a `MegamorphicCache` lookup when every case is a plain load or miss, a replace or transition, or an `in` hit or miss, none of them through a global proxy. Poly-proto cases must be under half the list for get and `in` (`thresholdForUndesiredMegamorphicAccessVariantListSize`), and absent for put, where the case's structure and every prototype's must also be mono-proto and leave `put` and `getPrototype` alone (`canUseMegamorphicPutFastPath`). By id, the name must not be an index or `__proto__`, nor, for get and `in`, `length`, `name` or `prototype` (`canUseMegamorphicGetById`, `canUseMegamorphicPutById`). Only `AccessType::GetById`, which `get_by_id` shares with the by-id loads inside the iterator opcodes and `instanceof`, has a megamorphic getter: when every case is a getter, none through a global proxy or poly-proto, it folds into one instead, which finds the getter in the `MegamorphicCache` and calls it. The direct forms, private names and brands, and `delete` never fold.

The fold also clears the mirror, and the chain becomes the megamorphic node followed by the slow-path handler. For get, put and `in`, the slow call becomes the `*Megamorphic` operation. When that operation meets a base or key the cache cannot serve and the countdown allows it (`considerRepatchingCacheMegamorphic`), it gives up through `repatchGetBySlowPathCall` or its put and `in` siblings: the chain goes back to the bare slow-path handler, `m_cacheType` stays `Stub`, and the slow call becomes the `*GaveUp` operation. `instanceof` goes straight to its `*GaveUp` operation. Where no fold applies, the eighth case is compiled as final code and the slow call becomes the `*GaveUp` operation, which never caches, and every other give-up answer from the caching helpers ends the same way. Only the `*GaveUp` operations write `tookSlowPath`, so the bit means the IC gave up and a later execution still reached its slow path. `canBeMegamorphic` would allow an earlier fold, but nothing sets it.

## Reset

`PropertyInlineCache::reset` has three callers:

- GC finalization (`reconcileWeakReferencesAtGCEnd`), when the mirrored structure or any reference held by the inlined handler or the chain has died. It takes no `CodeBlock` lock, and afterwards it sets `resetByGC`, which nothing reads.
- `PropertyInlineCacheClearingWatchpoint`, when a watched condition breaks.
- The poly-proto route above.

Reset clears the mirrored structure and the inlined handler, leaving `byIdSelfOffset` and `m_inlineHolder` inert without the structure. If the IC held cases, it also replaces the chain with the bare slow-path handler, switches the slow call back to the `*Optimize` variant and sets `m_cacheType` to `Unset`, `get_length` included. Every field of the learning group survives. The megamorphic give-up in [Learning](#learning) also empties the chain, without calling `reset`, and leaves `m_cacheType` at `Stub`.

## Readers

OSR exit also reads the IC at runtime. When a DFG or FTL frame exits inside an inlined getter, setter or proxy trap whose caller runs in baseline, the return address is the `doneLocation` of the baseline IC at the call's bytecode index (`callerReturnPC`, with a `RELEASE_ASSERT` that the IC exists). A call site with a checkpoint, such as the property loads inside `instanceof` and the iterator opcodes, returns through the LLInt's checkpoint trampoline instead.

Seven status classes read the IC under the `CodeBlock` lock: `GetByStatus`, `PutByStatus`, `InByStatus`, `DeleteByStatus`, `InstanceOfStatus`, `CheckPrivateBrandStatus` and `SetPrivateBrandStatus`. Each starts from `PropertyInlineCache::summary`, which lists the case of the inlined handler and of each chain node (`listedAccessCases`) and checks, in order: a single `LoadMegamorphic`, `StoreMegamorphic` or `InMegamorphic` case, or its indexed form, gives `Megamorphic`; `tookSlowPath` or `sawNonCell` gives `TakesSlowPath`; an IC never considered gives `NoInformation`; anything else gives `Simple`. `Simple` and `TakesSlowPath` have "makes calls" variants, chosen when a listed case does calls (`AccessCase::doesCalls`, which also counts C++ accessors, the megamorphic getter and stores, the intrinsic size getters of resizable or growable shared typed arrays and `DataView`s, and transitions that grow the out-of-line storage of an object that could have an indexing header). A slow or empty summary settles the status. Any other summary, `MakesCalls` included, lets the class look at `m_cacheType` and the cases, and a `Megamorphic` status comes out only while `tookSlowPath` is clear; the DFG then emits its megamorphic node (`GetByIdMegamorphic` and its siblings), which looks the `MegamorphicCache` up inline. The other two megamorphic cases go through the case scan: `GetByStatus` answers `MakesCalls` for the getter fold, because `GetByIdMegamorphic` serves only values, and `InstanceOfStatus` answers `Megamorphic` for `InstanceOfMegamorphic`, which the DFG compiles into its own `InstanceOfMegamorphic` node, an inline prototype walk, unless the site has a `BadType` exit. An IC that was considered but holds no case, because the site has not cached yet or was reset, reads differently per class:

| status class | considered, no case, no slow bit |
|---|---|
| `GetByStatus` | `NoInformation`, then the LLInt cache; for `get_length`, still `ArrayLength`, `LikelyTakesSlowPath` with no fallback |
| `PutByStatus` | `LikelyTakesSlowPath`, commented "we attempted to cache but failed" |
| `InstanceOfStatus` | `TakesSlowPath`, commented "conservative" |
| the other four | `NoInformation`, with no fallback |

An IC never considered and with no slow bit reads `NoInformation` in all seven, and only `GetByStatus` and `PutByStatus` then consult the [LLInt cache](#llint-property-caches). An IC left at `Stub` with no case reads `Simple` with no variants. If a `put_by_id` or a private-name put still has no information, the DFG plants a `ForceOSRExit` before the generic put; a get plants none, although a value profile with no prediction still forces one ([profiles.md](./profiles.md#drain)). A frequent exit site recorded in the `UnlinkedCodeBlock` for that bytecode (`BadCache` and related kinds) turns the status into its slow version whatever the IC says.

## In the FTL

Option initialization forces `useHandlerICInFTL` off, so the FTL uses `RepatchingPropertyInlineCache`. The FTL's get, put and `in` by-id sites, with-this included, are a slab of code in the function body. The runtime writes a first self access, or an array or string length, into the slab with the `structureID` as an immediate, and otherwise turns the slab into a jump to a stub holding every case (`rewireStubAsJumpInAccess`). New cases are buffered, and the stub is regenerated after several further trips that pass `countdown` (`initialRepatchBufferingCountdown`, then `repatchBufferingCountdown`), or at once when a cool-down begins. The other FTL sites start as a patchable jump and go straight to a stub.

# LLInt property caches

`get_by_id`, `get_length`, the `next` load of the two iterator opens, the `done` and `value` loads of `iterator_next` and the two `instanceof` loads each carry a `GetByIdModeMetadata`. Its mode is `Default` (structure ID and offset of an own data property), `ProtoLoad` (structure ID, offset and holder), `ArrayLength` or `Unset`, and its `hitCountForLLIntCaching` starts at `prototypeHitCountForLLIntCaching` (2). `performLLIntGetByID` resets the entry to `Default` and zeroes the count on every own data-property hit, storing the structure only if its accesses are cacheable and it needs no impure-property watchpoint. Each prototype hit on a data property decrements the count, and the one that reaches zero calls `setupGetByIdPrototypeCache` once. That setup gives up on a structure that prohibits caching or is impure, on a dictionary already flattened, or on a condition set that is invalid or not watchable; otherwise it installs `LLIntPrototypeLoadAdaptiveStructureWatchpoint`s in `CodeBlock::m_llintGetByIdWatchpointMap` and stores `ProtoLoad`. `setArrayLengthMode` zeroes the count too, and nothing rearms it. The only `setUnsetMode` call, in `setupGetByIdPrototypeCache`, is unreachable because `performLLIntGetByID` calls that function only for a value slot, so a miss is never cached. `get_by_id_direct` and `put_by_id` have simpler entries ([table](#table)), and private names and brands have entries of their own, which only the LLInt reads.

A `CodeBlock` born in baseline ([install.md](../baseline/install.md), third door or with the LLInt off) keeps these fields at their link state for its whole life, under default options. GC clears the entries whose references died (`CodeBlock::reconcileLLIntInlineCachesAtGCEnd`); a `Default` entry loses its structure and offset and keeps its zeroed count. A `ProtoLoad` entry is cleared by its watchpoints when a condition breaks, and by GC when the base structure or a watched object dies; for `iterator_next` and `instanceof` that clears both mode entries of the instruction.

`GetByStatus::computeFromLLInt` takes a `Default`-mode structure ID, or `get_by_id_direct`'s, and re-derives the offset with `Structure::getConcurrently`. It answers `NoInformation` for any other mode, a zero ID, an impure structure or a missing or custom property, and always for the by-val, with-this and private-name gets. `PutByStatus::computeFromLLInt` reads the two `put_by_id` structure IDs: with no new structure it returns a replace, and for a transition it re-derives the offset and, unless the put is direct, regenerates the setter-miss conditions. The cached offsets, the proto-load holder and the structure chain serve only the LLInt and GC.

# Call link info

## Fast path

The fast path loads the target (`m_monomorphicCallDestination`), the expected callee and the callee's `CodeBlock` from the IC ([compiler.md](../baseline/compiler.md#templates-that-leave-records)). On a matching callee the site calls the target, and it does so for any callee when the expected-callee field has its low bit set, which the polymorphic and virtual modes do by storing `1` (`polymorphicCalleeMask`); the target is then the polymorphic or the virtual-call thunk. On any other callee it calls `LLInt::defaultCall()`, which enters the link slow path. Before calling, it stores the IC's `CodeBlock` in the callee frame's `CodeBlock` slot, from which the callee's entry loads its base registers. Only `DirectCallLinkInfo`, which the DFG and the FTL create, rewrites a call instruction.

## Linking

`DataOnlyCallLinkInfo::initialize` starts the site in `Init`, or in `Virtual` when `useLLIntICs` is off. `linkFor` resolves the callee and then acts on the mode. A callee that is neither a `JSFunction` nor an `InternalFunction` goes to `handleHostCall` and leaves the IC untouched. For a `JSFunction`, it first prepares the callee's `CodeBlock`, so the callee exists from the first trip. In `Init`, the first trip sets `seenOnce` and links nothing; the second calls `linkMonomorphicCall`, which stores the callee, the entry point and the `CodeBlock`, records `lastSeenCallee` and registers the call in the callee `CodeBlock`'s `m_incomingCalls`. For a JS callee, the entry point is the arity-checking one when the call passes fewer arguments than the callee declares, or is varargs. In `Monomorphic` or `Polymorphic`, a missed `call` goes to `linkPolymorphicCall` and a missed `construct` to `setVirtualCall`.

`linkPolymorphicCall` rebuilds the `PolymorphicCallStubRoutine` from the old variants plus the new one. If any variant is a closure call, all of them become keyed by executable and `hasSeenClosure` is set; an `InternalFunction` variant then gets no slot and always misses. The site goes virtual past `maxPolymorphicCallVariantListSize` variants (8, or 5 for a top-tier or Wasm caller) or when any JS callee has no `codeBlockForCall()`. `setVirtualCall` sets `clearedByVirtual`.

A shared thunk reads `m_stub` from the `CallLinkInfo` and scans the stub's trailing `CallSlot`s, at most 32 bytes each: callee or executable, count, index, arity mode, target and `CodeBlock`. The counting thunk increments the matching slot's `m_count`. Stubs for a top-tier or Wasm caller, or with no slot, use a thunk that counts nothing, and such a stub has no edges for the status to read. Every rebuild creates fresh slots, so the counts cover only the calls since the last new variant.

## GC and tier changes

`CallLinkInfo::reconcileWeakReferencesAtGCEnd` unlinks a monomorphic call whose callee died. If that callee was a `JSFunction` whose executable is still alive, it sets `hasSeenClosure`; otherwise it sets `clearedByGC`. A polymorphic stub with a dead slot is unlinked and sets `clearedByGC`, and a dead `lastSeenCallee` is cleared under the same rule as the monomorphic callee. Unlinking resets the site to `Init` and clears `seenOnce`, so relinking takes two trips again. Nothing clears `clearedByGC`, `clearedByVirtual` or `hasSeenClosure`. When the callee's `CodeBlock` is replaced, `installCode` retargets or unlinks the incoming calls ([install.md](../baseline/install.md#installation), step 4).

## What the optimizing tiers take

`CallLinkStatus::computeFromCallLinkInfo` answers slow path when `clearedByGC` or `clearedByVirtual` is set, or when the stub has no edges. With edges, it sorts them by count and keeps as variants the first `maxPolymorphicCallVariantsForInlining` (5) with at least `frequentCallThreshold` (2) calls; the rest count as unknown. With no variant left, or fewer than `minimumCallToKnownRate` (0.51) known calls per unknown one, it answers slow path; otherwise it returns the variants, setting `couldTakeSlowPath` if any call was unknown. Without a stub it returns `lastSeenCallee`, reduced to its executable when `hasSeenClosure` is set, or nothing. Exit sites adjust the result: `BadType` and `BadExecutable` add the slow path, and `BadConstantValue` turns a stub-based status into a closure call and adds the slow path to any other; for a `CodeBlock` still in the LLInt, those exit sites answer slow path before the IC is read. An optimizing compile first consults the ICs and recorded statuses of the code it replaces (`ICStatusContextStack`) and, for an origin that code did not inline, merges in the baseline's status; the baseline alone is the fallback.

A DFG compile outside the FTL acts only on a status with exactly one variant and no slow path. It inlines that callee or, when the call shape, the exit sites and the executable allow it, emits a `DirectCall` behind a callee check. Every other status becomes a generic call, because switching over several callees is FTL-only (`usePolymorphicCallInlining`), so per-callee counts reach the DFG only through the thresholds above. An empty status rules out inlining even for a proven-constant callee, since `refineStatically` needs a variant, although strength reduction still turns a call to a constant `JSFunction` or a function allocation into a `DirectCall`. Inlining also needs the callee's baseline or LLInt `CodeBlock` (`baselineCodeBlockFor`).

# Scope caches

Linking runs `JSScope::abstractResolve` in `CodeBlock::finishCreation` and keeps its answer in the metadata of `resolve_scope`, `get_from_scope` and `put_to_scope`: a `ResolveType` plus the fields its type needs, listed in the [table](#table). Each access has a single answer, so an update overwrites those fields with no case list or stub. The type only moves forward, in both the plain and the `WithVarInjectionChecks` forms: from `UnresolvedProperty` to `GlobalProperty` when the slow path finds the property on the global object, and to `GlobalLexicalVar`, directly or from `GlobalProperty`, when the name resolves to a global lexical binding (`tryCacheGetFromScopeGlobal` and `tryCachePutToScopeGlobal`, and `slow_path_resolve_scope` and `operationResolveScopeForBaseline` for `resolve_scope`). The baseline compiles against the type in the metadata at compile time, which may already be promoted.

Linking normalizes some types first. `resolve_scope` never sees `ResolvedClosureVar`. `get_from_scope` turns `ResolvedClosureVar` into `ClosureVar` without resolving, and `ModuleVar` into `ClosureVar` over the module environment. `resolve_scope` with `ModuleVar` stores the module environment in the metadata and also holds it as a constant of the `CodeBlock`.

Most closure and module types are baked into the code with no type check. [compiler.md](../baseline/compiler.md#sharing-between-codeblocks) lists each baked shape, and explains why `get_from_scope` with `ClosureVarWithVarInjectionChecks` always calls the C++ operation.

A global type's fast path first reloads the type from the metadata and compares it with the compiled one. `resolve_scope` then compares the global lexical binding epoch for `GlobalProperty`. `get_from_scope` and `put_to_scope` with `GlobalProperty` check the global object's structure and index its butterfly, and with `GlobalVar` or `GlobalLexicalVar` they read or write through the stored pointer; `GlobalLexicalVar` adds a TDZ test on every read and on writes outside initialization, and `GlobalVar` writes check that the variable is not read-only. A write takes the slow path while the variable's watchpoint set is valid, so the slow path can fire it, and writes inline once the set is invalidated or absent; linking invalidates the set of a `ClosureVar` write and stores none. Types other than the compiled one go through shared thunks in `resolve_scope` and `get_from_scope`, which dispatch on the type at runtime, and through an inline dispatch over the six global types in `put_to_scope`. `Dynamic`, like a `put_to_scope` on `ModuleVar`, always takes the slow path.

# Math inline cache

A MathIC's inline code follows the arithmetic profile at compile time ([profiles.md](./profiles.md#arithmetic-profile)), and [compiler.md](../baseline/compiler.md#templates-that-leave-records) describes its shapes and the code locations the IC records. The IC lives in the artifact's `MathICHolder` and keeps a pointer to the profile in the `UnlinkedCodeBlock`, so every `CodeBlock` sharing the artifact shares both; the emitted code reaches the IC through an absolute pointer, and nothing ties the IC back to its bytecode.

With profiling emitted, the slow call is the profiled repatching operation while the inline code is a patchable jump or a minimal fast path, and the profiled non-optimizing operation when it is the full snippet. Without profiling it is always the repatching operation. Either repatching operation calls `generateOutOfLine`, which patches the artifact's code in place, at most twice. An empty profile at compile time sets `m_generateFastPathOnRepatch`. The first call then clears it and tries a fast path specialized to the types observed so far; on success it links the inline jump to that snippet and, if the snippet needs no further repatching, repoints the slow call to the non-optimizing variant. Otherwise, or on a later trip, it repoints the slow call first and then emits the full snippet, keeping the installed code if generation or allocation fails. Repointing keeps the call's arguments. The profiled non-optimizing variants of `add`, `sub` and `mul` take the IC and read its profile, but `negate`'s, `operationArithNegateProfiled`, takes a `UnaryArithProfile*` and receives the IC's address. From then on that site ORs its observations into the IC's first halfword, the low bits of `m_arithProfile`, and its profile in the `UnlinkedCodeBlock` stops learning from the slow path. The DFG and the FTL use the same class, bound to the baseline's profile: their repatching call still records operand types there, but their ICs emit no profile writes and never observe results; results from those tiers reach the profile only through OSR exit.

# Table

Per-VM and per-function caches (`HasOwnPropertyCache`, `MicrotaskCallCache` and the allocation profiles in `FunctionRareData`) are left out, and so are the caches only optimized code owns: `RepatchingPropertyInlineCache`, `OptimizingCallLinkInfo` and `DirectCallLinkInfo`.
