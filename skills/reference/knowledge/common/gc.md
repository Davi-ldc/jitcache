# Abstract

JSC's collector has two kinds of cycle. The full one visits the whole heap. The eden one visits only what was allocated since the previous collection and the old objects that a `WriteBarrier` noted as changed (`Heap::writeBarrierSlowPath`), and treats the rest as live without looking at it. A request can name the kind: JSC's GC timers do, the full one asking for a full and the eden one for an eden (`FullGCActivityCallback::doCollection`, `EdenGCActivityCallback::doCollection`), and so do explicit calls such as `collectNow(Sync, CollectionScope::Full)`. When it names neither, as with the request that allocation triggers (`Heap::collectIfNecessaryOrDefer`) and the routine one from Bun's own GC timer (`GarbageCollectionController::perform_gc`), the edens before it choose between the two: one that ends with the room still left below the heap's ceiling under a third of that ceiling marks the next such request as full, and the mark holds until a full starts. Such a request also becomes a full when memory is critical (a footprint above 80% of the available memory), and with `useGenerationalGC` off, or in mini mode, every cycle is full (`Heap::shouldDoFullCollection`).

With the world stopped, the GC gathers the roots: it scans the stacks word by word and reruns the sets the `VM` keeps. With the world running, the parallel markers only follow edges inside the heap, starting from what has already been reached. In both cases, marking is draining a work stack: every object reached goes onto it, and draining is popping one off, following its fields and pushing whatever it reaches. The two rounds take turns: the GC stops the world, gathers roots and drains in slices of 0.3 ms or of 30% of the time the gathering took, whichever is greater. When a slice ends with work left, the scheduler hands the world back with a probability equal to the mutator's utilization, which starts at 70% and falls as the mutator spends the cycle's allocation headroom; below 1%, it keeps the world stopped until marking ends (`StochasticSpaceTimeMutatorScheduler::synchronousDrainingDidStall`). With the world released, the parallel markers drain until the work or the headroom runs out; then the GC stops the world again and, since the stack changed in the meantime, gathers the roots once more (`Heap::runConcurrentPhase`). As soon as a round with everything stopped adds nothing, it has the whole state and can move on. With `useConcurrentGC` off, the world stays stopped for the whole marking (the `Heap` constructor).

Then, with the world still stopped, the GC walks the revisit list: in the marked code blocks it drains the profiles, if the block is LLInt or baseline (a DFG or FTL one leaves that to its baseline alternative, `CodeBlock::reconcileWeakReferencesAtGCEnd`), resets the inline caches whose structures died and disconnects the calls whose callee died; for the ones left unmarked, the owner executable is the one that acts, jettisoning the code block and clearing the edge to it. This pass frees no cell, no executable memory and no `BaselineJITData`; the cases and handlers a reset deletes are plain malloc objects. Right after it, in the same stop, `deleteUnmarkedCompiledCode` destroys the IC stubs that lost their last reference and that no stack is executing, and, on a full, `releaseUnusedSharedBaselineCode` drops the baseline code that only the UCB holds and whose last owner CB died more than 45 s ago, under the defaults; both can return executable memory to the pool (`Heap::runEndPhase`).
