# Locks

Locks divide access to VMs, `CodeBlock`s, `Structure`s, symbol tables, compilation queues, thunks and allocators between the GC/compilation threads and the main thread. The `JSLock`, one per VM, guarantees that only one thread runs JS at a time; compilation and marking do not need it. When that thread acquires the lock, heap access comes with it. In some cases, such as waiting for a compilation, it can give that permission back so the GC can stop the world, while keeping its monopoly on running JS in that VM.

The `JITWorklist` organizes compilation requests, including requests from different VMs, with JS threads enqueuing and workers dequeuing requests under `m_lock`. The GC takes `m_rightToRun`, which the workers yield at safepoints, to visit the plans and the compilation's references; the baseline can keep compiling inside that window, but it waits for the GC to hand the lock back before leaving it.

`CodeBlock::m_lock` coordinates changes to the ICs with the reads done by compilation and marking, but it does not protect every field. Profiles are written and drained without it, and a `CallLinkInfo` can be disconnected while the compiler holds the lock: the operation can start from the callee, which does not know which CB owns that cache. The `CallLinkStatus` query tolerates this because the stub it has already loaded stays alive until the next GC, and the stub's variant list does not change after creation.

| lock | what it protects | who takes it and where |
|---|---|---|
| `JSLock` (`VM::m_apiLock`) | JS execution in a VM | The thread that enters the VM, through `JSLockHolder`; it is recursive. Compilation and marking do not depend on it. |
| `JITWorklist::m_lock` | queues, stages and ready plans | The JS thread in `enqueue` and `removeAllReadyPlansForVM`; workers in the `AutomaticThread` loop that calls `poll` (`AutomaticThread::start`) and at the edges of `work`; the GC in `visitWeakReferences` and `removeDeadPlans`. Compilation and finalization run outside it. |
| `JITWorklist::m_suspensionLock` | one pool suspension at a time, across all VMs | The GC in `suspendAllThreads`, before taking the workers' rights to run; `resumeAllThreads` releases it after handing all of them back. When the collector has suspended the workers, `resumeThePeriphery` takes each visitor's right to run before `resumeAllThreads`, so the nesting order is this lock, then the workers' rights, then a visitor's right. |
| `JITWorklistThread::m_rightToRun` | entry into and exit from the regions the GC can visit | The worker outside safepoints; the GC in `suspendAllThreads`. `Safepoint::begin` releases it and the destructor takes it back. That wait does not hold `JITWorklist::m_lock`. |
| `SlotVisitor::m_rightToRun` | a marker's visits to cells, including the value-profile drain in `CodeBlock::visitChildren` | Each visitor for the whole of `SlotVisitor::drain` and `performIncrementOfDraining` (the mutator's incremental marking, skipped under GC deferral), yielding at `safepoint()` after each batch of up to `minimumNumberOfScansBetweenRebalance` (100) cells; a marker waiting for work in `drainFromShared` does not hold it. The conductor in `resumeThePeriphery`, one visitor at a time, to update its stopped-mutator flag. A thread that holds every visitor's right knows that no concurrent visit is in flight and none can start. Constraints also visit cells outside this lock, but only in the fixpoint, with the world stopped. It is the markers' counterpart of `JITWorklistThread::m_rightToRun`. |
| `CodeBlock::m_lock` | certain ICs, fields and references of the CB | The runtime when repatching (`tryCacheGetBy`, `tryCachePutBy`, `tryCacheInstanceOf`); the compiler in `GetByStatus::computeFor` and `CallLinkStatus::computeFor`; the GC in `visitChildren` (before the drain) and `ScriptExecutable::visitCodeBlockEdge`. `DirectCallLinkInfo::repatchSpeculatively` takes the callee's. The body of `jettison` does not acquire it. |
| `UnlinkedCodeBlock::m_lock` | initialization of `m_liveness`, and the exit profile | Compiler threads in `livenessAnalysisSlow`; writes to the `DFG::ExitProfile` in `add`, and queries in `QueryableExitProfile::initialize` and in the callers of `ExitProfile::hasExitSite`, which receives the lock already held (`bytecode/DFGExitProfile.cpp`, `CallLinkStatus::computeExitSiteData`). It does not cover all of the UCB's profiles. |
| `UnlinkedCodeBlock::cellLock()` | publication of the bytecode, vectors and rare data | The generator in `UnlinkedCodeBlockGenerator::finalize`; the GC in `UnlinkedCodeBlock::visitChildrenImpl`. The generator releases it before issuing the write barrier. |
| `Structure::m_lock` | property table, transitions and replacement sets | The mutator when changing/materializing the table and preparing watchpoints; the compiler in `getConcurrently`; the GC in `visitChildrenImpl`. The lookup can take the lock of the ancestor that has the table, one at a time. |
| The object's `cellLock()` | concurrent accesses to the object during validation and butterfly shrinking | The compiler when validating `PropertyCondition::Equivalence`; the mutator in `Structure::flattenDictionaryStructure`. When both are needed, the object's lock comes before `Structure::m_lock` (`runtime/JSCell.h`). |
| `StructureCache::m_lock` | map of reusable shapes | The mutator when inserting/clearing; the compiler in `emptyObjectStructureConcurrently`. The mutator's normal lookup does not take the lock (`runtime/StructureCache.cpp`). |
| `SymbolTable::m_lock` | entries, watchpoints and the derived vector `m_localToEntry` | The mutator; the DFG in `Graph::tryGetConstantClosureVar`; the GC in `visitChildrenImpl`. The DFG releases it before registering the dependency in the graph. |
| `JSGlobalObject::m_referencedGlobalPropertyWatchpointSetsLock` | the name → watchpoint set map | Lookup in `getReferencedPropertyWatchpointSet` and insertion in `ensureReferencedPropertyWatchpointSet`, under `ENABLE(DFG_JIT)`. It does not cover every later use of the set. |
| `RepatchingPropertyInlineCache::m_bufferedStructuresLock` | structures and identifiers buffered in the repatching IC | The runtime in `considerBufferingStructure`; the GC in `visitBufferedStructures` and `pruneDeadBufferedStructures`. The CB's write barrier comes after the lock is released. |
| `DirectEvalCodeCache::m_lock` | changes to and visits of the direct eval cache | The mutator in `setSlow` and `clear`; the GC in `visitAggregateImpl`. The normal lookup does not take the lock (`bytecode/DirectEvalCodeCacheInlines.h`). |
| `DFG::Plan::m_mustHandleValueCleaningLock` | the one-time cleaning of the OSR entry's dead locals | The compiler and the GC in `cleanMustHandleValuesIfNecessary`. The subsequent visit to the values happens outside this lock. |
| `VM::m_scratchBufferLock` | the scratch buffer list, its growth, and the clearing of the active lengths | Compilation/runtime in `scratchBufferForSize` and `clearScratchBuffers`; the GC in `gatherScratchBufferRoots`. It does not cover each emitted access to the contents. |
| `CodeBlockSet::m_lock` | the CB registry | Insertion in `CodeBlockSet::add`, from the `CodeBlock` constructors; iteration in `CodeBlockSet::iterate` (behind `Heap::forEachCodeBlock` and `JSGlobalObject::bumpGlobalLexicalBindingEpoch`) and `iterateCurrentlyExecuting`; the conservative scan in `ConservativeRoots::add`, which marks the CBs it finds. While the VM runs, `VMTraps` takes it to test stack frames against the set before installing trap breakpoints (with `tryLock` in its signal handler) and to walk every CB, jettisoning those with breakpoints; `SamplingProfiler::takeSample` takes it after the machine-threads lock, and `VMInspector`, a debugging tool, with `tryLock`. Dead CBs leave the set in `clearCurrentlyExecutingAndRemoveDeadCodeBlocks`, in the collector's End phase, without the lock; `CodeBlockSet::remove` has no caller. |
| The `MarkedBlock`'s `CountingLock` and `BlockDirectory::m_bitvectorLock` | mark transitions and the blocks' allocation state | In `aboutToMarkSlow` and `Handle::didConsumeFreeList`, the block comes before the directory. `Handle::decommitUnusedPages` also takes the header lock to harvest the marks and releases it before the decommit: non-Windows branch, with `decommitUnusedMarkedBlockPages`, eligible pages/block, outside Structure spaces/shutdown, and after a full (or an eden, enabled by its own option). |
| `WarmUpBlockProvider::m_lock` | the reserve of pre-touched `MarkedBlock`s and the helper's state | The mutator in `tryTake`; the helper at the edges of `refill`, without holding it while allocating/touching pages. It is only reached through the allocator with `MarkedBlock` size/alignment, `useWarmUpMarkedBlocks`, a nonzero count and the `warmUpMarkedBlockStartAfterBlocks` threshold reached; outside mini mode and `MALLOC_HEAP_BREAKDOWN` (`heap/FastMallocAlignedMemoryAllocator.cpp`). |
| `JITThunks::m_lock` | the map of thunks by generator | `ctiStubImpl`, including on a hit and during generation. It is recursive because generating a thunk can request others. |
| Each lazy thunk's lock | generation of that entry | `JITThunks::lazyCommonThunk`, when the thunk has not been generated yet, with a recheck inside the lock. The generator publishes the state with release; a ready hit reads it with acquire, without the lock. |
| `FTL::Thunks::m_lock` | the maps between `SlowPathCallKey` and thunk | Generation/lookup in `getSlowPathCallThunk` and reverse lookup in `keyForSlowPathCallThunk`. |
| `pas_heap_lock` | global structures of the libpas executable heap | With `ENABLE(LIBPAS_JIT_HEAP)`, in `jit_heap_add_fresh_memory`; on the slow path of `jit_heap_try_allocate` when it creates a size directory or a small/medium page, or allocates a large object; and, for large objects, also in `jit_heap_get_size`, `jit_heap_shrink` and `jit_heap_deallocate`. It is not taken on every request (`libpas/src/libpas/pas_try_allocate_common.h`, `libpas/src/libpas/jit_heap_config.c`). |
| `FixedVMPoolExecutableAllocator::m_lock` | jump islands; without libpas, also the executable allocation records | On ARM64, `makeIsland` and the return of islands through `handleWillBeReleased`. Without libpas, the `MetaAllocator` uses the same lock to allocate, shrink and free blocks, including on x86-64. |
| `FixedVMPoolExecutableAllocator::m_pageLock` | per-page writer counts and RX/RWX protection switches | `startWriting` and `finishWriting`, only with `ENABLE(MPROTECT_RX_TO_RWX)`; it is not held while the code is being written (`jit/ExecutableAllocator.cpp`). |

In the baseline, the profile drain comes before the safepoint, and `compileAndLinkWithoutFinalizing` runs entirely inside it (`jit/BaselineJITPlan.cpp`, `jit/JITSafepoint.cpp`). In the DFG frontend, `RUN_PHASE` opens and closes a `GraphSafepoint` before running the phase, under `safepointBeforeEachPhase`, which is on by default (`dfg/DFGPlan.cpp`). The FTL also has safepoints that wrap `B3::prepareForGeneration` and `B3::generate` (`ftl/FTLCompile.cpp`).

The `JSLock`, described in [basics.md](../../basics.md#locks), can be acquired at request time and at installation without staying held between the two. This census leaves out the collector's internal coordination, such as the marking mutex and the conn handoff, except for the visitors' rights to run, which a thread outside the collector can take to wait out concurrent visits. It also leaves out the locks under `ASSERT_ENABLED` and the conditional instrumentation.
