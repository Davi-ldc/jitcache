# Abstract

Profiles record, per instruction, what went through it, so that the optimizing tiers can speculate. The LLInt and the baseline store raw samples on the hot path, and drains at tier-up, in the GC, in the DFG parser and, for allocation profiles, at the next allocation classify them into type bitmasks and clear the slots. A sample is not a GC reference, so a drain that comes late can read a cell that has died. Predictions also accumulate in the `UnlinkedCodeBlock`, which outlives its `CodeBlock`s; the bytecode cache carries none of them. `BytecodeList.rb` declares which opcodes carry each profile: 53 opcodes carry at least one, 16 an `ArithProfile`, 28 a `ValueProfile` and 17 an `ArrayProfile`, eight of them both of the last two. The value and arithmetic profiles are addressed by an index that the opcode carries as an operand; the array profile is embedded in the metadata, with no index.

1. `ValueProfile` stores the `JSValue` produced by the instruction. A drain classifies it, accumulates its type in `m_prediction` and clears the slot (`m_buckets[0]`) in the same step. LLInt and baseline write the samples; DFG and FTL consult the prediction, and their OSR exits, which return to the baseline or the LLInt, also feed the profiles. There are 35 slots across the 28 opcodes: `iterator_open`, `async_iterator_open` and `iterator_next` have three each; `instanceof`, two.

2. `ArrayProfile` observes the base of an indexed or `length` access or of a for-in enumeration, the array argument of `new_array_with_species`, the receiver (`this`) of the calls that carry this profile, and the iterable of a `for-of`. It stores two `StructureID`s, one for the last structure accessed and one for the speculation failure, from which the drain derives the storage formats (the array modes), plus access flags: whether the access went out of bounds, whether a store landed in a hole, whether the object still has the realm's original `Array` or `TypedArray` structure. It too is read only by the DFG and the FTL.

3. `ArithProfile` records which types came in on each side of an arithmetic operator and whether the result left their domain, with an int32 or int52 overflow, a `-0` or a BigInt. It is the only one of the three that the baseline reads to decide the shape of the code it emits. It holds no cell or structure, so it lives only in the `UnlinkedCodeBlock`, shared by every `CodeBlock` of that body. The other two sample a `JSValue` or a `StructureID`, so their slots live in the `CodeBlock` metadata, and only their predictions merge into the `UnlinkedCodeBlock`. A body whose bytecode adds no metadata entry and no value profile, such as `function id(x) { return x; }` (only `enter` and `ret`), gets no table at all: `UnlinkedMetadataTable::link` returns null, and so does `CodeBlock::metadataTable()`. The native walkers (`CodeBlock::forEachValueProfile`, `forEachArrayAllocationProfile`, `updateAllArrayProfilePredictions`) test for that first, since the table's accessors would dereference null. Such a body can still be hot and reach the baseline and the DFG, with its argument profiles, its counters and the property ICs of opcodes that carry no metadata (`in_by_id`, `del_by_id`, `del_by_val`), all of which live outside the table.

Of the records here, the baseline reads at compile time only the arithmetic profiles, `m_enumeratorMetadata` and, with the type profiler on, `TypeLocation::m_lastSeenType`; the rest serves the DFG and the FTL. [compiler.md](../baseline/compiler.md#inputs) lists every input of a baseline compilation. The table at the end also covers the other per-site records: the exit profile, the lazy-operand and `catch` profiles, the array allocation profile, the enumerator and iteration modes, a few opcode flags, the records of the type and control flow profilers, and the LLInt's tier-up counter.

# Arithmetic profile

Sixteen opcodes carry an arithmetic profile: nine binary ones, `add`, `sub`, `mul`, `div`, `bitand`, `bitor`, `bitxor`, `lshift` and `rshift`, and seven unary ones, `inc`, `dec`, `negate`, `to_number`, `to_numeric`, `bitnot` and `unsigned`, each with a `profileIndex` that addresses a 16-bit `BinaryArithProfile` or `UnaryArithProfile` in the `UnlinkedCodeBlock` (`BinaryArithProfileBase`/`UnaryArithProfileBase`; accessors `binaryArithProfile`/`unaryArithProfile`). Living there puts it out of reach of `metadataTableRegister`, which addresses the `CodeBlock`'s metadata table, so the emitted code reaches it by absolute address (`emitUnconditionalSet`), and the LLInt loads it through `CodeBlock::m_unlinkedCode` (macro `updateBinaryArithProfile`).

Each side has three flags, `TypeInt32`, `TypeNumber` and `TypeNonNumber`, accumulated by OR on the paths that collect profiles. For `add`, `sub`, `mul` and `negate`, an empty profile never reaches the generator: `JITMathIC::generateInline` emits a patchable jump and lets the first execution choose ([inlinecaches.md](./inlinecaches.md#math-inline-cache)). Otherwise, in `add`, `JITAddGenerator::generateInline` compares the bitmasks of the operand pair for exact equality: only int32 on both sides (or a side that is an int32 constant, which needs no profile) gets the minimal inline code; only non-numbers on both sides gets no fast path at all; any other combination calls for the full snippet, with int+int, int+double, double+int and double+double. `sub` and `mul` also have a double+double-only path for when both profiles recorded only doubles; in `mul`, that form further requires that neither operand be a constant (`JITSubGenerator::generateInline`, `JITMulGenerator::generateInline`).

The other half of the field is what happened to the result, seven bits: int32 and int52 overflow, `-0` and a double that is not `-0`, non-numeric and the two BigInt bits (`ObservedResults::Tags`), for the DFG to speculate on. The baseline consults them only to decide whether it still needs to emit a profiling write (`shouldEmitSetDouble` and its siblings): the shape it emits comes from the input types, and in `add` the overflow on the int32 path goes to the slow path through `branchAdd32(Overflow, …)`. What gets recorded depends on the path: `observeResult` and `emitSetDouble` classify any double conservatively, setting four bits at once, `Int32Overflow | Int52Overflow | NonNegZeroDouble | NegZeroDouble`. `updateArithProfileForBinaryArithOp` and the double path of `JITMulGenerator::generateFastPath`, on the other hand, test some of these conditions separately, including `-0` and int52 overflow; both int52 tests allow an intentional false positive at `-2^51`. Once set, a bit is never cleared: every writer ORs into the current value, and the only function that would return a subset, `withoutNonNumber()`, has no caller.

# Drain

The LLInt and the baseline store raw samples, which keeps their hot paths cheap: a `JSValue` into `m_buckets[0]` and a `StructureID` into the array profile. The drain turns these samples into the `m_prediction` and `m_observedArrayModes` bitmasks, which the DFG and the FTL use to speculate. For the value profile, `ValueProfileBase::computeUpdatedPrediction` classifies the sample, merges the type into `m_prediction` and clears the slot. The parser can request this update when it queries a profile: `CodeBlock::valueProfilePredictionForBytecodeIndex` calls that routine before returning the prediction. If there is neither an accumulated prediction nor a usable sample, the query returns `SpecNone` and `ByteCodeParser::getPrediction` injects a `ForceOSRExit`, except for `call_ignore_result`, which gets `SpecFullTop`, and `tail_call`/`tail_call_varargs`, which take the prediction of the nearest inlining caller that is not a tail call, or `SpecFullTop` when there is none.

For the array profile, the one-argument `ArrayProfile::computeUpdatedPrediction` swaps both `StructureID` slots for zero and classifies each nonzero one. The parser calls it one profile at a time before reading the modes (`ByteCodeParser::getArrayMode`), and so does the fixup phase (`FixupPhase::attemptToMakeGetArrayLength`), on the thread that compiles. The helpers that the baseline's by-val ICs call on a miss also classify, at runtime on the thread that executes JS: before repatching an indexed access, `operationGetByValOptimize`, `operationGetByValWithThisOptimize`, `operationInByValOptimize` and the `put_by_val`/`put_by_val_direct` ones pass the base's current structure to the two-argument overload, which merges that structure's modes and flags into the profile, or replaces the modes at the first pruning, and leaves both slots as they are. When the baseline emits profiling, that structure is the one the fast path has just stored in the slot (`JIT::emit_op_get_by_val`), so the helpers only run the drain's classification early. The DFG passes these helpers a dummy profile from its `JITData`, and the FTL passes null (`SpeculativeJIT::compileGetByVal`, `FTL::LowerDFGToB3`).

Besides these individual queries, the engine updates the value profiles as a group. `updateAllNonLazyValueProfilePredictionsAndCountLiveness` walks the argument profiles, then the metadata ones (`CodeBlock::forEachValueProfile`), draining each one and merging its prediction with the one kept in the `UnlinkedCodeBlock` (`UnlinkedValueProfile::update` writes the union to both sides), and then drains the `catch` buffers without merging them. The correspondence with the UCB's profiles is positional, with no key and no check; builtins stay out of this aggregation, through the `if (!isBuiltinFunction)` guard. At the baseline→DFG tier-up, this same loop counts the profiles whose prediction is not `SpecNone`, with and without the arguments, and `shouldOptimizeNowFromBaseline` turns the counts into the coverage rates that decide whether to compile or defer ([basics.md](../../basics.md#tier-up)).

There are four contexts. In LLInt→baseline, the drain is the first step of the compilation plan (`BaselineJITPlan::compileInThreadImpl`), which runs on a pool thread with `useConcurrentJIT` and on the calling thread without it; the slow path (`jitCompileAndSetHeuristics`) drains nothing, whether it dispatches a plan or installs the code another `CodeBlock` of the body left in the `UnlinkedCodeBlock`. In baseline→DFG, the drain runs on the thread that executes JS (`operationOptimize`): through `updateAllPredictions` below the threshold, on the delays that rearm the counter (a termination request, the debugger, `m_shouldAlwaysBeInlined`) and after a failed compilation; and past the threshold inside `shouldOptimizeNowFromBaseline`, unless the delay counter has already reached `maximumOptimizationDelay`. A `CodeBlock` that cannot compile, a compilation in flight and an existing optimized replacement leave without draining. The two also differ in scope: the LLInt→baseline one drains only the value profiles, lazy ones included, while the baseline→DFG one also drains the array and array allocation profiles. The third is GC marking: on the first visit to a `CodeBlock` in LLInt or baseline (`CodeBlock::visitChildren`, only through the `SlotVisitor`), the marker drains the value profiles on its own thread, even with the world running. The fourth is the finalization of that same cycle, which drains everything (`CodeBlock::reconcileWeakReferencesAtGCEnd`) in every `CodeBlock` in LLInt or baseline visited in that cycle: the bit that registers the block in the set is set at the end of `CodeBlock::visitChildren` and cleared at the end of finalization, so in an eden cycle, cold code marked in an earlier cycle is left out.

Nothing locks a drain against the writers or against other drains. The aligned slot rules out torn samples, but a sample stored between the drain's read and its clear is lost, and overlapping drains, such as the marker, a plan thread and `operationOptimize`, can drop prediction bits in their non-atomic merges; both only cost precision.

Allocation profiles have one more drain, on the thread that executes JS: at the next allocation through the profile, `ArrayAllocationProfile::selectIndexingType` compares the last array's indexing type with the hint and, when they differ, folds the array into the hint with `updateProfile`, which clears the pointer. Compilers read only the hint (`selectIndexingTypeConcurrently`, `vectorLengthHintConcurrently`) and never follow the pointer.

## Stale samples

The slot does not count as a live reference, so a sample that is not classified in time can become a pointer to memory that has already been recycled; the `HeapVerifier` has a dedicated test for a zapped cell found in a slot. An eden cycle revisits an old `CodeBlock` only if it is on the stack or in a live compilation plan when the cycle scans for executing code, was executing or compiling when the previous cycle ended, or was write-barriered since. Profile writes issue no barrier, while LLInt cache fills and inline cache updates do. An old `CodeBlock` that ran between two collections without touching a barriered field therefore keeps its samples through the next eden, whose finalizer skips it, even when the sampled cells die in that eden. The next drain that reaches the `CodeBlock` reads those stale samples: the first visit of a full collection, the finalizer of a cycle that visits it, the baseline plan (value samples only), `operationOptimize`, DFG parsing or, for an allocation profile, the next allocation through it. The value drain reads only words inside the cell (`speculationFromValueForProfiling`), the array drain decodes the `StructureID` and reads the `Structure`, and `ArrayAllocationProfile::updateProfile`, which never runs on a compilation thread, dereferences the last array and its butterfly.

# Lifetime

Predictions merged into the `UnlinkedCodeBlock` outlive its `CodeBlock`s, and so do the arithmetic profiles, which live nowhere else. Ordinary GC discards cold code by finalizing the edges of the `FunctionExecutable`, and explicit deletion goes through `ScriptExecutable::clearCode`, which, for a function, clears `m_codeBlockForCall` and `m_codeBlockForConstruct` without touching the unlinked one. References to function UCBs can be cut by `Heap::deleteAllUnlinkedCodeBlocks`, which calls `UnlinkedFunctionExecutable::clearCode` on every live executable to drop both the call and the construct UCB, and by the `UnlinkedFunctionExecutable`'s finalizer, whose `clearIfDead` lambda drops the unmarked ones; for program, eval and module, `ScriptExecutable::clearCode` also clears the reference to the unlinked one. Dropping a reference does not destroy a UCB that another owner still reaches. If the same UCB survives, the `CodeBlock` created afterwards is born with its value predictions at `SpecNone`, and the stored union comes back at its first merge.

A new UCB starts with zeroed profiles, both when it is generated from source (`generateUnlinkedFunctionCodeBlock`, inside `unlinkedCodeBlockFor`) and when it is decoded. The on-disk bytecode cache carries no observations at all: it serializes the four counts (value, array, binary arith and unary arith), and the `UnlinkedCodeBlock`'s decode constructor rebuilds the four vectors zeroed. The in-memory `CodeCache`, on the other hand, with `useCodeCache` on, also keeps UCBs decoded from the provider and lets the observations accumulated afterwards be reused (`CodeCacheMap::findCacheAndUpdateAge`).

# Table

A census of the per-site records the engine keeps for profiling, plus the LLInt's tier-up counter, which also serves as an activity signal for aging. The tier-up counters of the other tiers, each exit's count and the `Profiler::Database` counters under `useProfiler` are left out; [basics.md](../../basics.md#tier-up) covers the tier-up and exit counters, and [inlinecaches.md](./inlinecaches.md#table) the inline caches. A C++ helper called by the emitted code counts as runtime. The drain and the merge fit none of the columns, although they write the prediction and clear the slot; the rows name them only where nothing else writes a field. Where a compile-time cell says DFG, read DFG and FTL: the FTL runs the same `DFG::ByteCodeParser`, and it is named only where it diverges.
