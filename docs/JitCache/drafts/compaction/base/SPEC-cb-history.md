# SPEC-cb history

Rationale and review records for [SPEC-cb.md](SPEC-cb.md). Nothing here binds; where this file and the SPEC differ, the SPEC wins.

## Authoring (thread-prep run, THREAD sha256 `83e03d4b…2bc62`)

The design was written from the current THREAD with no earlier SPEC at its path. It records no THREAD gap: every decision that binds another part is either settled by THREAD or stated as a requirement on the part THREAD names as owner (R-UCB, R-INT).

### Why the state is dense and positional

Every CB-lane field lives at a position fixed by native index spaces: argument index, value-profile offset, and metadata-ID order within an opcode's metadata array. THREAD lets a section refer to another lane's content only through such spaces, and the UCB lane guarantees them. Dense arrays per family make validation a count comparison (V2 to V4) and seeding a lockstep walk with `MetadataTable::forEach<Op>`, with no search and no key decoding. A sparse form with keyed records would save bytes only for cold sites, and a body is captured after its baseline compile, when most sites have run. Install time is bounded by THREAD and memory is cheap at this size, so the dense form wins.

Families are a fixed table rather than (opcode, field) pairs stored in the file: the header's build ID already pins `OpcodeID` values and metadata layouts, and the table generated from the native macros keeps the merge order and this order the same by construction.

### Why two sections

Scoring reads only the summary, at the key's first scoring, and THREAD makes each lane write its summary part into the body file. Keeping it in its own section lets the glue read a few hundred bytes instead of the whole state. The summary keeps per-slot categories because THREAD lists them as summary content; the score is derived from them at decode, so the file carries no redundant scalar to keep consistent.

### Why the counter travels raw and the engine re-slices it

THREAD makes progress and base threshold state that must equal its capture record, while the memory-pressure slice is recomputed against the consumer's pool. Storing the raw triple (`m_counter`, `m_totalCount`, `m_activeThreshold`) keeps P exact, since `double(float) + int32` is exact in double for every pair native code stores (the counter's magnitude never exceeds the total's by more than the slice ceiling, or the total is 0), and lets `finishCounter` hand the restored counter to `ExecutionCounter::checkIfThresholdCrossedAndSet`, the engine's own check, instead of re-deriving `setThreshold`'s arithmetic in JITCache. An earlier draft re-derived it; replacing that with the native call removed a copy of engine logic that a WebKit bump could silently diverge from.

The infinite threshold is the one case kept out of the native call: `setThreshold` would call `deferIndefinitely` and drop the progress. `handleExitCounts` can leave an infinite threshold with a positive total, so the case is reachable and the captured slice is kept.

The final `float(P + s)` rounds like the native `m_totalCount = trueTotalCount + threshold`; I7 states the exact relation instead of claiming bit equality for huge counts.

The raw triple is not process-independent, and the SPEC no longer claims it is (round 1). For a finite threshold, the split between `m_counter` and `m_totalCount` holds the producer's memory-pressure slice, and every unclipped native re-slice adds the fractional part of its slice to P, because `setThreshold` truncates `m_counter` but keeps the fraction in `m_totalCount` (N4). A record of P, T and the infinite threshold's slice alone was considered and rejected: P is `double(float) + int32`, and splitting an arbitrary P back into a float total and an int32 counter that sum to it exactly is not always possible, while the raw pair is exact by construction. The consumer reads only P and T for a finite threshold, so the producer's slice stays local; U4 checks it with two records that differ only in the split.

### Why the aging resample belongs here

Setup samples `m_previousCounter` from a fresh counter. Restoring progress afterwards would make the next old-age check see "activity" and renew a lease the CB never earned. THREAD keeps time leases local and lists "resamples aging" in the install sequence right after the re-slice; the field is CB heuristic state and the resample reads the counter this lane just wrote.

### Why P11 is seeded before setup

`optimizeAfterWarmUp` in setup reads `reoptimizationRetryCounter()`. Seeding it first means setup arms a threshold native code could have armed for this history, even though `finishCounter` overwrites the counter. Seeding P10 at the same time costs nothing and keeps the CB scalars in one step.

### What waits for the DFG capture or stays local

`m_hasBeenCompiledWithFTL` is set only by the DFG's FTL tier-up; THREAD's settled rule makes state that DFG or FTL code sets wait for the DFG capture. Reoptimization counts and lazy-operand profiles are also written by DFG paths, but THREAD names both explicitly as travelling (heuristic history; lane 3's scope and the summary), and the explicit statement wins over the general rule. `m_osrExitCounter` belongs to optimized CBs only. Standalone failure buckets and every other bucket hold pending samples; a drained bucket is empty, so leaving the bucket out loses nothing a drain would have kept.

`OpGetByValWithThis::Metadata::m_arrayProfile` first travelled as family A16, on the view that the IC slow operation's classification makes it learned state. Round 2 reversed this: nothing outside that classification ever reads the profile (N2), so it falls under THREAD's "recomputes before anything reads it" and stays local. See round 2, finding 4.

`ToThisClearedByGC` travels like `CallLinkInfo`'s cleared-by-GC bit: it is scalar history, while the cached structure beside it is a cell cache that starts at link state.

### Validation split

The always-on rules (V1 to V15) bound values to what keeps the engine safe: indexes, enum cases, shift widths, the assertions of the engine's own constructors, and allocation shapes that would corrupt arrays. Plausibility checks that native code satisfies but the engine does not need (the newborn link state, non-negative progress under a finite threshold) are strict-only, so a native behavior this SPEC did not model cannot turn cache activity off for every user.

Lazy-operand keys get no plausibility check at all. The first draft bounded tmps by `maxNumCheckpointTmps` in V13 and checked the CB's frame in a strict S4, on the premise that keys index the CB's own frame. Round 1 showed the premise false (N7): a key's operand is the exiting `GetLocal`'s, remapped into the machine frame of whichever compile inlined the CB, so an inlined CB holds locals past its own `numCalleeLocals()` and tmps shifted by `InlineCallFrame::tmpOffset`, and private tmps start past `numTmps()` even in the root frame. No check against the CB can tell such a key from a forged one, and the engine only hashes and compares keys, so V13 now enforces what the key's constructors assert plus the absence of constant registers, and nothing about the frame. A tmp ceiling such as the 10-bit `tmpOffset` range plus `maxNumCheckpointTmps` was rejected too, because an inlinee's own private tmps add to it without bound.

Superseded in part: since "Drain after the thread-prep run", item 3, V1 to V15 are strict checks too, and normal mode applies none of them (SPEC-cb.md section 3.4).

### Native edits and the manifest

The three owned edits add accessors to classes no other lane touches (`ArrayProfile`, `ArrayAllocationProfile`, `CompressedLazyValueProfileHolder`). `CodeBlock.h` is the hub several lanes may need, so its two additions, the seed function and the twins-only aging getter, go through the integrator's manifest. `appendOperandValueProfileForRestore` exists because `addOperandValueProfile` searches linearly before each append, which would make restoring n profiles quadratic after V13 has already proven the keys distinct.

Superseded in part: "Kept minors from the thread-prep run", batch 4.7, removed `appendOperandValueProfileForRestore`; P3 seeds through the public `addOperandValueProfile`, and SPEC-cb.md section 9.1 explains why its linear search is accepted.

### Options

The fixed rows are the options folded into the transported base threshold (THREAD names them), the derived `reoptimizationRetryCounterMax`, the two rewriters of those thresholds (`jitPolicyScale`, `forceEagerCompilation`), `useArrayAllocationProfiling`, and the entry increment that defines the floor. The deferral pair `minimumOptimizationDelay` and `maximumOptimizationDelay` is fixed by analogy with the cool-down pair THREAD fixes for the ICs lane: both give a transported count its meaning. Options that only shape the consumer's own slice, coverage policy or aging stay free.

### Gap candidates checked and found settled

- Which progress the summary's tie-break uses: the lane writes the summary, and THREAD Maintenance already defines P (floored at zero, capped at the active threshold); one value serves both.
- Whether a failed always-on check of a saved summary during capture is invalid material or a recording fault: the summary is received material, and THREAD Failures turns cache activity off on invalid material.
- Whether the pairing guard at capture is a recording fault: it is a check that guards a capture, the class THREAD's settled rule gives.
- Who resamples aging: the field is CB heuristic state, lane 3's scope.
- Lazy-operand keys use virtual registers and tmps of a machine frame (N7). They refer to no other lane's content and to no other body: the bytecode index belongs to the profiled CB, which the UCB lane's index-space guarantee covers, and the operand is an opaque hash-map key that the consumer's DFG matches only if it builds the same inlining layout, as the producer's would. (The authoring draft said the keys index the CB's own frame; round 1 corrected it.)

## Reviews

### Round 1 (THREAD sha256 `83e03d4b…2bc62`)

Five findings, all verified against THREAD and the code and accepted. None needed THREAD, so the revision records no THREAD gap.

1. Blocker, native lens: S4 rejected lazy-operand keys that native code produces. Verified in `Graph::methodOfGettingAValueProfileFor` (the method takes the exiting `GetLocal`'s operand), `ByteCodeParser::get` (which calls `getDirect(m_inlineStackTop->remapOperand(operand))`), `InlineStackEntry::remapOperand` and `remapOperand` in `bytecode/InlineCallFrame.h` (shifts by `stackOffset` and `tmpOffset`), `MethodOfGettingAValueProfile::emitReportValue` (adds the key on `baselineCodeBlockForOriginAndBaselineCodeBlock`, the inlinee's baseline CB) and `ByteCodeParser::injectLazyOperandSpeculation` (looks up the same remapped key in the inlinee's `m_lazyOperands`). With strict on by default, SC1 would have ended production at the first delta capture of an inlined CB that saw an exit. Revision: S4 and `CBCheck::StrictOperandRange` are deleted, and S4 is gone from SC1, I13, U3 and section 7. N7 states where keys come from, and U3 and the corpus now check that out-of-frame keys pass.
2. Blocker, native lens: V13's tmp ceiling rejected native tmp keys and missed `Operand::isValid()`. Verified in `ByteCodeParser::tmpOffsetForInlineeOf` (the caller's offset plus its `numTmps()` plus its private tmps), `ByteCodeParser::allocatePrivateTmps` (a relative base of `numTmps() + m_numPrivateTmps`, so 4 or more in a root frame with checkpoints), `CodeBlock::numTmps` (0 or `maxNumCheckpointTmps`, which is 4), and `LazyOperandValueProfileKey(BytecodeIndex, Operand)`, which asserts `m_operand.isValid()`. `VirtualRegister(invalidVirtualRegister).isLocal()` is false, so the old kind check let that value through as an `Argument`. Revision: tmps need only `operandValue >= 0`; `Argument` and `Local` operands need kind agreement, `isValid()` and not `isConstant()` (`ByteCodeParser::newVariableAccessData` asserts the last); U2's V13 mutations are listed explicitly.
3. Blocker, implementability lens: the same defect as 1 and 2, seen from an implementer's side. It also suggested a corpus body whose DFG exits happen inside an inlined callee that reads a checkpoint tmp, which section 11.3 now has. That body uses a caller that iterates too, because `tmpOffsetForInlineeOf` shifts the callee's tmps only past tmps its callers hold. The optional ceiling it suggested (the 10-bit `tmpOffset` range plus `maxNumCheckpointTmps`) was not adopted, for the reason given under "Validation split".
4. Major, native lens: `m_previousCounter` had no getter, so the P12 twin, I7 and U4 could not be written. Verified: `CodeBlock::m_previousCounter` sits in a private section of `bytecode/CodeBlock.h`, and only `snapshotExecutionCounterForAging(float)` writes it from outside `CodeBlock.cpp`. Revision: M1 adds `float previousCounterForAging() const` under `ENABLE(JITCACHE_TWINS)`, listed in section 9.4, and the unit-test target builds with that switch (R-INT-10, M3). While writing the check, the comparison was also corrected to `previousCounterForAging() == float(count())`: `snapshotExecutionCounterForAging` narrows the double `count()` to float, and `CodeBlock::shouldJettisonDueToOldAge` compares in float, so equality with the double `count()` can fail for counts that a float cannot hold exactly.
5. Major, native lens: I1's byte-identity claim was false. Verified in `ExecutionCounter::setThreshold` (truncated `m_counter`, unrounded `m_totalCount`), `applyMemoryUsageHeuristics`, `ExecutableAllocator::memoryPressureMultiplier` (pool `bytesAllocated`) and `CodeBlock::predictedMachineCodeSize` (the VM statistic `machineCodeBytesPerBytecodeWordForBaselineJIT`). Predictions are not reproducible either: a drain classifies only the latest sample, value drains run at GC-driven times (profiles.md, "Drain"), and baseline-to-DFG crossings, which also drain, move with the code-size-dependent multiplier, so even with GC timers off the drain points can differ between processes. The reviewer's fallback (compare T and `floor(P)`, run with deterministic GC) was not adopted: `floor(P)` can still differ when the accumulated fractions cross an integer, and predictions still vary. Revision: I1 now states the structural property and names the counter triple as the one place a producer statistic reaches the bytes, used by the consumer only as P, T and the infinite threshold's slice. N4 records the truncation, the fraction and the multiplier's inputs. The cross-process byte test is gone, and U4 instead checks that two records differing only in the split restore identical counters. I7's float-exactness remark was also corrected, since a fractional P is common.

### Round 2 (THREAD sha256 `83e03d4b…2bc62`)

Seven findings, all verified against THREAD and the code and accepted. None needed THREAD, so the revision records no THREAD gap. Dropping A16 renumbered the families: the allocation hints are now F16..F19, the iteration modes F20..F23, the enumerator modes F24..F28, `to_this` F29 and `jneq_ptr` F30. The findings below use the new numbers.

1 to 3. Blockers from the native, implementability and simplicity lenses, one defect: V8 accepted any copy-on-write type at an `op_new_array_buffer` site (F19), including types below the literal's own. Verified in `ArrayNode::emitBytecode` (the literal's type is `CopyOnWrite` ORed with the least upper bound of its constants, and the instruction is emitted only for a non-empty, all-constant literal), `link_arrayAllocationProfile` in `CodeBlock::finishCreation`, `ArrayAllocationProfile::updateProfile` with `leastUpperBoundOfIndexingTypes` (`std::max`, capped at Contiguous for a copy-on-write hint and tagged again), `slow_path_new_array_buffer` and `operationMaterializeObjectInOSR` (case `PhantomNewArrayBuffer`), both of which copy the literal into a butterfly of the hint's type, `JSCellButterfly::setIndex` (no conversion) and `JSCellButterfly::visitChildrenImpl` (contiguous only). A forged or mismatched record could therefore put cells into an unscanned Int32 butterfly or turn them into doubles, against section 3.4's own guarantee and THREAD's "JITCache always verifies everything it receives". Revision: V8 now bounds the F19 hint below by the instruction's `m_recommendedIndexingType`, found by `m_metadataID` in one walk over the instructions. The bound is read from the instruction in both `prepare` and SC1, so one predicate serves both. Reading the newborn CB's own hint at `prepare`, which the native lens suggested, would equal the instruction's type only while the CB is at its link state, and SC1 needs the instruction anyway, because the live CB's own hint is the value under test. The walk costs one pass over the bytecode and runs only when F19 has entries; B1 measures it. The walk also rejects an F19 entry with no instruction or with two. That case is native-impossible: rewinds drop only metadata-free opcodes and generatorification replaces only `op_yield` and the generator-frame instruction. N8 records the facts, and U2 has the mutations.

4. Blocker, simplicity lens: A16 carried a profile nothing reads. Verified: `CodeBlock::getArrayProfile` covers only `FOR_EACH_OPCODE_WITH_SIMPLE_ARRAY_PROFILE` and `OpIteratorNext`, so the DFG parser, the fixup phase and both OSR exit compilers never reach it. The DFG's `op_get_by_val_with_this` case uses only `GetByStatus`. The LLInt's handler is `slowPathOp(get_by_val_with_this)`, whose `slow_path_get_by_val_with_this` ignores the profile. Neither merge walks it, so the samples the baseline stores are never drained. `operationGetByValWithThisOptimize` classifies into it, and `InlineCacheCompiler` code ORs flags into it, but the only reads of its modes and pruning mark happen inside `ArrayProfile::computeUpdatedPrediction(CodeBlock*, Structure*)`, which writes back into the same profile. THREAD keeps local what the consumer "recomputes before anything reads it", and nothing ever reads this profile. Richness also argued for dropping it: THREAD counts each slot as "what the native merge leaves for the DFG", and the DFG never sees these flags. Revision: A16 is gone; section 1 lists the profile among the state that stays native, and every array flag in the summary now pairs with its UCB copy. Removing it also removed `numberOfPairedArrayProfileFamilies`, the unpaired summary rule and the exceptions in I8 and I11. The header gained `reserved1` so that it stays 160 bytes with 31 family counts. The layout version stays 1, since nothing has shipped.

5. Major, native lens: `verifyTwins` and I9 were not pinned before `installCode`. Verified in `CodeBlock::visitChildren` (the first `SlotVisitor` visit of a baseline CB runs `updateAllNonLazyValueProfilePredictions`) and `UnlinkedValueProfile::update` (writes the union into both copies). The install deferral holds back only the stopped-world phases, so a concurrent marker can reach the CB as soon as `installCode` stores it and barriers the executable. The UCB copies the UCB lane restores often carry bits the CB copy lacks, so a twin check after `installCode` would fail at random. Revision: section 5.1 makes `verifyTwins` step 6, between `finishCounter` and `installCode`, and says why. R-INT-6 and the comment in section 6.1 follow, and I9 now holds until publication. N11 records the facts, and the concurrency corpus case imports under `collectContinuously`.

6. Major, implementability lens: V9's 15-bit bound admitted modes the DFG cannot parse at sync sites. Verified in `ByteCodeParser::handleIteratorOpen` and `handleIteratorNext`. They mask only bits whose protocol watchpoint is invalid, count `std::popcount(seenModes)` cases, branch each non-last fast case to a `failedBlock` that only a later case consumes, and end with `ASSERT(!failedBlock)`; a bit with no case leaves a reachable block without a terminal. The open handler has cases for the 13 bits `iteratorOpenTryFastImpl` records, and the next handler for the 10 bits its native writers record (`iteratorNextTryFastImpl`, `operationIteratorNextTryFast`, the LLInt's `op_iterator_next`, `JIT::emit_op_iterator_next`). The async handlers mask their input to the bits their writers record: `asyncIteratorOpenTryFastImpl` records `Generic`, `FastAsyncGenerator` and `AsyncFromSync`, and `slow_path_async_iterator_next_with_driver`, the LLInt and the baseline record `Generic` and `FastAsyncGenerator`. Revision: V9 bounds each opcode by its native writers' bits (`0x1fff`, `0x1ff1`, `0x6001`, `0x2001`). For the async families these match what the DFG keeps after masking, so the reviewer's alternative of `0x7fff` there was not adopted. The narrower native sets also keep stray bits away from `canUseFastIterationMode`, which counts every non-Generic bit. The masks are `constexpr` and shared with SC1, N9 records the facts, and U2 has the mutations. V9 does not cap the number of fast bits at `maxNumberOfFastIterationModes`: the DFG emits one case per bit, and the runtime only degrades new modes to `Generic` once two are seen, so a larger set is a superset the engine handles safely.

7. Major, implementability lens: seeded `FastMap` or `FastSet` bits at an `iterator_open` site trip a DFG assertion in a realm that has not created a `Map` or `Set`. Verified: `handleIteratorOpen`'s two cases `ASSERT_WITH_MESSAGE` on `mapProtoEntriesFunctionConcurrently()` and `setProtoValuesFunctionConcurrently()`. Both are lazy properties, materialized by `MapPrototype::finishCreation` and `SetPrototype::finishCreation` for the lazy `Map` and `Set` classes or by their own getters. The map and set protocol watchpoint sets start valid and mask nothing. `getIterationMode` returns `FastMap` or `FastSet` only when the symbol iterator equals the materialized function, so natively the bit implies it. In a release build `Graph::freeze` of null gives the empty value, and a single-mode site exits on every run, which means jettison churn the JITCache-off run never has. Revision: `seedLinkedState` ends with a realm step that calls `mapProtoEntriesFunction()` or `setProtoValuesFunction()` on the CB's global object when an F20 record carries the bit. That restores the native invariant without dropping the bits, which THREAD carries. The getter allocates the `JSFunction` the first time in a realm, and the `NativeExecutable` that `JITThunks::hostFunctionStub` caches the first time in the VM. It generates no code, since neither intrinsic has a thunk generator and the native-call thunk is an eager VM thunk. The function is unreachable from JS until the prototype installs that same function, so the JS-reachable heap matches a JITCache-off run. The allocation runs under the install deferral, where it cannot start a collection, and only for a seed that needs it, which keeps it within THREAD's "no work ahead of demand". THREAD forbids cell allocation only during capture, so this is a lane decision, not a THREAD gap; R-INT-3 now states that `seedLinkedState` may allocate. I3, I4 and the new I14 say so, and U7 and a corpus case test it. Two alternatives were rejected. Stripping the bits would drop transported state and break the twin. A DFG edit that masks a bit whose function is missing would add an engine change THREAD does not list, for a state native code cannot reach.

While verifying 7, every other realm read behind this lane's seeds was checked. The other `iterator_open` cases read functions and structures the realm creates eagerly: the Array, Iterator and String prototypes' functions and the iterator structures. The async handlers read link-time constants that `AsyncIteratorPrototype` and `AsyncGeneratorPrototype`, both created with the realm, materialize. `iterator_next` reads only VM sentinels and watchpoint sets. Array profiles looked like a second case. With `UsesNonOriginalArrayStructures` clear, a single typed-array mode gives the DFG an `OriginalNonArray` class whose original structure comes from `typedArrayStructureConcurrently`, and typed-array classes are lazy. Captures can even hold such a mode with the flag clear for a cross-realm array, because OSR exit ORs modes in directly and leaves the flag to a drain of the pending failure structure, which capture never reads. The DFG handles a missing class, though: `ArrayMode::originalArrayStructures` wraps the null structure in a `TinyPtrSet`, which is then empty, so `FixupPhase::checkArray` emits `CheckArray` instead of `CheckStructure`, and `ArrayMode::alreadyChecked` tests typed arrays by speculation. No realm step is needed there; section 13 notes it.

The revision also corrected I3. It claimed that `AssertNoGC` "checks the cell part in debug builds". `AssertNoGC` asserts only in allocation and collection paths that run outside a GC deferral (`tryAllocateCellHelper`, `Heap::collectIfNecessaryOrDefer`), so under the deferrals of the finalize hook and of installation it checks nothing. I3 now says so, and U8 calls the lane's entry points outside any deferral so the check bites.

### Round 3 (THREAD sha256 `83e03d4b…2bc62`)

Three findings, all verified against THREAD and the code and accepted; two got a different fix than the one suggested. None needed THREAD, so the revision records no THREAD gap.

1. Major, implementability lens: the P12 twin re-ran a computation whose input moves. Verified: `ExecutionCounter::checkIfThresholdCrossedAndSet` calls `hasCrossedThreshold` and `setThreshold`, both call `applyMemoryUsageHeuristics`, and that calls `ExecutableAllocator::memoryPressureMultiplier`, which reads `FixedVMPoolExecutableAllocator::bytesAllocated()`. The count is the atomic `m_bytesAllocated`, which `fetch_add` and `fetch_sub` update from whichever thread allocates or frees executable memory, JIT worker threads in `LinkBuffer` and other VMs included. A recomputation in `verifyTwins` could therefore truncate to another slice or flip the crossing, and the concurrency corpus case, which imports while DFG compiles run, would fail at random.

   Revision: `finishCounter` returns a `CBCounterRestore` (the crossing, the native slice and the armed slice), the glue passes it to `verifyTwins` (R-INT-6), and `verifyTwins` compares the counter with it without calling pool-dependent code. So that the check does more than restate `finishCounter`'s arithmetic, I7 adds an envelope no pool can move. `memoryPressureMultiplier` clamps M at 1.0, and `applyMemoryUsageHeuristics` asserts it; the slice ceiling C, `maximumExecutionCountsBetweenCheckpoints(CountingForBaseline, codeBlock)`, reads only options and the CB's bytecode cost and code type. Hence for `P < T - min(T, C) / 2` the native check cannot cross (`hasCrossedThreshold` compares P with `M·T - min(T, C) / 2`, and `setThreshold` with `M·T`) and its slice is at least `trunc(min(T - P, C))`, and no slice exceeds C. U4 keeps the independent native reference, a stack `BaselineExecutionCounter` checked on the same CB right after `finishCounter`, in a VM with `useConcurrentJIT` off that is alone in its process, so nothing changes the pool between the two calls. U9 tests the envelope. A return value was chosen over the suggested `mutable` field or out parameter: it keeps `finishCounter` `const` and the import a read-only view of its span, and the same record feeds the bench report (R-INT-11) in every build. The other suggestion, checking only the floor and the algebra, would have left the record unchecked against P and T.

2. Major, implementability lens: task 7 promised B4 and B5, and nothing could measure them. Verified: the first `operationOptimize` crossing (`jit/JITOperations.cpp`), the DFG compile (`DFG::compileImpl`, `dfg/DFGDriver.cpp`) and the function's return all happen outside every lane call; section 9 listed no edit there, and section 6.3 had no requirement for a bench output, so even B1 to B3 had no stated route. THREAD Restoration gives the residue to the bench loop ("the bench measures that residue").

   Revision: task 7 is gone. The glue measures B1 to B3 around the lane's calls and hands the bench each import's `CBCounterRestore` (R-INT-11). The residue and the time to the first DFG compile are named as the bench loop's measurements, with no lane hook. Native code already reports both events: under `verboseOSR`, `operationOptimize` prints "Entered optimize with bytecodeIndex = …, executeCounter = …" for the CB, and under `logCompilationChanges`, `DFG::compileImpl` prints "DFG(Driver) compiling …". Neither option touches baseline emission: in `jit/`, `verboseOSR` appears only in `BaselineJITPlan`'s success and failure lines, `JITOperations.cpp` and `JITToDFGDeferredCompilationCallback.cpp`. Both options are therefore free under THREAD Storage. The floor's corpus case now names the same `verboseOSR` line as its observation, since it measures the same crossing. The reviewer's first alternative, an R-INT for native hooks in `operationOptimize`, at DFG plan start and at function return, was not adopted: it would put bench instrumentation into native files no lane owns (`JITOperations.cpp` also holds the `negate` operations the Image lane edits), for a measurement THREAD assigns to the bench loop. It is no THREAD gap either. THREAD names the bench as the owner of the residue, and timing the lane's calls is glue, which THREAD gives the integrator.

3. Major, simplicity lens: strict capture allocated scratch the budget never charged. Verified: section 5.2 said `prepare` allocates scratch for V8's per-site types and V13's duplicate-key test, section 6.1 shared those predicates with SC1, capture charged only its two sections, and THREAD Session charges every byte JITCache owns for production.

   Revision: both checks run in place, in `prepare` as in SC1, and capture allocates only its two charged buffers. V8's F19 bound walks the instructions and checks, for each `op_new_array_buffer`, the record at its `m_metadataID` (`forEachNewArrayBufferLiteral`). Both readers of the hint (`slow_path_new_array_buffer`, and `operationMaterializeObjectInOSR` for `PhantomNewArrayBuffer`) reach it through `bytecode.metadata(codeBlock)`, which `CodeBlock::metadata` resolves by indexing the opcode's array with that ID, so the per-instruction bound covers every hint a reader can reach. The round 2 rejection of an entry that no instruction or two instructions name is gone: the first is never read, the second is checked against both, and the one-to-one mapping belongs to the instruction stream the UCB lane guarantees. The facts behind "native bytecode has neither case" were rechecked: `BytecodeGenerator::rewind` drops only the compare or test that `fuseCompareAndJump` and `fuseTestAndJmp` fold into a jump, the `op_mov` of `emitMove`'s peephole and the `op_typeof` of the peepholes in `tryEmitTypeofIsUndefinedForStringComparison` and `emitEqualityOpImpl`, and `BytecodeGeneratorification::run` replaces only each `op_yield` and the generator-frame instruction. V13's uniqueness test became an order: capture sorts array 4 by key inside its charged buffer, and V13 requires strictly increasing keys, which one pass checks. Nothing native depends on the holder's order (`LazyOperandValueProfileParser::initialize` builds a map, `addOperandValueProfile` returns the one matching profile, and `CompressedLazyValueProfileHolder::computeUpdatedPredictions` visits them all), and a record's fields are exactly what key equality compares (the defaulted `LazyOperandValueProfileKey::operator==`, and `Operand::operator==` on kind and value).
