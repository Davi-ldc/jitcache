# JITCache harness

This document says how JITCache is tested and measured, and what counts as passing. [THREAD](THREAD.md)'s Verification section is the contract, and this document cites it instead of restating it. The tests themselves live in the SPECs, each lane's in its own; [SPEC-integrator.harness.md](specs/SPEC-integrator.harness.md) holds the runner's mechanics, and the implementation tasks hold everything else.

## Principles

Tests and microbenchmarks of single cases are the core of the feedback loop. When a promise can be stated as a count or as an identity of code, a test checks that count or that identity, and no timing stands in for it: the skipped warm-up is a set of per-body event counts, and "Other VMs emit unchanged" is a comparison with the pinned engine's code. Time is measured only where no deterministic form exists: THREAD's installation bound and the bench's workloads. Benches are alerts from one checkpoint to the next, never targets. THREAD's priorities are relative, and pushing one number at any cost breaks its intentions.

## Criteria

| THREAD guarantee | observable | passes when | when it runs |
|---|---|---|---|
| A consumer run is observably identical to the JITCache-off run (Verification) | the oracle | output and heap description equal | every run of every test |
| Each restored piece equals its native twin or capture record; a lane lands when its pieces do (Verification, Execution) | the twin report | no difference; a skip only in a run where it is allowed; a heap coincidence that does not repeat | every test |
| An import runs without interpreting, compiling again or relearning (opening) | per-body event counts | the counts the case determines, exactly | every test that imports |
| Other VMs emit unchanged (Capture) | the pin comparison | no difference outside the two native fixes | the end of every task |
| Failures and their outcomes (Failures) | fault injection | the outcome THREAD gives, `status` naming the step, twins and oracle clean afterward | every test of a failing step |
| Commits are process-crash-consistent (Capture) | producer kills | the state harness section 12 gives at each point | every kill test |
| The same guarantees under concurrent schedules (Capture, Storage) | the concurrency family | no failure in `concurrencyRepetitions` repetitions | one repetition at the end of a task that touches those paths; all of them at each milestone |
| Importing a body costs at most a fixed fraction of compiling it (Verification) | a microbenchmark per body | alerts only, when the ratio exceeds `installationBoundFraction` for a body of at least `installationBoundSmallestBody` | each milestone, in the release build |
| A consumer's first run matches the producer's warmed run; capture pause, memory and serialization (opening, Verification) | the workloads' startup, first call and catch-up, each beside its memory and pauses | alerts only | each milestone, in the release build |

Every other behavior THREAD states, such as the session's results, identity and its misses, the header's checks, the locks and maintenance, is checked by the lanes' ordinary tests, each with the criterion it states.

Some statements are held by argument and review, and no test checks them:

- JITCache adds no threads and never pauses native GC or compiler threads (THREAD's opening).
- An overlapping drain costs only precision (THREAD Capture); the concurrency family checks that it costs nothing more.
- The list of allocations whose failure turns cache activity off is exhaustive (THREAD Failures).
- A design that works only while JITCache stays baseline-only is a defect (THREAD's opening).
- A caller of `delta` holds no JSC-internal lock, a duty JSC cannot check (THREAD Session).
- Power-loss durability, which THREAD Capture excludes.

## Tests

A test checks one case, is deterministic and passes or fails; the cadence below says when it runs. A case is a path the design tells apart, such as a reference kind, an IC state, a request point or a step that can fail. The implementation task that creates a case writes its test and its microbenchmark, and tests the case's combinations with the cases it can meet in one body or one run: defects gather where cases meet, and the task that adds a case knows which ones it meets. Combinations across lanes, at the seams of THREAD's capture and install order, belong to the integrator's tasks.

Each test says in words which claim it checks. Each test also checks that its case happened: an import test, that the body was imported; a fault test, that the fault fired. A test whose case did not happen fails.

Tests run in the twins build (`bun build.ts twins`, profile `debug-local-twins`), which compiles the twin checks in (`ENABLE(JITCACHE_TWINS)`, THREAD Execution), and in the plain `debug-local` build, with ASan, LSan and `jsc --destroy-vm`. Tests of the host's own paths also run inside Bun, built with `bun build.ts bun-twins` (harness section 7.7).

`image/islands.js` runs only in release aarch64 builds, the one place where its images patch through jump islands, and `image/budget.js` runs its full sweep of producer limits only at milestones.

A test asserts only what its case determines, so its runs fix the schedule. The runner turns background compilation off (`useConcurrentJIT=false`) in test runs, and each baseline compilation then runs on the thread that runs JavaScript. The image's twin needs that schedule: it recompiles the body from the inputs the producer's compiler read, and a compiler on a worker thread reads them while the script keeps running and can still change them, so what the recording saw and what the compiler read could differ (SPEC-image.md section 11.3). The concurrency family covers the other schedule. A count a test asserts must not depend on when the collector runs or when a time lease expires.

A failure that does not repeat is still a failure, of the code or of the test, and the run that showed it counts as failed; no test is rerun until it passes. The runner repeats on its own only a sequence whose sole failure is an address coincidence inside the heap, which it runs once more (harness section 7.5). The concurrency family runs its scripts many times on purpose, and a single failure among them fails it.

## What the tests observe

Each guarantee maps to one observable. Six families cover THREAD's guarantees today. The rest grow with the tasks: a task that adds a case adds the observable that checks it, in one of these families or a new one.

### The JITCache-off oracle

THREAD Verification, first sentence. After each sequence the runner runs the script again with JITCache off and compares standard output byte for byte, which carries the results, exceptions and stack traces the script prints. In twins builds it also compares the engine's description of the heap JavaScript can reach after a full collection, since a script cannot see closure variables, internal slots or private names (harness sections 6 and 7.6). Every JITCache test checks this besides its own observable.

### Each lane's twins

THREAD Verification's sentences on native twins, relocation, capture records and test builds, and THREAD Execution's rule that a lane lands when its pieces equal their twins. In the twins build each lane checks its restored pieces where they land, against twins the consumer computes and, for state the engine cannot recompute, against the capture record: SPEC-ucb.md section 13.2, SPEC-image.md section 11, SPEC-cb.md section 11.1 and SPEC-ics.md section 11.1. All of them write one twin report, and the report is the observable: a difference fails the run, a relocation coincidence fails it outside the heap and repeats the sequence once inside it, and a skipped check fails the run as THREAD Verification's skip rule says (harness sections 2 to 4, 7.4 and 7.5). Placement and address randomization move every compared domain between producer and consumer (harness section 4).

### The off path emits the pin's code

THREAD Capture: "Other VMs emit unchanged." THREAD Native fixes allows two exceptions in native code, the `super_construct` store in `JIT::compileOpCall` and the `negate` operations. With no recorder attached, every body of the corpus therefore compiles to the code the pinned engine emits for it, except at those sites (SPEC-image.md I4). The observable compares each body's baseline code from this build and from a build of the pin (`bun build.ts pin`), instruction by instruction, with each address replaced by what it names and the effects of the random draws removed (the entry's `nop`, and constant blinding on x86_64). The pin cannot be instrumented, so both builds describe their code only through what the engine prints, and the comparison names the addresses itself: with the collector off, each address names one object for the whole run, and the two runs agree when they reference the same objects in the same order (harness section 11).

### The skipped warm-up

THREAD's opening paragraph: an import runs "without interpreting the body, compiling it again or relearning its profiles". Per-body event counts show it: bytecodes the LLInt executes, baseline and optimizing compiles, OSR exits, jettisons and reoptimizations. A test asserts the counts its case determines. An installed import, for instance, executes no bytecode in the LLInt and compiles no baseline code, and a case states what it expects of the optimizing counts against the JITCache-off run and the producer's warmed run. The bench reads the same counts on its workloads as trends. Twins builds count each event once per body, where the engine performs it; a script reads the counts of its functions, and the end of a run writes them for every body (harness section 10). Only twins builds count, so the bench reads its counts from twins-build runs of its workloads and its times from release runs.

### Fault injection

THREAD Failures and the crash consistency THREAD Capture gives commits. Each step that can fail is made to fail on purpose: executable allocation (`useExecutableAllocationFuzz`), the producer limit, the store and the writer (the flags of harness section 5.1), and invalid material in a body mutated after it was sealed. The observable: `status` names the failing step, the outcome is the one THREAD Failures gives, a later consumer passes every twin, and the output still equals the JITCache-off run. Each fault test requires its step to happen. Only some steps leave evidence that the fault came before its effects were written: committed bytes show a late DFG-plan fault (a carried deferred baseline counter) and a late IC-handler fault (a given-up site, in a script whose sites cannot give up otherwise), and the image twin shows a late MathIC-snippet fault. The baseline and FTL plans have no evidence beyond their step (SPEC-integrator.md section 15.2). The writer's hooks fail one step of its n-th commit or compaction as if the system call had failed with EIO. A producer is also killed at each point of a commit and on each side of a compaction's rename, and the next consumer and `compact` must find what THREAD Storage gives a crash at that point (harness section 12).

### Concurrency

Some of THREAD's statements hold under schedules that a deterministic test fixes away: recording on a JIT worker, a capture while markers and compiler threads drain profiles (THREAD Capture), `delta` with plans in flight, an import beside concurrent DFG compiles, and a producer that commits while another process imports (THREAD Storage). This family runs the corpus with `useConcurrentJIT` on and concurrent collection forced (`collectContinuously`), in the twins build. Its observable is everything that still applies under those schedules: the oracle, every twin check that runs (the image check skips in such runs, harness section 7.4), and ASan. The family passes when `concurrencyRepetitions` repetitions of every script show no failure; one failure fails it, and the task that owns the path turns the failure into a deterministic test wherever a schedule can be forced. A producer that commits while another process imports runs as a Bun-hosted script that spawns the second process with `Bun.spawn`, so the runner still runs one process at a time. ThreadSanitizer is not part of the harness: its target runs with the JITs disabled, where no JITCache path runs. Weak memory ordering cannot show on an x86_64 host or under QEMU, only on the Ampere A1, where this family has not run yet (see Platforms).

## Benches

Benches run in the release build (`release-local`) through the same runner, builds and corpus as the tests, with the bench report on (harness section 9). The runner's bench mode runs every corpus case the release build runs in plain mode (harness section 9.4), and the `thread-bench` workflow runs it at each milestone, compares it with the previous milestone and writes the milestone's results. Every number is reported with the process's memory and the pauses JITCache caused beside it (harness section 9.2). The machine lock keeps builds and tests off the machine while a bench runs, and the runner records the load average before, after each copy and after. This machine is noisy anyway, so local numbers are signals, and the runner interleaves the runs it compares, so drift spreads across them.

Microbenchmarks give the numbers we can use. A case's script serves its test and its microbenchmark. Each measured span is read in `microbenchProcesses` fresh processes and its minimum is the value, since interference on a shared machine only adds time to it; the median is reported beside it to show the spread. The exception is a request's apart total, the rest of the request's CPU time after its counted total, which interference during counted work shortens, so its minimum can come from a disturbed copy. The spans the installation bound reads (a request's counted total, an install's total, a native compilation and its finalization) are the wall time between their two ends, capped at the thread CPU time read just outside them, so each holds about one vDSO clock read and none of the CPU clock's system calls. The parts, steps and stages inside those spans would put their own clock reads in them, so they are timed only under `jitCacheBenchBreakdowns`, which runs that set the bound leave off; the runner's `--bench-breakdowns` and `bound.ts --breakdowns` turn it on to explain a ratio, and such a run sets none. A microbenchmark never fails a change. Against its own history it raises an alert when its minimum moves by more than `microbenchAlertPercent`. The installation bound is a far stronger and steadier signal than the workload ratios, because the expected gap between an import and a native compile is large. Its own bench, `PerformanceTests/JITCache/bound.ts`, sets each body's import against its native compile over JetStream2's JS-only tests and a size sweep of generated functions, with the bench mode's tallies.

The macro benches measure what a serverless deployment pays: what each request costs a fresh Bun process, and how long the process takes to finish. Each case in `PerformanceTests/JITCache` is a small app that exports a fetch handler, called the way a serverless platform calls a function, with up to ten request variants; a call sends one request. Every process runs pinned to one CPU with `taskset` and with Bun's shipped configuration, so concurrent JIT stays on and the JIT worker competes with execution, as on a small serverless instance. The driver, `bench.ts` in the same directory, checks that each process saw one CPU and kept its JIT worker threads, and that every process of a case and branch computed the same checksum for each call, whatever its variant. Each case runs in two branches: fixed, where every call sends request variant 1, and varied, where the calls cycle through the case's request variants. Two cases port Bun's own benches with their servers inside the measured process: express and postgres. postgres sends the one request its upstream bench sends, so it runs in the fixed branch alone, and it queries a PostgreSQL server outside the process, which `postgres.sh` runs on other CPUs, so it runs only when `--cases` names it.

Each case also runs in variants, the ways a function deploys, which the driver's `--variants` chooses, all four by default. `source` runs `run.ts`, which imports the case's app through Bun's runtime transpiler cache. The other three run the app built by the measured Bun, once per case before the first repetition, from an entry that imports the app, its requests and `calls.ts`, the module that makes the calls in every variant. `bundle` runs the `app.js` of `bun build --target=bun --format=esm`, with JITCache's flags before it; `compile` runs the standalone executable of `bun build --compile --format=esm`, which takes JITCache's flags from `BUN_OPTIONS`; `compile-bytecode` runs the same executable built with `--bytecode`, which adds Bun's bytecode cache. A build gets the processes' environment, since the bundler writes the `NODE_ENV` it sees into the app. Each variant has its own producers and artifacts, and a producer runs the same build as its consumers. pdf reads its documents relative to its own source file, so it runs only from source. For each case and branch the summary compares startup plus request 1, request 3, requests 2 to 35 and requests 2 to 500 of every variant with JITCache off and as a consumer against `compile-bytecode` with JITCache off, Bun's bytecode cache alone, which decides whether JITCache keeps supporting apps built with `--bytecode`. Beside them it gives the size of each build and artifact and, from the bench reports, the bodies each consumer installed or seeded.

The headline metric is per-request latency, consumers against JITCache off in both branches: the median and p90 of request k for k = 1 to 50, of the sum of requests 2 to 35 in each process, and of request 1 plus startup, which must not be worse than with JITCache off. Request k is call k as `calls.ts` times it, startup is Bun's clock at the ready line (the clock starts when Bun creates its VM, before JSC's VM and JITCache's `start`), and p90 is the nearest rank. The summary gives requests 1, 2, 3, 5, 10, 20, 35 and 50, the sum and request 1 plus startup for each mode of each variant, with each mode's medians against its reference's, and `request-curves.tsv` holds every k. Time to finish is secondary: wall time, the CPU time of all threads, the time after 1, 10, 50, 100 and 500 calls, and the exit time, the wall time left after Bun's clock at the end line, which also holds the exec before that clock starts. The target is a real case at least 20% faster to finish than with JITCache off.

A producer serves 100 calls of its branch and calls `delta` at exit (Bun's `--jitcache-delta-at-exit`, on by default). Two scenarios then compare consumers of its artifact with JITCache-off processes of the same Bun build: 50 calls and 500 calls. The 500-call scenario also runs consumers of a producer that never calls `delta` (the same producer with `--jitcache-delta-at-exit=0`), whose artifact keeps only the captures made at each baseline compile. Two comparisons are opt-in: the driver's `--delta-capture` passes Bun's `--jitcache-delta-capture` to the producers, and a second value adds producers that call `delta` under it and their consumers; `--compare-llint-progress` adds consumers that arm the LLInt counters of imported bodies from zero (`jitCacheImportLLIntProgress` off). Each comparison runs three repetitions, each with fresh producers, of ten processes per mode, interleaved, and reports each repetition's ratio beside the pooled one. Timed processes write no bench report, whose clock reads only consumers would pay; untimed runs of the same configuration write it for the per-body numbers.

A census run per case, branch and variant counts compiles by call, baseline, DFG and FTL, in a JITCache-off process and in each warm consumer mode, all running 500 calls, from JSC's `logCompilationChanges` log split by the call markers `calls.ts` writes. DFG and FTL compiles count when the call's thread requests them. JSC logs no baseline request, so a baseline compile counts when the JIT worker starts it, in the call during which the worker took the CPU, and a plan still queued at exit does not count; `verboseCompilationQueue`, which logs every request, can deadlock and stays off. The baseline compiles show how soon bodies leave the LLInt with JITCache off and in a consumer. A producer that stops at 100 calls takes warm baseline state only from bodies still in baseline then, so most DFG compiles should come after call 100.

Cold processes come in pairs per scenario, case, branch and variant, three in each repetition: a consumer and a JITCache-off process that both start after the files their variant reads from storage left the page cache, and the consumer's artifact too, so both pay the same reads but the artifact's. `source` reads the Bun executable, `PerformanceTests/JITCache` with its `node_modules` and the run's transpiler cache; `bundle` reads the Bun executable and `app.js`; the compiled variants read their executable. Every process of a run uses that run's own transpiler cache (`BUN_RUNTIME_TRANSPILER_CACHE_PATH`), which therefore holds only what the bench reads. The driver drops each file with `posix_fadvise` and checks with `mincore` that no page stayed, both through Bun's FFI, retrying while a process it just reaped still maps the files. It reads every dropped file back after the cold process, so the processes after it start warm, and records each process's reads from storage (getrusage's block input). The kernel's inode and directory caches stay warm, since dropping them needs root.

N1 and C1 are the first calls of a JITCache-off process and of a consumer, and Ck a consumer's k-th call. W is the producer's warmed call: the median of its calls 91 to 100. The ratios C1/N1 and Ck/W are signs that something may be wrong; `catchUpMargin`, the ratio within which a call counts as caught up, is a reasonable number approved from the first measurement, not a gate. W holds optimizing code that this version's consumer compiles natively, so some residual is expected, and the per-body event counts and each lane's bench measurements explain it, beside the two measurements THREAD leaves to the bench: the floor's residue (Restoration) and the samples a process's last `delta` loses (Capture, SPEC-cb.md B4). JetStream2's JS-only tests in the jsc shell and a short Bun CLI run on fixed input are workloads still to define. The human runs the macro benches; the bench workflow runs the microbenchmarks only.

An alert fails no change: it opens an investigation, and the milestone's results record what explained it.

The bench also proposes the numbers THREAD leaves to it, which the SPECs name as parameters: it proposes each value from its first measurement, and a value is recorded here only after human approval.

## Cadence and results

The implementation workflow has one builder and runner, so builds stay within CLAUDE.md's limits and never run at the same time.

- Every change: the twins build, then the touched lane's directory and the integrator's directory in twins mode, the lane's C++ tests, and the Bun-hosted runs when the change touches a host path (Bun's bindings, or the wiring of `start` and `delta`).
- The end of a task: every directory in twins mode, every C++ test, the plain `debug-local` run, the pin comparison, one repetition of the concurrency family when the task touches its paths, and the microbenchmark of a task that changes a measured span. A task that touches ARM64 code (assembler forms, fixups, patching, islands, ARM64 branches in emitters) also runs the image and integrator directories on the Ampere A1, in both builds.
- Each milestone, one per lane that lands (THREAD Execution) and one for the integrator: the release build's benches and a plain run of every directory in it, `concurrencyRepetitions` repetitions of the concurrency family, every directory on the Ampere A1, and the CPU-model checks under QEMU. Release code differs from debug code (debug builds add a consistency check around every bytecode), so code that only release emits, such as an ARM64 call and pointer sharing a fixup site, meets the JITCache-off oracle there. A milestone's runner runs pass `--milestone`, which adds the sequences scripts leave to milestones.

The runner writes each run's results as JSON lines under the build root. Each milestone commits one summary, `PerformanceTests/JITCache/<milestone>.md`, with the commit, the builds and machines, each family's outcome, the bench numbers and each alert with what explained it. A check the cadence prescribes that nobody ran is written down as not run, and a result is written only from a run. A milestone may close with an unexplained alert only when todo.md holds an entry for it with a hypothesis.

## The runner

Tests and benches run through `Tools/Scripts/run-jitcache-tests`, whose modules and the pin comparison (`pin-compare.ts`) sit in `Tools/Scripts/jitcache/`, and `testjitcache`, which SPEC-integrator.harness.md specifies: the twins build (section 1), the twin report and checks (sections 2 and 3), address-space placement (section 4), the jsc, `bun:jsc` and `$vm` helpers (section 5), the heap description (section 6), the runner's directives, sequences, checks, oracle and Bun-hosted runs (section 7), the C++ test framework (section 8), the bench report and the bench mode (section 9), the per-body event counts (section 10), the pin comparison (section 11), the producer kills (section 12) and the harness's own tests (section 13). The head of `Tools/Scripts/jitcache/scripts.ts` lists the directives a script and each test directory's `defaults.txt` can declare.

## Platforms

JITCache supports Linux x86_64 and ARM64 (THREAD's opening). x86_64 native, on this machine, is the main loop and runs every family. ARM64 builds are cross-compiled here (the build table of CLAUDE.md's "JITCache" section) and run natively on an Oracle Cloud Ampere A1, a Neoverse-N1 machine: the cadence copies the aarch64 builds and the runner's files to it, keeping their paths relative to the build snapshot and its build root, runs the runner and the per-architecture self-tests there, and brings the logs and results back. Real hardware shows what emulation cannot: LeakSanitizer, weak memory ordering, instruction-cache maintenance, address randomization, and the time a run takes, so a test's premises meet a native schedule. The A1's generic timer, which both of the bench's clocks read there, ticks at 25 MHz, so every time a report holds is a multiple of 40 ns.

One machine has one set of CPU features, so QEMU user mode stays for the CPU-model checks, the scripts that declare `jitcache-qemu-cpu` (`integrator/cpu-vector.js`): the release build with the sysroot, and the ASan build with the run-time root `~/jitcachearm/arm64-glibc-root` and `ASAN_OPTIONS=detect_leaks=0`, since LeakSanitizer cannot start its tracer under QEMU. Those checks switch the CPU features JSC depends on. Those are the bits the header's CPU vector records on ARM64 (SPEC-integrator.md section 5.2, N11): LSE, JSCVT, FP16, FRINTTS, SHA3 and DotProd, which `MacroAssemblerARM64::collectCPUFeatures` reads from the kernel's HWCAP bits, while `supportsFloatingPointRounding` and `supportsCountPopulation` are always true there. QEMU switches them by CPU model: `cortex-a53` has neither JSCVT nor LSE, `neoverse-n1` (Graviton2's core) adds LSE, and `neoverse-v1` (Graviton3's core) and `max` add JSCVT. The release build cannot run under `cortex-a53`, because the mimalloc it links executes LSE instructions at startup (SPEC-integrator.harness.md N27), so every QEMU run of the cadence goes twice: under `max`, and under `cortex-a53` for the debug builds or `neoverse-n1` for the release build. JSCVT changes baseline code (`JITRightShiftGenerator`) and FP16 the IC cases `Repatch.cpp` caches, and every bit takes part in the header's comparison, so a producer and a consumer under different vectors also check that `start` rejects the artifact. The A1's own vector has LSE, FP16 and DotProd and lacks JSCVT, FRINTTS and SHA3.
