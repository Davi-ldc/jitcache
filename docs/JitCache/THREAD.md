# JITCache

JITCache saves a body's baseline code together with what the engine learned while running the body in the LLInt and baseline, so that a later VM runs that code from the body's first call, without interpreting the body, compiling it again or relearning its profiles, and its optimizing tiers then compile natively from that warm state. A producer VM records each baseline compilation as it emits it and saves the body to a file; a consumer VM that later creates the same body imports the file instead of generating and compiling the body.

Per body, the file carries the UCB core with its parse fields and UCB feedback, the baseline image with its side tables and MathIC state, the native keys of the support code that image calls, CB feedback and counters, call-link history and IC learning state. Everything else the baseline phase learned travels too, while what the consumer measures about its own process, or recomputes before anything reads it, stays local. Each omission saves a large cost at a negligible effect: support code, which the consumer generates natively; IC cases, which native caching rebuilds at each site's first slow-path visit; callee distributions, which hang on callee cells and restart natively with each new variant; the value profiles of `catch` entries, whose buffers the consumer allocates at the first catch; the UCB feedback of a specialization an embedder's cache decoded beside the requested one, which only a cache holding both of a function's specializations produces; and the CB caches that hold cells, which start as native linking leaves them. A SPEC cannot add one. Producer heaps and suspended frames are never restored, higher tiers compile normally in the consumer, WebAssembly JIT code is out of scope, and the targets are Linux x86_64 and ARM64, debug and release; on other platforms JITCache's code compiles and `start` returns rejected.

JITCache captures baseline code first; later versions add DFG and then FTL. This version captures a body only while it runs in baseline, by design: once a body tiers up, its file keeps the last baseline capture, and the DFG capture will update that baseline capture and add the DFG CB beside it. Other state that DFG or FTL code sets and no section names as travelling, such as `ScriptExecutable::m_didTryToEnterInLoop`, waits for the DFG capture. Formats, keys and hooks admit more than one tier per body, and a design that works only while JITCache stays baseline-only is a defect.

Within a VM, JITCache's own steps run on the VM's thread while JS is paused, and recording runs inside native compilation on whichever thread compiles. JITCache adds no threads, does no work ahead of demand and never pauses native GC or compiler threads. Outside recording, capture and first installation, its overhead is near zero.

Execution performance comes first, then capture pause, installation memory, producer memory and serialization time. Installation time has a bound instead: importing a body must cost at most a fixed fraction of compiling it natively. The import's cost is the VM thread's CPU time for everything JITCache does at the body's request point and from the native link that creates the body's first CB until JITCache returns after `installCode`; the native cost is the CPU time of the body's baseline compilation after its profile drain, plus its finalization without relinking incoming calls. Neither side counts parsing, bytecode generation or decoding, `finishCreation`, LLInt execution, the key digest with the context digests and each TDZ environment's first digest, or reading and faulting the artifact, which are measured separately with cold and warm page caches, and both run with per-VM support already generated. The bench sets that fraction and the smallest body the bound covers.

SPECs hold layouts, signatures, native edit lists, tests and the native evidence behind them.

## Session

`start(vm, config)` configures a VM, with the caller holding the API lock and heap access. Called before the VM's first global object, it covers every body, builtins included; a later call misses the bodies created before it and everything nested in them. Bun calls `start` right after constructing each configured VM, and the jsc shell calls it before creating its first global object. The host decides which VMs to configure, where their config comes from and when to call `delta`. JITCache has two public interfaces: a C++ API for any host that embeds JavaScriptCore (`JITCacheAPI.h` and `JITCacheMaintenance.h`), and, on top of it, Bun's command-line flags, which are Bun's whole user-facing configuration. The config names the artifact path, the role (`Consumer`, `Producer` or `ConsumerProducer`), the producer working-memory limit and `strict`, which is off unless the host turns it on. The limit charges every byte JITCache owns for production, from live provenance and kept summaries to the section bytes each lane builds and the writer's buffers; it charges no JSC cell, source text or executable memory, and neither the parent-key registry nor the digests kept for identity, which serve every role; the registry's few fields that only production reads, bounded by its records, are not charged either. Normal mode checks the artifact's integrity, its header, keys and checksums, and trusts the rest, because an artifact that carries machine code must be as trusted as the binary that runs it. Strict also validates the full structure of what JITCache reads and the assumptions it makes, and the SPECs decide which assumptions it covers. A failed strict check is invalid material when it rejects bytes read from the artifact, whether an import, an installation or a capture's scoring read them, or an assumption an installation makes about the consumer's own objects, and a recording fault when it rejects what a capture builds from the producer's own state.

`start` returns created, opened, busy, rejected or fault. A Producer creates a new artifact and gets created; a Consumer or ConsumerProducer opens an existing artifact whose header matches and gets opened, and a ConsumerProducer keeps producing on it. `start` rejects a Producer whose path already holds an artifact, a Consumer or ConsumerProducer whose artifact is missing or incompatible, and any call made while a fixed option lacks its required value. It returns busy for a producing role while another producer or maintenance holds the lock, and fault when it cannot read, write or validate the artifact. Busy and rejected record nothing, so the host may call `start` again. Created, opened and fault configure the VM for good, with no reconfiguration, pause, restart or close; after fault, cache activity stays off. Attaching a debugger also turns cache activity off for good, because the attach turns on the PC-to-origin maps that the fixed options keep off.

`status(vm)` reports state, progress and faults, naming the failing step, without doing work. `delta(vm)`, exposed only in C++, saves what each body learned since its compilation. It requires a producer role, the API lock, heap access and no collector phase on the calling thread, and it rejects any other call without work; holding no JSC-internal lock is a documented duty of the caller, which JSC cannot check. The API returns results and diagnostics, never callbacks.

## Identity

A body key combines the body's persistent identity, its call or construct specialization and the code-generation mode stored in its UCB. A root's identity is its kind (program, module, indirect eval, Function-constructor body or builtin), a SHA-256 digest of its transformed source and the request's strict and with-scope bits, plus the parameter-end offset for Function-constructor bodies. A nested function is identified by its parent's key, its declaration or expression table and its index there, which generation reproduces for the same parent whether that parent was imported or generated. A direct eval is identified by its caller's key, the call site's bytecode index and the evaluated text's digest. Each body also records the context it was generated under (the offset of its source in the provider, the creation parameters of the UFE that holds a root, a direct eval's TDZ and private-name sets), and a differing context misses.

A UFE keeps no pointer to its parent UCB, so each VM keeps a parent-key registry. Whenever a UCB is generated, decoded or imported, the registry records the request key of each root UCB and, for each child UFE, its parent key, table and index. Function-constructor bodies and builtins are roots held by a UFE, so their key is recorded on that UFE when it is created. The UFE's and UCB's destructors remove the entries, and a UCB or UFE without a recorded key misses.

Native UCB and CB ownership and sharing stay as they are: JITCache seeds a UCB or CB only once, before it is published or first runs, and adds no history merges, while native merges continue. An import that meets a live UCB for its body, generated natively or imported from an older file, reuses it when the keys match and misses otherwise; differences in captured feedback or counters alone are no mismatch, and with strict on, the import also checks a reused UCB against the digest of the captured core. A UCB keeps the key it was recorded under. `SourceCodeKey` ignores the with-scope bit, so a CodeCache hit can serve a UCB to a request whose key differs in that bit; that request misses. The decode from a bytecode cache ignores the bit as well, so a decoded root whose with-scope bit differs from its request's gets no key, and nothing in it imports or is captured.

## Storage

```text
parent/
  .cache.producer.lock
  cache/
    header
    bodies/
      <body-key-hash>.bin
```

Each body is one immutable, uncompressed file: an envelope, a section directory and typed, checksummed sections. Each section belongs to the lane that writes it and is opaque bytes to the container, which only locates and checksums it; the integrator (see Execution) builds the directory, the envelope and the header from what THREAD and the SPECs declare. A section refers to another lane's content only through native index spaces (bytecode, constant, identifier and profile indexes, the function and switch tables, the metadata layout, mold order), and to another body only by that body's key, as DFG code that inlines callees will need; the UCB lane guarantees that an imported or reused UCB has the producer's index spaces. The UCB section describes the body's children without their bytecode, since each child is a body of its own. Bodies share nothing across files, and packaging is external. The header holds the full ELF build ID of the loaded binary (and of the engine object when it is separate), the effective values of the must-match options after `Config::finalize`, and the exact effective CPU feature vector from the assembler's predicates. Binaries without a build ID cannot use the cache.

Each JSC option belongs to exactly one class: must-match, fixed or free. An option that can change captured code, how its source parses or what transported state means is must-match when Bun itself sets it (`useExplicitResourceManagement`, `useImportDefer` and `evalMode`) and fixed at its default otherwise. Among the fixed ones THREAD relies on: `useJIT`, `useBaselineJIT`, `useDFGJIT` and `useBaselineJITCodeSharing` on; `useLOLJIT`, `forceUnlinkedDFG`, the debugger and ShadowChicken code options (`forceDebuggerBytecodeGeneration`, `debuggerTriggersBreakpointException`, `alwaysUseShadowChicken`), the instrumentation that embeds VM addresses and the options that make a new VM build PC-to-origin maps (`useSamplingProfiler`, `alwaysGeneratePCToCodeOriginMap`) off; the thresholds folded into a transported base threshold and the cool-down pair at their defaults. `start` checks fixed options against JITCache's own table of required values, [options.md](options.md), which lists every must-match and fixed option with the lanes whose state depends on it, because JSC drops its defaults once options freeze. Every other option, browser-only and WebAssembly options included, is free.

The producer and maintenance take a non-blocking lock on the sibling lock file, which survives artifact deletion and is never replaced; the producing VM holds it for its life, so a process that outlives that VM can start another producer. Consumers take no lock. They pin the directory whose header they validated and keep each validated payload alive while any import borrows it, so a replaced or deleted file stays readable for imports already made while new imports open the current file. A producer may commit while other VMs or processes consume.

## Capture

Producer VMs record provenance while emitting, never afterward. Baseline compilations and MathIC regenerations run in a recording scope: emitters annotate each reference with its typed target and emit it unblinded and unfolded, the assembler records its fixed-footprint encoding at a data label, and `LinkBuffer` translates labels to final offsets after compaction; literals keep native blinding. On ARM64, recording also fixes the footprint of the forms whose length depends on a value or a distance: a cached temp register is reused only for the same reference, `structureIDBase` gets one fixed form, and each external conditional branch goes through a local `b`, so only the `b` carries a fixup. Every image byte that depends on the process, the VM, a UCB or another allocation belongs to exactly one fixup, while literals, internal branches and layout offsets fixed by the header carry none. The rank case jumps of an inline `switch_string` are the one exception: their targets follow the order of the case atoms' addresses, so each carries a fixup. The same rule covers the side tables, the IC molds and the MathICs: a code address (a call's or IC's return point, a switch or code-map entry, a MathIC location) travels as an offset into its image or snippet, a UCB identifier or arithmetic profile as its UCB index, and an immortal VM identifier by name. Recording also writes the facts the compilation baked from its CB (its capability class, its taint and the kind and depth of every unguarded scope access) to a baked-facts section that installation compares. Each record hangs off the `BaselineJITCode` whose code it describes and dies with it. Other VMs emit unchanged.

A CB is eligible while it is its executable's `replacement()`, its JIT type is `BaselineJIT` and its code is shareable and recorded. A body is captured right after each baseline compilation, at the end of the success path of `BaselineJITPlan::finalize`, after `installCode` and `jitSoon`, when its CB is eligible. That capture holds the LLInt phase's feedback and call links but no warm ICs, MathICs or baseline counter, so hosts call `delta(vm)` on an idle producer, typically when a serverless runtime is about to stop an instance. `delta` walks every live CB with `Heap::forEachCodeBlockIgnoringJITPlans`, which completes no pending plan, captures each eligible one whose UCB has a recorded key, imported CBs included, and for each key writes the richest capture when it beats the saved body. In ConsumerProducer mode, an imported `BaselineJITCode` carries the record recording would have left, rebuilt from the body file, and its later MathIC regenerations record like any other.

Capture reads each profile's accumulated state from its own owner, CB or UCB (predictions, array modes and flags, allocation hints, counters), under the locks native readers take (`CodeBlock::m_lock` for ICs, the UCB's lock for exit sites). It never reads, classifies or clears a pending sample, so it never touches a cell a sample may still name. Markers and compiler threads drain this state without locks, and an overlapping drain costs only precision: a drain caught midway equals a sample not yet drained, and a capture lacks only such samples. The next `delta` carries them once the producer's drains fold them, but a process's last `delta` loses them; the bench measures how often one of them carries a type its slot never saw. Capture calls nothing that drains, materializes a property table, allocates a cell or stops for the collector, so no stopped-world GC phase runs while it reads code, link products, MathIC state, IC data and call-link state, which only the VM thread and those phases change.

Capture then scores the candidate against the summary of the saved body, which each lane writes into the body file and which is read at the key's first scoring: per-slot profile categories, array flags, exit sites, the count of IC sites with cases and the baseline counter progress, marked when the polymorphic rule of Restoration withholds it. A category is one bit of a slot's `SpeculatedType`, or of an arithmetic profile's observed types and results; the CB lane writes the value, argument and lazy-operand categories and the array flags, each already unioned with the UCB copy it pairs with by position, and the baseline counter progress with that mark; the UCB lane writes the arithmetic categories and the exit sites; and the ICs lane writes the count of IC sites with cases. Richness counts one unit per type category in each value, argument, lazy-operand or arithmetic profile slot, one per array flag other than the pruning mark and one per exit site, each slot taken as the union of its CB and UCB copies, which is what the native merge leaves for the DFG; array modes do not count, because first-run pruning can shrink them. A capture of a higher tier wins first; between captures of the same tier, the richer one wins, because a type seen once tends to return and a missing one costs exits and recompiles; more IC sites with cases break a tie, then a capture whose counter progress the polymorphic rule withholds beats one whose progress travels, then more baseline counter progress, and a remaining tie keeps the saved body. On acceptance, capture writes before JS resumes: a writer with bounded memory streams the body to a temporary file, rereads and validates it, and publishes it with `renameat`. Commits are independent and process-crash-consistent; power-loss durability is excluded.

## Restoration

A UCB is imported where the engine requests one: for program, module, eval, Function-constructor, builtin and child bodies. Each request point reads the UCB core from the body file, validates its key and reference closure, restores parse fields and seeds UCB feedback, and only then returns the UCB in place of the generated one, so its native holder, the UFE slot or the CodeCache, publishes it as it would a generated UCB. Where the native path decodes the UCB from a bytecode cache instead (the CodeCache's decode from the provider, a UFE slot decoded on demand), the decode stays, and the import checks the decoded UCB, seeds it and attaches its pending import before publication. Bun's `vm.Script` and `vm.compileFunction` with cachedData keep Bun's own decode, which sets `cachedDataRejected`, and the UCB that decode yields gets no recorded key, so nothing in it imports or is captured; `vm.Script`'s runs, which never use that UCB, import at the program request point, and `vm.compileFunction` without cachedData imports there like any program. Misses take the native path, and a body whose UCB Bun drops after the entry script of `bun run`, or on `Bun.gc(true)`, goes through its request point again at its next request. ESM keeps Bun's `module_info` or ordinary analysis, native instantiation, live imports, TDZ and top-level await; nothing runs without source, and no analysis is cached.

An imported body's first CB installs where a newborn CB receives its first code: before `setupLLInt` in `prepareForExecutionImpl`, and at the top of `JIT::compileSync` for LLInt-off creation. Both points come after the native test of the UCB's sharing slot, so a `BaselineJITCode` already parked there wins, as it would for any newborn CB, and the import stays pending until a newborn CB finds the slot empty. The install function compares the baked-facts section with the linked CB. With the LLInt on, it also applies `shouldJIT`, the gate the LLInt's own tier-up applies; that gate depends only on options and the body, so a failure leaves every CB of the body native and drops the import. The install function prepares the image, the seeds and the IC state privately, under its own GC deferral, so a failure writes nothing to the CB; it then seeds the CB, runs native setup, attaches the IC state, re-slices the baseline counter against the consumer's pool at least two entry increments short of crossing, resamples aging and calls `installCode`. Each seed thus lands in its native owner before any reader or writer: UCB feedback, the LLInt counter included, before publication; CB metadata, call-link history included, after linking and before the CB has a JIT type; the baseline counter and the IC state after setup. Metadata is seeded field by field, never by copying whole entries, because one entry can hold profile fields beside a `CallLinkInfo`.

The counter floor lets the first invocation of a body that neither loops nor recurses cache its hot property accesses and link its calls before the first DFG compile parses. In other bodies the counter can cross during that invocation, and the sites it has not reached compile as generic accesses and calls without inlining, with a `ForceOSRExit` at each `resolve_scope` still unresolved; the bench measures that residue. A body with a property IC whose captured record lists two or more cases, megamorphic folds aside, carries no baseline counter progress: one consumer invocation rebuilds only the cases it meets, so a DFG compile at the floor would speculate on those alone, and the BadCache exits that follow would enter the exit profile and slow every later compile at those sites. Its quick tier-up bits, reoptimization counts and profiles still travel. The ICs lane supplies that bit to the CB lane at capture, and also sets it for a call site the producer left polymorphic when the ICs SPEC shows that such a site meets the same exits. A baked-fact mismatch leaves that CB native and keeps the import for the next newborn CB of the same UCB, which installs it with the captured state. A pending import lives in its UCB's registry entry from publication until a CB installs it or the `shouldJIT` gate drops it, and otherwise goes with the UCB; a baked-fact mismatch keeps it, invalid material turns cache activity off and leaves it to die with its UCB, and it never sits in the UCB's sharing slot, whose doors would install it with fresh CB state and whose release would free a `BaselineJITCode` no CB owns. A CB that already ran in the LLInt receives no imported state, and the CBs after the one that installs share the image natively, the shared `BaselineJITCode`'s state included (coverage rates, MathIC patches), with fresh CB state.

The image is allocated with `JITCompilationCanFail`, copied once and patched with the assembler's own link writers, which place ARM64 islands; flush, fence and code-size sample follow native finalization. String switches keep the producer's tree: the consumer writes its own atom for each recorded rank and retargets that rank's case jump. Because the image compares a string constant by pointer as an atom (in `stricteq` and its siblings), every string constant that was an atom when the producer captured the body is an atom in the consumer before any CB installs the image: the UCB lane carries constant atom-ness and interns those constants before it publishes an imported or seeded UCB, and a reused UCB that cannot guarantee it misses. MathICs keep their targets, regeneration flag, snippet and maps, and the consumer rebuilds each generator from its instruction. A support reference is its native key with process-local parts replaced by build-stable symbols, and the consumer resolves it through the native lookup, which generates missing support as the VM's first use of it would. Images avoid every piece of VM data that exists lazily or only under an option (the ShadowChicken log, the exception-fuzz buffer, the loop-hint counters, the per-bytecode profiler), because debugger code generation needs an attached debugger, which turns cache activity off, and the other options are fixed off.

Heuristic history travels as captured: counter progress and base thresholds, profile deferrals, reoptimization counts, quick tier-up bits, the UCB's `didOptimize`, coverage rates and IC cool-down counts, failure effects included, such as a failed FTL compile clearing the quick FTL bit. The baseline CB's FTL-failure flag stays local, because nothing reads it on the baseline path and the consumer's first DFG compile of the body re-evaluates the gates that set it. `m_shouldAlwaysBeInlined` stays local as well: setup, host entries and each caller's first linked call derive it again in the consumer. A child UFE's singleton bit, `m_singletonHasBeenInvalidated`, travels in its parent's UCB feedback, while a root UFE's stays local: reading the body file when a root UFE is created, which JSC and Bun do eagerly for many builtins, would be work ahead of demand. Keeping it local costs at most one jettison when a second closure appears, and mono-proto allocation by `ObjectAllocationProfileBase::initializeProfile` until a second function of that executable exists; both costs are speed only. With `forceUnlinkedDFG` fixed off, the only baseline or DFG failures that leave a persistent record come from lack of memory, which never reaches a capture. Memory-pressure slices are recomputed against the consumer's pool, and time leases and VM statistics stay local. The UCB's LLInt counter travels as native finalization leaves it; the request point arms it before publication without a slice, as the native initial arming does, since no CB exists yet, and no `jitSoon` or `jitNextInvocation` follows an import.

## Caches

Scope metadata and the CB caches that hold cells evolve natively from their link state, as in any CB born in baseline. The baseline `super_construct` template stores back the callee it loaded instead of `new.target`, so a CB born in baseline never fills that cache; JITCache makes the template store `new.target`, as the LLInt does, which fixes native CBs born in baseline as well. A regenerated `negate` MathIC passes its own address to a slow operation that takes a profile, so it ORs observations into its profile pointer and its UCB profile stops learning; JITCache makes that operation read the profile through the IC, as `add`, `sub` and `mul` do, which fixes native code as well. Call sites come back seen-once with their scalar history (closure, cleared by GC, cleared by virtual dispatch, varargs maximum), so the first call links natively without creating callee CBs early; a site the producer left virtual comes back virtual through `CallLinkInfo::setVirtualCall`, the native route into a mode native linking never leaves.

Each property IC comes back with its considered and non-cell bits, its cool-down state with the repatch count rewound by the captured case count, so re-caching those cases does not count twice toward a cool-down, and its wait counter at zero, so the native slow path records the consumer's own case at the site's first visit, from the actual operands and after the normal lookup. A site the producer folded megamorphic comes back with `canBeMegamorphic`, which makes `tryFoldToMegamorphic` apply its fold rules from the first case, and a site that gave up with no case listed comes back given up, with `tookSlowPath` and its `*GaveUp` slow call. A site that gave up with cases still listed (an eighth case compiled as final code, a `GiveUpOnCache` after earlier cases, a folded `instanceof`) comes back on its `*Optimize` slow call, empty, with its captured learning, and the native path gives up again if it must. The considered bit matters before that visit: a DFG compile that parses a put site whose IC had cases emits a generic put with its own IC, where an IC never considered would get a `ForceOSRExit`. Restoration emits no IC code, and native caching keeps its own effects at that slow path, such as flattening a dictionary or materializing a property table.

## Failures

In a VM, invalid material turns cache activity off and abandons preparation, because an artifact that produced one invalid body is not trusted for the next. So does an executable allocation that fails for lack of memory in a tier's plan, an IC stub or handler, a MathIC snippet or JITCache's own image: a pool that cannot hold a plan cannot hold an image either, and the VM thread raises the fault inside the operation that surfaces the failure, before its effects are written, which keeps those effects out of every capture. The list is exhaustive: the other allocations that may fail, in Yarr, Bun's FFI thunks and stubs and WebAssembly, keep native behavior. Capture and `delta` never finalize plans, so a plan that fails after its body was captured changes only the live VM, and the committed body stays valid. Installed UCBs and CBs stay valid, and pending imports and image records die with their owners, without a sweep. Misses are normal, and unrecoverable native failures keep JSC behavior.

A recording fault ends production in that VM for good: a charge past the producer limit, or a storage failure while writing, rereading, validating or publishing a body. Uncommitted work is canceled without retry or catch-up, a `delta` stops at the fault and reports what it committed before it, and a later `delta` reports the fault. Recording runs on a JIT worker or on the VM thread, so a charge past the limit fails on whichever thread makes it; it marks the record incomplete and fails every later charge, and the VM thread raises the fault then or at its next capture or `delta`. Neither VM destruction nor process exit performs an implicit `delta`: committed bodies survive, canceled writes cannot commit, and the next `clean` reports abandoned temporaries.

## Maintenance

`clean(path)` and `compact(path, ratio, options)` share a synchronous, VM-independent CLI backend, refuse busy artifacts, and report outcomes, diagnostics and reclaimed bytes. Clean removes abandoned temporaries, never committed bodies. Compact cleans, then plans whole-body eviction: ratio, in [0,1], is the fraction of the post-clean bytes to evict, so zero only cleans, and bodies are evicted in increasing order of (L + P) / B. B is the body file's size, L is the LLInt tier-up threshold the import skips, as the UCB's history scaled it at capture, and P is the captured baseline counter's progress, floored at zero, capped at its active threshold and zero for a body that carries none, both in execution-counter points. The score is thus the warm-up, in execution-counter points, that importing a body saves per byte. The writer stamps L, P and a commit identifier, the body version compact compares, in the envelope, so planning reads envelopes only and runs in bounded memory.

A plan that evicts every body, because ratio is 1 or because reaching the ratio takes them all, deletes the whole artifact, header included, and needs confirmation. The CLI asks "This operation will delete the entire cache. Ok? (y/n)"; `options` can carry the answer for non-interactive runs, and without it compact changes nothing and returns the plan. Compact holds the producer lock while planning and applying, releases it while it waits for confirmation, then reacquires it and applies only if body versions and the plan are unchanged. Interruption may leave a partial eviction but never an incomplete survivor.

## Verification

The native path with JITCache off is the oracle, and any miss falls back to it: a consumer run must be observably identical to a JITCache-off run in results, exceptions, stack traces and the heap that JavaScript can reach after a full collection, except for results that depend on how close the stack is to its limit, which a skipped parse or an earlier tier-up changes; a test that reaches the limit prints only that the stack-overflow `RangeError` happened, never the depth it reached. Each restored piece must also equal its native twin, the value the engine itself produces for that piece, computed in the consumer process by test builds, with every process, VM, UCB, support and Structure-reservation address differing between producer and consumer. That relocation requirement skips a target inside an object loaded at its link-time address, as Bun's build flags load the engine, and skips every target of a body the importing process captured itself. State the engine cannot recompute, such as heuristic history, predictions, counter progress and base thresholds, must equal its capture record. Only test builds record what the twins need: the producer's random draws and the inputs each compilation and MathIC regeneration read, the atom-ness of string constants included. A twin check that skips itself fails the run exactly when concurrent JIT is off in the process that imports the body and in every process whose captures it imports, directly or through a recapture, which keeps the original compilation's record. Every test runs with strict on, and the bench measures the default.

## Execution

The work splits into four lanes by the native object that holds each piece of state, so that encoding, storing and restoring one piece is one decision with one owner. Each lane is one SPEC that its agents implement without redesigning; a decision that binds two lanes is a contract in this document, and a lane decides alone only what no other lane depends on. JITCache's code lives in `Source/JavaScriptCore/jitcache/`, in namespace `JSC::JITCache`, and the test builds Verification relies on are those with `ENABLE(JITCACHE_TWINS)`.

1. UCB: keys, the parent-key registry, every request point, the UCB core with its parse fields and child descriptors, UCB feedback with the LLInt counter, and pending imports.
2. Image: recording and fixups, the baseline image with its side tables and MathICs, the coverage rates `BaselineJITCode` holds, baked facts, support references, the `negate` operations and the image's preparation at install.
3. CB state: the CB's metadata profiles, argument and lazy-operand profiles, the baseline counter and the CB's heuristic state.
4. ICs and call links: property-IC learning state, call-link history and the `super_construct` store in `JIT::compileOpCall`.

An integrator is derived from the frozen lane SPECs: the header and the option table assembled from the lanes' rows, the container, the writer, locks, the entry points, the capture and install glue that calls the lanes in this document's order, the fault plumbing and maintenance. It provides `JSC::JITCache::didFailExecutableAllocation`, callable with `CodeBlock::m_lock` held, and calls it on the failure path of `BaselineJITPlan::finalize` and in `DFG::Plan::finalize` when the plan recorded an executable-allocation failure; the ICs lane calls it at the three `didFailToAllocate()` branches of `InlineCacheCompiler`, for IC stubs and handlers, and the Image lane at MathIC regeneration in every tier. The integrator decides only what it alone owns, such as byte layouts, checksums, section type ids, file names and API signatures, against requirements the lane SPECs state; the UCB lane owns the canonical key bytes the body-key hash reads. Each lane lands when its pieces equal their twins, and none changes what an earlier one accepted. When DFG and FTL arrive, every tier's code bytes, including what its ICs and direct calls patch into them, belong to an image lane, and the data-driven IC learning and call links of every tier belong to the ICs lane.

Then a bench loop until a consumer's first run matches the producer's warmed run and the installation bound holds per body, with provenance and recorder use measured so the producer limit stays out of normal runs.
