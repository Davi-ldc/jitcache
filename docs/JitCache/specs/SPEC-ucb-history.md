# SPEC-ucb history

Why the decisions of [SPEC-ucb.md](SPEC-ucb.md), [SPEC-ucb.codec.md](SPEC-ucb.codec.md) and [SPEC-ucb.analysis.md](SPEC-ucb.analysis.md) that are not obvious were taken: for each, what first seemed right, the evidence that changed it and the intent that came out. Nothing here binds an implementer.

## What a context holds

THREAD lists a context's parts as examples: a source offset, the creation parameters of a root's UFE, a direct eval's TDZ and private-name sets. A generation input that is in neither the key nor the context lets two different UCBs share one body, so the context also took the script mode, the derived and eval context types, the arrow-context bit and a direct eval's flags, each constant for most requests. A child got only its offset, since its parent's key and context seemed to pin everything else.

At webkitbun `2e2aa229` the source's first line was missing. The lexer numbered lines from `SourceCode::firstLine()`, and three fields of the child descriptors were absolute: a class constructor's class source, the positions of class elements and a field initializer's first-line offset. Two `vm.Script`s with one text and different `lineOffset` values produced different UCBs under one key and context, and an import reported the producer's lines from field initializers and static blocks, or a line near 2^31 when the consumer's start line was lower. Every context then recorded the first line of its source, a child its own. The start column was proposed and refuted, since it shapes no UCB (F21), and rebasing the absolute lines at decode was rejected, since a decoded UCB would no longer encode to its payload's bytes.

At webkitbun `0c06faad` the first line left the contexts again. The engine now keeps positions as offsets only: `JSTextPosition` lost its line, the UFE its line fields, and lines are derived when something reports them, from the provider's text and start position (F21). The three absolute fields are gone, so a UCB is the same at any start line, and the CodeCache serves it that way. Keeping the field would have cost more than needless misses: `SourceCode::firstLine()` now builds the provider's line-start table, which reads the whole text, at the first context a request computes, on exactly the `--compile` paths F25 keeps from reading text (SPEC-ucb.md section 3.3, I23).

## Payload parts the native decode leaves for later

At `0c06faad` a native decode from an owned or persistent payload leaves UFE members, symbol table entries, a module's function declarations and, from a persistent payload, expression info in the payload, and materializes each at its first use (F28). The JITCache decode first inherited it: the core's `CachedBytecode` has a destructor, which the engine counts as owned. A deferred part would then be decoded from the pack's mapping after `decodeUnlinkedCodeBlockCore` returned, outside the validating decode, at a point where a failure can no longer abandon the import, and the UFE would keep the `ValidatedBody` and its mapping alive, a mapping compaction may already have replaced. The JITCache decode turns deferral and borrowing off and decodes everything at once (codec E6); the cost falls in decoding, which THREAD's bound leaves out, and generation, which an import replaces, makes everything at once too.

## Line starts belong to the provider

At `0c06faad` generation stores the provider's line-start table in a global UCB when something had built it, and the bytecode cache encodes it, so that a module decoded from a payload need not scan its text for lines (F21). Whether the table existed at generation depends on the provider's history, such as an error that reported a line or an earlier generation of the same text, so two generations of one program would encode to different cores, breaking S1 and twin T1. The table is a function of the provider's text, and the provider builds it when something first asks; the core leaves it out (codec E15).

## UCB value and array copies travel with an image

At `0c06faad` a UCB's value and array profiles, the copies its CodeBlocks fold theirs into, exist only once `BaselineJITPlan` has allocated them, and never for a builtin (F6). Before, a body without an image carried its copies, which then made its whole richness. A capture without an image now carries none, even when its UCB had them before its CodeBlocks died: the consumer runs it in the LLInt, where the native path allocates none, and its richness is its arithmetic categories and exit sites (THREAD Capture). The feedback section keeps V and A as the UCB's counts in both cases, so C3 checks them, and a byte says whether the arrays follow.

An import with an image skips `BaselineJITPlan`, so nothing would allocate the copies, and the CodeBlocks' drains would fold nowhere: the copies would stay empty where the producer's run had filled them, and the native twin would differ. Allocating them in the install glue was considered and left to the lane: an imported UCB gets them before publication, where the lane seeds them, and a live UCB gets them before its attach, so every UCB a pending import reaches has them before any CodeBlock installs it (SPEC-ucb.md sections 5.3 and 7.3.3, I28).

## Holder digests and TDZ chains

A child's key names its parent's key, table and index, and its context only its kind and offset, so the parent's context, which shapes the child UFE too (a parent at another provider offset gives its children other source positions), enters neither. C10 closes that wherever a match relies on generation inputs, at an import and at an attach: the requesting UFE's holder digest must equal the one the producer's body was generated from (SPEC-ucb.md sections 3.4 and 4.4). Root contexts first digested a hand-listed set of creation fields. The descriptor, the codec's encoding of the UFE alone, replaced that list, since the codec already writes every field generation reads and E1 and E2 make it independent of the UFE's slots and its own parse.

The descriptor first included the UFE's TDZ chain. Every function of a module holds a chain ending in a link that names each lexical binding of the module (F26). The holder digest, run at every function import, every attach to a generated or imported UCB and every capture, encoded and sorted those enclosing environments each time; every function core whose generation created closures repeated the names, captures and core digests encoded them, and an import decoded and interned them only to drop the duplicate. `CachedPtr::encode` deduplicates by address within one encoder, but across bodies the cost grew with functions times bindings, and per body with the bindings, so a small function at the top of a large bundle would have broken THREAD's installation bound.

A function core writes its chains relative to its holder's, and a chain equal to the holder's becomes one start record (codec E12, I25). The holder digest takes the chain out of the descriptor and appends a chain digest, one hash per link over its environment's digest and its parent's. Each environment's digest is kept in the environment and freed with its names, because a registry map keyed by address would have to pin the environment, keeping a scope's names alive after its code died, or hook `CompactTDZEnvironmentMap::Handle::~Handle`, which cannot reach the VM. Links are not memoized: a chain has one link per enclosing lexical scope that declares something, and each costs one 80-byte hash. The kept digest is charged to no production limit, since it serves every role and its release runs where no budget is reachable; THREAD Session exempts the digests kept for identity.

Three proposals were not adopted. A marker for "the holder's chain" written after the links a generation created is what the start record already does, without the encoder knowing which links its own generation made. Memoizing links as well as environments buys nothing at one hash per link. Build-time holder digests for JSC builtins would need a second definition of the descriptor in the Python builtins generator, and a builtin's holder digest runs only beside an import or attach that costs far more, or at a capture.

A later profile of the request point on the Ampere A1 put the holder digest and its matching at 4 to 5 us per imported body. In an elysia consumer, 354 of the 700 imports per process were child functions. C10 cannot simply be skipped, even for a child whose UFE its imported parent's decode made: a child's key is its parent's key, table and index, and its context only its kind and offset, so a child body captured under an older version of its parent, since recaptured, still matches the key while its UFE differs. A capture therefore lists the holder digest of each child UFE, computed from the producer's own UFE, and a child of a parent imported in this VM compares that entry instead of encoding its UFE (SPEC-ucb.md section 3.4). The entry equals what computing would give, since the decode reproduces the descriptor the core encodes and the UFE's chain is the parent's holder chain plus the links the core writes relative to it, whose content the parent's own C10 or context matched; strict computes the digest anyway and holds the entry to it, so every strict import checks that argument. Locally it took an elysia consumer's holder digest from 0.74 us to 0.02 us per child body, 348 us to 7 us per process. Chaining each child's context to its parent's context digest would also have pinned the child's UFE wherever the parent was generated or imported, but it changes what a child's context records, which THREAD Identity fixes, and needs the parent's chained digest at every child capture; the listed digests leave THREAD's rules as they are.

## Contexts are digested where they are read

Every request first computed its context with its key, before `bodyVersion` said whether the artifact held a body, and every record stored the digest, in every role. Two contexts cost far more than a short hash. A root UFE body's context holds a holder digest, a whole JITCacheCore descriptor encode with its zeroed first page and its maps. A direct eval's context sorts every TDZ and private name of the scope chain, which `JSScope::collectClosureVariablesUnderTDZ` gathers from every lexical, catch and module scope at each `DirectEvalCodeCache` miss. The first call of every builtin and `new Function` body, and every such direct eval, paid an encoder run or a sort of thousands of names, usually for a key with no body, against THREAD's "no work ahead of demand"; a root body's import also digested its holder twice, for its context and for C10.

Only matches and captures read a context digest. A request computes its context at the first comparison with a body and keeps it with the holder digest, so C10 reuses the digest a root's context took. A record keeps the context's inputs (`RecordedContext`), from which an attach or a capture computes the digest, for a root body with its UFE's holder digest, which cannot change while the UFE lives (SPEC-ucb.md sections 3.4 and 3.6, I21). A direct eval's sets live only on `JSC::eval`'s stack, and a copy per record would keep every binding name of the scope chain for each eval UCB, so its record keeps the digest its import computed or, in a VM whose production is active, one computed at the record. The counters `contextDigests` and `holderDigests` make the rule observable (U8, `context-on-demand.js`).

Skipping C10 for a root whose context matched proved unnecessary once the request keeps the holder digest: C10 is then a 32-byte comparison. A later review held that a producer sorts a direct eval's sets once more per eval; the native request already sorts the same names when generation interns them, and the lane digests a direct eval's context only when an import found a body or a producing VM records the UCB.

## Supplied root digests

Every root key digest first hashed the root's whole transformed source, in every role, builtins at their creation. F25 shows paths where the engine reads no text: `bun build --compile` records each module's hash, so a CodeCache lookup reads no text, an import replaces the parse that would, and release builds create builtins from build-time metadata, many of them for bodies that never run. The hash put its cost on the startup paths JITCache exists for, against the near-zero overhead THREAD's opening gives outside recording, capture and first installation.

A root's digest comes from where its text was produced when that place recorded one (SPEC-ucb.md sections 3.5 and 7.2.6): the builtins generator writes each JSC builtin's digest beside its metadata, and a provider may return one from `SourceProvider::jitCacheSourceDigest()`, which Bun fills for compiled modules and internal modules, whose roots take the digest of the provider's whole source. A supplied digest is trusted as `hash()` is. The generator's digest belongs to the build and is checked as the codec's round trip is, by U9 and debug assertions. A provider's digest belongs to the embedder's output, where a mistake gives two texts one key; only an import acts on the key alone, so strict verifies the digest there, once per provider in the VM (S2), and the registry keeps the provider beside every key derived from the root, so that a function body of the tree is verified at its own import. Verifying at every request would bring the cost back, and verifying at capture protects nothing the consumer's check does not. A direct eval needs no verification: its key ends in the digest of its own text, so a wrong upstream digest can change only the caller key it is found under. S2 therefore never runs for a direct eval, and its records keep no provider.

The A1's startup profile (2026-10-13) then showed root digests at 0.64 ms of hono's 47.7 ms consumer startup and 0.44 ms of react-ssr's: `bun run` loads node_modules from Bun's runtime transpiler cache, whose providers supplied no digest, so every consumer hashed every module's text again. The cache entry now carries the digest of its output, computed once when the entry is written. `ResolvedSource` first carried a pointer to the executable's bytes; a cache entry is freed before the provider exists, so the struct holds the 32 bytes inline with a flag. Non-ASCII UTF-8 output gets none rather than a digest of transcoded text the writer never held.

The internal modules' digests were first to grow each record of the builtins section and bump its format version, but `src/exe_format/builtins.rs` reads that section from another platform's executable with a fixed record size. The digests sit in a table that the header's first reserved word locates. Two alternatives were not adopted. Per-body text digests for roots and function bodies would read source text at capture and hash nested ranges once per nesting level to speed up an opt-in mode. A per-provider cache of computed digests would serve no path, since none computes one provider's digest twice except an attach after released parked code, and Bun's internal modules make a new provider per global object.

## Keys read a snapshot of the request's features

Keys first read the executable's `lexicallyScopedFeatures()` when they were computed. The request's own native steps overwrite that field with the parse's, generation through `generateUnlinkedCodeBlockImpl` and a CodeCache hit through `recordParseFromUnlinkedCodeBlock` (F18). A Producer computed its first key after generation and recorded a `"use strict"` program under strict 1, while a Consumer computed it before generation under strict 0, so the body never imported; a hit replaced the request's with-scope bit with the cached UCB's. The request objects snapshot the features in their constructors, before any native step, which is the value the native `SourceCodeKey` is built from, and keys, contexts and the twin generator read only the snapshot (SPEC-ucb.md section 7.1, I20, U3, `role-keys.js`).

## The bytecode cache's codec in a JITCache mode

A UCB core is the whole output of generation, and the bytecode cache already encodes every part of it, including cells that are hard to transport (symbol tables, template descriptors, immutable butterflies, big integers) and the child UFEs with their rare data and TDZ links. Bun maintains that codec, and its rewrite made the format deterministic. A codec of JITCache's own would duplicate several thousand lines and drift from the engine. The cost is surgery at each gap the native form leaves (SPEC-ucb.codec.md section 4): child bodies (F7, E1), external strings (off), a payload with no checksums of its own (F8), which the container's checksum covers, UFEs that decode as cache-born (F9, E5), hashed map layouts (F10, E3) and whole TDZ chains (F26, E12). A symbol lookup that fails during decode becomes a decoder failure (E4) instead of a `RELEASE_ASSERT`, because a body naming a private name the VM lacks must be invalid material, not a crash.

## A core's content is its encoding

THREAD asks strict to check a reused UCB against the digest of the captured core. The first idea was a canonical walk over the index spaces other lanes use. Once the codec is deterministic, its encoding is that canonical form, covering every index space and everything else observable in the core, so `coreDigest` hashes the section, and both strict checks of the first design, a round trip of every import and the reuse check, became an encode and a hash.

Those encodes ran through the bytecode cache's `Encoder` inside the request point: a zeroed first page of 64 KiB, deduplicating maps, and `Encoder::release` copying every page into one buffer before SHA-256 read it, once per import with strict on. The round trip only repeats a property of the build. The decode depends only on the validated bytes, E3 and E4 turn what it cannot reproduce into decoder failures, and E8 and E9 keep the VM's mutable state out of the bytes, so a wrong codec fails the same bodies in every run, which T1 checks on every twins import and U7 over a corpus. The round trip went; the reuse check stayed as S1, since THREAD Restoration requires it and it tests generation inputs a run can falsify (SPEC-ucb.md sections 4.3 and 10.2). Codec rule E10 starts JITCacheCore encoders at a 4 KiB page that doubles, and E11 hashes the pages in place through chunk entry points, so neither a match nor a holder digest allocates or copies a payload; B7 measures what remains.

A review proposed a hash-only walk over the fields the codec writes, carried as a separate digest. It was rejected as a second definition of a core's content, to be tracked by hand through each WebKit bump, where a field it missed would let two different UCBs match silently.

## Hashed declaration maps keep their layout

`CachedInlineMap::decode` reserves capacity and re-adds entries, which reorders a map above nine entries (F10). `ProgramExecutable::initializeGlobalProperties` creates global vars in that order, so a program with more than nine vars imported through the native codec would enumerate `globalThis` differently from the JITCache-off run and report another redeclaration error first. The native bytecode cache has the same property, but an import would bring it into runs that generate natively. No insertion order reproduces a layout in general, since growth rehashes and deletions leave tombstones, so `InlineMap` gained a checked layout restore and the JITCache mode transports the exact bucket layout (codec E3 and section 5). The record grows for the native cache too, which keeps one record shape and costs a few bytes per hashed map.

The restore first listed only what a correct layout needs, and three resealed layouts still crashed a strict decode. A power-of-two capacity far above the entries made it allocate without bound, so it gained the shrink rule's minimum load, which every native map meets. A deleted marker cannot live in a `VariableEnvironment` map, whose traits are `HashTraits<RefPtr<UniquedStringImpl>>` over `PackedRefPtr` keys: the deleted key `(T*)-1` does not survive the six-byte packing, so restoring one asserts in debug and refs an invalid pointer in release. Nothing removes from these maps, so E3 refuses the bit; changing the parser's key traits would be a native edit for a layout only a resealed file carries. A null key, which the validating decode gives a malformed string, crashed the probe walk's hash, so the restore refuses empty and deleted keys before hashing any, and E13 states the same rule for every container the core decodes.

## Butterflies built from atom strings

`ArrayNode::emitBytecode` gives an all-atom-string literal the structure `cellButterflyOnlyAtomStringsStructure` and makes each element the VM's canonical `JSString` for its atom, and `indexOf` and `includes` take a pointer-comparison fast path on it (F23). The codec's decode gave every butterfly the plain structure and plain strings, so an import differed from its native twin. The form travels as a bit map in the identity section, which the codec leaves untouched, and only an import acts on it: after the reference-closure checks it rebuilds each marked butterfly as generation does, interning every element through `atomStringToJSStringMap`, because the fast path's absence test reads that map and a structure switched without interning would make `indexOf` return -1 wrongly (SPEC-ucb.md sections 4.2 and 7.3.1 step 8, T6, I22). The map was chosen while natively decoded UCBs were matched by their core encoding, which a form written into the core would have broken; with no decoded code matched, the form could move into the core, and the map stays only because moving it would change the codec and the identity section for no measured gain. A live UCB keeps the form its native path gave it, which is its native twin's.

## `RegExp` constants by pattern and flags

`CachedRegExp::encode` wrote the cell's atom, specific pattern and parsed bit. A `RegExp` constant is a cell the VM shares, and `RegExp::deleteCode` clears the atom and specific pattern on every live `RegExp` whenever `VM::deleteAllCode` runs, as `Bun.shrink()` makes it (F22). A core's encoding then depended on whether code deletion had run since generation, and a decode could return a live cell in another state, so the strict checks and T1 failed on legitimate bodies. Codec rule E9 writes only the pattern and flags in the JITCache mode, decoding takes `RegExp::create`, the call generation makes, and C5 checks that the result is valid, since generation emits only valid patterns.

## The ordered-hash-table sentinel by identity

The codec first carried every constant cell by content, as the bytecode cache does. JSC's `Map` and `Set` `forEach` builtins hold the VM's ordered-hash-table sentinel as a constant and end their loop by comparing it by identity with the storage the iteration intrinsics return (F27). An imported copy has the sentinel's structure and length, so the core bytes (T1) and the structure check (T6) matched while the loop never ended: debug builds assert in the iteration helpers, and release builds read past the empty storage. A census of what generation puts among a UCB's constants found no other such cell: the native decode returns the VM's small strings, its zero `BigInt` and its `RegExp` cells as the consumer VM's own, and the other VM and realm cells bytecode compares by pointer are link-time constants. The sentinel gets its own kind, written by identity and decoded as the consumer's own (codec E14). Making the intrinsic a link-time constant, as `sentinelString` is, would keep the cell out of the UCB, but it changes the bytecode and baseline code of both builtins in every VM, which THREAD allows only for its two native fixes.

## Decoded code gets no key

Code the native path decodes from a bytecode payload was first kept and matched: the decode ran unchanged, and the request point matched the decoded UCB to a body by its core encoding, atomized the string constants that were atoms in the producer, seeded it before publication and attached its pending import, because nothing pins a payload's generation inputs (option values, the with-scope bit, Bun's bytecode optimizer) and a decoded UCB differs from a generated one in atom-ness, butterfly form and hashed declaration layouts (F10, F19, F23). That took a provenance field and an atom map in every body, a record of the butterfly map a decoded UCB was matched with so that a recapture stayed importable, a hook in `functionDeclSlow` for module declarations a decode leaves in its payload, a miss for a module that still held one, and a matching path beside the attach.

The macro bench on the A1 (2026-10-16) showed Bun's bytecode builds starting fastest, JITCache on top of them adding 2 to 8 ms, about half of it the content matching, and JITCache's later requests faster than the bytecode builds'. Part of the bytecode builds' lead over JITCache is the module analysis they precompute ([A module's analysis goes through Bun's module info](#a-modules-analysis-goes-through-buns-module-info)). Bun's internal modules were then to keep a decoded path identified by their record's place in a payload the header's build ID pins. At bun-v1.4.3 that payload exists only in an executable built with `--compile --bytecode`: `bun build` writes it per app into the executable's `.bun` section, which the build ID does not cover (F5), so two compiled apps of one Bun can hold different code at one place.

So no decoded code gets a key, Bun's internal modules included: JITCache carries an app's bytecode itself, an app is built without `--bytecode`, Bun warns when it meets such code, and a module's analysis travels with its body instead (SPEC-ucb.analysis.md). The decode hooks, the matching of decoded UCBs and everything they needed went (SPEC-ucb.md section 7.2.5); generated and imported UCBs hold only atom string constants, so no atom map is needed either.

## A module's analysis goes through Bun's module info

A hook in `JSModuleLoader::makeModule`'s parse branch seemed simplest: one engine edit that builds the record with JSC's own API from a format of JITCache's own, and it works in the jsc shell too. Davi chose Bun's path instead. On the A1, bytecode builds started 2.6 to 17 ms faster than JITCache without them, and JSC's analysis of the five bench bundles costs 0.5 to 8.3 ms on x86. The facts allow that path. Bun's self-contained form carries every form the analysis parse records, and Bun builds records from it for every ESM bytecode build. A provider's type is fixed at construction, but every input of the module's key is in hand there. Making every ESM provider BunTranspiledModule and deciding later in `Bun__analyzeTranspiledModule` was rejected, because a miss would then go through `fallbackParse`, which skips JSC's `attachErrorInfo` and memory report. Intent: Bun's provider creation asks JITCache for the bytes, a hit becomes module info, and a miss leaves the provider Module and JSC's parse untouched.

## The producer captures the analysis the parse built

Serializing every module's analysis at load, or re-running the analysis at capture, seemed natural. Re-running it allocates a `JSModuleRecord`, which a capture may not do. Serializing at load is work for modules that are never captured. Records Bun builds from its printer's module info under test isolation differ from the parse's: they set `m_isTypeScript` and record type-only imports as SingleTypeScript. A consumer outside isolation parses, so such records must never travel. Intent: the module's request keeps a weak handle on its linker when the provider is Module. The capture encodes from that handle, or copies the saved body's section when it has no live source, which keeps the analysis a ConsumerProducer imported.

The rule first said only when the handle is kept: when a module request records, imports or is served a UCB. Served UCBs reach the engine through the attach, whose first check turns away every VM that does not import, so a step placed among the attach's checks would never let a Producer replace a dead source, which a `JSModuleRecord` that died leaves behind. Intent: one step, `keepModuleAnalysisSource`, runs after each record and before the attach's first check. Making a `Weak` calls `Heap::didAllocate`, which can run incremental marking, so the step makes it with the registry's lock released (SPEC-ucb.analysis.md section 4.1).

## The analysis import reads one section

`openBody` checksums every section, and the module's request opens the same body again moments later. A large bundle's module core is megabytes, so opening it twice doubles the CRC work. Intent: the integrator reads the analysis section alone, with the framing checks and that section's CRC.

## A damaged saved analysis ends the capture

A capture without a live analysis source first treated `Unusable` from `readBodySection` like `Absent` and wrote the body without the section. `Unusable` means the integrator found the saved body damaged and raised invalid material, which turned cache activity off and ended production; the glue then committed the body anyway, and `delta` went on committing later keys. The scoring read checksums only the summary sections, so this read is the first to meet a damaged `ucb.analysis`. `buildSections` returns `SavedAnalysisUnusable`, which the glue does not raise again and which commits nothing (SPEC-ucb.analysis.md section 4.2); the integrator also tests production after each build, for invalid material raised anywhere inside one.

## Module digests count where the work happens

The analysis import derives a module's root digest at provider creation, and the module's request takes it back from the provider (SPEC-ucb.analysis.md sections 5.1 and 5.2). Counting the import's digest as a request counts one would count each module twice in `suppliedSourceDigests` when Bun supplied a digest, and under strict would count the hash that checks a supplied digest as a digest computed from text. Leaving the request's take uncounted would need the provider to say who set its digest, through a second virtual in the exported `SourceProvider.h`, for a statistic. The import counts only the hashes it makes, `sourceDigests` for a text hashed for want of a supplied digest and `suppliedDigestVerifications` for one hashed to check a supplied digest, and the request counts its take as it counts any provider's digest. A module whose text the import hashed therefore counts once in each, which B1 states.

## A module that carries bytecode imports no analysis

Nothing first kept a provider with `bytecode_cache` from the analysis import. Two cases reach it: an ES module that Node's compile cache serves, whose first run generates and is captured while later runs decode, and a bundle built with `--bytecode` and ESM output but without `--compile`, which gets no module info, since `LinkerOptions::generates_module_info` requires an executable. The import is correct there, because the analysis depends only on the text, but the module's UCB decodes and gets no key, while THREAD makes a matching key the condition for an imported analysis and has decoded code import nothing. The import skips such providers, and the module's analysis is parsed natively (SPEC-ucb.analysis.md section 5.2).

## Charges inside the encoder

The first design charged only the encoder's pages and claimed an overshoot of one page after a refusal. The encoder also allocates its deduplicating tables, the closures it defers and per-record scratch (varint buffers, sort vectors, 8-bit string copies, packed tails), and once a charge is refused the encode cannot unwind inside a record, so it runs to its end, with pages doubling to 64 MiB. Codec rule E7 charges the tables and scratch as they grow and makes a refusal sticky, I16 and B6 state the real overshoot, the rest of one encode, and `UCBSections` holds its budget and releases its charge when destroyed (SPEC-ucb.md section 8.1). Charging an estimate before the encode was not adopted, since no count bounds an encode before it runs, and neither was a reused scratch page, which would break the offsets later records and `release` read.

## Parse fields and singleton state

Native generation creates a child UFE with zero features and no captured variables, and the child's own parse fills them. A producer's parent encoded after some children ran would carry parsed values, so the JITCache mode writes them unparsed (E2) and each child's body restores its own at its request (SPEC-ucb.md section 7.4); F3 makes that restore load-bearing. Learned bits go the other way. A child UFE's `m_singletonHasBeenInvalidated` is learned at run time and read when the parent links, so it travels in the parent's feedback. `SymbolTable` singletons propagate from the CodeBlocks' realm clones into the UCB's tables (F14), and the bytecode cache writes none of that state, so the feedback section has one bit per constant (section 5.2, C9).

A root's own bit, on a Function-constructor or builtin UFE, was first read from the root's captured body when the root was created, since `link` reads it right after creation. Global object setup creates many builtins eagerly (`JSC_BUILTIN_FUNCTION_WITHOUT_TRANSITION`, thirteen in `ArrayPrototype::finishCreation` alone), so a consumer's first global object opened and validated every captured builtin body, including those that never run. Validating lazily and caching the opened body was proposed; it still opened a file per captured root during setup, against THREAD's "no work ahead of demand". The root bit stays local (THREAD Restoration; SPEC-ucb.md section 5.1). It has two readers, both through the executable's singleton that `link` derives from it. The root's own DFG compile folds `GetCallee` to a constant while the singleton holds (`ByteCodeParser::get`, the `GetCallee` case of `AbstractInterpreter`), so a consumer without the bit can jettison that code once, when a second function of the executable appears after the compile. `ObjectAllocationProfileBase::initializeProfile` (`bytecode/ObjectAllocationProfileInlines.h`) allocates `this` poly-proto only when both the executable's poly-proto set and its singleton are invalidated, so until a second function exists in the consumer, `new` of such a root allocates mono-proto objects where the producer allocated poly-proto ones. Both costs are speed only, and a JITCache-off run pays them at the same points.

## Arming the LLInt counter

THREAD's "travels as native finalization leaves it" and "arms it without a slice" were read together: the capture records the base threshold T and the progress P, which right after finalization are `jitSoon`'s, and the import re-arms with no CodeBlock, as `UnlinkedCodeBlock`'s constructor does. The first arming copied `ExecutionCounter::setThreshold`, which truncates the slice into `m_counter` but adds the untruncated slice to `m_totalCount`, so `count()` gained up to one point (F20). `jitSoon` arms against a fractional memory-pressure multiplier, so the progress after finalization is fractional and T4 failed on most bodies. The arming truncates before adding, which keeps `count()` at P and crosses after the same points as native (SPEC-ucb.md section 5.5, I12, U6).

A deferred counter, at `INT32_MAX`, is accepted and armed exactly, since `deferIndefinitely`'s state is native, although no native capture holds one. The LLInt defers its counter only when `shouldJIT` fails (`entryOSR`, `loop_osr` and `replace` in `llint/LLIntSlowPaths.cpp`), which then fails for every CodeBlock of the body, so none of its compilations is captured, and `BaselineJITPlan::finalize` defers it only after the fault R-INT-11 raises first. Rejecting `INT32_MAX` as invalid material was not taken.

## Every exit site counts toward richness

THREAD's richness counts one unit per exit site. A review showed a path by which an import could lower what later consumers start from. A non-looping body whose captured progress had crossed reached `operationOptimize` at its second invocation, with no IC cases restored, and a DFG compile that parsed an IC listing one of a site's shapes speculated with `CheckStructure`, whose exits are `BadCache`. When the exits jettisoned the code, `CodeBlock::tallyFrequentExitSites` added the site of every exit with a nonzero count to the UCB's exit profile, and from then on `hasBadCacheExitSite` made `GetByStatus` and its siblings return their slow version. Richness ranks before the IC count, so a ConsumerProducer's recapture after such a jettison won and wrote the induced sites into the artifact; `DFG::ExitProfile` only appends and seeding carries the captured list, so each generation could only add such sites. A lane-local exclusion of exit sites at bytecodes whose captured IC listed several cases would have bound the ICs lane, the integrator's scoring and this lane's summary at once.

THREAD's polymorphic rule removes the cause: a body with a property IC whose captured record lists two or more cases carries no baseline counter progress (the ICs lane's `hasPolymorphicSite`, then the CB lane's capture), so it never gets the early compile. Every exit site counts (SPEC-ucb.md section 5.6). A recapture of an imported body still carries every exit site its import seeded, and SPEC-integrator.md IB10 measures the sites added per ConsumerProducer generation.

## The registry's lock, lazy child identities and shared parent nodes

Sweeping happens on the thread that holds heap access (F12), so the registry seemed to need no lock. A sweep can run a destructor in the middle of a JITCache step on that same thread, so the registry has a lock whose rules, a leaf with no cell allocation, no GC-deferral change and no reference dropped inside, make that reentrancy safe (SPEC-ucb.md section 6.3). Child identity digests are computed at the body's request, since most nested functions of a large module never run and eager digests would cost native generation one SHA-256 per child (section 6.1).

Each child entry first copied its parent's 40-byte key and provider reference, so an entry cost about as much as the UFE cell in a table at most half full. The children of one recorded UCB share one `ParentIdentity` node, so an entry is a reference, a table and an index, 16 bytes, and B5 reports the per-UFE figure. A per-parent child vector was not adopted, since `identityOf` must find a UFE's identity from the UFE alone, and reserving the maps from the table counts was not either, since a growing WTF map cannot reserve and its growth is amortized.

## Misses are stamped with index tokens

The first attach kept a miss flag that never expired, which kept a ConsumerProducer from reusing a UCB whose body it later committed itself. A miss then stamped the commit identifier of the file it opened, but stamps were compared with the index's version, which a lagging index never matched. R-INT-3 has `bodyVersion` answer a token from the integrator's index with no envelope read. Stamps and skips compare tokens, the matched-body shortcut compares commit identifiers, and an open that finds no body stamps the token (SPEC-ucb.md section 7.3.2). The same index answer removed the second file open that first imports made.

## A live UCB is met only at its holder

THREAD's "an import that meets a live UCB for its body reuses it" had two readings. A global lookup of live UCBs by key would hand one UCB to two holders, which native code never does and THREAD Restoration rules out, so the lane reads it as an import at a request point whose holder already holds a UCB, attaching a pending import and never seeding a published UCB (SPEC-ucb.md section 7.3.3). The first attach computed the full request key, a whole-source SHA-256, at every CodeCache hit on a recorded UCB without parked code, and re-encoded the UCB for the reuse check at every re-attach. The record keeps its key's root bits and the commit identifier it was matched at. The attach checks the sharing slot, the index token and the stamp first, compares the bits, computes the source digest only when an attach would follow, skips the key for UFE bodies, whose record is their identity by construction, and re-attaches at a matched identifier without re-checking (I21, B3).

The source digest at a global attach guarded against `SourceCodeKey`, which compared no text under `USE(BUN_JSC_ADDITIONS)`, serving a block to another text with the same hash. At `0c06faad` the key compares the texts of two different sources again (F4), so a hit implies the request's key apart from the with-scope bit, which the record's key features still check; the attach no longer computes a source digest, and no CodeCache hit reads a source's text for JITCache (SPEC-ucb.md section 7.3.3 step 4, I21).

## Bun's `cachedData` paths

The first design served `vm.compileFunction`'s decoded user function as a live UCB, attached without seeds. A later one keyed a decoded root by its payload's with-scope bit and edited Bun's `NodeVM.cpp` so the wrapper's key reached its children. Bun's `vm.compileFunction` generates `cachedData` under a global scope extension it never clears while its run path generates the wrapper without it (F11), and a decode's `SourceCodeKey` check ignores the with-scope bit, so neither key held. Bun's `vm.Script` and `vm.compileFunction` with `cachedData` keep Bun's own decode outside JITCache, with no Bun edit, and what it yields gets no key, as all decoded code does; `vm.compileFunction` without `cachedData`, or with data its decode rejects, imports at the program request point (SPEC-ucb.md section 7.2.5).

A review reported that the decode reads a freed `cachedData` span. That happened with JITCache off as well, so it belonged to Bun; the lane neither edits that decode nor reads what it yields, and `compile-function.js` called the user function only in release runs, which ASan does not instrument. Bun 1.4.3 decodes an owned copy of the data (F11), and the test calls the function in every run.

## `vm.Script` requests at construction, on an executable of its own

`vm.Script`'s runs were first taken to import at the program request point, and `vm-script-cached-data.js` looked for the import in `runInThisContext`. Bun's `constructScript` requests the program through `NodeVMScript::unlinkedCodeBlockFor` before it reads `cachedData`, so that a SyntaxError throws at construction as it does in Node, and the Script keeps that UCB. Every run passes the UCB to `JSC::evaluate` as a precompiled block, which `ProgramExecutable::initializeGlobalProperties` takes without a request (F11). A Consumer therefore imported at construction and made no request in the run. Deferring Bun's request to the run would take a Bun edit and lose the construction-time SyntaxError. The import stays at construction, the first run's CodeBlock installs it, and the test checks the construction and the run in windows of their own (SPEC-ucb.md sections 7.2.5 and 13.3).

The with-scope tests first ran their program through `vm.runInThisContext` after `vm.compileFunction`, on the reading that every later request in the realm carries the with-scope bit. `unlinkedCodeBlockFor` requests on a `ProgramExecutable` it creates, which starts with no features and which nothing marks, and the executable `Interpreter::executeProgram` marks for the run makes no request. Every request a `vm.Script` makes therefore keeps the clear bit, with JITCache off as well. `with-scope.js` captured no body under the set bit, and its ConsumerProducer, whose only expectation was to install nothing, passed anyway; `role-keys-bun.js` passed without making a set-bit request. A root takes the bit from the extension only where the code that creates its executable reads it: `executeProgram`, which Bun's CommonJS wrapper reaches, every creator of an indirect eval, and the Function constructor (F11). The tests make their set-bit requests with an indirect eval, the simplest of these, and `with-scope.js`'s ConsumerProducer must miss `NoBody` and generate the body under the set bit (SPEC-ucb.md section 13.3).

## Parse-time stack depth

An import cannot reproduce the `RangeError` the parser would raise at a given stack depth, so the first design imported regardless, as a native CodeCache hit does. That skipped the native error even where the request itself was already past the limit. Before its first step the import misses `Stack` when `!vm.isSafeToRecurse()`, the limit `Parser::canRecurse` tests, so the native parse throws its `RangeError` as with JITCache off; only a parse whose own recursion would pass the limit from a shallower depth still imports, and THREAD Verification exempts results that depend on how close the stack is to its limit (SPEC-ucb.md section 7.3.1). A depth margin as a bench parameter was rejected: it would miss imports where the native parse succeeds and still could not predict a parse's own depth.

## Plan-site faults go through the integrator

No part first owned the executable-allocation fault of a DFG or FTL plan, though THREAD Failures required it before the failure's effects are written. DFG and FTL plans that cannot allocate install a `FailedFinalizer` on the compiling thread, the failure surfaces in `DFG::Plan::finalize`, and the callbacks then defer the baseline counter and clear the quick DFG or FTL bit; a failed baseline plan defers this lane's LLInt counter in `BaselineJITPlan::finalize` (F24). Three of those writes are this lane's state. `FailedFinalizer` records no cause, and a plan that fails for another reason, such as `FTL::canCompile`, must keep its effects, which THREAD carries. R-INT-11 asks the integrator, which owns the fault plumbing, to raise the fault before any of the failed plan's effects is written (SPEC-ucb.md section 9.2). The integrator raises it in the baseline plan's failure case and in `DFG::Plan::finalize` before the callback, with a cause flag on `DFG::Plan` that the compiling thread sets where the allocation fails (SPEC-integrator.md section 9). The other `JITCompilationCanFail` sites, in Yarr, Bun's FFI thunks and stubs and WebAssembly, write nothing a capture reads, so they keep native behavior. THREAD Execution names the plan sites, and THREAD Failures makes the list of the other sites exhaustive.

## Normal mode and strict

The lane first checked every section rule and C1 to C9 at every import. THREAD made strict opt-in, with normal mode checking only the artifact's integrity: its header, keys and checksums. The section rules and C1 to C9 became strict checks, SV1 to SV3 beside S1 and S2, and with strict off the parse functions read fields where the layouts put them. What chooses a body stays in both modes: key, context and C10, since those comparisons choose a body rather than check one. C6, the decode's own report, runs at every import, because the codec's root, symbol, layout and start-record checks are part of decoding (SPEC-ucb.md section 10.2).

A review found the decoder's checks shallow for nested records. Codec rule E13 defines the validating decode strict runs: placement of every nested record, tags in range, every native assertion about payload data checked before it fires, string hashes and ordinals, and an instruction stream that walks whole from start to end, which keeps the other lanes' strict walks inside it. Judging instruction operands was not taken. JSC has no validator for operands, jump and handler targets or the counts that size a UCB's tables; the checksum and the build ID pin those bytes; the encoder copies the stream verbatim, so a writer or codec bug shows as broken structure, which E13 catches; and an artifact rewritten so that its operands are wrong could carry wrong machine code as easily, the case THREAD Session's trust rule covers.

A stored identity key that differs from the body's own was first a quiet stamped miss (`KeyCollision`). The pack's index names a body by its whole key, and container check B3 matches the envelope's key to the key of the index entry, so such a key contradicts the body's own envelope and is invalid material at `ucb.identity` in both modes (SPEC-ucb.md section 7.3.1 step 4a).

## NaNs a decode accepts

A review found that the validating decode accepted a `Double` constant holding a NaN that the baseline's `negate` fast path turns into a cell pointer, since that path flips bit 63 of the boxed value. The first rule demanded the pure NaN `jsNaN()` of every `Double` record, on the belief that generation stores every NaN that way. Generation purifies only constant registers (`BytecodeGenerator::addConstantValue`): an array literal's element keeps the NaN the parser folded, such as `1e400 * 0`, with the bits the CPU gives it (`0xfff8000000000000` on x86_64) and its sign flipped by a folded negation, so that rule rejected cores generation wrote. Limiting it to constant registers was not adopted either, because `-arr[0]` negates an element through the same fast path. Every `Double` record must decode to a double whose negation is pure as well (`isImpureNaN`), which is exactly what the fast path needs and what every generated NaN satisfies (codec E13).

## The validating decode shares what the native decode shares

The validating decode first bypassed the decoder's offset cache, so it checked a record wherever a slot reached it. A review found two faults in the bypass. A crafted core whose many TDZ links name one environment record made the decode quadratic in time and memory, and a valid core that shares a record decoded it into two objects where the native decode gives one. E13 then kept the cache, recorded the type each offset was decoded as, and said that every record decodes once and the decode stays linear in the payload. The code written to that rule showed the last clause held only for the records the cache serves. A record the encoder writes once per owner cannot be shared, the two string record types are one type, and records reached in place, through constant slots and owners' rare-data slots, decode at each reach, as they do natively. Two reviewers then asked for linearity for those too, which would mean marking every record a decode reaches in place and failing a second reach. That was not adopted. A generated core names an in-place record from one slot only, apart from strings, which decode to one atom whichever slot reaches them. A crafted core costs at most what the native decode costs, and THREAD Session trusts an artifact as far as the binary that runs its machine code, so strict checks a core's structure and is no defense against a core built to be slow. The cache kept its purpose: a valid core decodes to the object graph the native decode gives (codec E13).

## Decode shortcuts were measured and dropped

The core decode is the largest part of a request point, so two shortcuts were built under Bun 1.4.2 and measured on the Ampere A1. A lean decode for cores the decode does not validate skipped the second parse of child records and sized the decoder's string table once. It made a local decode 4 to 8% faster for cores of 512 bytes to 4 KB, but saved only 0.01 to 0.33 ms per consumer process, with per-body decode times within noise. Reading an imported UCB's instruction stream in place from the pack's mapping, as Bun's `useBorrowedBytecodeFromCache` did for its own cache, saved 0.08 to 0.2 µs per body, at most 0.2 ms per process. Both were reverted. Trimming around the `CachedTypes` decoder does not move the decode; a core laid out to be adopted in place rather than rebuilt might, and todo.md keeps that idea.

## The codec rebuilt on upstream's at `0c06faad`

The merge rebuilt `CachedTypes.cpp` and `.h` from upstream's and applied the mode rule by rule. Where the bounded read
first went into `VarintReader` itself, it added a branch to every native varint read, a cost the bytecode cache would

## U8 runs once per configuration

One `$vm.jitCacheUCBSelfTest()` call was meant to cover U8, but `start` fixes a VM's role and strictness for good, and invalid material turns its cache activity off for good (THREAD Session and Failures), so U8's parts need several roles, both strict values and a sticky fault. The first answer kept the shell entry point and gave it a scope, with a JS script driving one run per configuration and the invalid-material case last. Once `testjitcache` existed, each test got a fresh VM of its own, so U8 became five tests, one per configuration, and the shell entry point and its script went (SPEC-ucb.md section 13.1). The other parts need no configuration and run once each.

The case of a wrong supplied digest first ran with the other parts of its configuration. T7 reports a supplied digest that differs from its text wherever a request takes one, and a check that tolerates no undeclared difference then fails every configuration that took a wrong digest. The case runs alone, in the one test that expects exactly its difference (SPEC-ucb.md section 13.1). Tolerating the difference in the other configurations too would excuse the differences of U8's own imports there.

## Request-point work and the installation bound

THREAD's bound first counted the seeding done during decoding and nothing else of the request point, and its list of costs measured separately named the decode, the key digest and reading the artifact. Matching, the closure checks, the section parses, parse fields and records fell in neither, although all of them run before the native link that opened THREAD's window: `ScriptExecutable::newCodeBlockFor` calls `unlinkedCodeBlockFor` before `FunctionCodeBlock::create`, and a global executable holds its UCB before its CB exists. The lane counted them toward the bound with the seeding and left the native decode, the key and context digests and `openBody` where THREAD put them. Each TDZ environment's first digest, which grows with the enclosing scopes and not with the body, counts with the key digest. THREAD Verification adopted that accounting. The butterfly rebuild counts inside the bound, since it is JITCache work and not decoding, and strict's checks stay out, since the bound is measured with strict off (SPEC-ucb.md section 14, B2).

## A producer prints its consumer's traces

`start-line.js` runs one text under a producer's `lineOffset` 0 and a consumer's 10. The runner compares both runs with one JITCache-off run of the same options, which follows the consumer path (SPEC-integrator.md R-ALL-4), so the producer must print the traces under 10. Throwing from the text under 10 after the capture shows 0's lines instead: the CodeCache serves the text the generation under 0, since `SourceCodeKey` holds no position, and a field initializer and a static block kept absolute lines at webkitbun `2e2aa229`. The implementer gave the producer an oracle run of its own through a JSC option that changes nothing (`--useV8DateParser=true`, which Bun already sets), read back by the script to choose its path. All three reviewers called that a design change: it makes an `Off` run follow the producer path, against R-ALL-4, and ties the test to an unrelated option. A text with one trailing space misses the CodeCache and is generated afresh. With Bun's debug twins build and JITCache off, its traces under 10 equal, line for line, those of a process that ran only the text under 10, while the text itself, run under 0 first, shows 0's lines (measured on 2026-10-11). So the producer prints the consumer's traces from that text, and R-ALL-4 and the runner stay as they are.

At `0c06faad` a UCB holds no line (F21): the UCB the CodeCache serves under 10 reports 10's lines, so the producer throws from the same text, and the trailing space went with the field initializers' absolute lines.

## Bodies that ran without compiling are captured

Captures first held only compiled bodies. On the Ampere A1 under Bun 1.4.2, the bodies a consumer still generated natively were the ones its producer had run without compiling: 263 per hono process, 11.4 ms of generation, 647 in elysia (26.5 ms), 231 in webhook (10.3 ms), 80 in react-ssr (16.7 ms) and 16 in preact-ssr (2.6 ms). They left a consumer's startup plus request 1 2 to 5 ms slower than JITCache off. With them captured at `delta`, startup plus request 1 became 8 to 38% faster than off in the five cases, while the same build with the delta capture `compiled` stayed 2 to 3.5 ms slower in hono, elysia and webhook. The producer's exit pays for it: its `delta` took 16.1 ms against 6.7 ms in hono (339 bodies and 1.40 MB against 39 and 0.68 MB) and 28.8 ms against 9.9 ms in elysia (739 bodies against 60), where a producer without `delta` exits in about 5.5 ms. The default `all` rests on that gain, and `compiled` keeps the cheaper exit for a host that wants it.

## Bodies that ran without compiling are found through the registry

The capture of bodies that ran without compiling (THREAD Capture, decided on 2026-10-14) first looked like an extension of phase 1: delta already visits every live CodeBlock and turns away the LLInt ones at eligibility, and their UCBs are safe to read. The bodies it is for are mostly run-once code, whose LLInt CodeBlocks die after their five-second window or at the first collection that finds them old, well before a serverless instance stops; their UCBs live on in their UFEs' slots, and only the parent-key registry still names them (`UCBRegistry::m_codeBlocks`). So delta walks the registry (SPEC-ucb.md section 8.3). The registry's lock is a leaf, and a cell's liveness test takes its block's lock, so the walk copies the records out under the lock and tests each UCB with `isPendingDestruction()` afterwards; a UCB the last collection condemned keeps its fields until it is swept, but its constants and child UFEs may already be swept.

## A body ran when its LLInt counter says so

A UCB's existence proves a request, not an execution: `CachedCall` prepares a callee before any call, a module is generated when it is linked, and Bun's `vm.compileFunction` links a wrapper it never runs (`sortStableSort`, `JSModuleRecord::getOrMakeExecutable`, F11). Capturing every recorded UCB would fill the artifact with bodies the consumer may never request and charge production for them. The LLInt counter is the one signal every run leaves: each prologue adds five points to the body's counter, and a deferral, `INT32_MAX`, happens only at a crossing or after a compile a crossing started (`llint/LLIntSlowPaths.cpp`). Only the VM thread writes it and it holds no cell, so reading it at a capture is exact. Arithmetic profiles and UCB predictions were rejected as signals: int-only operations take LLInt fast paths that write no profile, and an LLInt CodeBlock merges its predictions into the UCB only at a collection's visit.

## Fifteen points short of crossing

THREAD's first wording armed an imported body without an image with its captured progress as is, as a body with an image. A body whose producer stopped one prologue short of the threshold would then cross at its first consumer entry and compile there, from feedback the consumer's LLInt had not yet added to, and every site the first invocation had not reached would compile cold. The cap of one full LLInt invocation, five points at the prologue and ten at the return, lets that invocation complete in the LLInt, profiling its sites, before its return crosses; the baseline counter's floor in Restoration follows the same idea. Compact scores such a body by the progress its import carries, since that, not the whole threshold, is the warm-up the import saves (THREAD Maintenance). Whether the carried progress pulls native compiles early enough to cost requests on one CPU is a measurement, so the free option `jitCacheImportLLIntProgress` arms the counter from zero for the bench's comparison.

## Records keep their holder, which its destructor clears

The core's encoding and the identity section need the UFE that produced a function UCB (codec E12, section 3.4), which buildSections used to take from the CodeBlock. A UCB keeps no pointer to its UFE, and the UFE's slots are private, so a capture without a CodeBlock takes the holder from the record. A live CodeBlock keeps its UFE alive through its executable, but a conservative root can keep a UCB after both its CodeBlocks and its UFE are gone, and an address reused by a later UFE would hand the capture another function's chain and parse fields. Testing the holder through its registry identity was rejected for that reuse. The registry instead keeps, per holder, the UCBs whose records name it, and the UFE's destructor hook clears their field, so a holder in a record is always a UFE that has not been destroyed; delta still skips one that is dead but unswept. Only a producing VM with the delta capture All keeps holders, which bounds the cost to the VMs that walk the registry.
