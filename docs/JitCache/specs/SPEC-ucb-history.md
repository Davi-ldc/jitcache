# SPEC-ucb history

Why the decisions of [SPEC-ucb.md](SPEC-ucb.md) and [SPEC-ucb.codec.md](SPEC-ucb.codec.md) that are not obvious were taken: for each, what first seemed right, the evidence that changed it and the intent that came out. Nothing here binds an implementer.

## What a context holds

THREAD lists a context's parts as examples: a source offset, the creation parameters of a root's UFE, a direct eval's TDZ and private-name sets. A generation input that is in neither the key nor the context lets two different UCBs share one body, so the context also took the script mode, the derived and eval context types, the arrow-context bit and a direct eval's flags, each constant for most requests. A child got only its offset, since its parent's key and context seemed to pin everything else.

The source's first line was missing. The lexer numbers lines from `SourceCode::firstLine()`, and most of a UCB stores lines relative to its source, which is why the native CodeCache serves one UCB to sources at different lines. Three fields of the child descriptors are absolute (F21): a class constructor's class source, the positions of class elements, which a field initializer's parse restores into the lexer, and the initializer's first-line offset, which comes from a default token location and so equals minus the parent's first line. Two `vm.Script`s with one text and different `lineOffset` values produced different UCBs under one key and context. An import then reported the producer's lines from field initializers and static blocks, or a line near 2^31 when the consumer's start line was lower, and strict turned the cache off at an attach.

Every context records the first line of the source its body was produced from, a child its own, since its key carries the parent's key but not the parent's context (SPEC-ucb.md section 3.3, I23). A field initializer's linked source starts on line 1 under any first line, so its context cannot tell two first lines apart; its holder UFE's element positions differ instead, and C11 misses. The review that found this also proposed the start column, which was refuted: it shapes no UCB (F21). Rebasing the absolute lines at decode was rejected: the decoder would need the request's `SourceCode`, the encoder would rewrite three fields against a base the initializer's clamped source hides, and a decoded UCB would no longer encode to its payload's bytes, all for a case that arises mostly from `vm.Script` with `lineOffset`.

## Holder digests and TDZ chains

Once decoded parents were keyed by their payload's bits, a child's key pinned its UFE only if the payload's generator ran with the fixed option values, which nothing records (F4). C11 closes that wherever a match relies on generation inputs, at an import and at an attach to a generated or imported UCB: the requesting UFE's holder digest must equal the one the producer's body was generated from (SPEC-ucb.md sections 3.4 and 4.4). Root contexts first digested a hand-listed set of creation fields. The descriptor, the codec's encoding of the UFE alone, replaced that list, since the codec already writes every field generation reads and E1 and E2 make it independent of the UFE's slots and its own parse.

The descriptor first included the UFE's TDZ chain. Every function of a module holds a chain ending in a link that names each lexical binding of the module (F26). The holder digest, run at every function import, every attach to a generated or imported UCB and every capture, encoded and sorted those enclosing environments each time; every function core whose generation created closures repeated the names, captures and core digests encoded them, and an import decoded and interned them only to drop the duplicate. `CachedPtr::encode` deduplicates by address within one encoder, but across bodies the cost grew with functions times bindings, and per body with the bindings, so a small function at the top of a large bundle would have broken THREAD's installation bound.

A function core writes its chains relative to its holder's, and a chain equal to the holder's becomes one start record (codec E14, I25). Chains compare by environment object, which the VM interns by content: a natively decoded UCB's links are fresh objects, so comparing links would cut its chains elsewhere than a generated UCB's and break I14. The holder digest takes the chain out of the descriptor and appends a chain digest, one hash per link over its environment's digest and its parent's. Each environment's digest is kept in the environment and freed with its names, because a registry map keyed by address would have to pin the environment, keeping a scope's names alive after its code died, or hook `CompactTDZEnvironmentMap::Handle::~Handle`, which cannot reach the VM. Links are not memoized: a chain has one link per enclosing lexical scope that declares something, and each costs one 80-byte hash. The kept digest is charged to no production limit, since it serves every role and its release runs where no budget is reachable; THREAD Session exempts the digests kept for identity.

Three proposals were not adopted. A marker for "the holder's chain" written after the links a generation created is what the start record already does, without the encoder knowing which links its own generation made. Memoizing links as well as environments buys nothing at one hash per link. Build-time holder digests for JSC builtins would need a second definition of the descriptor in the Python builtins generator, and a builtin's holder digest runs only beside an import or attach that costs far more, or at a capture.

## Contexts are digested where they are read

Every request first computed its context with its key, before `bodyVersion` said whether the artifact held a body, and every record stored the digest, in every role. Two contexts cost far more than a short hash. A root UFE body's context holds a holder digest, a whole JITCacheCore descriptor encode with its zeroed first page and its maps. A direct eval's context sorts every TDZ and private name of the scope chain, which `JSScope::collectClosureVariablesUnderTDZ` gathers from every lexical, catch and module scope at each `DirectEvalCodeCache` miss. The first call of every builtin and `new Function` body, and every such direct eval, paid an encoder run or a sort of thousands of names, usually for a key with no body, against THREAD's "no work ahead of demand"; a root body's import also digested its holder twice, for its context and for C11.

Only matches and captures read a context digest. A request computes its context at the first comparison with a body and keeps it with the holder digest, so C11 reuses the digest a root's context took. A record keeps the context's inputs (`RecordedContext`), from which an attach or a capture computes the digest, for a root body with its UFE's holder digest, which cannot change while the UFE lives (SPEC-ucb.md sections 3.4 and 3.6, I21). A direct eval's sets live only on `JSC::eval`'s stack, and a copy per record would keep every binding name of the scope chain for each eval UCB, so its record keeps the digest its import computed or, in a VM whose production is active, one computed at the record. The counters `contextDigests` and `holderDigests` make the rule observable (U8, `context-on-demand.js`).

Skipping C11 for a root whose context matched proved unnecessary once the request keeps the holder digest: C11 is then a 32-byte comparison. A later review held that a producer sorts a direct eval's sets once more per eval; the native request already sorts the same names when generation interns them, and the lane digests a direct eval's context only when an import found a body or a producing VM records the UCB.

## Supplied root digests

Every root key digest first hashed the root's whole transformed source, in every role, builtins at their creation. F25 shows paths where the engine reads no text: `bun build --compile` records each module's hash so that a launch from bytecode never pages in its source, Bun's standalone internal modules decode through `decodeBuiltinFunction`, which reads only the provider's length, and release builds create builtins from build-time metadata, many of them for bodies that never run. The hash put its cost on the startup paths JITCache exists for, against THREAD Session's near-zero overhead outside recording, capture and first installation.

A root's digest comes from where its text was produced when that place recorded one (SPEC-ucb.md sections 3.5 and 7.2.6): the builtins generator writes each JSC builtin's digest beside its metadata, and a provider may return one from `SourceProvider::jitCacheSourceDigest()`, which Bun fills for compiled modules and internal modules. Bun's internal modules are created or decoded, and both forms take the digest of the provider's whole source, so their identities agree. A supplied digest is trusted as `hash()` and a bytecode payload are. The generator's digest belongs to the build and is checked as the codec's round trip is, by U9 and debug assertions. A provider's digest belongs to the embedder's output, where a mistake gives two texts one key; only an import acts on the key alone, so strict verifies the digest there, once per provider in the VM (S2), and the registry keeps the provider beside every key derived from the root, so that a function body of the tree is verified at its own import. Verifying at the decode would bring the cost back, and verifying at capture protects nothing the consumer's check does not. A direct eval needs no verification: its key ends in the digest of its own text, so a wrong upstream digest can change only the caller key it is found under. S2 therefore never runs for a direct eval, and its records keep no provider.

The internal modules' digests were first to grow each record of the builtins section and bump its format version, but `src/exe_format/builtins.rs` reads that section from another platform's executable with a fixed record size. The digests sit in a table that the header's first reserved word locates. Two alternatives were not adopted. Per-body text digests for roots and function bodies would read source text at capture and hash nested ranges once per nesting level to speed up an opt-in mode. A per-provider cache of computed digests would serve no path, since none computes one provider's digest twice except an attach after released parked code, and Bun's internal modules make a new provider per global object.

## Keys read a snapshot of the request's features

Keys first read the executable's `lexicallyScopedFeatures()` when they were computed. The request's own native steps overwrite that field with the parse's, generation through `generateUnlinkedCodeBlockImpl` and a CodeCache hit through `recordParseFromUnlinkedCodeBlock` (F18). A Producer computed its first key after generation and recorded a `"use strict"` program under strict 1, while a Consumer computed it before generation under strict 0, so the body never imported; a hit replaced the request's with-scope bit with the cached UCB's. The request objects snapshot the features in their constructors, before any native step, which is the value the native `SourceCodeKey` is built from, and keys, contexts and the twin generator read only the snapshot (SPEC-ucb.md section 7.1, I20, U3, `role-keys.js`).

## The bytecode cache's codec in a JITCache mode

A UCB core is the whole output of generation, and the bytecode cache already encodes every part of it, including cells that are hard to transport (symbol tables, template descriptors, immutable butterflies, big integers) and the child UFEs with their rare data and TDZ links. Bun maintains that codec, and its rewrite made the format deterministic. A codec of JITCache's own would duplicate several thousand lines and drift from the engine. The cost is surgery at each gap the native form leaves (SPEC-ucb.codec.md section 4): child bodies (F7, E1), external strings (off), borrowed streams (F7's assertion, E3), checksums that a persistent or option-disabled decoder skips (F8, covered by the container), UFEs that decode as cache-born (F9, E6), hashed map layouts (F10, E4) and whole TDZ chains (F26, E14). A symbol lookup that fails during decode becomes a decoder failure (E5) instead of a `RELEASE_ASSERT`, because a body naming a private name the VM lacks must be invalid material, not a crash.

## A core's content is its encoding

THREAD asks strict to check a reused UCB against the digest of the captured core. The first idea was a canonical walk over the index spaces other lanes use. Once the codec is deterministic, its encoding is that canonical form, covering every index space and everything else observable in the core, so `coreDigest` hashes the section, and both strict checks of the first design, a round trip of every import and the reuse check, became an encode and a hash.

Those encodes ran through the bytecode cache's `Encoder` inside the request point: a zeroed first page of 64 KiB, deduplicating maps, and `Encoder::release` copying every page into one buffer before SHA-256 read it, once per import with strict on and once per natively decoded UCB in every mode. The round trip only repeats a property of the build. The decode depends only on the validated bytes, E4 and E5 turn what it cannot reproduce into decoder failures, and E10 and E11 keep the VM's mutable state out of the bytes, so a wrong codec fails the same bodies in every run, which T1 checks on every twins import and U7 over a corpus. The round trip went; the reuse check stayed as S1, since THREAD Identity requires it and it tests generation inputs a run can falsify (SPEC-ucb.md sections 4.3 and 10.2). Codec rule E12 starts JITCacheCore encoders at a 4 KiB page that doubles, and E13 hashes the pages in place through chunk entry points, so neither a match nor a holder digest allocates or copies a payload; B7 measures what remains.

A review proposed a hash-only walk over the fields the codec writes, carried as a separate digest. It was rejected as a second definition of a core's content, to be tracked by hand through each WebKit bump, where a field it missed would let two different UCBs match silently.

## Hashed declaration maps keep their layout

`CachedInlineMap::decode` reserves capacity and re-adds entries, which reorders a map above nine entries (F10). `ProgramExecutable::initializeGlobalProperties` creates global vars in that order, so a program with more than nine vars imported through the native codec would enumerate `globalThis` differently from the JITCache-off run and report another redeclaration error first. The native bytecode cache has the same property, but an import would bring it into runs that generate natively. No insertion order reproduces a layout in general, since growth rehashes and deletions leave tombstones, so `InlineMap` gained a checked layout restore and the JITCache mode transports the exact bucket layout (codec E4 and section 5). The record grows for the native cache too, which keeps one record shape and costs a few bytes per hashed map.

The restore first listed only what a correct layout needs, and three resealed layouts still crashed a strict decode. A power-of-two capacity far above the entries made it allocate without bound, so it gained the shrink rule's minimum load, which every native map meets. A deleted marker cannot live in a `VariableEnvironment` map, whose traits are `HashTraits<RefPtr<UniquedStringImpl>>` over `PackedRefPtr` keys: the deleted key `(T*)-1` does not survive the six-byte packing, so restoring one asserts in debug and refs an invalid pointer in release. Nothing removes from these maps, so E4 refuses the bit; changing the parser's key traits would be a native edit for a layout only a resealed file carries. A null key, which the validating decode gives a malformed string, crashed the probe walk's hash, so the restore refuses empty and deleted keys before hashing any, and E15 states the same rule for every container the core decodes.

## Atom-ness travels beside the core

The baseline's strict-equality templates compare a constant string by pointer only when it is an atom, so the image needs string constants atom-backed where the producer's were. Generation makes every constant an atom; the native decoder leaves long ones plain unless it already holds the atom, and property-key uses and the decoder's string table later atomize them in place (F19). The first design wrote each constant register's atom-ness into the core. Two decodes of one bytecode-cached payload whose functions first ran in different orders then had different atom-ness and encoded differently, and a decoded function never matched a body captured from a generated one.

The codec decodes every string constant register as an atom and writes no atom-ness (E10), and the identity section's atom map carries the producer's (SPEC-ucb.md section 4.2). A live decoded UCB that disagrees with the map misses `AtomMap` instead of being invalid material, since it disagrees legitimately (C10). Seeding atomizes a decoded UCB's marked constants before publication with `JSString::swapToAtomString`, which allocates no cell and which JSC's decoder string table already uses (section 7.3.3). Two later checks refined that step. Native atomization always marks the cell as an atom (`markAsAtom`), and value profiling reads the mark, so `atomizeStringConstant` follows `JSString::toAtomString` (section 4.5). A constant decoded from an embedder's string table is one VM-wide cell that published UCBs share, so the step rests on `swapToAtomString`'s contract for concurrent readers rather than on the UCB being unpublished, and I18 says the shared cells become atoms too, as a property-key use makes them natively.

The guarantee runs one way: every constant that was an atom at capture is an atom at install, and a UCB can hold more. The Image lane reconciled its R-UCB-1 with that: it records which operand each strict-equality template compared inline, its twin takes that choice back, and R-UCB-1 asks only that every constant compared inline be an atom here, so extra atoms change neither an import nor its twin (SPEC-ucb.md section 9.1).

## Butterflies built from atom strings

`ArrayNode::emitBytecode` gives an all-atom-string literal the structure `cellButterflyOnlyAtomStringsStructure` and makes each element the VM's canonical `JSString` for its atom, and `indexOf` and `includes` take a pointer-comparison fast path on it (F23). The codec's decode gave every butterfly the plain structure and plain strings, so an import differed from its native twin. Writing the form into the core would have made a generated function's core differ from a natively decoded one's whenever it has such a literal, and matching a decoded UCB against a generated body would then miss. The form travels as a second bit map in the identity section, and only an import acts on it: after the reference-closure checks it rebuilds each marked butterfly as generation does, interning every element through `atomStringToJSStringMap`, because the fast path's absence test reads that map and a structure switched without interning would make `indexOf` return -1 wrongly (SPEC-ucb.md sections 4.2 and 7.3.1 step 8, T6, I22). A decoded or live UCB keeps the form its native path gave it, which is its native twin's.

## `RegExp` constants by pattern and flags

`CachedRegExp::encode` wrote the cell's atom, specific pattern and parsed bit. A `RegExp` constant is a cell the VM shares, and `RegExp::deleteCode` clears the atom and specific pattern on every live `RegExp` whenever `VM::deleteAllCode` runs, as `Bun.shrink()` makes it (F22). A core's encoding then depended on whether code deletion had run since generation, and a decode could return a live cell in another state, so the strict checks, decoded-UCB matching and T1 failed on legitimate bodies. Codec rule E11 writes only the pattern and flags in the JITCache mode, decoding takes `RegExp::create`, the call generation makes, and C5 checks that the result is valid, since generation emits only valid patterns.

## The ordered-hash-table sentinel by identity

The codec first carried every constant cell by content, as the bytecode cache does. JSC's `Map` and `Set` `forEach` builtins hold the VM's ordered-hash-table sentinel as a constant and end their loop by comparing it by identity with the storage the iteration intrinsics return (F27). An imported copy has the sentinel's structure and length, so the core bytes (T1) and the structure check (T6) matched while the loop never ended: debug builds assert in the iteration helpers, and release builds read past the empty storage. A census of what generation puts among a UCB's constants found no other such cell: the native decode returns the VM's small strings, its zero `BigInt` and its `RegExp` cells as the consumer VM's own, and the other VM and realm cells bytecode compares by pointer are link-time constants. The sentinel gets its own kind, written by identity and decoded as the consumer's own (codec E16). Making the intrinsic a link-time constant, as `sentinelString` is, would keep the cell out of the UCB, but it changes the bytecode and baseline code of both builtins in every VM, which THREAD allows only for its two native fixes.

## Embedder payloads match by content

Equal key and context were first taken as proof that a natively decoded UCB was the body's. Provenance then entered every context: a decoded UCB's hashed declaration maps can iterate differently (F10), so importing a capture of one where the native path generates would change `Object.keys(globalThis)`, and matching a generated body against a decoded UCB would fail strict and turn the cache off over a legitimate deployment difference. Two facts broke the premise itself. Bun's `vm.compileFunction` generates `cachedData` under a global scope extension it never clears while its run path generates the wrapper without it (F11), and the decode's `SourceCodeKey` check ignores the with-scope bit (F4); nothing records the option values a payload's generator ran with either. A natively decoded UCB therefore matches only by its core digest, in both modes, and a difference is a miss.

Provenance left the context and became an identity-section field, first checked for programs and modules only. A function body captured from a lazily decoded slot could then replace generation, or attach to a generated UCB on key, context and holder alone. With a payload generated under other bytecode-relevant options, that installed an image on a UCB with another instruction stream when strict was off, and turned the cache off over a third-party difference when it was on. One rule serves every core kind: a body of provenance `EmbedderDecoded` matches only a natively decoded UCB, by its core (SPEC-ucb.md sections 7.3.1 step 4b and 7.3.2). An import then takes only `Generated` bodies, so its constants are atom-backed where the producer's were, and a capture can write an imported UCB as `Generated`.

A ConsumerProducer that seeded a decoded function from a `Generated` body and recaptured it richer still wrote `EmbedderDecoded`, so consumers that generate the function missed it; that cost was first accepted. Keeping the matched body's butterfly map in the record (`generatedButterflyMap`) removed it: the match proved the core encoding equal to the body's `coreDigest`, and a core never changes once made, so the capture writes `Generated` with the kept map (section 8.2). A predicate on the integrator was proposed and not adopted, since the lane can keep the provenance itself.

## Charges inside the encoder

The first design charged only the encoder's pages and claimed an overshoot of one page after a refusal. The encoder also allocates its deduplicating tables, the closures it defers and per-record scratch (varint buffers, sort vectors, 8-bit string copies, packed tails), and once a charge is refused the encode cannot unwind inside a record, so it runs to its end, with pages doubling to 64 MiB. Codec rule E8 charges the tables and scratch as they grow and makes a refusal sticky, I16 and B6 state the real overshoot, the rest of one encode, and `UCBSections` holds its budget and releases its charge when destroyed (SPEC-ucb.md section 8.1). Charging an estimate before the encode was not adopted, since no count bounds an encode before it runs, and neither was a reused scratch page, which would break the offsets later records and `release` read.

## Parse fields and singleton state

Native generation creates a child UFE with zero features and no captured variables, and the child's own parse fills them. A producer's parent encoded after some children ran would carry parsed values, so the JITCache mode writes them unparsed (E2) and each child's body restores its own at its request (SPEC-ucb.md section 7.4); F3 makes that restore load-bearing. Learned bits go the other way. A child UFE's `m_singletonHasBeenInvalidated` is learned at run time and read when the parent links, so it travels in the parent's feedback. `SymbolTable` singletons propagate from the CodeBlocks' realm clones into the UCB's tables (F14), and the bytecode cache writes none of that state, so the feedback section has one bit per constant (section 5.2, C9).

A root's own bit, on a Function-constructor or builtin UFE, was first read from the root's captured body when the root was created, since `link` reads it right after creation. Global object setup creates many builtins eagerly (`JSC_BUILTIN_FUNCTION_WITHOUT_TRANSITION`, thirteen in `ArrayPrototype::finishCreation` alone), so a consumer's first global object opened and validated every captured builtin body, including those that never run. Validating lazily and caching the opened body was proposed; it still opened a file per captured root during setup, against THREAD's "no work ahead of demand". The root bit stays local (THREAD Restoration; SPEC-ucb.md section 5.1). It has two readers, both through the executable's singleton that `link` derives from it. The root's own DFG compile folds `GetCallee` to a constant while the singleton holds (`ByteCodeParser::get`, the `GetCallee` case of `AbstractInterpreter`), so a consumer without the bit can jettison that code once, when a second function of the executable appears after the compile. `ObjectAllocationProfileBase::initializeProfile` (`bytecode/ObjectAllocationProfileInlines.h`) allocates `this` poly-proto only when both the executable's poly-proto set and its singleton are invalidated, so until a second function exists in the consumer, `new` of such a root allocates mono-proto objects where the producer allocated poly-proto ones. Both costs are speed only, and a JITCache-off run pays them at the same points.

## Arming the LLInt counter

THREAD's "travels as native finalization leaves it" and "arms it without a slice" were read together: the capture records the base threshold T and the progress P, which right after finalization are `jitSoon`'s, and the import re-arms with no CodeBlock, as `UnlinkedCodeBlock`'s constructor does. The first arming copied `ExecutionCounter::setThreshold`, which truncates the slice into `m_counter` but adds the untruncated slice to `m_totalCount`, so `count()` gained up to one point (F20). `jitSoon` arms against a fractional memory-pressure multiplier, so the progress after finalization is fractional and T4 failed on most bodies. The arming truncates before adding, which keeps `count()` at P and crosses after the same points as native (SPEC-ucb.md section 5.5, I12, U6).

A deferred counter, at `INT32_MAX`, is accepted and armed exactly, since `deferIndefinitely`'s state is native, although no native capture holds one. The LLInt defers its counter only when `shouldJIT` fails (`entryOSR`, `loop_osr` and `replace` in `llint/LLIntSlowPaths.cpp`), which then fails for every CodeBlock of the body, so none of its compilations is captured, and `BaselineJITPlan::finalize` defers it only after the fault R-INT-11 raises first. Rejecting `INT32_MAX` as invalid material was not taken.

## Every exit site counts toward richness

THREAD's richness counts one unit per exit site. A review showed a path by which an import could lower what later consumers start from. A non-looping body whose captured progress had crossed reached `operationOptimize` at its second invocation, with no IC cases restored, and a DFG compile that parsed an IC listing one of a site's shapes speculated with `CheckStructure`, whose exits are `BadCache`. When the exits jettisoned the code, `CodeBlock::tallyFrequentExitSites` added the site of every exit with a nonzero count to the UCB's exit profile, and from then on `hasBadCacheExitSite` made `GetByStatus` and its siblings return their slow version. Richness ranks before the IC count, so a ConsumerProducer's recapture after such a jettison won and wrote the induced sites into the artifact; `DFG::ExitProfile` only appends and seeding carries the captured list, so each generation could only add such sites. A lane-local exclusion of exit sites at bytecodes whose captured IC listed several cases would have bound the ICs lane, the integrator's scoring and this lane's summary at once.

THREAD's polymorphic rule removes the cause: a body with a property IC whose captured record lists two or more cases carries no baseline counter progress (the ICs lane's `hasPolymorphicSite`, then the CB lane's capture), so it never gets the early compile. Every exit site counts (SPEC-ucb.md section 5.6). A recapture of an imported body still carries every exit site its import seeded, and SPEC-integrator.md IB10 measures the sites added per ConsumerProducer generation.

## The registry's lock, lazy child identities and shared parent nodes

Sweeping happens on the thread that holds heap access (F12), so the registry seemed to need no lock. A sweep can run a destructor in the middle of a JITCache step on that same thread, so the registry has a lock whose rules, a leaf with no cell allocation, no GC-deferral change and no reference dropped inside, make that reentrancy safe (SPEC-ucb.md section 6.3). Child identity digests are computed at the body's request, since most nested functions of a large module never run and eager digests would cost native generation one SHA-256 per child (section 6.1).

Each child entry first copied its parent's 40-byte key and provider reference, so an entry cost about as much as the UFE cell in a table at most half full. The children of one recorded UCB share one `ParentIdentity` node, so an entry is a reference, a table and an index, 16 bytes, and B5 reports the per-UFE figure. A per-parent child vector was not adopted, since `identityOf` must find a UFE's identity from the UFE alone, and reserving the maps from the table counts was not either, since a growing WTF map cannot reserve and its growth is amortized.

## Misses are stamped with index tokens

The first attach kept a miss flag that never expired, which kept a ConsumerProducer from reusing a UCB whose body it later committed itself. A miss then stamped the commit identifier of the file it opened, but stamps were compared with the index's version, which a lagging index never matched. R-INT-3 has `bodyVersion` answer a token from the integrator's in-memory index with no envelope read and no filesystem call. Stamps and skips compare tokens, the matched-file shortcut compares commit identifiers, and an open that finds the file gone stamps the token, so a body `compact` removed costs one failed open per UCB until the index forgets it (SPEC-ucb.md section 7.3.2). The same index answer removed the second file open that first imports and seeded decodes made.

An `AtomMap` miss was first stamped too. Atom-ness only grows, so it stamps nothing and sets `matchedBodyVersion`, and the next request repeats only C10 against the same file (section 7.3.4 step 5, I21). Dropping C10 was rejected, since THREAD keeps the miss.

## Decode points keep the native decode

The first design had the import replace the provider's decode at the CodeCache, since nothing observes that decode and the import carries feedback and an image the decode lacks. It served a UFE's lazily decoded slots as live UCBs, attached without seeds, on the premise that `decodeCachedCodeBlocks` publishes both slots before an import could run. The decoded UCBs sit unpublished until `m_isCached` clears (F1), so the premise was wrong. Replacing the requested slot's decode with an import was possible, but the imported UCB's children come from the JITCache codec, which writes no child bodies, so every descendant the producer never captured would be generated from source where the JITCache-off run decodes it cheaply, a startup regression for `--compile --bytecode`. Keeping the decode and seeding the decoded UCB before publication gives the holder exactly the native UCB, keeps the descendants lazily decodable, and costs what the import would (SPEC-ucb.md sections 7.2.2 and 7.3.3). THREAD Restoration adopted that rule.

Recording the other decoded slot first settled the request, so `new F()` on a function cached for call left the generated construct UCB unrecorded and its children without identity; `recordDecodedSlot` neither reads nor sets `settled` (I19). The other slot's UCB feedback never arrives, because seeding it would read a body nobody requested, against THREAD's "no work ahead of demand"; seeding it when the index lists its body was not adopted for the same reason.

## A live UCB is met only at its holder

THREAD's "an import that meets a live UCB for its body reuses it" had two readings. A global lookup of live UCBs by key would hand one UCB to two holders, which native code never does and THREAD Identity rules out, so the lane reads it as an import at a request point whose holder already holds a UCB, attaching a pending import and never seeding a published UCB (SPEC-ucb.md section 7.3.4). The first attach computed the full request key, a whole-source SHA-256, at every CodeCache hit on a recorded UCB without parked code, and re-encoded the UCB for the reuse check at every re-attach. The record keeps its key's root bits and the commit identifier it was matched at. The attach checks the sharing slot, the index token and the stamp first, compares the bits, computes the source digest only when an attach would follow, skips the key for UFE bodies, whose record is their identity by construction, and re-attaches at a matched identifier without re-checking (I21, B3). An attach to a live decoded UCB usually misses `AtomMap`; atomizing its constants at the attach was rejected, since THREAD seeds a UCB only before publication.

## Decoded roots and Bun's `cachedData` paths

The first design served `vm.compileFunction`'s decoded user function as a live UCB, attached without seeds. A later one keyed a decoded root by its payload's with-scope bit and edited Bun's `NodeVM.cpp` so the wrapper's key reached its children. Two facts stood against both: Bun's `vm.compileFunction` generates `cachedData` under a global scope extension it never clears while its run path generates the wrapper without it (F11), and the decode's `SourceCodeKey` check ignores the with-scope bit (F4). THREAD settled both cases. A natively decoded root whose with-scope bit differs from its request's gets no key, so it has no record, its children no identity, and nothing in it imports or is captured (SPEC-ucb.md section 7.3.3 step 1), which needs no record, no child identities and no core digest. Bun's `vm.Script` and `vm.compileFunction` with `cachedData` keep Bun's own decode outside JITCache, with no Bun edit, and `vm.compileFunction` without `cachedData`, or with data its decode rejects, imports at the program request point (section 7.2.5).

A review reported that the decode reads a freed `cachedData` span. That happens with JITCache off as well (F11), so it belongs to Bun; the lane neither edits that decode nor reads what it yields, and `compile-function.js` calls the user function only in release runs, which ASan does not instrument.

## Parse-time stack depth

An import cannot reproduce the `RangeError` the parser would raise at a given stack depth, so the first design imported regardless, as a native CodeCache hit does. That skipped the native error even where the request itself was already past the limit. Before its first step the import misses `Stack` when `!vm.isSafeToRecurse()`, the limit `Parser::canRecurse` tests, so the native parse throws its `RangeError` as with JITCache off; only a parse whose own recursion would pass the limit from a shallower depth still imports, and THREAD Verification exempts results that depend on how close the stack is to its limit (SPEC-ucb.md section 7.3.1). A depth margin as a bench parameter was rejected: it would miss imports where the native parse succeeds and still could not predict a parse's own depth.

## Plan-site faults go through the integrator

No part first owned the executable-allocation fault of a DFG or FTL plan, though THREAD Failures required it before the failure's effects are written. DFG and FTL plans that cannot allocate install a `FailedFinalizer` on the compiling thread, the failure surfaces in `DFG::Plan::finalize`, and the callbacks then defer the baseline counter and clear the quick DFG or FTL bit; a failed baseline plan defers this lane's LLInt counter in `BaselineJITPlan::finalize` (F24). Three of those writes are this lane's state. `FailedFinalizer` records no cause, and a plan that fails for another reason, such as `FTL::canCompile`, must keep its effects, which THREAD carries. R-INT-11 asks the integrator, which owns the fault plumbing, to raise the fault before any of the failed plan's effects is written (SPEC-ucb.md section 9.2). The integrator raises it in the baseline plan's failure case and in `DFG::Plan::finalize` before the callback, with a cause flag on `DFG::Plan` that the compiling thread sets where the allocation fails (SPEC-integrator.md section 9). The other `JITCompilationCanFail` sites, in Yarr, Bun's FFI thunks and stubs and WebAssembly, write nothing a capture reads, so they keep native behavior. THREAD Execution names the plan sites, and THREAD Failures makes the list of the other sites exhaustive.

## Normal mode and strict

The lane first checked every section rule and C1 to C9 at every import. THREAD made strict opt-in, with normal mode checking only the artifact's integrity: its header, keys and checksums. The section rules and C1 to C9 became strict checks, SV1 to SV3 beside S1 and S2, and with strict off the parse functions read fields where the layouts put them. What chooses a body stays in both modes: key, context, provenance, C10, C11 and a decoded UCB's core digest, since those comparisons choose a body rather than check one. C6, the decode's own report, runs at every import, because the codec's root, symbol, layout and start-record checks are part of decoding (SPEC-ucb.md section 10.2).

A review found the decoder's checks shallow for nested records. Codec rule E15 defines the validating decode strict runs: placement of every nested record, tags in range, every native assertion about payload data checked before it fires, string hashes and ordinals, and an instruction stream that walks whole from start to end, which keeps the other lanes' strict walks inside it. Judging instruction operands was not taken. JSC has no validator for operands, jump and handler targets or the counts that size a UCB's tables; the checksum and the build ID pin those bytes; the encoder copies the stream verbatim, so a writer or codec bug shows as broken structure, which E15 catches; and an artifact rewritten so that its operands are wrong could carry wrong machine code as easily, the case THREAD Session's trust rule covers.

A stored identity key that differs from the body's own was first a quiet stamped miss (`KeyCollision`). Files are named by their whole key and the container matches the envelope key to the name, so such a key is invalid material at `ucb.identity` in both modes (section 7.3.1 step 4a).

## The validating decode shares what the native decode shares

The validating decode first bypassed the decoder's offset cache, so it checked a record wherever a slot reached it. A review found two faults in the bypass. A crafted core whose many TDZ links name one environment record made the decode quadratic in time and memory, and a valid core that shares a record decoded it into two objects where the native decode gives one. E15 then kept the cache, recorded the type each offset was decoded as, and said that every record decodes once and the decode stays linear in the payload. The code written to that rule showed the last clause held only for the records the cache serves. A record the encoder writes once per owner cannot be shared, the two string record types are one type, and records reached in place, through constant slots and owners' rare-data slots, decode at each reach, as they do natively. Two reviewers then asked for linearity for those too, which would mean marking every record a decode reaches in place and failing a second reach. That was not adopted. A generated core names an in-place record from one slot only, apart from strings, which decode to one atom whichever slot reaches them. A crafted core costs at most what the native decode costs, and THREAD Session trusts an artifact as far as the binary that runs its machine code, so strict checks a core's structure and is no defense against a core built to be slow. The cache kept its purpose: a valid core decodes to the object graph the native decode gives (codec E15).

## Self-tests run once per configuration

One `$vm.jitCacheUCBSelfTest()` call was meant to cover U8, but `start` fixes a VM's role and strictness for good, and invalid material turns its cache activity off for good (THREAD Session), so U8's parts need several roles, both strict values and a sticky fault. `runUCBSelfTest` takes a `UCBSelfTestScope`: `Configured` runs the parts the VM's configuration allows and `InvalidMaterial` only the invalid-material case, and `self-test.js` drives one run per configuration with that case last (SPEC-ucb.md section 13.1). Self-tests that create their own VMs were not adopted.

The decoded program under a wrong supplied digest first ran under `Configured`. T7 reports a supplied digest that differs from its text wherever a request takes one, and a twins run fails on any difference it does not declare, so every run that took a wrong digest failed. Both cases of a wrong digest run under `InvalidMaterial`, in the one run where `self-test.js` declares T7's difference, and the self-test counts one difference per case (SPEC-ucb.md section 13.1). Declaring the difference in the other runs too would excuse the differences of U8's own imports there, and swapping the twin report for a throwaway one would add a twins-only integrator interface for one test.

## Request-point work and the installation bound

THREAD's bound first counted the seeding done during decoding and nothing else of the request point, and its list of costs measured separately named the decode, the key digest and reading the artifact. Matching, the closure checks, the section parses, atomization, parse fields and records fell in neither, although all of them run before the native link that opened THREAD's window: `ScriptExecutable::newCodeBlockFor` calls `unlinkedCodeBlockFor` before `FunctionCodeBlock::create`, and a global executable holds its UCB before its CB exists. The lane counted them toward the bound with the seeding and left the native decode, the key and context digests and `openBody` where THREAD put them. Each TDZ environment's first digest, which grows with the enclosing scopes and not with the body, counts with the key digest. THREAD's opening adopted that accounting. The butterfly rebuild counts inside the bound, since it is JITCache work and not decoding, and strict's checks stay out, since the bound is measured with strict off (SPEC-ucb.md section 14, B2).
