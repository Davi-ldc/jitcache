# SPEC-integrator history

Why the non-obvious decisions of [SPEC-integrator.md](SPEC-integrator.md) and its sub-SPECs are what they are: for each, what first seemed right, the evidence that changed it and the intent that came out, so a later revision does not go back to the obvious version. Nothing here binds.

## Interface and per-VM state

### The fault entry point names its site

The lanes first called `didFailExecutableAllocation(VM&)`, while each of their requirements asked for a diagnostic naming the failing site, which a one-argument function cannot give. THREAD Execution gives API signatures to the integrator, so the integrator added the site argument, and every lane's call passes it. The entry point records the fault with plain stores and frees nothing, because the ICs lane calls it under a `CodeBlock::m_lock` held through `GCSafeConcurrentJSLocker` and the Image lane forbids waiting for another thread. Production memory is therefore released later, by `releaseEndedProductionMemory()` at the next glue entry, which costs a flag test while production is active.

### Every refused production charge is `budget.limit`

Each lane's capture call first reported a refused charge as its own failure, so a producer that ran out of budget named a different step depending on which charge happened to be refused first, and a test of the producer limit could not name the fault it expects. Every refusal of a production charge is now raised as `budget.limit`, the budget's own fault, wherever it lands; when a lane's capture call fails while the budget has refused, the lane's check goes in the detail.

### The state is created and destroyed in task 7

The teardown hooks were first defined in task 2, so `VM::~VM` called them from task 2 on, while destroying a state runs the destructors of the producer lock, the opened artifact and the writer, which land in tasks 5 and 6; the store's tests also expected faults only a configured VM can raise, the writer's `rewriteSection`, in task 6, erased kept summaries, which task 9 introduces, and `start` created the Image lane's `Twins` object, whose class lands with that lane's task 11. Splitting the state's ownership by task, or keeping the late members in a sub-object whose destructor lives in the store's files, would still need those files at task 2's link. Since only `start` creates a state and only `didFinalizeHeap` destroys one, the constructor, the destructor and both hooks moved to task 7, when every type the state owns exists, the hooks beside `start` in `JITCacheAPI.cpp` and the constructor and destructor with the state's other members in `JITCacheVMState.cpp`; the store's reads came to return outcomes and know no VM, the kept-summary erase moved from the writer's `rewriteSection` into the capture glue's `rewriteSectionForTesting` (task 9), and `ValidatedBody` got a file of its own in task 2, because the UCB lane's pending imports hold one. The `Twins` object lives in an image twin-check state that the VM's first stash creates and `willDestroyVM` destroys, held through a deleter the creating file supplies: what the Image lane needs is a lifetime that covers every twin check until VM destruction, and that gives it without the state naming an Image-lane type.

### The state's private part lands with its first members

The private part of `VMState` was first written by task 7, beside the state's lifecycle, so that the header would change once, after every type the state owns existed. Tasks 2 and 5 define members that read it (the switches, the fault records, the budget and context, the opened artifact and the lookup override), so their definitions could not compile in task order. Declaring a member needs only its type's declaration, which task 0's headers and the UCB lane's task 0 provide, and the types a later task defines are held through pointers. Task 2 therefore writes the whole private part, tasks 5 and 7 define members against it, and task 7 still makes the header's last edit, the accessors later tasks use.

### Test bodies and a lookup override

SPEC-ucb.md U4 needs a pending import whose body asserts in its destructor, and U8 needs the engine's lookups to return crafted bodies, while `ValidatedBody` had only the store's constructor and the lookups had no override point. In twins builds `ValidatedBody::createForTesting` copies crafted sections into one aligned buffer and runs a callback from its destructor, and `setBodyLookupForTesting` makes `bodyVersion` and `openBody` answer from two functions. The override answers alone, without falling through to the store or moving a progress counter, and leaves role, strictness and activity as `start` and the faults left them, so a test that needs several configurations runs once per configuration. When the index came to hold tokens, the override's first function came to answer tokens too, kept apart from the commit identifiers its bodies carry.

### `productionActive` belongs to the lanes' interface

`productionActive()` began as one of the integrator's own members. The UCB lane then chose to digest a direct eval's TDZ and private-name sets only where something reads them, and those sets exist only during the eval's request, so a record keeps the digest only in a VM whose production is active, the only VMs that capture (SPEC-ucb.md section 3.4). The member moved into the lanes' interface, which task 2 defines, and the end of production also ends that digest.

### Strict: integrity in both modes, structure under strict

THREAD made strict off by default and had normal mode check only the artifact's integrity and trust the rest. The container therefore splits each check into an integrity part both modes run (the header digest, the key, the checksums, and the sizes and bounds those checksums need) and a structure part only strict adds (reserved bytes, tier, commit identifier, entry order and kinds, layout, required sections), which is what SPEC-ics.md R-INT-4 expects of the directory. The writer's reread could have followed the session's flag like every other read; it validates in full in both modes because THREAD Capture has the writer validate what it publishes. The lanes' summary readers take the strict flag, so a rejected saved summary is invalid material only with strict on.

### Which compilations record is decided at plan construction

SPEC-image.md R-INT-12 needs to know, on whichever thread compiles, whether a plan's compilation records. The integrator answers once, in `BaselineJITPlan`'s constructor, from `producerContext(vm)` and the registry's `keyOf`: both constructor callers, `jitCompileAndSetHeuristics` and `JIT::compileSync`, run on the VM thread, `keyOf` takes only the registry's leaf lock, and a flag written before the plan is enqueued needs no lock when the compiling thread reads it. Task 2 adds the member, false until task 7 computes it, so the Image lane's task 4 compiles against it without waiting on the registry; no compilation records before task 7 creates a state anyway.

### A ConsumerProducer rebuilds the image record only while production is active

Install step 7 first asked the Image lane to rebuild the image record in every ConsumerProducer, so one whose production had ended still built and charged a record that no capture would read. The rebuild was limited to active production, and the policy enum that carried the choice was then dropped as a restatement of whether a budget is passed: the step passes `producerContextIfActive()`'s budget or null, which is non-null exactly in a ConsumerProducer whose production is active, as SPEC-image.md R-INT-7 asks. With a null budget step 10 tests nothing, so a VM whose production ended raises no second `budget.limit`.

### Production memory is released by task 7's code

`releaseEndedProductionMemory` was first defined in task 9, beside the kept summaries it frees, but task 8's install function calls it before its step 1 and task 7's `willDestroyVM` frees the same memory, so the tree could not link in task order. Making task 8 wait for task 9 would have held the install glue behind the capture glue and still left task 7's teardown without the kept summaries' type. The state holds the kept summaries through a deleter their own file supplies, and destroying them releases their charges, so the function needs no type of the capture glue and lands in task 7 beside the teardown that calls it.

### Bun's module-analysis entry has a header of its own

`importModuleAnalysis` and `ModuleAnalysisImport` were first declared in `JITCacheAPI.h`, since Bun is the only host that asks and nothing else is exported for them. That header is the C++ API THREAD Session gives any host that embeds JavaScriptCore, while the function returns bytes in Bun's module-info format, which only Bun's loader reads. Davi moved both to `JITCacheBun.h` on 2026-10-17, the exported header of the entry points only Bun's integration calls, so `JITCacheAPI.h` stays host-neutral. The UCB lane still defines the function, and `ucb/UCBAnalysis.h` includes the new header as the one session header a lane reaches for it.

## The artifact

### Bodies are checksummed with CRC32C and versioned by random identifiers

Sections are guarded by CRC32C rather than SHA-256 because every import validates the whole body against damage, not against an adversary, and with SSE4.2 or ARMv8 CRC instructions it runs at several GB/s. The integrator's own CRC-32C first gave way to the engine's `crc32c` of `CachedTypes.cpp`, made external, so that one implementation served both formats. Webkitbun `0c06faad` (Bun 1.4.3) dropped the bytecode cache's per-record checksums and that function with them, so the CRC-32C is the container's own again, in the store, with the same polynomial and therefore the same bytes, and the engine edit is gone; reusing an engine checksum would tie the container's format to a bytecode-cache detail upstream can remove. Commit identifiers are random 64-bit values, since a counter would need shared state that survives artifact deletion and lock-file loss, and the UCB lane only needs "another version", never an order.

### One opened artifact per process

The shared object first decided at its build, from the building VM's role, whether it followed new commits, so Consumers sharing a producing VM's object never saw them. One object per VM would have fixed that, but Bun runs a VM per worker, and the workers of a producing process are the Consumers of its main VM's artifact: per-VM objects would read the index at each worker's start, keep an index per worker (a few megabytes each for tens of thousands of bodies) and make every worker catch up with each of the main VM's commits on its own. One object per process maps the pack and reads its index once, and the main VM's commits reach its workers at once through the writer's index update. Every object therefore follows the root whatever its holders' roles ([the pack](#readers-follow-the-packs-root)).

### A ConsumerProducer replaces an incompatible artifact

A ConsumerProducer facing an artifact another build wrote was first rejected at `start.incompatible`, like a Consumer, and so ran with JITCache off until someone deleted the artifact by hand. Yet it is the role that keeps a cache current across runs, and an upgraded binary meets exactly that artifact. It now replaces the artifact under the producer lock it already holds, and says so (section 3.2, step 7; container sub-SPEC section 1.4). A Producer still refuses an existing artifact and a Consumer an incompatible one, since neither writes on behalf of what it found.

Deleting `cache/` in place would have let a consumer of another process see a directory half emptied and half created. Instead the old directory is first moved aside to `.cache.replaced`, so a consumer that pinned it keeps a directory that only loses entries, as after a whole-artifact deletion, and the new artifact is created under the old name. With the pack, a consumer of another build that mapped the old pack keeps reading that mapping, whose bytes no one rewrites, until it exits.

A crash between the move and the creation leaves `.cache.replaced` and no `cache/`. A ConsumerProducer is then rejected at `start.artifact-missing` until a Producer creates an artifact, and `compact` returns `NoArtifact` before its cleanup reaches the leftover, which the next replacement or `compact` removes once an artifact exists. A ConsumerProducer that finds only `.cache.replaced` could finish the replacement instead, but that would change THREAD Session's rule that a missing artifact rejects a ConsumerProducer, which is product, so the window stays open.

At the same time `start`'s `Created` and `Opened` became one `Started`: the role already says which of the two happened, and a replacement is a third way to start that the step names, `start.replaced`.

### The app digest is 64 bits and only a gate

A digest of the code the host runs suggested the SHA-256 the body keys use, or an opaque byte string of any length. The digest only decides whether an artifact was made for this app: every body still matches by its own key, so two apps whose digests collide share no wrong code and only lose the gate, as apps that name none do. Davi chose XXH3-64 for Bun (2026-10-16), which Bun already carries (`bun_highway::xxhash3_64`) and which runs about an order of magnitude faster than SHA-256 over the entry Bun hashes before every start with JITCache on. The config therefore holds one `uint64_t`, opaque to JITCache and compared for equality only, and the header keeps it at a fixed offset beside a flag that says whether it names one, since any 64-bit value is a valid digest and none can mean "no app".

### The header's layout version 2

The app record changed the header's layout. Keeping layout version 1 seemed right, since nothing has launched and JITCache keeps no legacy format. But the Bun 1.4.2 beta wrote version-1 headers of the old layout, and under the new formula those fail as corrupt, a `Fault` at `start.header` that leaves JITCache off until someone deletes the artifact by hand. Read as another layout version, they are incompatible instead, so a ConsumerProducer replaces them and a Consumer says why it refused them, as the pack's version 2 did for old packs.

### The scoring read is the glue's own

The capture glue first scored through `openBody`, whose `Missing` covers `EMFILE`, `ENFILE` and `ENOMEM`, so a descriptor shortage at a key's first scoring read as no saved body, which any candidate beats, and could let a poorer capture replace a richer body. The glue got a scoring read of its own, whose `Unavailable` defers the key and which checks only the envelope, the directory and the three summary sections a score reads, so a ConsumerProducer's first scoring does not checksum a whole image inside the capture pause. Recording a kept summary at install, to spare a ConsumerProducer that first scoring, was rejected as work ahead of demand inside the bounded import window; IB7 measures those scorings, and stamping the committed score in the envelope is the first change to measure.

### The writer takes section sources and reads no lane format

The writer first mapped every committed file and ran the lanes' parsers on it. THREAD Storage makes sections opaque bytes to the container, THREAD Capture's "reread and validate" is what the container validation already does, and the reread compares each section with the checksum of the very bytes the lanes built, so parsing the file proved nothing that parsing those bytes would not, while it overrode three lanes' own choice of capture checks and parsed every strict commit inside the capture pause. The writer then took a `CommitSections` built from four lane types and called the Image lane's write functions by name, so test C7, which lands before any lane's capture code, could not build one. It now takes an ordered list of sources, each a kind, a size and either a span or a function pointer with an object that streams the bytes; a function pointer rather than a `WTF::Function` lets a commit allocate nothing beyond the staging buffer and lets the glue return the list by value. A source whose byte count differs from its size fails at `writer.section` rather than `writer.write`, since it breaks a lane's size contract rather than meeting an I/O error, and the diagnostic names the section and both counts.

### Charging hash tables and index entries

Kept summaries were first charged four bucket sizes per entry, meant to bound a hash table's storage without depending on WTF's growth policy. That was not a bound: WTF doubles a table above 1024 buckets once it is half full, so while a rehash holds the old table beside the new one the two take six buckets per entry, and a table starts at eight buckets; the rule became eight bucket sizes per table and six per entry. The index was at first exempt from the producer limit, though THREAD Session exempts only the parent-key registry and the identity digests. Of the index, production allocates exactly the entries the writer adds, so those are charged before the commit, and released with the rest of production memory rather than when the entry goes, since the shared entry stays to serve the process's importing VMs; the entries a reader creates when it reads the index or follows the root hold what every importing VM needs and are not production memory.

## Install and capture

### One install function with a point argument

THREAD's two install points became one function with a point argument. Before `setupLLInt` it replaces the LLInt setup and calls `installCode` itself, because THREAD's order puts the CB lane's twin check before `installCode` and measures the import until JITCache returns after it, so `prepareForExecutionImpl` skips its own trailing call; in `JIT::compileSync` the import replaces the plan, and `prepareForExecutionImpl` calls `installCode` a second time, as the LLInt-off route does natively. The function repeats its callers' sharing-slot and newborn tests, because `compileSync` has callers that make neither. `shouldJIT` was file-static, and giving it external linkage, unchanged, is the smallest edit that lets the gate be the LLInt's own.

### The kept score comes from the builders

THREAD reads a saved body's summary at the key's first scoring; the integrator keeps the score afterwards and replaces it at each commit, so a key never costs a second read while the VM holds the lock. The kept score was first computed from the committed file, then by re-parsing the summaries a capture had just built; both read back bytes whose score the builders already return, and with strict off the re-parse checked nothing while with strict on it imposed a check the UCB and ICs lanes chose not to make. The score now comes from the builders: the CB lane's `score()` is a function of its summary bytes (SPEC-cb.md I8), `captureBaselineICs` returns the count it writes into the section header (SPEC-ics.md section 5.6), and `liveRichness`, read in the same pause as `buildSections`, reads arithmetic profiles and exit sites that neither JS nor the collector can change during a capture (profiles.md, "Table"; SPEC-ucb.md F17). A marker's or a compiler thread's drain between the scoring and the build can still add bits, by folding in a pending sample, or drop them in a racing merge, so the capture re-tests `beats` with the built score and stops when the build no longer wins. A capture without an image first took its committed score from the feedback section it had just built, the one read back that II23 denies. It now keeps the score it was ranked with, `liveRichness` and the carried points of the UCB's LLInt counter, read before the build. No drain touches arithmetic profiles, exit sites or that counter, and nothing changes them during a capture, so the score describes the sections the build writes, as a tier-1 score does.

### The registry compares headers in every build

The registry first returned the live object for `cache/`'s inode and compared its header digest only in a debug assertion, which held while every input of the header was process-wide. The app record made the header depend on the config, so one process can meet two headers in one `cache/`: a Producer reusing the remnant of a whole deletion, or a host renaming another artifact's files in. Debug builds then aborted, and release builds faulted a Producer at `writer.open` or served a Consumer of one app another app's artifact. `take` now compares the digests in every build and builds a new object when they differ or the old object is gone.

### Every pack is retired before it goes

A whole deletion first marked only the pack it emptied and then unlinked the empty pack unmarked, and a Producer reusing a remnant renamed its pack over the remnant's unmarked. `follow` looks at the path only when the mapped file carries the mark, so a reader that reopened onto the empty pack kept it for good. That object was never gone, so `take` shared it with every VM that started after a Producer recreated the artifact in the same `cache/`, and those VMs missed every key. Every pack is now marked before it is unlinked or replaced. `take` also follows an object before it tests whether it is gone, which catches an object whose `cache/` was removed and whose inode number a new `cache/` received. The marks then made one old conflict reachable more often: an object that follows a retired pack onto a sound pack written under another header, because a deletion left a remnant that a Producer of another app or build reused, was marked damaged, which raises invalid material where maintenance promises its Consumers misses. The artifact that object checked no longer exists at the path, so a successor rejected only for its header digest now makes the object gone, as no pack at all does; any other rejection is still damage, and the prefix's checksum covers the digest, so a damaged digest byte fails the checksum first.

### The test rewrite copies every section a body holds

`rewriteSection`, the twins builds' way to damage a committed body in place, first copied the sections the body's
highest tier requires and refused any other kind. `ucb.analysis` is required by no tier, so the rewrite could not reach
it, which `module-analysis-invalid.mjs` and the shell's section helpers need, and a rewrite of another section of a
module's body committed the body without its analysis. The integrator lane found it while porting to 1.4.3. The rewrite
now copies every section the body holds and refuses only a kind the body does not hold.

### The glue tests production after a lane's build

The capture glue first stopped a capture only on a failure a lane returned. A module's build reads the saved body's `ucb.analysis` through `readBodySection` when the module has no live analysis source, and for a damaged section `readBodySection` raises invalid material itself and answers `Unusable`, which the UCB lane first read as no section. `buildSections` then succeeded after activity had gone off, the glue committed the body, and `delta` went on committing later keys. The case is reachable because the scoring read checksums only the three summary sections, so a damaged `ucb.analysis` first shows there. The UCB lane now returns `SavedAnalysisUnusable`, which the glue raises no second time, and the glue also tests `productionActive()` after `buildSections` and after each `commitCapture` of `delta`, so invalid material raised anywhere inside a lane's build stops the walk whatever the lane returns. The test first ran before each commit, which missed the last key of a phase: `delta` then returned `Completed` after its build had turned activity off.

### `delta` scores in two phases

Phase 1 reads under `CodeBlockSet::m_lock`, which `forEachCodeBlockIgnoringJITPlans` requires, and phase 2 reads saved bodies and writes files without it, because no file I/O should run under a lock the CodeBlock constructor takes. The CodeBlock pointers kept between the phases stay valid because nothing can complete a collection while the VM thread holds heap access, reaches no stop point and allocates no cell. Phase 1 first kept only the best candidate per key, so a `NotEligible` image dropped the key for that `delta`; it now keeps each key's candidates in score order and phase 2 tries the next one, as SPEC-image.md R-INT-6 treats `NotEligible` as an ineligible CB. A sorted vector of keys went too, since nothing read its order.

### Captures cannot nest

A `delta.reentrant` rejection, a capture-running mark and a twins-only capture probe once guarded against a capture starting inside another. Nothing reaches that state: a capture runs with JS paused and calls no host or JS function, since the API calls nothing back, finalizes no plan, and no lane's capture call walks the CodeBlocks with plan completion; the Image lane's twin compile runs at install, outside `BaselineJITPlan::finalize`. The probe existed only to create the state the guard rejected, so all three went, and a debug-build assertion that no capture is in progress at the finalize capture or `delta` checks II14's consequence at no release cost.

### Exit sites across ConsumerProducer generations

A review found that an imported body whose captured counter had crossed reached its first DFG compile at its second invocation, when each property IC held only what one invocation had cached. At a site the producer saw with several shapes, that compile took `BadCache` exits until it was jettisoned, `tallyFrequentExitSites` added the site to the UCB's exit profile, the richer recapture won and was committed, and every later consumer gave the site its slow status, so exit sites only accumulated across generations. Each step held in the code, and since the richness rule and the counter floor were THREAD's, the SPECs first added a measurement, IB10, which chains ConsumerProducer generations. THREAD then withheld counter progress from bodies with a polymorphic property IC, and the ICs lane extended the rule to polymorphic call sites, so IB10 now checks that consumer-induced exit sites no longer accumulate and sizes what the rule leaves. Bun's `delta` at exit stayed: THREAD leaves the idle point to the host, and calling `delta` less often would slow the ratchet without settling it.

### The executable-allocation fault list is exhaustive

The list of fault sites was first provisional. THREAD Failures made it exhaustive and keeps Yarr, Bun's FFI thunks and stubs outside a tier's plan, and WebAssembly native. Reading the FTL path showed that `FTL::LowerDFGToB3::compileCallFFIImpl` also sets `allocationFailed` when Bun's FFI invoke thunk cannot be allocated inside the plan's lowering, so that plan raises `exec-alloc.ftl-plan` like any FTL plan short of executable memory, while FFI thunks outside a plan stay native.

## Hosts

### Bun

Bun calls `start` in `Zig__GlobalObject__create`, right after it takes the API lock and before `JSVMClientData::create`, which is the last point before anything could create a builtin executable. Configuration first came from `BUN_JITCACHE_*` variables, read once per process like `BUN_JSC_*`. THREAD Session makes Bun's command-line flags its whole user-facing configuration, so Bun takes the jsc shell's flags with the same syntax (section 11.2), and the runner passes one set of flags to both hosts (harness sub-SPEC section 7.7). A worker of a process whose main VM produces gets `Busy` and falls back to `Consumer`, so workers still import what the main VM commits. A `Busy` from another process first fell back to `Consumer` too, so a `p` or `p-c` started beside a running producer quietly became a reader. It now fails as a Producer facing an existing artifact does, and warns on standard error even without `--jitcache-log`: a process asked to write never silently stops writing, which would hide that two producers were started.

Bun later dropped two of the shell's flags. `--jitcache-log` printed JSON lines no Bun user reads, and `--jitcache-max-memory` asked users to size a limit that the bench sets once for every host (`defaultProducerLimitBytes`), so the producer limit became the host's to set. The shell keeps both for the tests. Without the log, a Bun user would never learn that JITCache had turned itself off, so every way it does warns once per process, as `Busy` already did: a rejected `start` at once, and a fault at exit, the first point a host without callbacks can read it. The runner still needs Bun's final statuses, so twins builds write them when the run has a twin report.

Bun calls `delta` in `VirtualMachine::on_exit`, after the user's exit handlers and before teardown, the same point where it persists the Node compile cache. THREAD's "no implicit `delta`" constrains JITCache; the host chooses when to call it, and process exit is the idle point a serverless instance reaches. Bun first called it at every exit of a producing VM and dropped the shell's `--jitcache-delta-at-exit`. Davi made it opt-in on 2026-10-13, with that flag and the shell's syntax: the macro benches compare consumers of a producer with and without an exit `delta`, and a deployment decides whether its producers pay for one. Davi then made it the default on 2026-10-15: a producing role saves at exit unless `--jitcache-delta-at-exit=0`, which the benches' producer without a `delta` passes, and the flag takes a value as `--jitcache-strict` does. The jsc shell keeps its bare opt-in flag, since its test sequences choose per run.

The shell first called `delta` under its flag whatever the role and state, and got `delta.role` from a Consumer and the recorded fault from an ended production, while Bun called it only while production was active. Neither answer captures anything, and what an ended production held goes in `willDestroyVM`, so `finishHostRun` gives both hosts Bun's rule and one order: the `delta`, then the host's own lines, then the bench report's flush.

### Bun names the app by its entry file

THREAD has Bun digest its entry file before `start`. `RunCommand::boot` knows the entry path before it calls `VirtualMachine::init`, which creates the main VM and so reaches `configureVM`, so the digest is computed there and travels in the flags every `configureVM` reads. A worker first seemed to need a digest of its own script. But a worker runs part of the app its main VM started and, while the main VM produces, falls back to consuming that VM's artifact, which a digest of its own script would refuse, so a worker names its process's entry. `-e`, `-p`, `bun run -` and the Node REPL run no file, and their text stands for it. The digest first read whatever the entry path named, so a FIFO, `/dev/stdin` or a `/proc/self/fd/<n>` entry would block `boot`, or lose to the digest the bytes Bun's loader reads next, and a run with `--jitcache` would execute another program than the run without it. `boot` then opened the entry with `O_NONBLOCK` and hashed only a regular file, as the store reads its own files, but opening a FIFO's read end, even without blocking, completes a writer waiting in its own `open`, and the close that follows leaves that writer without a reader, so its bytes are lost and Bun's loader waits for a writer that is gone. `boot` now `stat`s the path first and opens only a regular file, then checks the descriptor again with `fstat`; any other entry names no app and is never opened.

### Bun warns where it hands JSC an app's bytecode

The warning was first meant for apps built with `--bytecode`. Every module Bun loads from a `ResolvedSource` passes through `Zig::SourceProvider::create`, which hands JSC the bytecode the source carries, so the warning sits there, once per process, and costs a process without `--jitcache` one test per such module. The same branch also receives the Node compile cache's bytecode, which `NODE_COMPILE_CACHE` or a CLI's own `module.enableCompileCache()` turn on, and whose UCBs get no key either. The `--bytecode` advice would mislead those users, so the compile cache gets a line of its own, told apart by the two fields only the `--bytecode` paths set (`already_bundled` and `origin_path`).

### `bun jitcache` is a subcommand

The SPEC first put `Tag::JITCacheCommand` in `src/runtime/cli/mod.rs`, which only re-exports `Tag` from `src/options_types/command_tag.rs`. With that file outside its task, the implementer matched the command word in a check of its own before `which()`, repeating `which()`'s rule for skipping leading flags. That works, but it is a second classifier that drifts when Bun changes `which()`, it leaves the crash report's command character unset, and it wires the command unlike every other subcommand. `bun jitcache` became a `Tag` like the rest, dispatched as `bun discord` is, without a context; `exec` takes the entries after the first `jitcache` in argv, which is the word `which()` matched, so nothing repeats its rule (maintenance sub-SPEC section 5).

### Bun declares the twins flags only in twins builds

The four flags of harness section 5.1 that Bun takes were first declared in every build, without help text, since `RUNTIME_PARAMS_` is a constant table and Rust had no twins switch, and section 11.2 allowed no new compile flag. A release Bun then accepted them silently, where an undeclared flag draws Bun's warning. Bun's other builds should carry exactly the flags Bun ships, so twins builds pass `--cfg=jitcache_twins` to rustc, the Rust counterpart of `ENABLE_JITCACHE_TWINS`, as a stated exception to that rule. The rule keeps Bun's flags so the engine sits where Bun's builds put it, and a cfg that only Bun's Rust reads leaves the engine's compile and link untouched. `JITCacheFlags` keeps one layout in every build, so the Rust and C++ sides never depend on the two switches agreeing.

### Bun's twins build reaches only exported headers

## Test builds and the harness

### Twins builds keep Bun's build flags, and the runner moves the heap

The twins profile was first to build position-independent, Bun's executable included, so that the engine image would move between processes. THREAD instead keeps Bun's build flags and skips the targets inside an object loaded at its link-time address, so no build is position-independent and `recordLayout` writes no engine line. A review then argued that the twins build's heap could not move either: ASan is on in Debug builds, bmalloc sends every allocation to ASan's allocator, and that allocator's space was taken to sit at a fixed base, so the VM, its cells and atoms would repeat between producer and consumer. A ten-line C program built by the pinned clang 21.1.8 with ASan placed its first allocation at a different base in each of three fresh processes, with the distances between allocations repeating exactly, position-dependent link or not, so on x86_64 the heap moves; ARM64 could not be measured, and older sanitizer releases did keep a fixed base. The harness therefore records three heap probes per process, and the runner calibrates before its first twins sequence and, where a probe repeats, hands the JSC heap to libpas with `WebKitMallocForceEnabled=1`, while H2 checks every domain. Turning ASan off would have taken it out of every twins run and handed the heap to Bun's debug mimalloc, whose arenas sit at address hints that a debug build does not randomize; consuming a random number of chunks before initialization would give each target too few positions for the dozens of heap fixups a body holds.

### Under QEMU the runner moves the heap with the guest stack

HARNESS.md runs ARM64 under QEMU user mode, but the runner had no way to start an aarch64 build, and harness section 4 assumed that address randomization moves the heap as on x86_64, with libpas as the fallback. Measured with `qemu-aarch64` 8.2.2, QEMU places every guest mapping itself from a fixed base and never randomizes them: two runs of the ASan or release jsc, or of Bun's ASan build, repeated every cell, structure, executable-pool and structure-reservation address, and `WebKitMallocForceEnabled=1` gave libpas addresses that repeated too, so the calibration would have stopped every ARM64 twins run. A placeholder the engine maps before `JSC::initialize` cannot move ASan's allocator, which reserves its space before `main`. QEMU maps the guest stack first, and a larger stack moved every later mapping by the difference once the step exceeded the allocators' alignment: a 64 KiB step moved jsc's ASan cells unevenly, since ASan's primary allocator aligns its space to 128 KiB, a 1 MiB step left Bun's cells in place, and 16, 32 and 64 MiB steps moved them by exactly that much. `-B`, the CPU model and the environment's size moved nothing, and `-R` only changed the fixed layout. A scratch aarch64 program showed that QEMU honours `MAP_FIXED_NOREPLACE`: with placeholders over its first 512 MiB and 4 GiB reservations, the second ones landed disjoint and at another 4 GiB base, so harness section 4's placement stays as written. The same runs settled the CPU matrix (harness N27): the release build died of `SIGILL` under `cortex-a53`, at the LSE instruction the mimalloc it links executes in `mi_process_init`, while the ASan builds of jsc and Bun ran under every model. Skipping the heap domain under QEMU would have been simpler, but ARM64 materializes addresses in value-dependent forms, and only heap addresses that differ between producer and consumer expose a reference the record missed.

### The oracle compares the reachable heap

THREAD Verification compares the heap JavaScript can reach, while a script can print only results, exceptions and stack traces: closure variables, internal slots and private names are invisible to reflection, and a walk written in JavaScript would run getters and traps. The description runs after the exit-time `delta`, so its full collection changes no capture.

The walk first listed an object's private brands in the order they were added, and a scope's row added to what any object writes. A namespace `import defer` created lists its exports only once its module has evaluated, since reading their names runs the evaluation, which the walk must not do.

The walk first ran under `DisallowVMEntry`, to enforce "runs no JavaScript". ## Maintenance

### `compact` at ratio 0 replaced `clean`

Maintenance first had two operations: `clean` removed what interrupted writes left, temporaries, a replaced directory and a remnant, and `compact` planned and applied evictions. Once the pack landed, `compact` at ratio 0 did all that `clean` did, the truncation to the valid end and the clearing of an abandoned retired mark included, so Davi removed `clean` from the C++ API, both command lines, the tests and THREAD. `compact` checks its ratio right after taking the lock, so a bad ratio removes nothing, and it finishes a header-less remnant whose pack holds no body at any ratio without asking.

### A damaged body is dropped by the rewrite

Planning first gave a body that failed its checks a score of minus infinity, so the plan evicted it first, which required planning to read and check every body. THREAD Maintenance has planning read only the pack's index, which repeats L, P and the size, so planning cannot see a damaged body. The rewrite validates each body in full before it moves it, leaves out one that fails and reports `damaged-body`; a damaged pack leaves no body to keep, so any ratio above 0 deletes the artifact and ratio 0 leaves the pack alone. Ratio 0 then left a dense pack's file alone without reading a body, and every `delta` ends with a dense pack, so `compact 0` on a producer's saved artifact kept a body that had rotted on disk, against THREAD Maintenance's "bodies that fail their checks". Always rewriting would have fixed it at the cost of rewriting every clean pack. A plan that keeps a dense pack's file now runs the compaction's own check on every live body through the mapping and rewrites the pack when one fails. The compaction that ends a `delta` keeps its shortcut: THREAD Storage asks a `delta` only for a dense pack, reading every body of a ConsumerProducer's pack at each exit, those other processes committed included, would cost the exit what no reader needs, and a body that rots after its commit fails its section checksums at any import, with strict on or off, and the next `compact` drops it.

## Options

### The option table lives in options.md

The SPEC first listed the fixed options itself, assembled from THREAD's list and every lane's rows. The must-match, fixed and free options of the five sets moved to options.md, whose fixed table keeps the row order `checkFixedOptions()` walks, so each option's class, value and reason sit in one table that every set cites; this SPEC keeps the header, the check and the build-time table.

### Bun 1.4.3's options

`useLazyCatchLiveness` stays free although only it sets the mark that a catch ran without its buffer: no baseline code reads the option, and catch state stays local in 1.4.3, so no carried state depends on it. It becomes fixed again once catch state travels, since a consumer with it off would read a carried mark that its own catches never produce. `startupJITDeferralScale` stays free although it moves every tier-up: Bun sets the scale after `start` (`--compile-jit-policy`, `Bun.unsafe.setJITPolicy`), so fixing the option would not fix the scale, and the scale leaves a counter's progress and active threshold alone, which is all a capture carries. `defaultErrorStackTraceLimit` is set by Bun and still free, because THREAD's must-match class covers only options that change captured code, parsing or what carried state means.

## An absent body loses to every candidate

The glue scored an absent saved body as the empty `CaptureScore`, which every capture beat while every capture was of tier 1. A capture without an image is of tier 0, and one whose UCB copies hold no category and whose counter carries no whole point, a body that ran once or was deferred, ties the empty score, so `beats` would have kept nothing for it, against THREAD's "any candidate beats an absent body". Such a body still saves its consumer the parse and the generation. The glue now compares with `beats` only when a saved score exists (section 8.2).

## The pack (container sub-SPEC)

### Readers follow the pack's root

The container first stored each body as a file in `bodies/`, renamed in from a temporary, and readers learned of another process's commits through an epoch in the lock file, an inotify watch and directory listings. A lookup could then miss a body on disk after an overflowed queue, a failed or deferred listing, or a producer killed between its rename and its epoch bump, and the design needed a listing interval, a pending-listing state and a rule for an `ENOENT` that races a newer token. THREAD Storage replaced the files with one log-structured pack whose root is the commit point, so that a commit costs only the body it writes and a consumer maps one file instead of opening one per body. A reader loads one word: an unchanged root costs one acquire load, and a larger one applies the index blocks appended since. The epoch, the listings, inotify and `fallbackListingIntervalMilliseconds` went with the files, and the lock file keeps only its tag and version.

### The root is one word without a checksum

The pack's root was first two 64-byte slots, each holding a generation, the valid end, the latest index block and a CRC, written alternately with `pwrite` after a sequentially consistent fence; a reader took the valid slot with the highest generation, so a torn slot fell back to the other. The CRCs were there because a `pwrite` does not promise one 8-byte store. An aligned 8-byte store through a shared mapping is one store, and the valid end only grows within a file, so it can also serve as the generation. The root became one word at offset 56, stored with release through a writable mapping of the prefix and loaded with acquire, and the prefix shrank from 256 to 64 bytes under layout version 2. A bit flip in the root, which the slot CRC caught, is now caught by structure: a root past the file fails when the pack is mapped, before any read could fault; a root that does not end in a block whose trailer gives its start fails the index walk; and a root that moved back is damage to an object that applied the later value. Every index block gained its trailer for this, so the root alone leads a reader to the latest index.

### The pack's layout version is read before its CRC

`decodePackPrefix` first checked the CRC before the layout version, as every other structure is checked. The format review of 2026-10-15 found that a layout-1 pack, which the beta snapshot's Bun wrote with a 256-byte prefix, failed under layout 2 with "the prefix's CRC differs", because each layout puts the CRC in another place. Maintenance then reported `damaged-pack`, and since `compact` evicts a damaged pack first, any ratio above 0 planned to delete the whole artifact behind the confirmation prompt. The version now comes right after the tag, both at the same place in every layout; a mismatch is another layout (`isOtherPackLayout`), which maintenance treats like an incompatible header, with no plan. Consumers were never at risk, since the header's build ID rejects such an artifact first.

### A moved root is checked against the file's size

At first only `MappedPack::map` compared the root with the file's size, and an object that followed a larger root trusted it, since only the producer moves it, under the lock, after extending the file. The format review found that a host replacing the pack in place, with `cp` or `rsync --inplace`, shrinks the inode under running consumers, whose next read past the new end dies with `SIGBUS`. `applyValidEnd` now takes one `fstatat` per root move, while the path names the mapped inode, and a root past the file is `container.pack` damage instead of a crash. A body borrowed before such a shrink can still fault; only a replacement by rename avoids that.

### Tokens are commit identifiers

With body files, the index held per-key tokens from a counter of its own, because commit identifiers lived only in envelopes, which no lookup could read without opening a file. The pack's index entry repeats the commit identifier, so the token is that identifier. It needs no counter and no system call, every process sees the same token for a body, and a compaction, which moves records but keeps their identifiers, changes no token, so the UCB lane does not reread bodies after one.

### Bodies are borrowed from the pack's mapping

A body was read into a buffer of its own because opening one mapped body file, checksums included, cost 19.5 µs on the Ampere A1 and unmapping it 12.2 µs. The pack is mapped once, at `start`, with room past the file's end for it to grow into, so an open borrows the body's bytes from that mapping, holds a reference that keeps the mapping alive, and copies nothing. The format review measured an open, with its index lookup, record-header CRC and checks B1 to B8, at a median of 1.6 µs per body in elysia.

### The scoring read follows the root

The scoring read opened a body by its name whatever the index held, because a producer killed between its rename and its epoch bump left a body on disk that no index listed. In the pack a body is committed exactly when the root covers it, so the scoring read finds a body through the current root, as `open` does, and `Absent` means that no committed body exists. Its own `Unavailable`, which defers the key, and its checks of the summary sections alone stay as they were.

### Every delta ends with a dense pack

The delta first compacted only once dead bytes passed half of the valid end, and later through an option with that default. Under that rule the producer's delta-at-exit pack for elysia carried 42% dead bytes, mostly superseded first captures, all of which a cold consumer reads from storage. THREAD Storage now has every `delta` end with a dense pack: `compactIfNeeded` rewrites whenever the pack holds a byte beyond its live records and one full index, so a delta that committed nothing costs only that test, and the option is gone.
