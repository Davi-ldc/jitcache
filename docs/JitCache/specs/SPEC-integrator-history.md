# SPEC-integrator history

Why the non-obvious decisions of [SPEC-integrator.md](SPEC-integrator.md) and its sub-SPECs are what they are: for each, what first seemed right, the evidence that changed it and the intent that came out, so a later revision does not go back to the obvious version. Nothing here binds.

## Interface and per-VM state

### The fault entry point names its site

The lanes first called `didFailExecutableAllocation(VM&)`, while each of their requirements asked for a diagnostic naming the failing site, which a one-argument function cannot give. THREAD Execution gives API signatures to the integrator, so the integrator added the site argument, and every lane's call passes it. The entry point records the fault with plain stores and frees nothing, because the ICs lane calls it under a `CodeBlock::m_lock` held through `GCSafeConcurrentJSLocker` and the Image lane forbids waiting for another thread. Production memory is therefore released later, by `releaseEndedProductionMemory()` at the next glue entry, which costs a flag test while production is active.

### Every refused production charge is `budget.limit`

Each lane's capture call first reported a refused charge as its own failure, so a producer that ran out of budget named a different step depending on which charge happened to be refused first, and a test of the producer limit could not name the fault it expects. Every refusal of a production charge is now raised as `budget.limit`, the budget's own fault, wherever it lands; when a lane's capture call fails while the budget has refused, the lane's check goes in the detail.

### The state is created and destroyed in task 7's file

The teardown hooks were first defined in task 2, so `VM::~VM` called them from task 2 on, while destroying a state runs the destructors of the producer lock, the opened artifact and the writer, which land in tasks 5 and 6; the store's tests also expected faults only a configured VM can raise, the writer's `rewriteSection`, in task 6, erased kept summaries, which task 9 introduces, and `start` created the Image lane's `Twins` object, whose class lands with that lane's task 11. Splitting the state's ownership by task, or keeping the late members in a sub-object whose destructor lives in the store's files, would still need those files at task 2's link. Since only `start` creates a state and only `didFinalizeHeap` destroys one, the constructor, the destructor and both hooks moved beside `start` in task 7, when every type the state owns exists; the store's reads came to return outcomes and know no VM, the kept-summary erase moved from the writer's `rewriteSection` into the capture glue's `rewriteSectionForTesting` (task 9), and `ValidatedBody` got a file of its own in task 2, because the UCB lane's pending imports hold one. The `Twins` object lives in an image twin-check state that the VM's first stash creates and `willDestroyVM` destroys, held through a deleter the creating file supplies: what the Image lane needs is a lifetime that covers every twin check until VM destruction, and that gives it without the state naming an Image-lane type.

### The state's private part lands with its first members

The private part of `VMState` was first written by task 7, beside the state's lifecycle, so that the header would change once, after every type the state owns existed. Tasks 2 and 5 define members that read it (the switches, the fault records, the budget and context, the opened artifact and the lookup override), so their definitions could not compile in task order. Declaring a member needs only its type's declaration, which task 0's headers and the UCB lane's task 0 provide, and the types a later task defines are held through pointers. Task 2 therefore writes the whole private part, tasks 5 and 7 define members against it, and task 7 still makes the header's last edit, the accessors later tasks use.

### Test bodies and a lookup override

SPEC-ucb.md U4 needs a pending import whose body asserts in its destructor, and U8 needs the engine's lookups to return crafted bodies, while `ValidatedBody` had only the store's constructor and the lookups had no override point. In twins builds `ValidatedBody::createForTesting` copies crafted sections into one aligned buffer and runs a callback from its destructor, and `setBodyLookupForTesting` makes `bodyVersion` and `openBody` answer from two functions. The override answers alone, without falling through to the store or moving a progress counter, and leaves role, strictness and activity as `start` and the faults left them, so a test that needs several configurations runs once per configuration. When the index came to hold tokens, the override's first function came to answer tokens too, kept apart from the commit identifiers its bodies carry.

### `productionActive` belongs to the lanes' interface

`productionActive()` began as one of the integrator's own members. The UCB lane then chose to digest a direct eval's TDZ and private-name sets only where something reads them, and those sets exist only during the eval's request, so a record keeps the digest only in a VM whose production is active, the only VMs that capture (SPEC-ucb.md section 3.4). The member moved into the lanes' interface, which task 2 defines, and the end of production also ends that digest.

### Strict: integrity in both modes, structure under strict

THREAD made strict off by default and had normal mode check only the artifact's integrity and trust the rest. The container therefore splits each check into an integrity part both modes run (the header digest, the key, the checksums, and the sizes and bounds those checksums need) and a structure part only strict adds (reserved bytes, tier, commit identifier, entry order and kinds, layout, required sections), which is what SPEC-ics.md R-INT-4 expects of the directory. The writer's reread could have followed the session's flag like every other read; it validates in full in both modes because THREAD Capture has the writer validate what it publishes. The lanes' summary readers take the strict flag, so a rejected saved summary is invalid material only with strict on.

### Which compilations record is decided at plan construction

SPEC-image.md R-INT-12 needs to know, on whichever thread compiles, whether a plan's compilation records. The integrator answers once, in `BaselineJITPlan`'s constructor, from `producerContext(vm)` and the registry's `keyOf`: both constructor callers, `jitCompileAndSetHeuristics` and `JIT::compileSync`, run on the VM thread, `keyOf` takes only the registry's leaf lock, and a flag written before the plan is enqueued needs no lock when the compiling thread reads it. Task 2 adds the member, false until task 7 computes it, so the Image lane's task 4 compiles against it without waiting on the registry; no compilation records before task 7 creates a state anyway.

### A ConsumerProducer rebuilds the image record only while production is active

Install step 7 first asked the Image lane to rebuild the image record in every ConsumerProducer, so one whose production had ended still built and charged a record that no capture would read. The rebuild was limited to active production, and the policy enum that carried the choice was then dropped as a restatement of whether a budget is passed: the step passes `producerContextIfActive()`'s budget or null, which is non-null exactly in a ConsumerProducer whose production is active, as SPEC-image.md R-INT-7 asks. With a null budget step 10 tests nothing, so a VM whose production ended raises no second `budget.limit`.

### Production memory is released by task 7's code

`releaseEndedProductionMemory` was first defined in task 9, beside the kept summaries it frees, but task 8's install function calls it before its step 1 and task 7's `willDestroyVM` frees the same memory, so the tree could not link in task order. Making task 8 wait for task 9 would have held the install glue behind the capture glue and still left task 7's teardown without the kept summaries' type. The state holds the kept summaries through a deleter their own file supplies, and destroying them releases their charges, so the function needs no type of the capture glue and lands in task 7 beside the teardown that calls it.

## The artifact

### Body files are named by the key's hex

THREAD's layout names `<body-key-hash>.bin`, which suggests hashing the key. The 40 key bytes are already a digest (a header of kind, specialization and mode, then a SHA-256 identity digest), so the integrator names the file by the key's hex and adds no second hash. A second SHA-256 would run at every request point and CodeCache hit, since the UCB lane calls `bodyVersion` there: a few hundred cycles per software block, so tens of thousands of requests in a large app's startup would spend milliseconds on names alone. With the key in the name the index is keyed by the key itself and is exact, so a mismatch between a file's name and its envelope is damage, never a collision.

### Bodies are mapped, checksummed with CRC32C and versioned by random identifiers

Reading a body into private memory would hold a second copy for as long as a pending import pins it; a `MAP_PRIVATE | MAP_POPULATE` mapping shares page-cache pages the kernel can reclaim, and THREAD ranks installation memory above serialization time. The mapping's cost is the fault a truncated file raises, which JITCache never causes and the trusted-artifact model accepts. Sections are guarded by CRC32C rather than SHA-256 because every import validates the whole file against damage, not against an adversary, and with SSE4.2 or ARMv8 CRC instructions it runs at several GB/s; the integrator's own CRC-32C implementation gave way to the engine's `crc32c` of `CachedTypes.cpp`, made external. Commit identifiers are random 64-bit values, since a counter would need shared state that survives artifact deletion and lock-file loss, and the UCB lane only needs "another version", never an order.

### Other processes' commits arrive through an epoch and inotify

The UCB lane tries again at the next request a body committed later, and UCB R-INT-3 forbids a filesystem call for an absent body, so polling the directory, or reading inotify at every lookup, would put a system call on every request point. The lock file, which exists anyway and is never replaced, carries a commit epoch that producers and maintenance bump after each publish or removal; a lookup compares one shared word and drains inotify only when the epoch moved. Body temporaries first lived in `bodies/`, where a commit raised four events; they moved to `cache/` and are renamed into `bodies/`, so a commit raises one event in the watched directory. The index is listed at `start` rather than at the first lookup, so the listing is the demand a consumer role creates and no directory scan lands inside a request point.

The writer's index update first assumed that its VM's `start` had drained the inotify queue. The queue also holds the events of the VM's own commits and of changes made before the VM took the lock, so step 8 of the commit (container sub-SPEC section 8.2) applies whatever events are queued, and records its own epoch bump as seen only when the bump replaced the last epoch the object saw and no listing is pending. An object that was behind then refreshes at its next lookup instead of taking its own bump as proof that it is current. An overflow or a read error during that drain marks a listing pending instead of listing inside the capture pause.

### One opened artifact per process

The shared object first decided at its build, from the building VM's role, whether it followed the epoch and watched the directory, so Consumers sharing a producing VM's object never refreshed. One object per VM would have fixed that, but Bun runs a VM per worker, and the workers of a producing process are the Consumers of its main VM's artifact: per-VM objects would list the directory at each worker's start, keep an index per worker (a few megabytes each for tens of thousands of bodies), take an inotify instance per worker from the user's 128, and make every worker refresh after each of the main VM's commits, listing the whole directory each time where inotify instances run out. One object per process costs one listing, one index and one instance, and the main VM's commits reach its workers at once through the writer's index update. Every object therefore follows the epoch and watches the directory whatever its holders' roles.

### Listings

Listing `bodies/` through `fdopendir(dup(bodiesFd))` shared the descriptor's offset, which glibc's `fdopendir` does not reset, so every listing after the one at `start` read nothing and emptied the index; a refresh that cleared the index before listing also left it empty when the listing failed. Each listing now opens `.` relative to `bodiesFd`, preferred to `rewinddir` because it shares no offset with any other user of the descriptor, and swaps in a new map only when it succeeds. A refresh whose listing fails keeps the old index and marks a listing pending, since retrying at every lookup would put a listing on every request point to recover bodies whose absence costs only a miss. Without inotify, or with a listing pending, a refresh lists at most once per `fallbackListingIntervalMilliseconds`, so a stream of external commits cannot make every lookup list. Building the map outside `m_indexLock` was rejected: the swap would drop what the writer's commit and the drained events recorded meanwhile, and merging them back would add the mechanism the interval makes unnecessary.

### The index holds tokens

The index first held each body's commit identifier, read from its envelope. UCB R-INT-3 then had `bodyVersion` answer from the index alone, so the index holds a token per key that changes whenever it learns of another body there, from an event, a listing that finds a new key or inode, or the writer's own commit; a listing keeps the token of a file it saw before, so a relisting after an inotify overflow, or every listing where inotify is unavailable, does not send the UCB lane back to bodies it already found not to fit. A read that meets `ENOENT` erases a key only while the key keeps the token read before its `openat`, because a token learned meanwhile names a body that arrived after that call and erasing it would hide the body. Compact index entries, a key fingerprint in an open-addressing table, wait for IB2 to measure what the index costs.

### The scoring read opens by name

The capture glue first scored through `openBody`, whose `Missing` covers `EMFILE`, `ENFILE` and `ENOMEM`, so a descriptor shortage at a key's first scoring read as no saved body, which any candidate beats, and could let a poorer capture replace a richer body. The glue got a scoring read of its own, whose `Unavailable` defers the key and which checks only the envelope, the directory and the three summary sections a score reads, so a ConsumerProducer's first scoring does not checksum a whole image inside the capture pause. That read first answered `Absent` for a key the index lacked, which required a producer's index to hold every body on disk, a second listing under the producer lock, and an argument about a producer that died between its rename and its epoch bump. It now opens the body by name whatever the index holds, at the cost of one failed `openat` for a key with no body, before a commit that costs far more. Recording a kept summary at install, to spare a ConsumerProducer that first scoring, was rejected as work ahead of demand inside the bounded import window; IB7 measures those scorings, and stamping the committed score in the envelope is the first change to measure.

### The writer takes section sources and reads no lane format

The writer first mapped every committed file and ran the lanes' parsers on it. THREAD Storage makes sections opaque bytes to the container, THREAD Capture's "reread and validate" is what the container validation already does, and the reread compares each section with the checksum of the very bytes the lanes built, so parsing the file proved nothing that parsing those bytes would not, while it overrode three lanes' own choice of capture checks and parsed every strict commit inside the capture pause. The writer then took a `CommitSections` built from four lane types and called the Image lane's write functions by name, so test C7, which lands before any lane's capture code, could not build one. It now takes an ordered list of sources, each a kind, a size and either a span or a function pointer with an object that streams the bytes; a function pointer rather than a `WTF::Function` lets a commit allocate nothing beyond the staging buffer and lets the glue return the list by value. A source whose byte count differs from its size fails at `writer.section` rather than `writer.write`, since it breaks a lane's size contract rather than meeting an I/O error, and the diagnostic names the section and both counts.

### Charging hash tables and index entries

Kept summaries were first charged four bucket sizes per entry, meant to bound a hash table's storage without depending on WTF's growth policy. That was not a bound: WTF doubles a table above 1024 buckets once it is half full, so while a rehash holds the old table beside the new one the two take six buckets per entry, and a table starts at eight buckets; the rule became eight bucket sizes per table and six per entry. The index was at first exempt from the producer limit, though THREAD Session exempts only the parent-key registry and the identity digests. Of the index, production allocates exactly the entries the writer adds, so those are charged before the commit, and released with the rest of production memory rather than when the entry goes, since the shared entry stays to serve the process's importing VMs; the entries listings and refreshes create hold what every importing VM needs and are not production memory.

## Install and capture

### One install function with a point argument

THREAD's two install points became one function with a point argument. Before `setupLLInt` it replaces the LLInt setup and calls `installCode` itself, because THREAD's order puts the CB lane's twin check before `installCode` and measures the import until JITCache returns after it, so `prepareForExecutionImpl` skips its own trailing call; in `JIT::compileSync` the import replaces the plan, and `prepareForExecutionImpl` calls `installCode` a second time, as the LLInt-off route does natively. The function repeats its callers' sharing-slot and newborn tests, because `compileSync` has callers that make neither. `shouldJIT` was file-static, and giving it external linkage, unchanged, is the smallest edit that lets the gate be the LLInt's own.

### The kept score comes from the builders

THREAD reads a saved body's summary at the key's first scoring; the integrator keeps the score afterwards and replaces it at each commit, so a key never costs a second read while the VM holds the lock. The kept score was first computed from the committed file, then by re-parsing the summaries a capture had just built; both read back bytes whose score the builders already return, and with strict off the re-parse checked nothing while with strict on it imposed a check the UCB and ICs lanes chose not to make. The score now comes from the builders: the CB lane's `score()` is a function of its summary bytes (SPEC-cb.md I8), `captureBaselineICs` returns the count it writes into the section header (SPEC-ics.md section 5.6), and `liveRichness`, read in the same pause as `buildSections`, reads arithmetic profiles and exit sites that neither JS nor the collector can change during a capture (profiles.md, "Table"; SPEC-ucb.md F17). A marker's or a compiler thread's drain between the scoring and the build can still add bits, by folding in a pending sample, or drop them in a racing merge, so the capture re-tests `beats` with the built score and stops when the build no longer wins.

### `delta` scores in two phases

Phase 1 reads under `CodeBlockSet::m_lock`, which `forEachCodeBlockIgnoringJITPlans` requires, and phase 2 reads saved bodies and writes files without it, because no file I/O should run under a lock the CodeBlock constructor takes. The CodeBlock pointers kept between the phases stay valid because nothing can complete a collection while the VM thread holds heap access, reaches no stop point and allocates no cell. Phase 1 first kept only the best candidate per key, so a `NotEligible` image dropped the key for that `delta`; it now keeps each key's candidates in score order and phase 2 tries the next one, as SPEC-image.md R-INT-6 treats `NotEligible` as an ineligible CB. A sorted vector of keys went too, since nothing read its order.

### Captures cannot nest

A `delta.reentrant` rejection, a capture-running mark and a twins-only capture probe once guarded against a capture starting inside another. Nothing reaches that state: a capture runs with JS paused and calls no host or JS function, since the API calls nothing back, finalizes no plan, and no lane's capture call walks the CodeBlocks with plan completion; the Image lane's twin compile runs at install, outside `BaselineJITPlan::finalize`. The probe existed only to create the state the guard rejected, so all three went, and a debug-build assertion that no capture is in progress at the finalize capture or `delta` checks II14's consequence at no release cost.

### Exit sites across ConsumerProducer generations

A review found that an imported body whose captured counter had crossed reached its first DFG compile at its second invocation, when each property IC held only what one invocation had cached. At a site the producer saw with several shapes, that compile took `BadCache` exits until it was jettisoned, `tallyFrequentExitSites` added the site to the UCB's exit profile, the richer recapture won and was committed, and every later consumer gave the site its slow status, so exit sites only accumulated across generations. Each step held in the code, and since the richness rule and the counter floor were THREAD's, the SPECs first added a measurement, IB10, which chains ConsumerProducer generations. THREAD then withheld counter progress from bodies with a polymorphic property IC, and the ICs lane extended the rule to polymorphic call sites, so IB10 now checks that consumer-induced exit sites no longer accumulate and sizes what the rule leaves. Bun's `delta` at exit stayed: THREAD leaves the idle point to the host, and calling `delta` less often would slow the ratchet without settling it.

### The executable-allocation fault list is exhaustive

The list of fault sites was first provisional. THREAD Failures made it exhaustive and keeps Yarr, Bun's FFI thunks and stubs and WebAssembly native. Reading the FTL path showed that `FTL::LowerDFGToB3::compileCallFFIImpl` also sets `allocationFailed` when Bun's FFI invoke thunk cannot be allocated inside the plan's lowering, so that plan raises `exec-alloc.ftl-plan` like any FTL plan short of executable memory, while FFI thunks outside a plan stay native.

## Hosts

### Bun

Bun calls `start` in `Zig__GlobalObject__create`, right after it takes the API lock and before `JSVMClientData::create`, which is the last point before anything could create a builtin executable. Configuration first came from `BUN_JITCACHE_*` variables, read once per process like `BUN_JSC_*`. THREAD Session makes Bun's command-line flags its whole user-facing configuration, so Bun takes the jsc shell's flags with the same syntax (section 11.2), and the runner passes one set of flags to both hosts (harness sub-SPEC section 7.7). A worker of a process whose main VM produces gets `Busy` and falls back to `Consumer`, so workers still import what the main VM commits. A `Busy` from another process first fell back to `Consumer` too, so a `p` or `p-c` started beside a running producer quietly became a reader. It now fails as a Producer facing an existing artifact does, and warns on standard error even without `--jitcache-log`: a process asked to write never silently stops writing, which would hide that two producers were started.

Bun calls `delta` in `VirtualMachine::on_exit`, after the user's exit handlers and before teardown, the same point where it persists the Node compile cache. THREAD's "no implicit `delta`" constrains JITCache; the host chooses when to call it, and process exit is the idle point a serverless instance reaches.

### Bun's twins build reaches only exported headers

Bun's `JSCInitialize` and `JITCacheHost::configureVM` first called the placement and layout functions through `JITCacheTwinsHarness.h`, which was not exported, while Bun's build sees JSC only through the build directory and the copied `Headers` and `PrivateHeaders`, so the `bun-twins` target could not compile. Reaching the source tree through Bun's `vendor/WebKit` symlink would have bypassed the rule SPEC-image.md section 14.4 states for every exported header. The exported twins header became `JITCacheTwinsHost.h`, named for who uses it, and declares with `JS_EXPORT_PRIVATE` and WTF and JSC types only everything a host calls in twins builds; `recordVMLayout` gained a `HeapProbes` parameter for the flag that had reached it through none. Task 14 ends by building `bun-debug` and `bun-twins`, which would have caught the defect.

## Test builds and the harness

### Twins builds keep Bun's build flags, and the runner moves the heap

The twins profile was first to build position-independent, Bun's executable included, so that the engine image would move between processes. THREAD instead keeps Bun's build flags and skips the targets inside an object loaded at its link-time address, so no build is position-independent and `recordLayout` writes no engine line. A review then argued that the twins build's heap could not move either: ASan is on in Debug builds, bmalloc sends every allocation to ASan's allocator, and that allocator's space was taken to sit at a fixed base, so the VM, its cells and atoms would repeat between producer and consumer. A ten-line C program built by the pinned clang 21.1.8 with ASan placed its first allocation at a different base in each of three fresh processes, with the distances between allocations repeating exactly, position-dependent link or not, so on x86_64 the heap moves; ARM64 could not be measured, and older sanitizer releases did keep a fixed base. The harness therefore records three heap probes per process, and the runner calibrates before its first twins sequence and, where a probe repeats, hands the JSC heap to libpas with `WebKitMallocForceEnabled=1`, while H2 checks every domain. Turning ASan off would have taken it out of every twins run and handed the heap to Bun's debug mimalloc, whose arenas sit at address hints that a debug build does not randomize; consuming a random number of chunks before initialization would give each target too few positions for the dozens of heap fixups a body holds.

### Under QEMU the runner moves the heap with the guest stack

HARNESS.md runs ARM64 under QEMU user mode, but the runner had no way to start an aarch64 build, and harness section 4 assumed that address randomization moves the heap as on x86_64, with libpas as the fallback. Measured with `qemu-aarch64` 8.2.2, QEMU places every guest mapping itself from a fixed base and never randomizes them: two runs of the ASan or release jsc, or of Bun's ASan build, repeated every cell, structure, executable-pool and structure-reservation address, and `WebKitMallocForceEnabled=1` gave libpas addresses that repeated too, so the calibration would have stopped every ARM64 twins run. A placeholder the engine maps before `JSC::initialize` cannot move ASan's allocator, which reserves its space before `main`. QEMU maps the guest stack first, and a larger stack moved every later mapping by the difference once the step exceeded the allocators' alignment: a 64 KiB step moved jsc's ASan cells unevenly, since ASan's primary allocator aligns its space to 128 KiB, a 1 MiB step left Bun's cells in place, and 16, 32 and 64 MiB steps moved them by exactly that much. `-B`, the CPU model and the environment's size moved nothing, and `-R` only changed the fixed layout. A scratch aarch64 program showed that QEMU honours `MAP_FIXED_NOREPLACE`: with placeholders over its first 512 MiB and 4 GiB reservations, the second ones landed disjoint and at another 4 GiB base, so harness section 4's placement stays as written. The same runs settled the CPU matrix (harness N27): the release build died of `SIGILL` under `cortex-a53`, at the LSE instruction the mimalloc it links executes in `mi_process_init`, while the ASan builds of jsc and Bun ran under every model. Skipping the heap domain under QEMU would have been simpler, but ARM64 materializes addresses in value-dependent forms, and only heap addresses that differ between producer and consumer expose a reference the record missed.

### When a skip fails a run

The Image lane's twins runs turned concurrent compilation off and failed on a skipped image check, while the ICs lane's kept the default and treated a skip as no difference; the first reconciliation failed a skip exactly when that run had concurrent compilation off. The image check also skips a body its producer compiled on a worklist thread, so THREAD Verification's rule fails a skip when that run and every earlier run of its sequence that produced have concurrent JIT off; an earlier Consumer run captures nothing, so its setting cannot cause a skip. `ics/` then turned concurrency off too, unless a run sets it, so ICs imports meet the image twin check; no ICs test needs worker compilation, and SPEC-ics.md T9's fuzz index is deterministic only with it off, since the fuzzer counts every thread's allocations.

### The oracle compares the reachable heap

THREAD Verification compares the heap JavaScript can reach, while a script can print only results, exceptions and stack traces: closure variables, internal slots and private names are invisible to reflection, and a walk written in JavaScript would run getters and traps. The engine therefore describes that heap, and the description leaves out what two runs JavaScript cannot tell apart may differ in: tiers, ICs, structures, storage and addresses, so the walk uses `getOwnPropertyNames` order and `VMInquiry` slots; weak reachability, which the conservative stack scan decides, so weak edges never give a cell an ordinal; and native hash orders, so scope variables sort by name and weak entries by their keys' ordinals. The shell's `arguments`, which holds the role, is left out, and Bun scripts describe roots of their own, because Bun's global object holds per-process state. A finalization registry's values that only it reaches and a pending promise's reactions are listed or omitted without being walked: JavaScript observes them only through what their callbacks do, which the rest of the output shows, and walking them would need a canonical form for unordered subgraphs and for the reaction forms. The description runs after the exit-time `delta`, so its full collection changes no capture.

The walk first listed an object's private brands in the order they were added, and a scope's row added to what any object writes. Both changed when the description was implemented. `BrandedStructure` keeps its brand chain private and exposes only `checkBrand`, so the walk tests every private symbol it reached and lists the brands in their ordinal order; JavaScript observes brands only through brand checks and `#x in o`, never their order, and recovering the addition order would need an engine edit with nothing to compare against. A scope written as any object would also list its own properties, which follow its symbol table's hash order, the very order its sorted variables exist to avoid, so a scope's row replaces the any-object part.

### The oracle compares every run that configures JITCache

The oracle first compared only a sequence's last run. SPEC-ics.md T9's one-Producer sequences had no other oracle, so the runner compares every run that configures JITCache, producers included. An oracle run sharing the compared run's paths could overwrite the description it is compared with, so each oracle run takes only the compared run's own options minus every `--jitcache` option and writes `oracle<j>.heap`, a path no run of the sequence writes.

### The runner fails undeclared faults and runs that install nothing

A strict check that fails at an import or install turns cache activity off and leaves the run on the native path, whose output still matches the oracle and whose later bodies meet no twin, so such a run passed unnoticed. Every run with JITCache now logs its final status, and the runner fails a run that wrote none unless it is expected to end by a signal, a run whose `activityFault` or `productionFault` names a step no directive declares, and a Consumer or ConsumerProducer run whose statuses add up to no install. Both fault fields are read, because `firstFault` alone would hide a fault that follows a declared one. A directive permits its step rather than requiring it, and a run may carry several, because the fuzz tests' step depends on n and may be none.

### Directives address runs by sequence

A directive's run index first applied to every sequence of a script, so a waiver meant for one sequence also dropped the install check in the others, and scripts could not tell their cases apart. The runner now passes each run its sequence index as `arguments[3]`, and a run index may be written `<sequence>:<run>`. The same grammar carries `jitcache-expect-twin`, which makes a declared twin report required and harmless, because SPEC-image.md T3's hook forces relocation pairs that the runner would otherwise fail.

### `testjitcache` applies options in the initialization callback

`testjitcache` first set its group's options before `JSC::initialize`, where `Options::setOptions` reaches an unconstructed `LazyNeverDestroyed` and the initialization's reset then overwrites the group. Following the jsc shell (`Options::initialize`, then `setOptions`, then `JSC::initialize`) is equally correct but splits initialization in two; the customization callback is how Bun's `JSCInitialize`, `testb3` and `testmasm` set options, gives the embedder the last word, and runs before `notifyOptionsChanged` derives the dependent options. Because `VM::~VM` asserts that the thread holds the API lock and `JSLockHolder::~JSLockHolder` drops its own reference before unlocking, the harness drops the test's reference inside the holder's scope, as `runJSC` does under `--destroy-vm`.

### Per-body event counts

HARNESS.md asserts per body the bytecodes the LLInt executes, the compiles, OSR exits, jettisons and reoptimizations, and the engine counts none of them per body: its event log feeds only the per-bytecode profiler THREAD keeps off, and its exit counters die with jettisoned CBs. Twins builds add counters to each `UnlinkedCodeBlock`, incremented where the engine performs each event, and an end-of-run dump whose total keeps the counts of UCBs that died earlier, which Bun's code deletion after the entry script would otherwise lose. H6 first checked the counts against log lines printed earlier than the counters, but `jettison` prints before its early returns and the DFG and FTL print their code before `Plan::finalize` can still fail, so H6 counts the lines printed where the counters sit. `jitcacheBodyEvents` once fell back to the UCB an `UnlinkedFunctionExecutable` holds, but those slots are private and the public accessor decodes, generates or imports; every test reads a function after a call created its CB, so the fallback went. A dead UCB retires its counts only when a sweep destroys it, and precise allocations wait for a collection's epilogue, so the dump calls `stopIfNecessary()` and then `sweepSynchronously()` first.

### The pin comparison names addresses itself

A first design counted on the disassembler to name operations and thunks. Operation labels exist only in Apple's internal ARM64E builds, x86_64's disassembler prints no label, and the baseline dump runs before the link tasks that write x86_64's calls to thunks, so the comparison names addresses itself: by code block, by the allocation headers `logJIT` prints, by the build's symbol table, and otherwise by the order in which a run first references an object, which is exact because both runs keep the collector off. It reads x86_64's thunk targets from the JIT dump, folds blinding, temporary-register constants and ARM64 branch compaction, and checks that both runs compile alike, since `BinarySwitch` seeds its shuffle from a process-wide counter. Blinding strikes one candidate in 64, so a twins-only switch forces it and H7 shows that every blinded form folds back. M3 places `m_jitCacheState` last in `VM`, so no field offset the code bakes moves.

### Producer kills

An abort before the rename covered one of the states a commit leaves on disk. Harness section 12 has seven `SIGKILL` points instead, one for each state the writer's system calls leave, from before the temporary exists to after the rename, and `SIGKILL` runs no handler or destructor, as a killed producer would not. `producer-kill.js` checks the outcome THREAD gives each: earlier bodies importable, the interrupted one absent or its earlier version intact, and a temporary that `clean` reports.

### Measurement choices

THREAD's installation bound has both sides measured with per-VM support already generated, so a `JITThunks` count of support generations flags the `install` and `compile` events that generated any, and IB3 sets those bodies aside; `JITThunks` keeps its members private, so it gained a public `noteSupportGeneration()` that the slow-path handler's site, outside the class, can call. On Linux the vDSO does not serve the thread CPU clock, so reading it around each step would put system calls inside the span it measures: the bound's spans read it only at their ends, one pair around the install function, and the step breakdown reads `CLOCK_MONOTONIC`, which the vDSO serves. Outside twins builds the install function's reference to the body is the last one, so the drop that unmaps it is timed apart as `bodyRelease`, measured with the reading it undoes, and one `pread` into an owned buffer is the first change to measure if it weighs.

### What the executable-allocation fault tests can see

The fault test first expected a fault for every n, but the fuzzer also fails allocations that keep native behavior, such as Yarr's, so each n accepts `null` and each of the five steps must appear somewhere in the range. The twins compare state the engine cannot recompute with its capture record, so they pass on a captured failure effect; the test instead reads the committed bodies after each fuzzed producer, through a consumer whose activity is on, and fails on a deferred LLInt counter in `ucb.feedback` or a carried, deferred baseline counter in `cb.state`, which a DFG-plan fault raised too late would leave. Its bodies stay below the reoptimization count at which `adjustedCounterValue` clips, where a deferred counter appears natively, and keep every site monomorphic, since a `NotCarried` section records no counter. The baseline-plan and FTL-plan sites leave nothing a capture can hold, because a body whose baseline plan failed never runs baseline again and an FTL failure only clears a bit native jettisons clear too, so they rely on their step appearing; the image twin, which replays MathIC regenerations, catches a late MathIC-snippet fault as long as the function stays in baseline through the `delta`.

### Imports a process captured itself

A ConsumerProducer imports bodies it committed itself, because the writer updates the index its own lookups read, and the twin check's relocation clause then saw every pair equal, which the runner fails for the pool and the structure reservation. The Image lane writes a capture-process token into the twins section and compares no relocation pair for a body its own process captured (SPEC-image.md section 11.4); the runner itself does nothing differently.

### The lanes' twin checks land before the glue that calls them

Task 8 waits in twins builds for each lane's twin check, which install steps 14 and 15 call, while the CB lane kept its twin check in one task with a corpus that needs this glue and the runner, and the ICs lane its twin API beside a runner sequence, so each plan waited on the other. The lanes split those tasks, and the task list states the rule the plans follow: a lane task that an integrator task waits on depends on no integrator task from that one on.
