# SPEC-ics history

For each decision of [SPEC-ics.md](SPEC-ics.md) that is not obvious, this file records what first seemed right, the evidence that changed it and the rule that came out, so that whoever revisits the decision does not return to the obvious version. Nothing here binds; where this file and the SPEC disagree, the SPEC wins. The entries follow the SPEC's order.

## The shape group stays as installation builds it

Restoring `m_cacheType` to `Stub` for a site that had cases looked faithful to the producer. It leaves an IC at `Stub` with no case, though, which the status classes read as `Simple` with no variants, a state native code reaches only after a megamorphic give-up. Leaving the shape group as installation builds it makes a restored, considered IC identical to a native IC after a reset, which is what THREAD Caches' example needs: `PutByStatus` answers `LikelyTakesSlowPath`, so the DFG emits a generic put instead of a `ForceOSRExit`. It also keeps "Restoration emits no IC code" literally true, since attach touches only the learning group, `canBeMegamorphic` and, for given-up sites, `m_slowOperation`.

## `resetByGC` travels

Nothing reads `resetByGC` today, so dropping it looked free. It is learned per site, like `clearedByGC` on call links, which THREAD carries, and THREAD's opening says that everything else the baseline phase learned travels too. It costs one bit.

## Dense records in native index spaces

Sparse call-link records keyed by bytecode offset were the first idea. A bytecode offset cannot be validated as an instruction boundary without walking the stream, while an (opcode, metadata ID) position is validated by comparing per-opcode counts, which prepare needs anyway. Dense records also make seeding one walk beside the metadata with no lookup, which matters for the installation bound. A call-link record is two bytes, so density costs little even for sites the producer never reached, and the group table lists only opcodes present in the body, which keeps a small body's section near 40 bytes of overhead instead of 128.

## A CB can have no metadata table

The first design walked metadata with `MetadataTable::forEach` in sizing, capture, A8, S2, seeding and the snapshot, assuming every CB has a table. `UnlinkedMetadataTable::link` returns null unless `addEntry` or `addValueProfile` ran, and many opcodes carry no metadata (`enter`, `ret`, `mov`, `in_by_id`, `del_by_id`, `del_by_val`, `has_private_name`, `has_private_brand`), so a hot body such as `function has(o) { return "x" in o; }` gets a null `CodeBlock::m_metadata` while still having a property IC. `MetadataTable::forEach` reads the offset table through `this`, and every native walker tests the table first (`CodeBlock::forEachLLIntOrBaselineCallLinkInfo`, `CodeBlock::reconcileLLIntInlineCachesAtGCEnd`).

Every walk now goes through the guarded walkers of `ICSites.h`, so a walk added later cannot skip the test. T12 and T3 each include a body without a table, one of them with a property IC, which exercises the property-IC path while the call-link path is empty.

## Records hold producer facts

The first sketch stored consumer values: `repatchCount` already rewound, a "given up" bit, no `countdown`. That makes the format encode policy, and THREAD Verification's rule that restored history must equal its capture record would then compare live state with a value the producer never had. Storing the raw learning group and the facts about cases and folds keeps the record a faithful observation, puts THREAD Caches' transformations in one pure function, and lets T3 check that function against an independent JS encoding of the same tables. It costs one byte per IC more than the transformed form.

A pure derivation also made the round trip checkable. A ConsumerProducer recapture once lost a restored fold, because restore wrote a fact that capture never read. The recapture functions give the record that a capture of the restored state yields, and deriving it again must give back the same consumer state (I5). T7 checks this for every record, and the twin check captures every import right after attach and compares, so every consumer test run verifies it and catches any field that restore writes and capture does not read.

## Checks run only under strict and copy no native table

At first the structural checks on the section always ran, since they verify received material and a failure would otherwise mean reading or seeding out of bounds, and only the checks of assumptions (native invariants among a record's facts, molds as baseline emits them, a pristine newborn CB) waited for strict. THREAD Session then made normal mode check only the artifact's integrity, which the integrator does, and trust the rest, because an artifact that carries machine code must be as trusted as the binary that runs it. So every check of this lane runs only under strict: A1 to A8, S1 and S2 in prepare, A1 and A2 when scoring reads a saved summary, and C1 with the two checks on the integrator's call in capture. Debug builds assert A1 to A6, the capture checks, and the A7 and A8 counts inside seeding and attach; S1, S2 and A7's per-mold pairing have no debug assertion. Every check of prepare runs before anything is written to the CB, because nothing can be checked after native setup without leaving a half-installed CB; in test builds the twin check verifies the state after setup instead.

The checks also stopped copying native decision tables. Capture once checked records against copies of the engine's slow-operation table per access type and of `tryFoldToMegamorphic`'s arms, a mold check required a folded site's access type to fold, and A5 also checked a recorded slow-operation kind. No restore step needs any of them. A recorded `Megamorphic` kind repeated `megamorphicCaseListed` ([below](#what-a-property-ic-record-keeps-about-cases-and-folds)), and `tryFoldToMegamorphic` returns null for an access type without an arm, so the fold check protected no restored state. Worse, a copy that missed an arm WebKit added would have made sites the derivation restores correctly a recording fault or invalid material. The record now holds `holdsGaveUp` in place of the operation kind, E3 maps each access type to its `*GaveUp` operation only, and an operation the lane does not know restores as a reset leaves the IC, in both modes. For the same reason no check bounds `caseCount` by the option's limit: no restore step reads the bound.

## What a property-IC record keeps about cases and folds

A record keeps four facts about a site's cases and folds apart (`caseCount`, `megamorphicCaseListed`, the fold bit `canBeMegamorphic` and `holdsGaveUp`), because the engine produces every combination that matters: a folded get with its `*Megamorphic` operation, a folded `instanceof` with its `*GaveUp` operation, a get that folded and then gave up (no case, `*GaveUp`, `m_cacheType` still `Stub`), and a site that gave up on its eighth case (eight cases, `*GaveUp`).

The record first held no fold bit, since a fold showed as a listed megamorphic case. Attach restores a fold only in `canBeMegamorphic`, though, so a ConsumerProducer whose `delta` recaptured an imported body before a folded site's first visit wrote the site as unfolded, and the richer recapture replaced the saved body: one generation lost the fold. On a baseline IC the bit can mean only a fold an import restored, because its only writers copy a mold's bit, nothing sets a baseline mold's bit, `reset` leaves it alone and `tryFoldToMegamorphic` is its only reader. Capture records it without ambiguity, under the native field's name, since the record holds producer facts and the fact is the field.

The record also first held a slow-operation kind (`Optimize`, `Megamorphic` or `GaveUp`) beside its fold bits. Only the `PromoteToMegamorphic` arms of `repatchGetBy` and its siblings install a `*Megamorphic` operation, and every path that removes the megamorphic case also replaces the operation, so that kind repeated `megamorphicCaseListed`, and the two fields became `stateBits`, with `holdsGaveUp` the one operation fact capture keeps.

## The summary counts property ICs only

THREAD gives the lane the count of IC sites with cases for the tie-break. Counting linked call sites as well was considered and rejected: the LLInt already links calls, so the capture at the end of `BaselineJITPlan::finalize` would score warm on call links while its property ICs are all cold, and the tie-break would stop telling a warm `delta` capture from the first one. Cases are `AccessCase`s, so the count covers property ICs only.

## The polymorphic bit, call sites included

A site the producer saw with several shapes comes back with no case, and a non-looping body whose captured counter progress had crossed reaches its first DFG compile early. That compile speculates on the shapes one invocation cached, then takes `BadCache` exits whose sites enter the exit profile and slow every later compile there, and those sites can accumulate through ConsumerProducer recaptures. At first THREAD stated no contract for this, so the CB lane kept a uniform counter floor, this lane exported nothing, and the bench was to measure the gap. THREAD Restoration then had this lane hand the CB lane a bit that withholds counter progress when a property IC's record lists two or more cases, megamorphic folds aside, and left call sites to this SPEC.

Call sites set the bit too, because the code shows they meet the same exits. A `Polymorphic` site comes back seen once without its stub, the consumer's first call links it monomorphically, `CallLinkStatus` answers the one `lastSeenCallee`, and a DFG compile at the floor inlines it behind a `CheckIsConstant` that exits with `BadConstantValue` when another callee comes, where the producer's DFG made a generic call. A stub with one slot, a site with `clearedByGC`, a virtual site and a monomorphic one stay out. The bit reads the captured record, as THREAD's rule says, so a recapture taken before a polymorphic site has cached two cases again drops it; B6 measures that case.

A saved body must keep the bit for THREAD Capture's tie-break, which ranks a withheld counter above one that travels just before it compares progress, and zero progress alone cannot say why it is zero. So the CB lane marks the counter withheld in its summary as well as in its state, and R-INT-3 scores the withheld counter on both sides.

## A site comes back given up only when it lists no case

The first derivation restored as given up every site that held a `*GaveUp` operation beside no megamorphic case. The folded `instanceof` was a special case, since there the native fold itself installs `operationInstanceOfGaveUp`, and restoring it given up would cost the inline prototype walk for good. The rule seemed safe for a site that gave up on its eighth case, on the belief that the producer's site would read `TakesSlowPath` after its next visit anyway. It does not: a visit with one of the cached shapes runs a handler and never reaches the `*GaveUp` operation, so `tookSlowPath` stays clear and the producer's DFG reads the cases as variants. Restored given up, every one of those shapes would call C++ for the CB's whole life, and the forced `tookSlowPath` would make the DFG's status `TakesSlowPath`. Such sites are common: a `length` access over several receiver kinds, a by-value get mixing indexed and named cases, any direct, private-name or delete site with eight shapes.

One native fact settled the rule. `PropertyInlineCache::reset` sends a site that holds cases back to its `*Optimize` operation, so natively a give-up lasts only as long as the cases beside it, while a give-up that holds no case is permanent, since nothing can reset it. JITCache drops every site's cases, so the give-up that survives that drop natively is exactly the one with no case. Hence `givenUp` is `holdsGaveUp && caseCount == 0`. The folded `instanceof` needs no special case under it: it lists `InstanceOfMegamorphic`, comes back folded, and its first caching visit reinstalls `operationInstanceOfGaveUp`, the producer's state. THREAD Caches then adopted the same rule.

Given up and folded are disjoint, because `foldsAtFirstCase` excludes `givenUp`. A site whose consumer replayed a restored fold and then gave up could carry both, but the fold bit would be inert there (a `*GaveUp` operation never caches, and nothing resets such an IC), and carrying it would make the restored states overlap and the recaptured record differ from its source for no behavioral reason.

## Every IC at a zero wait counter, every call site seen once

THREAD Caches brings each property IC back with its wait counter at zero and each call site seen once. A narrower reading would restore the captured `countdown` or seen bit for sites the producer never reached. Both rules are general, though, and their purpose, the consumer's own case at the first visit and the first call linking natively, applies equally to unreached sites; the narrow reading would make those sites one trip slower for no observable gain and would need the record to keep `countdown`. So both rules apply to every site, and the record still keeps the captured seen bit, for the round trip and for later tiers.

## Prepare reads the prepared `BaselineJITCode`

Prepare first read the molds from a `const BaselineJITCode&` that the Image lane did not expose before `commit`. Its prepared image offered only a mold count and `commit`, and `commit` adds to the VM's code-size statistic and writes the JIT dump, so calling it first would leave those effects behind a later ICs failure. A span of molds through a `PreparedImage::molds()` accessor was proposed. The Image lane instead added `PreparedImage::code()`, valid until `commit` or destruction and the same object `commit` returns. The whole object serves better than a span: `commit` hands that object to setup, so A7 pairs the records with exactly the molds setup turns into ICs, and the integrator cannot pass molds from anywhere else.

## E1 stores `new.target` as the LLInt does

The LLInt stores into `m_cachedCallee` without a write barrier, unlike `slow_path_create_this`, which uses `WriteBarrier::set` for its own cached callee. A weak cache in an old CB that an eden collection does not revisit can keep a pointer to a cell that died in that eden, and the DFG reads the cache with `unvalidatedGet` and freezes it. That hazard is native and already present for every CB that ran in the LLInt. THREAD asks for the template to store `new.target` as the LLInt does, so E1 matches the LLInt exactly, the missing barrier and the varargs form's cell check included. CBs born in baseline now share the hazard with LLInt CBs, and closing it would take both tiers at once, outside this lane's mandate.

E1 first seemed to matter only for CBs born in baseline. The template stores back the value it loaded, so a CB that tiered up from the LLInt also froze the LLInt's last answer, and E1 changes every CB while it runs baseline code. That is why T2 has a tier-up script and B5 a constructor that sees a second `new.target` after tier-up.

E1 was also once conditional on whether the Image lane edited `JIT::compileOpCall` for recording. That lane reaches the function only through `CallLinkInfo::emitFastPath` and leaves the `super_construct` block alone, so this lane applies E1 itself.

## One megamorphic predicate, one give-up table

Capture must decide whether a listed case is megamorphic. Copying the megamorphic case types into the lane would let the copy drift when WebKit adds one, so E4 moves the engine's file-static predicate into `AccessCase`, and the fold and the capture share it. E3 sits in Repatch.cpp for the same reason: the operations per access type are already chosen there, and its switch has no `default`, so a new access type breaks the build until it is classified. E3 once mapped every slow operation of an access type, with a copy of the fold arms beside it; only the `*GaveUp` mapping remains. It still names inline the operation five native give-up sites pass. A disagreement with the engine would cost only speed and no strict check reads it, so no assertion guards it; T3 checks the entries of the access types it drives.

## A capture's consistency comes from the pause

Capture and attach take `CodeBlock::m_lock` because every native reader of IC state on another thread takes it, and seeding takes none, since native linking writes call-link fields without it and the newborn CB is unreachable. The first account also credited the lock with a capture's consistency, which was wrong: the learning fields, `tookSlowPath` and `m_slowOperation` are written outside it, by `considerRepatchingCacheImpl`, the `*GaveUp` operations and `repatchSlowPathCall`. Consistency comes from where the writers run, the VM's thread while JS runs and the collector's stopped-world phases, neither of which overlaps a capture. A polymorphic call site's stub obeys the same argument: the VM's thread replaces or drops it, a collection's finalization unlinks it and only a collection frees it, where an earlier L4 had a collection doing all three.

`delta` may call capture while its walk holds `CodeBlockSet::m_lock`, and native code never takes that lock while holding a `CodeBlock::m_lock`. The argument first rested on `CodeBlockSet::remove`, which has no caller. It now rests on `CodeBlockSet::add` running only in the `CodeBlock` constructors, on dead CBs leaving the set at the End phase without the lock, and on the set's other takers (`ConservativeRoots::add`, `VMTraps`, `SamplingProfiler`, `VMInspector`) holding no `CodeBlock::m_lock` when they take it.

## The IC limit options are fixed

THREAD names the cool-down pair as fixed. `useLLIntICs` and `forceICFailure` were added as fixed because each changes what a carried state means: a `Virtual` site or a give-up would record the option instead of the site, and `forceICFailure` also sends `linkPolymorphicCall` virtual. The case and variant limits were first left free, on the view that they change only how the consumer caches next. A carried fold or `Virtual` mode records the limit the producer met, though, as a give-up records `forceICFailure`, so `maxAccessVariantListSize`, `thresholdForUndesiredMegamorphicAccessVariantListSize` and `maxPolymorphicCallVariantListSize` became fixed at 8, 0.5 and 8; Bun sets none of them, so none is must-match. The top-tier and WebAssembly call limits stay free, since only callers this version does not carry read them. The fixed list size also bounds `caseCount` at 8, which fits its byte without saturation, and keeps `listedAccessCases` inside its `Vector`'s inline capacity of 16, so capture allocates no memory under any configuration `start` accepts.

## ICs runs keep concurrent JIT off

This lane's twin check never skips itself, since it reads only the section and a CB no other thread can reach before `installCode`, in either JIT mode. The Image lane's twin check is exact only when the importing process and every process whose captures it imports compile without workers, and THREAD Verification fails a run on a skip exactly then. The `ics/` runs first kept concurrent JIT at its default, on, so the image check skipped every import there. The harness now turns concurrent JIT off in every directory unless a run sets it, so the image check compares the `ics/` imports and a skip fails the run. No ICs test needs worker compilation, and T9 needs it off: the executable-allocation fuzzer counts every thread's allocations, so a fuzz index names one allocation only when no worker compiles.

## The lane owns its test bindings' shapes

The first draft named a shell binding and two hooks without signatures, JS shapes or a handoff from producer to consumer, so the binding's author and the test author would have invented different shapes. The JS shape belongs to the lane: `functionSnapshotBaselineICs` builds the object and the integrator only registers it, R-INT-7 states the other shell functions and the runner as requirements, and `resources/ics.js` isolates the scripts from those names, so a different choice by the integrator changes one file. `jitcacheDelta()` exists only in test builds: THREAD Session lets the host decide when to call `delta`, and in those builds the jsc shell is that host, which keeps `delta` an entry point of C++ only.

A hook that ran prepare on an interpreted CB was dropped. It needed the body's prepared image and pending import, and what it tested, that an import never reaches a CB that ran in the LLInt, follows from where the integrator places the install points; S2 re-checks it under strict. T8 tests what the lane owns instead: seeds land only in the CB that installs the import. The checks that first needed a newborn CB and a prepared image became functions over plain data (molds as values, counts as an array), which also gave prepare one function per check, composed in a fixed order. The checks that need live objects use the newborn-CB recipe of the SPEC's live tests, so R-INT-9 needs no lane-specific hook.

The snapshot copies a weakly held cell, a `super_construct` cache's callee, so the shell function builds its result inside the `DeferGC` scope that took the snapshot; otherwise a collection could free the cell while the result was being allocated.
## Which capture the consumer imports in the tests

Every body under test runs under `noDFG`, which stays: without it a body tiers up and stops being eligible, the thresholds that would delay that are fixed options, and the capability class is a baked fact that must agree between runs. Under `noDFG`, a body whose producer state lay only in call links or in ICs without a case could tie with its finalize capture, and the counter, moved only by `op_enter`'s slow path, would decide; T3, T4 and T5 would fail or flake. Two fixes were offered. The SPEC takes the anchor: each checked body keeps a property IC that lists a case when it is passed to `delta`, which `resources/ics.js` checks, so a script that breaks the convention fails in its producer run every time. The other fix, comparing the consumer with whatever record the import used, was not taken: the twin check already makes that comparison, and when the import used the cold finalize capture, T3 would pass while testing nothing about the states it drives.

The argument that richness never shrinks needed two more pieces. `noInline` is one: a `noDFG` body is still an inlining candidate, and a caller's DFG compile, `toBaseline`'s own loop included, would bypass its ICs and drain its profiles on a compiler thread. `--useConcurrentGC=false` in producing runs is the other: the baseline plan drains before its safepoint without `CodeBlock::m_lock`, and a concurrent marker's first-visit drain could overlap it and land a stale merge after the finalize capture read a bit the plan had just added.

T10 first checked only that F's folded sites carry `canBeMegamorphic` in the Consumer, which holds whichever of F's captures the Consumer imports, since I5 makes the recapture of an untouched site derive the same state. F gained a witness site that only the ConsumerProducer reaches, with a number as its base, so `sawNonCell` in the Consumer shows that F's recapture is the body it imported. G, whose recapture must win on the IC count, needs a recapture that is not richer; `noDFG` keeps its baseline code from writing value or argument profiles, so only its ICs change.

## Task 6 lands before the integrator's glue

The integrator's install glue calls the twin check in twins builds, so a task that bundled `ICTwins` with a runner sequence would wait for that glue while the glue waited for it. Task 6 therefore holds no runner sequence: T2 runs in task 7, and task 6 lands with T11, which reads the snapshot, and T13, which tests the twin API on a live VM.

## No task owns the bench obligations

The list first ended with task 9, "B1 to B6 inside the integrator's bench loop", which owned no file. The integrator's events and IB10 already give B1 to B4 and B6, and a lane task with nothing to write left its implementer to invent bench code the glue owns, as the Image lane's task 13 did. Giving each lane accessors and one integrator task the reader was weighed and left for the bench loop to ask for, since HARNESS treats benches as alerts and no failing case needs it. The obligations stay in section 12, and THREAD Execution's bench loop takes them after the implementation.
