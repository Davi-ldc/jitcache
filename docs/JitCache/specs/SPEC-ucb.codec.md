# SPEC-ucb.codec: the core codec

Part of [SPEC-ucb.md](SPEC-ucb.md), which indexes it; the main file's facts (F1 to F30) and invariants apply here. This file specifies the encoding and decoding of a UCB core: the bytecode cache's codec in `runtime/CachedTypes.cpp` run in a JITCache mode, and the exact-layout transport it needs from `WTF::InlineMap`. Section 8 says how the mode is applied to the codec of webkitbun `0c06faad`. [SPEC-ucb-history.md](SPEC-ucb-history.md) records why the decisions that are not obvious were taken; it binds nothing.

## 1. The core

The core is everything generation produces for one body: the instruction stream, metadata layout, constants (symbol tables, template descriptors, regular expressions, big integers, immutable butterflies, strings), identifiers, jump tables, exception handlers, expression info, out-of-line jump targets (in the UCB's rare data), the global parse fields and declarations, a module's heap-allocated declaration slots, and each child UFE as a descriptor. The bytecode cache already encodes and decodes all of it, but its native form is unsuitable as it stands (F7, F9, F10, F21, F26, F28); the JITCache mode below closes each gap ([history](SPEC-ucb-history.md#the-bytecode-caches-codec-in-a-jitcache-mode)). The mode never changes what the native bytecode cache writes or reads, except for the record size of E3. The JITCache encoder only ever encodes a UCB the engine generated or the JITCache decode imported, and a UFE of one of those, since a UCB or UFE a native decode made gets no key (main file, section 7.2.5): none borrows its instruction stream or leaves a part in a payload (main file, F28).

## 2. Entry points

In `runtime/CachedTypes.h`:

```cpp
enum class UnlinkedCodeBlockCoreKind : uint8_t { Program = 0, Module = 1, Eval = 2, Function = 3 };   // the identity section's core kind

class CoreEncodingBudget {
public:
    virtual ~CoreEncodingBudget() = default;
    [[nodiscard]] virtual bool charge(size_t) = 0;   // before the encoder allocates that many bytes
    virtual void release(size_t) = 0;                // after it frees them
};

enum class CoreEncodeFailure : uint8_t { None, BudgetRefused };
enum class CoreDecodeFailure : uint8_t { None, Malformed, KindMismatch, UnresolvedSymbol, InconsistentMapLayout };

// `holder`, wherever an entry point takes one: for a function core, the UFE whose slot holds the UCB, or will hold it once
// decoded. Its TDZ chain is the start chain: a chain of the core equal to it is written as one start record, and that
// record decodes to it. Null for every other core kind.

// Encodes one UCB and its child descriptors, without child bodies. VM thread; allocates no cell. With a budget, on
// success exactly result->size() bytes stay charged and the caller releases them.
JS_EXPORT_PRIVATE RefPtr<CachedBytecode> encodeUnlinkedCodeBlockCore(VM&, const UnlinkedCodeBlock&, const UnlinkedFunctionExecutable* holder, CoreEncodingBudget*, CoreEncodeFailure&);

// Decodes a core. VM thread, API lock held; runs under DeferGC; allocates cells. The payload must start 8-byte aligned.
// `validate` makes the decoder check the core's structure as it goes; an import passes its session's strict flag.
// `source` is the request's source, whose provider the UCB is bound to and whose start offset places the children's
// sources in the provider's text.
JS_EXPORT_PRIVATE UnlinkedCodeBlock* decodeUnlinkedCodeBlockCore(VM&, Ref<CachedBytecode>, const SourceCode& source, UnlinkedCodeBlockCoreKind, const UnlinkedFunctionExecutable* holder, bool validate, CoreDecodeFailure&);

// The descriptor of one UFE: the record a JITCacheCore encoder writes for it as a child of its parent's core, alone, with
// the strings and records it points to, and with the UFE's own TDZ chain as the start chain, so that the chain is one start
// record. VM thread; allocates no cell. The budget behaves as for the core; null on refusal.
JS_EXPORT_PRIVATE RefPtr<CachedBytecode> encodeUnlinkedFunctionExecutableDescriptor(VM&, const UnlinkedFunctionExecutable&, CoreEncodingBudget*, CoreEncodeFailure&);

// The payload each encoder above would return, passed to `sink` page by page in payload order and never assembled.
// The budget behaves as for the encoders, every charge is released before the call returns, and on a refusal the
// sink sees nothing and the result is BudgetRefused. VM thread; allocates no cell.
JS_EXPORT_PRIVATE CoreEncodeFailure forEachUnlinkedCodeBlockCoreChunk(VM&, const UnlinkedCodeBlock&, const UnlinkedFunctionExecutable* holder, CoreEncodingBudget*, const ScopedLambda<void(std::span<const uint8_t>)>& sink);
JS_EXPORT_PRIVATE CoreEncodeFailure forEachUnlinkedFunctionExecutableDescriptorChunk(VM&, const UnlinkedFunctionExecutable&, CoreEncodingBudget*, const ScopedLambda<void(std::span<const uint8_t>)>& sink);

// The digest of a TDZ chain, which a holder digest takes in place of the chain's names: 32 zero bytes for a null chain.
// Each environment on the chain is digested at most once while it lives and keeps its digest; `environmentsDigested`
// gains one for each environment this call digested first. A budget, when given, is charged for each such environment's
// sort buffer while the buffer lives, and for the list of the chain's links while it lives when the chain has more links
// than the 32 the list keeps inline, charged before the list moves to the heap. Empty on a refusal; digests already kept
// stay. VM thread; allocates no cell.
JS_EXPORT_PRIVATE std::optional<std::array<uint8_t, 32>> tdzChainDigest(const TDZEnvironmentLink*, CoreEncodingBudget*, unsigned& environmentsDigested);
```

The start chain is E12's, `validate` turns on E13's validating decode, which the main file's import runs with strict on (main file, section 7.3.1 step 6), the chunk entry points are E11's, and the budget is charged as E7 says. The exported header gains no `jitcache/` include: it already includes `parser/VariableEnvironment.h`, which declares `TDZEnvironmentLink`, and the digest is a `std::array`. `tdzChainDigest` computes the chain digest of the main file's section 3.4. It lives in `runtime/CachedTypes.cpp`, whose `CachedTDZEnvironmentLink` and `CachedCompactTDZEnvironment` are already friends of `TDZEnvironmentLink` and `CompactTDZEnvironment`, and hashes with the main file's `SHA256`.

The descriptor is built like a payload: a 16-byte header holding magic `0x44424355` at offset 0, `rootOffset` at offset 8 (the offset of its `CachedFunctionExecutable` record from the descriptor's start) and zero bytes at 4 to 7 and 12 to 15, then `CachedFunctionExecutable::encode` into a JITCacheCore `Encoder` whose start chain is the UFE's own, then `release`, or the chunks of E11. E1, E2 and E12 make it independent of the UFE's slots, of the fields its own parse sets and of its TDZ chain, which the holder digest takes through `tdzChainDigest` instead, and section 6's properties make it deterministic, so the main file hashes it with that chain digest as the UFE's holder digest (main file, section 3.4).

## 3. Payload

| offset | size | field |
|---|---|---|
| 0 | 4 | magic `0x43424355` |
| 4 | 1 | core kind |
| 5 | 3 | 0 |
| 8 | 4 | `rootOffset`: offset of the root record (`CachedProgramCodeBlock`, `CachedModuleCodeBlock`, `CachedEvalCodeBlock` or `CachedFunctionCodeBlock`) from the payload start |
| 12 | 4 | 0 |
| 16 | | the encoder's allocations |

Encoding: construct the `Encoder` as section 4 says, with the holder's TDZ chain as its start chain for a function core, allocate the 16-byte header first, call `CachedCodeBlock<T>::create(encoder, ucb)` for the UCB's class (the call `encodeFunctionCodeBlock` makes for functions), store `encoder.offsetOf(record)` in `rootOffset`, run `encodeDeferred`, then `release`.

Decoding: `Malformed` when the payload is shorter than 16 bytes, its start is not 8-byte aligned, the magic or a zero field is wrong, or `rootOffset` is misaligned for the record or the record does not lie inside the payload; `KindMismatch` when the stored kind differs from the argument. Then create the `Decoder` with the provider, purpose `JITCacheCore`, the `validate` flag and, for a function core, the holder's TDZ chain as its start chain, and under `DeferGC` call the root record's `decode`. The native decode checks nothing of its own about the records it reads (F8), so a decoder failure comes only from the rules below (E3, E4, E12, E13); one recorded during the decode is returned and the UCB discarded.

## 4. The JITCache mode

`Encoder` gains `enum class Purpose : uint8_t { BytecodeCache, JITCacheCore }`, a `CoreEncodingBudget*` and a start chain (`const TDZEnvironmentLink*`, E12), constructor arguments defaulting to the native behaviour. `Decoder::create` gains the same `Purpose` (defaulting to `BytecodeCache`), a start chain (`RefPtr<TDZEnvironmentLink>`, defaulting to none) and a `validate` flag (defaulting to false, and allowed only with `JITCacheCore`), after its native `RecoverableCode`. `Decoder` gains `Purpose purpose() const`, `bool isFallible() const` (true for `JITCacheCore`), `bool validates() const`, `void noteFailure(CoreDecodeFailure)` (keeps the first), `CoreDecodeFailure failure() const`, `TDZEnvironmentLink* startChain() const`, the start chain `create` received or null, which E12's decode returns for the start record, and `std::span<const uint8_t> payloadSpan() const`, the span `m_payload` and `m_payloadSize` give, which E13 checks offsets against. In `JITCacheCore` the encoder is built with no external string table and `BytecodeCacheUpdatable::No`. No record carries a checksum, since the bytecode cache writes none (F8); the container's checksum covers the section (R-INT-3 of the main file). Strings are numbered (`NumberStrings::Yes`) within the payload only.

- E1. Child bodies omitted, since each child is a body of its own (THREAD Storage). In `JITCacheCore`, `CachedFunctionExecutable::headerFor` sets neither `HasCallSlot` nor `HasConstructSlot`, whatever the UFE's slots hold, and `CachedFunctionExecutable::encode` calls neither `Encoder::deferBody` nor `Encoder::addLeafExecutable`, so the decoded UFE has `m_isCached` false and empty slots. Neither function reads the UFE's slots in `JITCacheCore`.
- E2. Children's parse fields unparsed. In `JITCacheCore`, `CachedFunctionExecutable::packScalars` writes 0 for `m_features` in the hot scalars and `headerFor` omits `HasCapturedVariables`; `m_lexicallyScopedFeatures` is written as is: generation sets it at creation from the parent's parse, which has already read the child's directive prologue, and the child's own parse records the same value (twin T5 checks this). A child UFE thus decodes as the parent's generation creates it, before its own body is parsed. `packScalars` and `packedTail` take the encoder's purpose, as `tailSize` already takes the encoder, so that the size computed for the allocation matches what is written.
- E3. Hashed map layouts preserved. `CachedInlineMap` gains `uint32_t m_hashedCapacity` and `CachedVector<uint32_t> m_slots`. `BytecodeCache` writes 0 and an empty vector, and decodes as today. `JITCacheCore`, for a map whose storage is hashed, writes the entries in bucket order (its iteration order), `m_hashedCapacity = map.hashedCapacity()`, and in `m_slots`, for each occupied bucket in index order, `(index << 1) | isDeleted`. Decoding with a nonzero capacity collects the decoded pairs and, when no slot has the deleted bit, calls `restoreHashedLayout` (section 5); a deleted bit or a false return records `InconsistentMapLayout` and leaves the map empty. A `VariableEnvironment` map never holds a deleted bucket, since `VariableEnvironment::remove` has no caller, and could not restore one: its key traits, `HashTraits<RefPtr<UniquedStringImpl>>`, make the deleted key `(T*)-1`, which its `PackedRefPtr` key cannot store. Re-adding the entries in bucket order does not reproduce a hashed layout in general, since a key's bucket depends on the order its colliding keys arrived in and on when the table grew, hence the checked restore ([history](SPEC-ucb-history.md#hashed-declaration-maps-keep-their-layout)). A map in inline storage is written in its order, which is its insertion order, and re-adding reproduces it. The record grows, so `static_assert(sizeof(...))` pins of `CachedInlineMap`, `CachedVariableEnvironment` and the global code-block records take the sizes the compiler computes; the native cache keeps no compatibility across builds. `GenericCacheEntry::cachedTypesFormatRevision` goes from 13 to 14, which the native cache folds into the version it stores, so a build that shares an embedder's cache version with another never reads that build's records as its own.
- E4. Symbols that do not resolve fail the decode instead of the process. In `CachedUniquedStringImplBase::decode`, when `BuiltinNames::lookUpWellKnownSymbol` or `lookUpPrivateName` returns null and the decoder is fallible, call `noteFailure(UnresolvedSymbol)` and return `SymbolImpl::createNullSymbol()`, which is distinct per call so no table built from it has duplicate keys; a non-fallible decoder keeps the `RELEASE_ASSERT`. The UCB under construction is discarded.
- E5. UFEs decoded as generated. The decoding constructor of `UnlinkedFunctionExecutable` initializes `m_isGeneratedFromCache` to `decoder.purpose() != Decoder::Purpose::JITCacheCore`, so an imported child keeps weak UCB edges where a generated one would (F9).
- E6. Nothing borrowed or deferred. In `JITCacheCore`, `Decoder::create` leaves `canBorrowPayload()` and `canDeferIntoPayload()` false whatever the payload's ownership, `decodeUnlinkedCodeBlockCore` creates the decoder with `Decoder::RecoverableCode::No`, so nothing registers with `VM::persistentBytecodePayloads()`, and `stringsToPrefetch()` returns null, so the decode never reads the embedder's string table, which a core never names (section 4). The core's `CachedBytecode` wraps the section span with a destructor that drops the reference to the `ValidatedBody`, and a payload with a destructor counts as owned, so without this rule the native decoder would defer into the pack's mapping (F28). The decode therefore copies strings, the instruction stream, the metadata steps, the expression info and the line starts out of the payload, and decodes every UFE member, every symbol table entry and every module function declaration at once. Nothing decoded points into the pack's mapping or keeps the `Decoder`, and because of E1 no UFE holds a cached slot, so the reference to the body ends when the decode returns. A member decoded later from the mapping would escape the validating decode (E13) and could fail after the import was published, where it can no longer be abandoned ([history](SPEC-ucb-history.md#payload-parts-the-native-decode-leaves-for-later)).
- E7. Charges. With a budget, the encoder charges everything it allocates for an encode (THREAD Session). The module record writes its declaration offsets straight from the slots object, without the vector copy upstream's conditional expression makes, so that copy is never allocated and needs no charge; the bytes are the same. `Encoder::allocateNewPage` calls `budget->charge(size)` before allocating a page. `Encoder` gains `chargeGrowth(size_t)` and `releaseGrowth(size_t)`, no-ops without a budget, which charge the rest as it grows:
  - the encoder's tables: right after an insertion into `m_ptrToOffsetMap`, `m_stringsByContents`, `m_arraysByHash` or `m_sharedPrivateNameEnvironments`, the change in the container's `capacity()` times its entry size; and at each `deferBody` or `deferCold`, the closure it stores, plus the deque's new buffer whenever its entry count reaches its capacity, which `Deque::expandCapacity` takes from 16 entries and doubles, so the encoder follows it by counting entries (in `JITCacheCore` each code block's record defers one cold closure, its expression info, nothing defers a body, E1, and nothing defers line starts, E15);
  - the scratch an encode builds and frees within one record (the `VarintWriter` buffers, among them the one `CachedCodeBlock::create` refills inside `Encoder::mallocPlaced`, the `EncodingOrder::sort` vectors, `CachedUniquedStringImplBase::Shape`'s 8-bit copies, the `packedTail` vectors and the vector `CachedExpressionInfo::pack` returns): its capacity once allocated, released when it is freed;
  - the encode's other allocations, as they grow: its page list (`Encoder::m_pages`), the out-of-line candidate lists of `m_arraysByHash`, the metadata steps `CachedMetadataSteps::compute` builds and the slot list of a hashed declaration map. A deferred closure stays charged until the encode ends.

  A refusal sets a sticky refused flag and the allocation happens anyway, since the encoder cannot unwind inside a record. The encode then runs to its end: every later charge is refused (THREAD Failures), and each of those allocations happens too. After the first refusal the encoder calls the budget no more, so a budget that would accept a later charge holds none: every later charge counts as refused without a call, and `releaseGrowth` releases nothing. The owner releases `Encoder::chargedBytes()`, what the budget accepted before the refusal, once the encoder is gone. `encodeUnlinkedCodeBlockCore` then charges the payload size before `release`, refuses to release when anything was refused, frees the encoder, releases every charge the encoder made, and returns either the payload with its size charged or null with `BudgetRefused` and nothing charged. A refused charge therefore overshoots the limit by the rest of that one encode: its later pages, each up to 64 MiB as E10 doubles them, and its later growth of tables and scratch (main file, I16 and B6) ([history](SPEC-ucb-history.md#charges-inside-the-encoder)).
- E8. String constant registers decode as atoms. Generation makes every string constant register an atom, while the native decoder leaves most long ones plain and their atom-ness depends on its decode history (main file, F19). The baseline's `stricteq`, `nstricteq`, `jstricteq` and `jnstricteq` templates emit their constant-string fast path only for an atom (`tryGetAtomStringConstant` in `jit/JITOpcodes.cpp`). In `JITCacheCore`, `CachedJSValuePool::decode` takes whether it decodes the code block's own constant registers, which the code block's record says and `CachedImmutableButterfly` does not, and decodes each such `String` as the atom `CachedUniquedStringImplBase::decode` returns, wrapped by `jsString`, which gives the VM's own empty and one-character strings (main file, F27); an inline string already decodes as one. The pool's other decode, `decodeWithStringPrefetch` over the embedder's string table, never runs in `JITCacheCore`, whose decoder has no table to prefetch from (E6). The encoder writes `String` by content in every purpose, so a core's bytes record no atom-ness, and none needs to travel: every string constant register the encoder meets is an atom, since it encodes only generated or imported UCBs (section 1), and an imported UCB's are all atoms, as generation makes them. Values inside constant cells keep their native decode, so immutable butterfly elements stay on `decodePlainString` and every butterfly gets the plain structure `JSCellButterfly::create` gives. `CachedImmutableButterfly` writes the indexing mode, length and values, never the structure; the butterflies generation builds from atom strings travel in the identity section's butterfly map, and an import rebuilds them in that form after the decode (main file, F23 and section 7.3.1, step 8). `BytecodeCache` keeps decoding `String` as today.
- E9. `RegExp` constants by pattern and flags. In `JITCacheCore`, `CachedRegExp::encode` writes the pattern and the flags, with `m_parsed` 0, `m_numSubpatterns` 0, an empty atom and `SpecificPattern::None`, so decoding always takes `RegExp::create`, the call generation makes (`RegExpNode::emitBytecode`). The atom and specific pattern are compilation state of a cell the whole VM shares through `RegExpCache::lookupOrCreate`, which `RegExp::deleteCode` clears on every live `RegExp` (main file, F22), so a record that wrote them would depend on whether code deletion or a recompile ran since generation ([history](SPEC-ucb-history.md#regexp-constants-by-pattern-and-flags)). `BytecodeCache` keeps its record, whose parsed fields spare the native decode a parse.
- E10. Page policy. `Encoder::allocateNewPage` asks for `encoderMinPageSize << min(pageCount, 14)` bytes in `JITCacheCore`, so the first page is 4 KiB and each later one doubles, and keeps `encoderMinPageSize << min(pageCount + 4, 14)` in `BytecodeCache`, whose first page is 64 KiB. Every page is zeroed (`Page` allocates with `zeroedMalloc`, because alignment gaps end up in the payload). A page boundary moves padding, since `allocateNewPage` aligns the current page's end before opening the next, so the policy is part of the payload format; every `JITCacheCore` encoder uses it, and equal UCBs still encode to equal bytes (section 6).
- E11. Pages hashed in place. `Encoder` gains `forEachPage(const ScopedLambda<void(std::span<const uint8_t>)>&)`, which aligns the current page's end as `release` does and passes each page's used span in order. `release` copies exactly those spans, in that order, into one buffer, so their concatenation is the payload. The two chunk entry points of section 2 run their encode as the releasing ones do up to `release` (the header, the root record, `rootOffset`, `encodeDeferred`), check E7's refusal, then call `forEachPage` in place of `release`, so no payload-sized buffer is allocated or copied. The main file feeds the chunks to SHA-256.
- E12. TDZ chains relative to the holder's, so that no function core or descriptor repeats the enclosing scopes' names (main file, F26). In `JITCacheCore` the `Encoder` and the `Decoder` take a start chain: the holder's chain for a function core (section 2), the UFE's own chain for a descriptor, and none otherwise. The two places that write a `CachedRefPtr<CachedTDZEnvironmentLink>`, `CachedFunctionExecutable::encode` for a UFE's chain (`m_members.live().parentScopeTDZVariables`) and `CachedTDZEnvironmentLink::encode` for a link's parent, go through one helper. When a start chain is set and the chain to write equals it, meaning as many links and, link by link, the same `CompactTDZEnvironment` object, which the VM's interning makes equality of content, the helper encodes the start chain's own pointer in its place ([history](SPEC-ucb-history.md#holder-digests-and-tdz-chains)). Every such chain then shares one record, and `CachedTDZEnvironmentLink::encode` writes that record as the start record: an empty handle and an empty parent. No native link has an empty handle, since each holds an environment from `CompactTDZEnvironmentMap::get`. Any other chain is written as today, link by link, until what remains equals the start chain. The comparison reads only link and environment pointers, at most one pair per link of the shorter chain. On decode, `CachedTDZEnvironmentLink::decode` in `JITCacheCore` returns the decoder's start chain for the start record, with one reference added for the decoder's finalizer to release, as it releases one for each link it allocates. A start record decoded without a start chain, or a record whose handle is empty and whose parent is not, records `Malformed` and decodes as null. A decoded function core's children therefore hold their own links over the requesting UFE's chain object, as generation leaves them, and a core holds only the links its own generation created. `BytecodeCache` has no start chain, so it never writes a start record, and its decode is unchanged.
- E13. The validating decode. `decodeUnlinkedCodeBlockCore` sets `Decoder::validates()` from its `validate` argument, which the main file passes as strict. Without it, a decode checks what section 3, E3, E4 and E12 check, and trusts the rest of a core whose section the container's checksum covered (THREAD Session). With it, each read checks what it is about to read, and a failure calls `noteFailure(Malformed)` and decodes that record as the empty value of its type (a null pointer, an empty container or string, `jsUndefined()` for a constant). The decode then finishes without reading outside the payload, asserting or crashing, and `decodeUnlinkedCodeBlockCore` reports the failure and discards the UCB. The checks fall into six groups:
  - Placement. Every record that a decode reaches through an offset lies wholly inside `Decoder::payloadSpan()` and is aligned for its type. Every child slot of a code block, a function declaration or expression, names a record: the encoder fills every slot, so an empty one fails, as the region check of the codec before 0c06faad refused it, instead of leaving a null child for linking to dereference. In the same way every slot of a code block's identifier array, and of an eval record's variables and function hoisting candidates, names a string, since linking, property accesses and an eval's declarations hash each one, and every function declaration has a nonempty `name()`, which global code instantiates it by. A code block has one representation per constant, since `CodeBlock::setConstantRegisters` reads one for each, and at most as many binary and unary arithmetic profiles together as instruction bytes, since the decode allocates them and each belongs to one instruction. That covers `CachedPtr`, `CachedRefPtr`, `CachedOptional`, `CachedArray`, `CachedVector` and the maps and sets built on it, `CachedBitVector`, `CachedJSValuePoolRef`, a `Double` constant's eight bytes and a `CachedBigInt`'s digits. A record's size comes from its type and its count, computed with overflow checks. Every variable-length part is read through a reader whose limit is the payload's end (`BoundedVarintReader`, beside the unbounded `VarintReader` that the native decode keeps as upstream wrote it; the parse code both decodes share is a template over the reader), and an overrun fails: a string record's characters; a UFE record's slots and varint tail (`CachedFunctionExecutable::view`, which reads the hot and cold scalars), and its rare data's header, present members and class-source varints; a code block's varint tail (`CachedCodeBlock::readTail`), each array of its region (`Layout`'s steps, instructions, constants and their representations, identifiers and child slots, at `regionBegin + at`, with `recordOffsetInRegion` at most the record's own offset) and its extras; and an expression-info record's count, varint head and payload words, whose size `ExpressionInfo::payloadSizeInBytes` gives with overflow checks. A slot the decode needs filled must be filled: `CachedPtr::get` and `CachedOptional::decodeAsPtr` assert that natively. Each child slot's record is placed and aligned before it is read, because `CachedPtr` asserts alignment in debug builds. The decoder's offset cache (`Decoder::cachedPtrForOffset`) serves the records a decode reaches through `CachedPtr`, as natively, and also records the type each offset was decoded as and marks a record when its decode starts. A slot whose offset names a record already decoded as another type fails; `CachedStringImpl` and `CachedUniquedStringImpl` count as one type, since the encoder shares a string record between them by content. A slot that reaches a record whose decode has not returned fails as a loop. A slot of the same type shares the decoded object, as the native decode does, except for a record the encoder writes once per owner (a child's `CachedFunctionExecutable` and its `CachedFunctionExecutableRareData`, a `CachedCodeBlockRareData`, a `CachedScopedArgumentsTable`): its decoded object has one owner, so a second slot naming it fails. Every record the cache serves therefore decodes once. Records reached in place, through a constant slot, a `CachedOptional` or an owner's rare-data slot that `CachedVariableEnvironment` and `CachedSymbolTable` read directly, are checked and decoded at each reach, as the native decode treats them. A crafted core that names one of them from many slots costs what it costs natively: strict checks structure, and THREAD Session's trust in an artifact that carries machine code covers the rest ([history](SPEC-ucb-history.md#the-validating-decode-shares-what-the-native-decode-shares)).
  - Tags. Every value a decode switches on or casts to an enum lies within the values its encoder writes. That covers a `CachedJSValue` kind, a `CachedHandlerInfo` type and a code block's packed scalars (code type, constructor kind, derived and eval context types, parse mode, code-generation mode). A UFE record's parse mode, its packed fields and its lexically scoped features fall under the same rule. A `JSCellButterfly` constant's indexing type must be one of the three copy-on-write array types, and a symbol table entry must carry `SymbolTableEntry::SlimFlag`. A string slot tagged as an external-string ordinal fails, since a `JITCacheCore` encoder never writes one (section 4). The bits a `JITCacheCore` encoder never sets must be clear: `HasCallSlot`, `HasConstructSlot` and `Updatable` in a UFE header (E1 and section 4), `HasCapturedVariables` with `m_features` 0 (E2), every bit of a UFE header outside `CachedFunctionExecutable::Header`'s (bits 8 to 15 and 24 to 31), of a UFE's packed flags above `ExecutableIsBuiltinDefaultClassConstructorShift`, of a UFE rare data header outside its four `Has` bits, of a code block's packed flags above `CodeBlockIsBuiltinDefaultClassConstructorShift`, and of a code block layout outside `LayoutHasMetadata` and `LayoutHasExtras`. A `CachedRegExp` must have `m_parsed` and `m_numSubpatterns` zero, an empty atom and `SpecificPattern::None`, as E9 writes it, and flags within `Yarr::Flags`. A UFE record's parse mode is a function parse mode (`isFunctionParseMode`), since generating its body asserts one, and its default-constructor bit comes only with `ConstructorKind::Base` or `Extends`, the two kinds `BuiltinExecutables::defaultConstructorSourceCode` has a source for. Every `bool` a record holds (a `CachedVariableEnvironment`'s two flags, a global code block's `m_hasCapturedVariables`, a `CachedBigInt`'s sign) is a byte of 0 or 1, read as a byte before the member is loaded as a `bool`. `ClassElementDefinition::Kind`, `SymbolTable::ScopeType` and every `SourceCodeRepresentation` must lie within their enumerators. A value a `JITCacheCore` encoder never writes fails: an inline string of length 0, a `RegExp` with a null pattern, a global code block whose line starts are not empty (E15), and a registered symbol whose well-known bit equals its private bit, which `CachedUniquedStringImplBase::decode` asserts against.
  - Native assertions. Every condition the native decode asserts about payload data is checked before the call that asserts it. `UnlinkedMetadataTable::expandSteps` asserts that the metadata steps name strictly increasing opcodes below `s_offsetTableEntries - 1` and lay out a table whose offsets fit 32 bits. `JSBigInt::tryCreateWithLength` needs a length of at most `JSBigInt::maxLength`, and `ScopedArgumentsTable::tryCreate` a length whose offsets the payload holds. `Decoder::setAtomForOrdinal` asserts that a string ordinal is below the payload's size. A key equal to its container's empty or deleted value fails, and the decode leaves it out of the container: `HashTable::add` and `InlineMap::add` assert against such keys and a string key's hash dereferences it, while a malformed string record decodes to null, the empty value of every string-keyed container. A hashed `InlineMap` restore refuses such a key itself (section 5). The UFE's decoding constructor asserts that a class source comes only with `IsClass` and reads the rare data unconditionally, so a validating decode checks that pair first, and when a failed record left the rare data null it drops the rare data and the assertion skips it.
  - Strings. A string record's stored hash must equal the hash `StringImpl::hash()` gives its characters, because `AtomStringImpl::add` takes the stored hash as given. A record whose ordinal the decoder already holds must have that atom's characters. A string record carries an ordinal exactly when it is neither a symbol nor empty, since a `JITCacheCore` encoder numbers every other string (`NumberStrings::Yes`) and `CachedUniquedStringImplBase::decode` reads the ordinal before the symbol bit. A `String` constant or butterfly element never names a symbol's record, since a `JSString` never holds a symbol.
  - Records. A record that the native decode would follow without end, or turn into a value that breaks a native invariant, fails. A TDZ chain is walked iteratively, so no recursion depends on its length, and a link met twice in one chain fails. A butterfly's element pool holds only the kinds `ArrayNode::emitBytecode` takes from a `ConstantNode`, `Null`, `True`, `False`, `Int32`, `Double`, `String` and `BigInt`, so never `Undefined`, `Empty`, a symbol table, a butterfly, a `RegExp`, a template descriptor or the sentinel (E14), and a `CopyOnWriteArrayWithInt32` butterfly holds only `Int32`, since the DFG reads its elements as boxed int32s without checking their tag. Every `Double` record, a code block's constant register or a butterfly's element, decodes to a value for which `JSValue::isDouble()` holds, never one that names a cell, and whose negation is no impure NaN either (`!isImpureNaN(-value)`, `runtime/PureNaN.h`): the baseline's `negate` fast path flips bit 63 of the boxed value, which turns a double whose negation is impure into a value that names a cell. Every NaN generation writes passes: a constant register holds `jsNaN()`, and an element holds a NaN the parser folded, with the bits the CPU gives it and possibly its sign flipped ([history](SPEC-ucb-history.md#nans-a-decode-accepts)). A `CachedCompactTDZEnvironment` holds no null name, and its stored hash is the exclusive-or of its names' hashes, since `CompactTDZEnvironmentMap::get` interns an environment by the hash it is given. A `CachedTemplateObjectDescriptor` has no null raw string and as many cooked strings as raw ones. A double butterfly holds no NaN element (`CachedImmutableButterfly::hasWellFormedElements`): generation never writes one, since double storage reads any NaN as a hole, and `JSCellButterfly::get` asserts it on double storage. A `CachedBigInt`'s top digit is not zero, since a `JSBigInt` keeps its digits trimmed. A bit vector of at most `BitVector::maxInlineBits()` bits has exactly that many and bit 63 of its word set, as the encoder writes an inline vector, since the copy overwrites the whole inline word and a clear top bit turns it into a pointer. A list switch table holds an even number of entries, key and offset pairs, with distinct keys, and every `m_indexInTable` of a string switch table is below its decoded entry count, which sizes the table the tiers link into. A constant whose representation is `Integer` or `Double` is a number. A module's heap-allocated declaration count equals its scope offsets' count and is at most its declarations, and its environment offset names a constant register below the constant count that holds a `SymbolTable`. Each entry of a program's var declarations is a var, a function or a sloppy-mode hoisted function, as `ProgramExecutable::initializeGlobalProperties` asserts. A child's source, `startOffset` plus `sourceLength`, ends within the text it is cut from: the default constructor's source for a default constructor, and otherwise the provider's text, measured from the request's start offset, since the child's offsets count from the start of the root's source; and each class element definition's position, and its initializer position when it has one, lies in `[0, length]` of the provider's text, where the lexer's buffer starts.
  - Instructions. The decoded stream is walked from offset 0. Each instruction starts with an opcode below `NUMBER_OF_BYTECODE_IDS`, after at most one `op_wide16` or `op_wide32` prefix, and is not itself a prefix, `op_yield` or `op_create_generator_frame_environment`, which generatorification rewrites before generation finishes and which neither the LLInt nor the baseline executes; its whole `BaseInstruction::size()` lies inside the stream; and the walk ends exactly at the stream's end. Every later walk over the stream, by `CodeBlock::finishCreation` and by the other lanes' strict checks, then stays inside it.

  The expression info's words are walked once as `ExpressionInfo::Decoder::decode` reads them, with every bound it asserts or assumes checked: from the first word, each entry is wide words ending in a Basic word; an Extension word, outside an extension, continues the entry in the next island of the extension area, the islands following one another in the order the entries reach them and filling that area; an ExtensionEnd word, inside an island, returns to the word after the Extension word, as a Basic word that ends an island's entry does; an AbsInstPC word is an entry's first word; a MultiWide word has at most four value words, in the area it lies in; the entries end exactly at the main area's end, and each chapter starts at an entry, in increasing order.

  The validating decode checks the core's structure, not what its content means: instruction operands, jump and exception-handler targets, expression-info positions (the instruction, divot, start and end values the words encode, not their structure), symbol-table scope offsets, a module's heap-allocated declaration scope offsets, a UFE's absolute positions (`unlinkedFunctionStart`, `parametersStartOffset`, `unlinkedFunctionEnd`) and class source, which reach the text only through `SourceProvider::getRange`, whose substring clamps, a `LinkTimeConstant`'s index, which the main file's C5 checks, and the counts that size a UCB's own tables at link time (its value and array profile counts and frame sizes) are left to the container's checksum and the header's build ID, which pin those bytes (THREAD Session). The main file's strict checks compare the profile counts with the feedback section (C3).

## 5. `InlineMap` exact-layout transport

In `Source/WTF/wtf/InlineMap.h`, public members of class template `InlineMap`, for a serializer that must reproduce a map's iteration order exactly:

```cpp
bool usesHashedStorage() const { return !isInline(); }
unsigned hashedCapacity() const;   // asserts usesHashedStorage()

// functor(unsigned index, bool isDeleted, const Entry* entry) for each occupied bucket in index order; entry is null when isDeleted.
template<typename Functor> void forEachOccupiedBucket(const Functor&) const;

// Precondition: the map is empty and inline. Rebuilds hashed storage of `capacity` buckets holding `entries`, in order, at the
// non-deleted indices of `slots` and deleted markers at the deleted ones. Returns false and leaves the map empty and inline unless:
// capacity is a power of two greater than InlineCapacity; the slot indices are strictly increasing and below capacity; the
// non-deleted slots number entries.size(); no key is the empty or the deleted value; the keys are distinct; at least one bucket
// stays empty and (entries.size() + deleted - 1) * loadFactorDenominator < capacity * loadFactorNumerator, the most a native map
// holds; capacity <= entries.size() * minLoadInverse, the least a native map holds, since a removal that leaves less shrinks the
// table; and each key's probe sequence from HashArg::hash(key), as findKeyOrEmptyOrDeleted walks it, meets only occupied buckets
// before its own. Every condition but the probe walk is checked before the table is allocated, and the key values before anything
// hashes a key, because HashArg::hash may dereference one (IdentifierRepHash::hash does).
bool restoreHashedLayout(unsigned capacity, std::span<const uint32_t> slots, Vector<Entry>&& entries);
```

`Entry` is the map's key-value pair type. The minimum load bounds the table a layout can make the restore allocate by the entries the layout holds. The probe check costs one walk per key and makes every lookup of a restored map find its key; the empty bucket makes every miss terminate. A restored map then behaves, for lookups, additions and removals, exactly as the map it was taken from, because a hashed `InlineMap`'s behaviour depends only on its capacity, its buckets and its deleted count.

## 6. Determinism

Invariant I14 of the main file rests on these properties of the JITCache mode, which the twins check (T1) and the self-test probes (section 7):

- pages are zero-initialized, and under the one page policy every `JITCacheCore` encoder uses (E10) their growth and alignment depend only on the sequence of allocations;
- strings are normalized to 8-bit when Latin-1 and numbered in encode order; no external table is used; no string's atom-ness and no butterfly's structure is written (E8);
- a `RegExp` is written as its pattern and flags only (E9);
- `CachedHashMap`, `CachedHashSet` and `CachedCompactTDZEnvironment` write in `EncodingOrder`;
- an inline-storage `InlineMap` writes its insertion order, which generation fixes; a hashed one writes its layout, a function of its insertion history and of `IdentifierRepHash`, which for atoms is the string's content hash;
- no checksum, updatable field, child body or line-start table is written (section 4's opening, E1, E15);
- TDZ chains are written relative to the holder's chain (E12), so the bytes depend on which of the UCB's or UFE's chains end in that chain and never on the names the enclosing scopes declare, which the holder digest pins instead (main file, section 3.4);
- doubles are written as their bits: the generator stores a NaN constant register as `jsNaN()` and a folded NaN element with the bits the CPU gives it, which the header's build ID pins.

The keys of the `VariableEnvironment`s a program or module UCB holds are atoms: `@` names need `exposePrivateIdentifiers`, which is fixed off (options.md), and builtins are functions, which hold no `VariableEnvironment` in their UCB. A symbol key, whose hash is per process, would make a hashed layout process-dependent; the self-test asserts that no corpus program produces one.
