mechanical

Requirement. SPEC-ucb.md section 2, rule F11: "The host function sets the parsing context's global scope extension before calling `constructAnonymousFunction` and never clears it (`setGlobalScopeExtension`), so later requests in that realm carry the with-scope bit". SPEC-ucb.md section 13.3, row `with-scope.js` (Bun), which has no rule ID: "programs and indirect evals evaluated after it carry the with-scope bit (`Interpreter::executeProgram`, `globalFuncEval`). One program text evaluated before and after that call, with a body captured for each bit". Section 13.3, row `role-keys.js`, relies on the same sentence for its Bun variant, "a program evaluated after `vm.compileFunction` has left its context's global scope extension set (as in `with-scope.js`)".

Why the code cannot meet it as written. The request that `vm.Script` makes after `vm.compileFunction` keeps the clear bit, in native Bun with JITCache off as well. `vm.runInThisContext` is `new Script(code).runInThisContext()`. The `Script` constructor calls `NodeVMScript::unlinkedCodeBlockFor`, which requests the UCB through `CodeCache::getUnlinkedProgramCodeBlock` on a `ProgramExecutable` it creates for that call. That executable starts with no features, and nothing marks it with `setTaintedByWithScope`. `NodeVMScript::evaluate` then hands the block to the `JSC::evaluate` overload that takes a precompiled block. `Interpreter::executeProgram` marks only its own executable, and `ProgramExecutable::initializeGlobalProperties` takes the precompiled block through `recordParseFromUnlinkedCodeBlock` without making a request, which also overwrites that executable's features with the block's clear ones. Every request a `vm.Script` makes therefore carries the clear bit, before the call and after it. Each key matches the UCB its request generated, so THREAD Identity holds and this is native behavior JITCache does not change (SKILL Scope). Taken literally, the row's "one program text" evaluated through `vm.runInThisContext` can never produce a request under the set bit. In the failing ladder run the Consumer's evaluation after the call attached the clear-bit body (attaches 1, `RequestKey` misses 0), which is correct for a clear-bit request. For the same reason the ConsumerProducer's request matched the Producer's clear-bit body, and nothing was ever captured under the set bit. `jitcache-expect-no-install` accepts zero installs, so that second flaw went unnoticed.

What the code does instead. `with-scope.js` evaluates the one text with an indirect eval, `(0, eval)(text)`, at both points. That is the other carrier the 13.3 row names. `globalFuncEval` reads `globalScopeExtension()` when it creates the `IndirectEvalExecutable`, so the evaluation after `vm.compileFunction` carries the set bit. Indirect evals go through `CodeCache::getUnlinkedGlobalCodeBlock` like programs, with a `SourceCodeKey` that keeps only the strict bit (F4), so the Consumer still meets the clear-bit UCB through a CodeCache hit and misses `RequestKey` in `attachLive` step 4. The ConsumerProducer now checks that its evaluation after the call imports nothing, misses `NoBody` and generates a record, which confirms that a body is captured for each bit. The module part is unchanged, because Bun runs a CommonJS wrapper with `JSC::evaluate` and no precompiled block, so `Interpreter::executeProgram` marks the executable that makes the request. The test's header states which carriers read the extension. Two things are asked of other tasks. The SPEC's F11 should say that the bit reaches requests whose executable reads the extension (`globalFuncEval` for an indirect eval, `Interpreter::executeProgram` for a program run without a precompiled block), and that `vm.Script` requests the UCB on an executable of its own that keeps the clear bit. The `with-scope.js` row should read "one text evaluated by an indirect eval". `JSTests/jitcache/ucb/role-keys-bun.js` uses `vm.runInThisContext` for its "program under a scope extension", so it passes without ever producing a set-bit request. It needs its own item, probably the same switch to an indirect eval, and the `role-keys.js` row needs the same correction.

Evidence. `runInThisContext` in `~/bun/src/js/node/vm.ts` builds `new Script(code, options)`. `NodeVMScript::unlinkedCodeBlockFor` and `NodeVMScript::evaluate` are in `~/bun/src/jsc/bindings/NodeVMScript.cpp`, which carries no JITCache edit. The `JSC::evaluate` overload taking `UnlinkedProgramCodeBlock* precompiled` (`runtime/Completion.cpp`) and `ProgramExecutable::initializeGlobalProperties` (`runtime/ProgramExecutable.cpp`) are identical in the webkit-pin worktree. `Interpreter::executeProgram` calls `setTaintedByWithScope` when `globalObject->globalScopeExtension()` is set. `globalFuncEval` in `runtime/JSGlobalObjectFunctions.cpp` passes `TaintedByWithScopeLexicallyScopedFeature` to `IndirectEvalExecutable::tryCreate` under the same test. `CodeCache::getUnlinkedEvalCodeBlock` calls `getUnlinkedGlobalCodeBlock`, and `CodeCacheMap::findCacheAndUpdateAge` (`runtime/CodeCache.h`) excludes `UnlinkedEvalCodeBlock` from `fetchFromDisk`. `attachLive` in `Source/JavaScriptCore/jitcache/UCBImport.cpp` counts `MissReason::RequestKey` when `keyFeaturesOf(state)` differs from `record->keyFeatures`. `JSTests/jitcache/ucb/compile-function.js` and `role-keys.js` use the same `misses.NoBody` and `records.Generated` statistics for a ConsumerProducer that generates.
