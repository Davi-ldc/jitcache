Requirement. SPEC-image.md section 2, N18: "`CodeBlock::~CodeBlock` sets `didOptimize` in the UCB's unlinked metadata to `False` while it is indeterminate, unless `Heap::isShuttingDown()`". Section 16.1, T21: "A CB of the same body linked natively and left unreachable the same way sets it to `False` (N18)." Section 11.3, step 1: "The twin has its own metadata table".

Why the code cannot meet it as written. The destructor writes `didOptimize` only inside `if (m_metadata && !m_metadata->isDestroyed())`, and a CB gets `m_metadata` from `UnlinkedMetadataTable::link()`, which returns null unless the bytecode generator added a metadata entry or a value profile (`addEntry`, `addValueProfile`). T21's bodies were `function (a, b) { return a + b; }`, which emits only `enter`, `get_scope`, `mov`, `add` and `ret`. None of these has metadata, and `add` keeps its profile in the UCB (`addBinaryArithProfile`). So no CB of that body has a table: the twin has none, the check that the twin leaves `didOptimize` at `Indeterminate` passed without testing the twin's exemption, and the native CB's death could never write `False`. The measure run showed exactly that: the twin count went from 1 to 0, `didOptimize` stayed `Indeterminate`, and only the final `False` check failed.

What the code does instead. The code under test follows section 11.3, step 2: `forgetImageTwin` runs first in `~CodeBlock`, and only a twin skips the write. The fix is in the test. In `imageTwinDiesWithoutWritingDidOptimize`, both bodies now read `captured`, a variable of `makeBodies`. Linking resolves it as `ClosureVar`, so `resolve_scope` and `get_from_scope` give every CB of the body a metadata table and a value profile, and their baseline code is inline loads with no slow case, IC, thunk or new fixup kind. With a table, the `Indeterminate` check after the first collection depends on the twin's exemption, and the native CB's death writes `False`. The test's comments say why the bodies read a captured variable. T21 does not name a body, so reading it as requiring one whose CBs have a metadata table meets it in full. The SPEC only has to add that condition to N18, T21 and section 11.3, step 1. No code or other task changes.

This is also the first unit test that runs `Twins::checkImage` over scope accesses (T9 stops at `compareBakedFacts`). If the twin check reports a difference for the `ResolveScopeType` or `GetFromScopeType` inputs, that is a defect in `ImageTwins.cpp` for task 11 to fix, and the test should not go back to a body without a table.

Evidence. `CodeBlock::~CodeBlock` in `bytecode/CodeBlock.cpp` (the `writesDidOptimize` guard and the `m_metadata` condition); `UnlinkedMetadataTable::link`, `addEntry` and `addValueProfile` in `bytecode/UnlinkedMetadataTableInlines.h`; `ProfiledBinaryOpWithOperandTypes` and `op_add` in `bytecode/BytecodeList.rb`; `UnlinkedCodeBlockGenerator::addBinaryArithProfile` in `bytecode/UnlinkedCodeBlockGenerator.h`; `emit_op_resolve_scope` and `emit_op_get_from_scope` in `jit/JITPropertyAccess.cpp`; `forgetImageTwin` and `rememberImageTwin` in `jitcache/ImageTwins.cpp`; `imageTwinDiesWithoutWritingDidOptimize`, `imageImportAndCheckTwin` and `imageLinkUnreachableCodeBlock` in `jitcache/tests/ImageRecordingTests.cpp`. The CB lane's `cbTwinsReadNoMetadataTable` (`jitcache/tests/JITCacheCBTwinsTests.cpp`) relies on the same native fact for `function id(x) { return x; }`.
